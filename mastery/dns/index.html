DNS Mastery

DNS is a globally distributed, hierarchical, eventually-consistent key-value store that maps names to records — but under interview pressure the real material is the resolution walk (stub → recursive → root → TLD → authoritative), the caching layers keyed by TTL, anycast, GSLB routing policies, DNSSEC's chain of trust, and why "it's always DNS" is empirically true. This page pushes past "DNS turns names into IPs" into RRSIG chains, negative caching via SOA minimum, Kaminsky poisoning, and CoreDNS in Kubernetes.

Interview Explanation — 30 seconds

Say this: "DNS is a hierarchical, cached, UDP-first (port 53) lookup system that resolves a name to records. Your stub resolver asks a recursive resolver; on a cache miss the recursive does the iterative walk — root servers hand back the TLD nameservers, the TLD hands back the domain's authoritative nameservers, and the authoritative returns the actual answer. Every record carries a TTL, so answers are cached at the OS, browser, and resolver, which is why changes propagate slowly and unevenly. It's eventually consistent by design, favouring availability and read scale over freshness."

Interview Explanation — 2 minutes

The fuller answer names the pieces an interviewer fishes for:

  • Actors: the stub resolver (in libc / the OS, does no recursion), the recursive resolver (8.8.8.8, 1.1.1.1, your ISP — does the work and caches), the root (13 named servers a–m.root-servers.net, anycast to 1500+ instances), the TLD servers (.com run by Verisign), and the authoritative nameservers for the zone.
  • Query types: the stub sends a recursive query (RD bit set — "get me the final answer"); the recursive resolver performs iterative queries (RD ignored, servers return referrals, not answers).
  • Caching: positive answers cached for their TTL; negative answers (NXDOMAIN) cached per the SOA minimum field (RFC 2308). Layered at browser (~60s Chrome), OS stub, and resolver — which is why low TTLs are honoured by resolvers but often ignored by clients.
  • Records: A/AAAA (IPv4/IPv6), CNAME (alias, illegal at the zone apex → vendors offer ALIAS/ANAME), MX, TXT (SPF/DKIM/DMARC), SRV, NS, SOA, PTR (reverse via in-addr.arpa), CAA (which CAs may issue certs).
  • Availability tricks: anycast puts the same IP in many locations and BGP routes you to the nearest; GSLB uses DNS to steer traffic with latency/geo/weighted/failover policies.
  • Security: DNSSEC signs records (RRSIG/DNSKEY/DS, chain to the root KSK) to stop cache poisoning — it authenticates, it does not encrypt. DoT/DoH add the privacy/encryption on the wire.
  • Transport: UDP/53 by default; falls back to TCP/53 when the response is truncated (TC bit) or too big, and for zone transfers (AXFR/IXFR). EDNS0 (OPT record) negotiates larger UDP payloads (typically 1232 bytes post-DNS-flag-day to avoid fragmentation).

Internal Working

  1. Application call: the app calls getaddrinfo(); glibc's stub resolver checks nsswitch.conf order (files → dns), reads /etc/hosts, then /etc/resolv.conf for nameserver and search/ndots options.
  2. Query construction: the stub builds a DNS message: a 12-byte header (16-bit ID/txid, flags incl. RD=1, QDCOUNT/ANCOUNT/NSCOUNT/ARCOUNT) plus a Question section (QNAME, QTYPE, QCLASS=IN). It picks a random source UDP port and random txid (both anti-spoofing).
  3. Recursive resolver receives it: checks its cache. On a hit within TTL it answers immediately. On a miss it starts the iterative walk.
  4. Root query: resolver asks a root server (from its hardcoded root hints / priming query) for www.example.com A. Root returns a referral: the NS records for com. plus glue A/AAAA records in the Additional section.
  5. TLD query: resolver asks a .com TLD server; it returns a referral to example.com's authoritative nameservers (again with glue).
  6. Authoritative query: resolver asks the zone's authoritative server, which returns the answer with the AA (authoritative answer) bit set and a TTL.
  7. Cache & return: resolver caches each RRset by (name, type) for its TTL, then returns the final answer to the stub. The stub caches per the OS, and hands the IP to the app.
  8. Negative path: if the name doesn't exist, an authoritative server returns RCODE 3 (NXDOMAIN) with an SOA in the Authority section; the resolver caches the negative answer for min(SOA minimum, SOA TTL).
Watch out: the header ID is only 16 bits (65 536 values). Before source-port randomization, that was the entire spoofing entropy — the root cause of the Kaminsky attack. Modern resolvers add ~16 bits of random source port for ~2^32 combined entropy, and DNS-0x20 (random case in QNAME) on top.

Why was this built?

  • Pre-DNS, name→address mapping was a single file, HOSTS.TXT, maintained by SRI-NIC and downloaded by every host on ARPANET. It didn't scale: one authority, one file, growing collisions, and every change needed a central edit and a re-fetch.
  • Paul Mockapetris designed DNS in 1983 (RFC 882/883, later 1034/1035) to be hierarchical (delegated authority per zone), distributed (no single server holds everything), and cached (TTL-driven) so it could scale to the whole internet with local read performance.
  • The key insight: delegation. The root delegates .com to Verisign; Verisign delegates example.com to its owner. Each zone is administered independently, and caching means most lookups never touch the root at all.

DNS wins because it's universal, cacheable, human-readable, and vendor-neutral. Most real systems use DNS plus a registry: DNS for the coarse public/edge layer, a registry or service mesh for fast-moving internal endpoints.

Advantages

  • Massive read scale via caching: a popular record served from millions of caches; origin authoritative load is a rounding error.
  • Decentralised authority: each zone owner controls their records; no central bottleneck for edits.
  • Availability-first: anycast + many authoritative servers + caching means DNS keeps answering even during partial outages (stale-but-serving).
  • Universal indirection layer: change an IP without touching clients; enables blue/green, failover, and GSLB.
  • Cheap and ubiquitous: every OS, language, and network device speaks it.

Drawbacks

  • Eventual consistency: TTL + layered caches make propagation slow and uneven; you cannot reliably "instantly" move traffic.
  • Coarse load balancing: DNS resolves to an IP per query, not per request; clients cache and stick, so weights are approximate.
  • Client TTL disobedience: browsers, JVMs (networkaddress.cache.ttl historically ∞), and OS caches ignore low TTLs, breaking failover assumptions.
  • Plaintext by default: UDP/53 is unencrypted and unauthenticated — enables surveillance and (without DNSSEC) poisoning.
  • Blast radius: a bad zone push or a resolver outage takes down everything by name — the reason for the meme.

Trade-offs

  • Low TTL vs cache efficiency: 30–60s TTL enables faster failover but multiplies resolver/authoritative query volume and raises latency on misses. High TTL (hours/days) is efficient but pins you to stale answers.
  • Availability vs consistency (CAP): DNS deliberately picks AP — it serves cached/stale answers rather than fail, which is great for uptime and bad for correctness during changes.
  • DNSSEC integrity vs complexity/fragility: signing prevents poisoning but adds key management, larger responses (fragmentation risk), and a whole class of validation-failure (SERVFAIL) outages.
  • DoH privacy vs operator visibility: encrypting to a third-party resolver hides queries from the ISP but centralises them and breaks split-horizon/enterprise filtering.
  • Anycast simplicity vs debugging: one IP everywhere is elegant but "which POP answered?" becomes a routing question.

When NOT to use it

Watch out — anti-use-cases:
  • Per-request load balancing / instant failover. Client caches and non-compliant TTL handling make DNS LB approximate. Use an L4/L7 LB or service mesh for real balancing; keep DNS pointing at the LB's stable VIP/anycast IP.
  • Fast-changing internal service endpoints (pods churning every few seconds). Use a service registry / mesh with push updates; DNS convergence is bounded below by TTL.
  • Session stickiness or stateful routing. DNS has no notion of a session; it answers per lookup.
  • Storing large or secret data in TXT records. TXT is abused as a config channel — but responses balloon, fragment, and are world-readable.
  • Relying on DNS as your only health check. Basic DNS returns records regardless of backend health; you need GSLB with active health probes or a real LB.

Production Architecture

A typical global topology: clients hit a recursive resolver, which walks the hierarchy to an anycast authoritative provider (Route 53 / NS1 / Cloudflare) that runs GSLB with health checks and routing policies, returning the IP of the closest healthy edge/LB.

flowchart TD
  App["App getaddrinfo"] --> Stub["Stub resolver libc"]
  Stub --> Rec["Recursive resolver cache"]
  Rec -->|miss| Root["Root anycast a-m"]
  Root -->|referral com| TLD["TLD servers Verisign"]
  TLD -->|referral zone| Auth["Authoritative GSLB provider"]
  Auth -->|A record healthy edge| Rec
  Rec -->|answer TTL| Stub
  Auth --> HC["Health checks probes"]
  HC --> Edge["Edge LB nearest POP"]

The authoritative layer is where the intelligence lives: it holds health-check state and routing policy. On each query it decides which A record to return based on the client's resolver IP (or EDNS Client Subnet), latency maps, and endpoint health. The recursive resolver's cache is the enemy of fast failover here — which is why GSLB TTLs are typically 30–60s.

Production Problems

  • Stale records after a cutover: you lowered TTL too late; old caches still send traffic to the dead IP for hours. Fix: lower TTL days before the change.
  • Negative-cache lockout: a record was queried before it existed; NXDOMAIN got cached for the SOA minimum (e.g. 3600s), so new records don't appear for an hour.
  • Resolver overload / TTL stampede: a hot record's TTL expires and thousands of clients miss simultaneously, hammering the authoritative server (thundering herd).
  • SERVFAIL from DNSSEC: an expired RRSIG or a KSK rollover gone wrong makes validating resolvers reject the whole zone.
  • CNAME chains & apex breakage: someone put a CNAME at the apex, or built a 6-deep CNAME chain adding lookups and latency.
  • EDNS/fragmentation black holes: large signed responses fragment; a middlebox drops fragments; resolution intermittently fails until TCP fallback (which some firewalls also block on 53).
  • ndots=5 in Kubernetes: every external lookup tries 4 cluster search-domain permutations first, quadrupling DNS QPS and adding latency.

Debugging Guide

dig +trace www.example.com          # walk root -> TLD -> authoritative yourself
dig @8.8.8.8 example.com A          # ask a specific resolver, bypass local cache
dig @1.1.1.1 example.com A +short   # just the answer
dig example.com SOA                 # read the SOA minimum (negative TTL) and serial
dig example.com NS                  # who is authoritative
dig +dnssec example.com             # show RRSIG/AD flag (DNSSEC validated)
dig -x 93.184.216.34                # reverse PTR lookup
dig example.com A +tcp              # force TCP to test truncation/firewall
dig example.com A +noedns           # test EDNS/fragmentation issues
drill -TD example.com               # ldns: full DNSSEC chain-of-trust trace
nslookup -type=MX example.com       # quick record check
kdig +tls @1.1.1.1 example.com      # DoT (port 853) test
dig +short CHAOS TXT id.server @ns   # which anycast instance answered
  • Read the flags: aa = authoritative answer, ad = DNSSEC-authenticated, tc = truncated (retry TCP), ra = recursion available.
  • Read the RCODE: NOERROR, NXDOMAIN (name doesn't exist), SERVFAIL (resolver/validation failure — often DNSSEC or upstream), REFUSED (server won't answer you).
  • Compare resolvers: if @8.8.8.8 works but your resolver doesn't, it's a local cache/resolver problem, not the zone.
  • Check propagation: query multiple authoritative NS directly (dig @ns1... @ns2...) to confirm they agree; mismatched serials mean a stalled zone transfer.
  • Capture the wire: tcpdump -ni any port 53 or port 853 to see actual queries, retries, and TCP fallback.

Scaling

DNS scales on two axes: read scale via caching (TTL) and availability/proximity via anycast + many authoritative servers. The authoritative provider fronts the same IP from dozens of POPs; BGP steers each resolver to the nearest, absorbing volumetric DDoS by spreading it geographically.

flowchart LR
  R1["Resolver EU"] --> A["Anycast IP one address"]
  R2["Resolver US"] --> A
  R3["Resolver APAC"] --> A
  A --> P1["POP Frankfurt"]
  A --> P2["POP Virginia"]
  A --> P3["POP Singapore"]
  P1 --> Z["Zone data replicated"]
  P2 --> Z
  P3 --> Z
  • Caching is the primary scaler: a 1-hour TTL means the authoritative sees ~1 query/hour/resolver for that record regardless of downstream volume.
  • Anycast gives near-linear capacity by adding POPs and near-zero added latency; it's also the main volumetric-DDoS defence.
  • Serve-stale (RFC 8767): resolvers keep answering with expired data if the authoritative is unreachable — trades freshness for availability.
  • Prefetch / async refresh: resolvers refresh popular records before TTL expiry to avoid the stampede on a hot miss.
  • Multiple authoritative providers (e.g. Route 53 + NS1) removes the single-provider blast radius exposed by the 2016 Dyn outage.

Security

  • Cache poisoning (Kaminsky, 2008): attacker races the real answer with spoofed responses guessing txid. Mitigations: 16-bit txid plus source-port randomization (~2^32 entropy), DNS-0x20 case randomization, and ultimately DNSSEC.
  • DNSSEC (chain of trust): each RRset is signed → RRSIG; the public key is a DNSKEY; the parent zone holds a DS record (hash of the child's key-signing key); the chain climbs to the root KSK, whose trust anchor is shipped with resolvers. Validating resolvers set the AD bit. It authenticates and guarantees integrity — it does not encrypt, and it enables zone-walking unless NSEC3 is used.
  • DoT (853) / DoH (443): encrypt the stub↔resolver hop against eavesdropping and tampering. DoH hides inside HTTPS so it can't be blocked by port; both centralise trust in the chosen resolver.
  • Amplification DDoS: small spoofed query → large response (ANY, DNSSEC) reflected at a victim. Mitigations: disable open recursion, Response Rate Limiting (RRL), refuse ANY, BCP38 anti-spoofing.
  • Domain/registrar hijack & NS takeover: registrar-lock, DNSSEC, and CAA records (limit which CAs issue certs) reduce hijack impact.
  • Dangling records / subdomain takeover: a CNAME pointing at a deprovisioned cloud bucket/app lets an attacker claim it. Audit and remove stale records.
  • Data exfiltration via DNS tunnelling: encode payloads in QNAMEs to a controlled authoritative server; detect via entropy/volume of TXT/long-label queries.

Performance

  • Latencies: cache hit tens of microseconds to a low ms; cold full walk 4 round trips (root→TLD→auth→answer) often 50–200ms depending on geography. This is why the first request to a new host is slow.
  • UDP payload limit: classic 512 bytes; EDNS0 negotiates larger, but post-2020 DNS flag day the safe default is 1232 bytes to avoid IP fragmentation. Bigger → truncation → TCP fallback (extra RTT + handshake).
  • Connection reuse: DoT/DoH keep TCP/TLS sessions open (TFO, 0-RTT) to amortise handshake cost across many queries.
  • Tuning knobs: TTL (freshness vs QPS), ndots in Kubernetes (drop from 5 to 1–2 for external-heavy pods), resolver cache size and prefetch, EDNS buffer size, and negative-cache TTL via SOA minimum.
  • NodeLocal DNSCache in Kubernetes runs a per-node cache (169.254.20.10) to cut CoreDNS QPS, avoid conntrack races, and drop tail latency; force TCP upstream to sidestep UDP conntrack bugs.
  • Throughput: a tuned CoreDNS/BIND/Unbound instance handles tens to hundreds of thousands of QPS per core; the bottleneck is usually cache misses hitting upstream, not local CPU.

Common Mistakes

  • Lowering TTL at cutover time. Fix: lower it days ahead — the old high TTL is still cached everywhere.
  • Expecting instant failover from DNS. Fix: use a load balancer / anycast VIP for real failover; DNS moves traffic in TTL-scale time.
  • CNAME at the zone apex. Fix: use the provider's ALIAS/ANAME (or A record); a CNAME at apex conflicts with the mandatory SOA/NS records.
  • Trusting client TTL compliance. Fix: assume JVM/browser/OS pin longer than your TTL; design failover to tolerate it.
  • Forgetting to re-sign / rotate DNSSEC keys. Fix: automate RRSIG resigning and KSK/ZSK rollover; alert on expiry headroom.
  • Wildcards masking NXDOMAIN. Fix: understand a *.example.com wildcard answers everything, hiding typos and takeover risk.
  • Single authoritative provider. Fix: multi-provider NS delegation to survive a provider outage.
  • Debugging via the OS cache. Fix: query authoritative NS directly with dig @ns to see truth, not a stale cache.

Interview Follow-up Questions

  1. What actually happens when you type a URL and press enter (DNS part)?
    1. Stub → recursive → root → TLD → authoritative; cache checked at each layer.
  2. Recursive vs iterative query — who does which?
    1. Stub sends recursive (RD=1); recursive resolver does iterative walks receiving referrals.
  3. Where is DNS cached and for how long?
    1. Browser, OS stub, recursive resolver — each up to the record TTL; negative answers per SOA minimum.
  4. Why is DNS propagation slow and uneven?
    1. Independent caches expire on their own TTL clocks; clients ignore low TTLs — no global invalidation.
  5. Why can't you put a CNAME at the zone apex?
    1. Apex must hold SOA/NS; CNAME must be the only record for a name — conflict. Use ALIAS/ANAME.
  6. How is negative caching implemented?
    1. NXDOMAIN + SOA in Authority section; cached for min(SOA minimum, SOA TTL) per RFC 2308.
  7. What is the SOA minimum field really for?
    1. Since RFC 2308 it's the negative-cache TTL, not the zone-wide default TTL.
  8. How does DNS-based load balancing work and where does it fail?
    1. Multiple A records / GSLB policy; fails because clients cache and ignore TTL — not per-request.
  9. What is anycast and how does it help DNS?
    1. Same IP announced from many POPs via BGP; nearest answers — proximity + DDoS absorption.
  10. Explain DNSSEC's chain of trust.
    1. RRSIG signs RRsets, DNSKEY holds keys, parent DS hashes child KSK, chain to root trust anchor.
  11. Does DNSSEC encrypt? What does?
    1. No — it authenticates/integrity only. DoT (853) and DoH (443) encrypt.
  12. Walk me through the Kaminsky attack and its mitigation.
    1. Race spoofed answers guessing txid; mitigated by source-port + txid + 0x20 randomization, and DNSSEC.
  13. What causes SERVFAIL?
    1. Upstream failure, resolver overload, or DNSSEC validation failure (expired RRSIG / broken chain).
  14. How does CoreDNS resolve svc.namespace.svc.cluster.local?
    1. Plugin reads the kubernetes API; A for ClusterIP, headless returns pod IPs, SRV for ports.
  15. Why does ndots=5 hurt Kubernetes DNS performance?
    1. External names try 4 cluster search domains first → 4x wasted queries and added latency.
  16. How do you do a zero-downtime DNS migration?
    1. Lower TTL days ahead, dual-run, flip records, watch traffic drain, restore TTL after.
  17. How would you debug "the site is down but the server is fine"?
    1. dig +trace, compare resolvers, query authoritative directly, check RCODE/flags, tcpdump 53.
  18. What is a TTL stampede and how do you prevent it?
    1. Synchronised misses on a hot record; prevent with prefetch, jitter, serve-stale, higher TTL.
  19. Why run multiple authoritative DNS providers?
    1. Single-provider outage (Dyn 2016) takes down everything by name; multi-provider removes that SPOF.
  20. What are DoH's downsides despite privacy gains?
    1. Centralises queries to one resolver, breaks enterprise/split-horizon filtering, hides from network ops.

Common Cross Questions

  • TCP/UDP & transport: "Why UDP for DNS, when TCP?" — expect UDP/53 default, TCP on truncation (TC bit), AXFR, and large/DNSSEC responses; EDNS0 buffer sizing.
  • TLS/certificates: "How does CAA relate to certs?" — CAA restricts which CAs may issue; ACME/Let's Encrypt uses DNS-01 challenge (TXT record) to prove domain control.
  • CDN & edge: "How does a CDN pick the edge?" — CNAME to the CDN, then GSLB/anycast + EDNS Client Subnet resolves to the nearest POP.
  • Load balancing: "DNS LB vs L4/L7 LB vs service mesh" — coarse/cached vs per-connection vs per-request with health and policy.
  • Kubernetes: "How does service discovery work?" — CoreDNS, ClusterIP vs headless, SRV records, ndots, NodeLocal DNSCache.
  • Email: "How does email auth use DNS?" — MX for routing, SPF (allowed senders), DKIM (public key), DMARC (policy) all as TXT/records.
  • Consistency models: "Is DNS strongly consistent?" — no, eventually consistent, AP in CAP terms; ties to caching and TTL.
  • Security: "How do you prevent hijack/poisoning?" — DNSSEC, registrar lock, CAA, port randomization, DoT/DoH.

Production Scenarios

Incident 1 — DNS cutover left half the traffic on the old server for hours

SymptomsAfter flipping the A record, ~40% of requests still hit the decommissioned host; errors climbing.
InvestigationOld record's TTL was 86400; dig @variousresolvers showed many still serving the old IP; JVM clients cached indefinitely.
Root causeTTL was lowered the same day as the change, so the old long-TTL answer was still cached everywhere.
SolutionKept the old host up as a proxy to the new one until caches drained; forced JVM networkaddress.cache.ttl=60.
PreventionLower TTL to 60s at least 2× the old TTL before any planned change; verify TTL propagation before cutover.
Interview answer"DNS changes are gated by the previously cached TTL. You must lower it well in advance, and design failover to tolerate clients that ignore TTL entirely."

Incident 2 — New subdomain returns NXDOMAIN for an hour after creation

SymptomsJust-created api2.example.com is unreachable for ~60 min despite the record existing at the authoritative.
Investigationdig @auth returns the record, but dig @8.8.8.8 returns NXDOMAIN; SOA minimum was 3600.
Root causeA health check queried the name before it existed; the NXDOMAIN got negatively cached for the SOA minimum.
SolutionWaited out / flushed resolver negative cache; created records before any component probes them.
PreventionSet a modest SOA minimum (e.g. 300s); provision DNS records before deploying dependents.
Interview answer"Negative answers are cached too, keyed by the SOA minimum. Query a name before it exists and you've poisoned the cache with NXDOMAIN for that duration."

Incident 3 — Zone-wide SERVFAIL after a DNSSEC key rollover

SymptomsValidating resolvers (8.8.8.8, 1.1.1.1) return SERVFAIL for the whole zone; non-validating resolvers work.
Investigationdig +dnssec shows RRSIG present; drill -TD shows the DS at the parent no longer matches the current DNSKEY.
Root causeKSK was rolled without updating the DS record at the registrar/parent — chain of trust broken.
SolutionPublished the correct DS at the parent (or rolled back to the old KSK) and waited for the parent TTL.
PreventionUse double-signing / RFC 5011 automated rollovers; alert on DS/DNSKEY mismatch and RRSIG expiry headroom.
Interview answer"DNSSEC failures are all-or-nothing: a broken chain makes validating resolvers reject the entire zone with SERVFAIL, while non-validating ones still work — a classic 'works for me' trap."

Incident 4 — Kubernetes latency spike traced to DNS

SymptomsService-to-external-API calls show +150ms p99; CoreDNS pods CPU-bound and QPS 5× baseline.
Investigationtcpdump in a pod shows 4 failed lookups (.svc.cluster.local, .cluster.local, etc.) before the real one; ndots=5.
Root causeDefault ndots=5 forces the resolver to try every search domain before treating the FQDN as absolute.
SolutionAppended a trailing dot to external names / set dnsConfig ndots=2; deployed NodeLocal DNSCache.
PreventionUse FQDNs for external calls, tune ndots per workload, cache locally on each node, force TCP upstream.
Interview answer"In Kubernetes, ndots=5 means an external name generates several wasted cluster-domain queries first; the fix is FQDNs, lower ndots, and a node-local cache."

Incident 5 — Third-party authoritative provider DDoS takes the whole product down

SymptomsEvery service unreachable by name simultaneously; servers healthy; "it's always DNS."
InvestigationAuthoritative provider status page reports a volumetric attack; queries to their NS time out globally.
Root causeSingle authoritative DNS provider was a single point of failure (the Dyn 2016 pattern).
SolutionAdded a second authoritative provider and split NS delegation across both; raised TTLs to ride out future blips.
PreventionMulti-provider authoritative DNS, anycast, higher TTLs for stable records, serve-stale on resolvers.
Interview answer"Names are the ultimate SPOF — if resolution fails, everything fails. Run at least two independent authoritative providers and keep TTLs high enough to survive a provider outage."

🎯 Deep-dive Q&A — model answers

Trace a full cold resolution of www.shop.example.com A, naming every message.

The stub builds a query (txid, RD=1, QNAME=www.shop.example.com, QTYPE=A) and sends it to the recursive resolver. Cache miss. The resolver sends an iterative query to a root server (chosen from root hints); the root returns a referral: NS records for com. plus glue A records in Additional (no answer, AA unset). The resolver queries a .com TLD server, which refers it to example.com's authoritative NS with glue. The resolver queries those; the zone may have shop.example.com delegated (another referral) or answer directly. The authoritative returns the A record with AA=1 and a TTL. The resolver caches each RRset by (name,type) for its TTL and returns the answer. Four RTTs worst case, but every step is independently cacheable so subsequent lookups skip most of it.

Why exactly can't a CNAME live at the zone apex, and what do ALIAS/ANAME do differently?

RFC 1034 says a CNAME must be the only record for a name — no other RRsets may coexist. The apex (example.com) is required to carry SOA and NS records, so a CNAME there is illegal. ALIAS/ANAME are a provider-side trick: the authoritative server resolves the target internally and synthesizes A/AAAA answers at query time, so from the wire it looks like normal A records at the apex while behaving like a CNAME operationally. The cost is the provider does the extra lookup and you rely on their resolution/health.

Explain the DNSSEC chain of trust record by record.

Each RRset (say the A records) is signed with the Zone Signing Key producing an RRSIG covering that RRset with an inception/expiry. The ZSK and KSK public keys are published as DNSKEY records; the KSK signs the DNSKEY RRset. The parent zone publishes a DS record — a hash of the child's KSK. To validate, a resolver fetches the A + RRSIG, the DNSKEY + its RRSIG, verifies the RRSIG with the DNSKEY, then verifies the DNSKEY against the parent's DS, and repeats up to the root, whose KSK is a pre-installed trust anchor. Success sets the AD bit. Any broken link → SERVFAIL. Note it authenticates only; the data is still plaintext, and NSEC records can enable zone-walking (NSEC3 hashes names to mitigate).

Walk through the Kaminsky attack and precisely why the mitigations work.

Pre-2008, a resolver's only spoofing entropy was the 16-bit txid. Kaminsky's insight: instead of poisoning one record and waiting for its TTL, trigger lookups for many non-existent subdomains (a1, a2, ...) and, for each, race spoofed referrals that inject a malicious NS/glue for the parent — no TTL to wait out, near-unlimited attempts. With only 65k txids, an attacker wins quickly. Mitigation adds ~16 bits of random source port (the attacker must guess port and txid ≈ 2^32) and DNS-0x20 (randomising QNAME case adds bits). This makes brute-forcing infeasible in the response window. DNSSEC removes the attack entirely because forged records fail signature validation. This is why source-port randomization was an emergency patch across all resolvers in 2008.

How does DNS-based GSLB actually decide what to return, and what's its blind spot?

The authoritative GSLB server holds live health-check state and a routing policy. On each query it inspects the source (the recursive resolver's IP, or the client subnet via EDNS Client Subnet), consults latency maps / geo databases / weights, filters to healthy endpoints, and returns the chosen A record(s) with a short TTL. The blind spot: it sees the resolver's location, not the client's — a user on 8.8.8.8 may be routed by Google's anycast egress, not their home. ECS partially fixes this by passing a truncated client subnet. And because clients cache the answer, GSLB decisions are sticky for the TTL regardless of changing conditions.

Design a zero-downtime migration of a high-traffic domain to a new IP.

Weeks ahead: confirm current TTL and lower it in stages down to 30–60s, waiting each time for at least the old TTL to elapse so caches pick up the shorter value. Stand up the new target and dual-run: keep the old IP serving (ideally proxying to new) so both work. Flip the A record; monitor traffic draining from old to new over ~2× the low TTL. Because some clients (JVM, browsers) ignore TTL, keep the old endpoint alive for a long tail — hours to days — as a proxy. Once traffic on old is negligible, decommission and restore a sane TTL. Never rely on DNS alone for the instant part; if you need instant, front both with an anycast VIP/LB and flip at that layer.

What's the difference between recursive and iterative, and why do stub resolvers not recurse?

A recursive query (RD=1) means "do all the work and give me the final answer" — the recursive resolver accepts responsibility for the whole walk. An iterative query means "give me your best answer or a referral" — servers return NS referrals rather than chasing them. Stub resolvers are intentionally minimal: they live in libc on every device, have no cache hierarchy, root hints, or DNSSEC validation machinery, and offloading recursion to a shared resolver maximises cache hit ratio across all clients. Making every stub recurse would hammer root/TLD servers and destroy caching benefits.

Why is DNS eventually consistent, and how would you reason about it in CAP terms?

There is no global invalidation — each cache independently expires entries on its own TTL clock, and clients may ignore TTLs. So after a change, different observers see different answers for a window bounded by the largest cached TTL. In CAP terms DNS chooses AP: during partitions or origin unavailability, resolvers keep serving cached/stale answers (serve-stale, RFC 8767) rather than failing. You get high availability and read scalability at the cost of freshness/consistency — which is the correct trade for a naming layer the whole internet depends on.

Explain EDNS0, the DNS flag day, and fragmentation black holes.

Classic DNS caps UDP responses at 512 bytes. EDNS0 adds a pseudo-OPT record letting client and server advertise a larger UDP buffer (e.g. 4096). But large UDP responses get IP-fragmented, and many middleboxes/firewalls drop fragments, causing intermittent, hard-to-debug failures — worsened by DNSSEC's big signed responses. The 2020 DNS flag day standardised a conservative default buffer of 1232 bytes (fits within typical MTU minus headers, avoiding fragmentation); anything larger sets the TC bit forcing TCP fallback. Debug with dig +noedns, +bufsize=1232, and forcing +tcp.

How does CoreDNS resolve services in Kubernetes, including headless and SRV?

CoreDNS runs with the kubernetes plugin watching the API for Services/Endpoints. A normal (ClusterIP) service svc.ns.svc.cluster.local resolves via an A record to the stable virtual ClusterIP (kube-proxy then load-balances). A headless service (clusterIP: None) returns one A record per ready pod, so clients see the actual pod IPs — used for stateful sets / client-side LB. SRV records _port._proto.svc.ns.svc.cluster.local expose named ports with priority/weight/port/target, letting clients discover both host and port. Pods get a resolv.conf with search domains and ndots=5, which is why external names need care.

What is a TTL stampede / thundering herd on DNS, and how do you prevent it?

When a very popular record's TTL expires, every downstream client/resolver misses at nearly the same instant and floods the authoritative server with simultaneous queries — a self-inflicted DDoS. Prevention: resolver-side prefetch (refresh hot records asynchronously just before expiry), TTL jitter so entries don't all expire together, serve-stale to answer with expired data while refreshing, request coalescing (dedupe concurrent identical queries into one upstream), and simply higher TTLs for stable records. Same pattern as cache stampede in application caches.

Why do people say "it's always DNS," and what makes DNS failures so pernicious?

Because DNS sits under everything: every service call, TLS handshake, and API request starts with a name lookup, so a DNS fault manifests as a total, cross-service outage while the servers themselves look healthy — the misleading part. It's also full of silent, delayed failure modes: cached stale/negative answers, TTLs you can't retroactively shorten, DNSSEC chains that fail all-or-nothing, ndots amplification, resolver overload, and single-provider blast radius (Dyn 2016). The failures are distributed, time-delayed, and cache-dependent, so 'works for me' is common and root-causing requires querying authoritative servers directly rather than trusting caches.

Compare DoT and DoH — when would you pick each?

Both encrypt the stub↔resolver hop with TLS. DoT runs on a dedicated port 853, so network operators can see (and choose to allow/block) DNS-over-TLS as a distinct protocol — cleaner for enterprise policy and observability. DoH tunnels DNS inside normal HTTPS on 443, indistinguishable from web traffic, so it's censorship-resistant and browser-native but harder for operators to manage and it can bypass local resolvers/split-horizon. Pick DoT for managed/enterprise networks that still want visibility; pick DoH for user-privacy against on-path ISPs. Both centralise trust in the chosen resolver and neither replaces DNSSEC (encryption ≠ authentication of the data's origin).

How would you architect DNS to survive the loss of an entire authoritative provider?

Delegate the zone to nameservers from two independent providers (e.g. Route 53 + NS1), each on its own anycast network, and keep both zones in sync via automation or a common source of truth. Resolvers will try the other provider's NS if one set times out. Keep TTLs high enough for stable records that resolvers ride through a multi-minute provider blip on cache. Enable serve-stale on your own resolvers. Add anycast and RRL for DDoS resilience, and monitor per-provider query success so you detect a degraded provider before it fails fully. This directly addresses the Dyn 2016 lesson: a single authoritative provider is a single point of failure for your entire product.

A record change 'isn't propagating.' Walk me through your diagnosis.

First, confirm the source of truth: dig @authoritative-ns record — is the new value actually published, and do all authoritative NS agree (compare SOA serials)? If they disagree, it's a zone-transfer/sync issue at the authoritative layer. If they agree, the delay is caching: check the record's TTL and how long ago it changed — the old value lives until the previously-cached TTL expires. Query public resolvers (@8.8.8.8, @1.1.1.1) to see cached state; check for a negatively cached NXDOMAIN (SOA minimum) if the name is new. Rule out client-side caching (browser, OS, JVM). Conclusion is almost always: it is propagating, bounded by TTL — not broken.
