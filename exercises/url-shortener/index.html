URL Shortener — Requirements Exercise

Design brief: Design a service that converts long URLs into short aliases and redirects users from a short alias back to the original URL.

Functional Requirements

  • Users can submit a long URL and receive a unique short link in return.
  • Accessing a short link must redirect the requester to the original long URL.
  • The system must guarantee that each generated short alias maps to exactly one long URL and is never reused.
  • Users can optionally request a custom alias (vanity URL), which must be rejected if already taken.
  • Users can optionally set an expiration date after which the short link stops resolving.
  • Registered users can view a list of the links they have created.
  • The system must track and expose click/analytics counts per short link (total clicks, and ideally referrer/geo/time breakdowns).
  • The system must validate submitted URLs and reject malformed input.
  • The system must detect and block links to known malicious or disallowed destinations.
  • Users can delete or deactivate a short link they own.
  • The same long URL submitted multiple times may either return a new alias or the existing one (behavior must be defined).

Non-Functional Requirements

  • Read-heavy workload: expect roughly a 100:1 redirect-to-creation ratio.
  • Scale target: ~100M new URLs created per month and billions of redirects per month.
  • Redirect latency should be low, with a p99 under ~100 ms.
  • Availability target of 99.99% for the redirect path, since broken links directly break users' shared content.
  • Short aliases must be as short as practical while supporting the projected total URL volume for several years.
  • Links must be durable and persist for at least the configured lifetime (default: indefinitely unless expired).
  • Alias generation must avoid predictable/enumerable sequences where enumeration is a privacy or abuse concern.
  • The system must withstand abuse (spam creation, click inflation) via rate limiting.
  • Cost per stored URL and per redirect should remain low at the target scale.

Assumptions & Out of Scope

  • Assume HTTP redirects are acceptable; building a full analytics/BI dashboard product is out of scope.
  • Assume authentication exists for account features; designing the auth system itself is out of scope.
  • Editing an existing short link to point at a different destination is excluded unless stated otherwise.
  • Assume standard web/mobile clients; no offline resolution is required.
