Performance & Re-renders React

Almost every React performance problem is a re-render problem — either too many components re-render, or one of them does too much work while it renders. Fixing it starts with knowing exactly what makes React run a component again, and that list is much shorter (and much dumber) than most people assume.

The single most misunderstood fact: React does not compare props before re-rendering a child. If a parent renders, its children render, identical props or not. Everything else on this page — memo, useCallback, moving state down — exists to work around that default.

What actually triggers a re-render

A function component runs again for exactly four reasons:

  • Its own state changed — a useState / useReducer setter produced a value that Object.is says is different.
  • Its parent re-rendered — unconditionally, by default, regardless of props.
  • A context it consumes got a new value — every consumer of that provider re-renders, and memo does not stop this.
  • Its key or element type changed — which is not a re-render at all but an unmount plus a fresh mount, losing all state.

Notice what is not on the list: "its props changed". Props changing is a consequence of the parent rendering, not an independent cause.

function Parent() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveChild />   {/* no props at all — still re-renders every click */}
    </div>
  );
}
Gotcha: "My child takes no props, so React skips it" is false. React has no idea the output would be identical until it runs the component and diffs the result. Bailing out is opt-in via React.memo.

Render phase vs commit phase — a re-render is not a DOM update

React works in two phases. The render phase calls your components and builds a new element tree; it must be pure, and it can be interrupted, thrown away or repeated. The commit phase applies the minimal set of DOM mutations React computed, then runs layout effects and passive effects.

Render phaseCommit phase
What runsYour component functions, useMemo, reducersDOM mutations, refs, useLayoutEffect, then useEffect
InterruptibleYes (concurrent rendering)No — synchronous and atomic
Side effects allowedNoYes
CostJS: calling functions, allocating elementsDOM writes, layout, paint

So a component that re-renders and produces the same output costs you JS time only — no DOM touch. That is why a "wasted render" of a leaf with three divs is genuinely free, and why memoizing it can be a net loss. Wasted renders matter when they are many (a long list) or expensive (heavy computation, big subtree).

React.memo — and the three ways it silently does nothing

memo(Component) wraps a component so React does a shallow Object.is comparison of each prop before re-rendering it. Equal props → React reuses the previous output and skips the subtree.

const Row = memo(function Row({ id, label, onSelect }) { … });
// optional second argument: custom comparator, returns true to SKIP the render
const Row = memo(RowImpl, (prev, next) => prev.item.id === next.item.id);

It is defeated whenever any prop is a new reference each render:

// ❌ all three defeat memo — new identity on every parent render
<Row style={{ color: 'red' }} />         // new object
<Row tags={[]} />                        // new array
<Row onSelect={() => pick(id)} />        // new function

// ❌ also defeated: children as JSX is a new element object every time
<Card><Row /></Card>                     // memo(Card) compares props.children — never equal

And memo does not block updates that come from inside: its own state, and any context it consumes, still re-render it.

Gotcha: a single unstable prop makes the entire memo wrapper dead weight — you pay the comparison cost and get zero skips. This failure is silent; only the Profiler reveals it.

useMemo / useCallback: referential stability first, caching second

Both cache a value across renders while the dependency array is shallow-equal. useCallback(fn, deps) is just useMemo(() => fn, deps).

  • Primary use — stable identity. Keep an object/array/function reference constant so a memo child, a useEffect dependency array, or a context value does not invalidate.
  • Secondary use — skipping expensive work. Real computation (sorting 10k rows, parsing, building an index) worth more than the memo bookkeeping.
  • They are not free. Each one allocates a closure and a deps array, compares deps every render, and holds the cached value alive. Memoizing x * 2 is strictly slower than recomputing it.
  • They are a hint, not a guarantee. React may discard a useMemo cache (e.g. to free memory); never rely on it for correctness.
// useCallback with no memo child downstream = pure overhead
const onClick = useCallback(() => setOpen(o => !o), []);   // pointless if <button> is the consumer

// useMemo that matters: the context value
const value = useMemo(() => ({ user, logout }), [user, logout]);
return <AuthCtx.Provider value={value}>{children}</AuthCtx.Provider>;
Senior tip: React 19's compiler (React Compiler / "forget") auto-memoizes at build time, which is why the community advice has shifted from "memoize aggressively" to "write clean code and let the compiler do it". Until you have it enabled, memoize deliberately, guided by the Profiler.

The free wins: move state down, pass children through

Structural fixes beat memoization because they cost nothing at runtime and cannot be silently defeated.

1. Push state down

// ❌ typing in the input re-renders the whole page
function Page() {
  const [text, setText] = useState('');
  return <><input value={text} onChange={e => setText(e.target.value)} /><HugeTree /></>;
}
// ✅ the state now lives in a leaf; HugeTree never hears about it
function SearchBox() { const [text, setText] = useState(''); return <input … />; }
function Page() { return <><SearchBox /><HugeTree /></>; }

2. Lift the expensive subtree into children

When state must stay at the top, pass the expensive part in as children. The element was created by the grandparent, so it is the same object across the stateful component's renders and React bails out of re-rendering it — no memo required.

function Counter({ children }) {
  const [n, setN] = useState(0);
  return <div onClick={() => setN(n + 1)}>{n}{children}</div>;  // children not re-created
}
<Counter><HugeTree /></Counter>   // HugeTree renders once
Note: this is the same bail-out memo uses — React compares the element object by reference. It just happens automatically because the JSX was evaluated one level up.

Lists, keys and virtualization

  • Stable keys. Use a domain id. An array index as key makes React reuse the wrong instance when items are inserted, removed or reordered — state and DOM attach to the wrong row. Index keys are only safe for a static, never-reordered list.
  • Never key={Math.random()}. Every render remounts every row: the worst possible outcome.
  • Memoize row components and pass primitives (id, and an onSelect that is stable) rather than freshly built objects.
  • Virtualize past roughly a few hundred DOM-heavy rows. Below ~100 simple rows it is unnecessary; above ~1,000 it is close to mandatory. Use react-window (tiny, fixed/variable size lists) or TanStack Virtual (headless, grids, dynamic measurement).

Virtualization renders only the visible window plus a small overscan, so cost stops scaling with data size:

<FixedSizeList height={600} itemCount={100000} itemSize={40} width="100%">
  {({ index, style }) => <div style={style}>{rows[index].label}</div>}
</FixedSizeList>
// ~15 visible + overscan ≈ 25 DOM nodes instead of 100,000
Gotcha: virtualized rows are not in the DOM, so browser Ctrl+F, print, and naive end-to-end selectors will not find them. That is a product decision, not just a technical one.

Code splitting, transitions and deferred values

Code splitting

const Settings = lazy(() => import('./Settings'));
<Suspense fallback={<Spinner />}><Settings /></Suspense>

Split at route boundaries first — that is where the payoff is largest and the loading state is expected. Then split heavy, rarely-opened widgets (rich text editors, charts, maps, modals). Splitting tiny components just adds network round-trips. Prefetch on hover/intent to hide the latency.

Keeping the UI responsive

  • useTransition — mark an update as non-urgent: startTransition(() => setQuery(v)). The typed character commits immediately; the expensive filtered list renders at lower priority and can be interrupted. isPending lets you show a subtle stale indicator.
  • useDeferredValue — the same idea when you only have a value, not a setter: const deferred = useDeferredValue(query), then render the expensive list from deferred.
Note: these do not make rendering faster. They change priority so the browser can paint the urgent update first. If a single render takes 400 ms, it still takes 400 ms — fix the algorithm or virtualize.

Measuring, and knowing when to stop

Measure first — never guess

  • React DevTools Profiler. Record an interaction, read the flamegraph and the ranked chart; each commit shows what rendered and "why did this render" (enable it in settings).
  • Highlight updates. DevTools setting that flashes a border around every re-rendering component — the fastest way to spot a cascade.
  • <Profiler> component. Programmatic timings in code: <Profiler id="list" onRender={(id, phase, actualDuration, baseDuration) => …}>. baseDuration is the cost without any memoization, so baseDuration - actualDuration is what memoization actually bought you.
  • Profile a PRODUCTION build. Development React is several times slower, double-invokes components under StrictMode, and carries warning machinery. Use react-dom/profiling (or the framework's profiling build) to keep the Profiler working in production mode.
  • Browser tools too. Performance panel for long tasks and layout thrashing; Lighthouse / web-vitals for INP and LCP, which are what users actually feel.

Premature optimization traps

  • Memoizing everything. Every memo/useMemo/useCallback adds allocation, comparison and cognitive cost. Net negative on cheap components.
  • Wrapping every callback in useCallback when the consumer is a plain DOM element that never compares props.
  • Memoizing a component that always gets a new prop — pure overhead, and it looks like it works.
  • Fixing renders instead of the real cost. 200 cheap renders are usually cheaper than one 300 ms JSON parse or one unvirtualized 5,000-row table.
  • Optimizing dev-mode numbers and chasing renders the user cannot perceive. If INP is fine, stop.
Senior tip: the order to reach for fixes is: (1) fix the algorithm or payload, (2) move state down / pass children, (3) virtualize long lists, (4) split code, (5) transitions, and only then (6) memo + useCallback — each backed by a Profiler before/after.

🎯 Interview questions

Does React skip re-rendering a child whose props did not change?

No. By default a parent re-render re-renders the whole subtree, identical props or not — React cannot know the output is the same without running the component. Skipping is opt-in through React.memo (or a class's shouldComponentUpdate/PureComponent), or it happens implicitly when the same element object is reused, as with children passed from a grandparent.

Why did adding React.memo change nothing?

Most likely a prop is a new reference every render — an inline object, array, arrow function, or children as JSX, all of which fail the shallow Object.is check. Or the re-render is not coming from the parent at all: memo never blocks the component's own state updates or a context value change.

When is useCallback pointless?

When the callback is only handed to a host element such as <button onClick>, which never compares props, or when the receiving component is not memoized. You then pay for a closure, a deps array and a comparison every render and skip nothing. It is worth it when the consumer is a memo component, a useEffect dependency, or part of a context value.

What is the difference between a re-render and a DOM update?

A re-render is the render phase — React calls your component and diffs the returned element tree. A DOM update happens in the commit phase and only for nodes that actually differ. A re-render that produces identical output costs JS time but touches no DOM, which is why isolated wasted renders are cheap and mass ones are not.

Index keys or ids?

Ids, unless the list is static and never reordered. Keys identify a child across renders; with index keys, inserting at the front makes React match old item 0 to new item 0, so it patches every row and leaves component state, inputs and focus attached to the wrong data instead of moving nodes.

How do you decide to virtualize?

By measuring: when the number of mounted DOM nodes makes mount time or scroll jank visible — practically a few hundred complex rows, or a thousand simple ones. Virtualization makes cost proportional to viewport size rather than data size, at the price of losing in-page find, print, and simple full-list selectors.

Why must you profile a production build?

Development React is significantly slower, ships warning and DevTools instrumentation, and under StrictMode intentionally double-invokes renders and effects. Dev timings therefore over-report cost and mislead about where it is. Use a profiling-enabled production build so the numbers reflect what users experience.
