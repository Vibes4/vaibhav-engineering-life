Redis Mastery

Redis is an in-memory, single-threaded data-structure server that answers most commands in tens of microseconds because everything lives in RAM, commands run one-at-a-time on an event loop (no locks), and its core structures are O(1) or O(log n). This page pushes past "Redis is a cache" into forks, copy-on-write, hash slots, eviction sampling, and the war stories that actually get asked at Staff level.

Interview Explanation — 30 seconds

Say this: "Redis is an in-memory key-value store where the value can be a rich data structure — string, hash, list, set, sorted set, stream, bitmap, HyperLogLog. A single thread executes commands off an event loop, so every command is atomic and there's zero lock contention; that's why p99 is sub-millisecond. It persists via RDB snapshots and/or an append-only file, replicates asynchronously to replicas, and scales horizontally with Redis Cluster across 16384 hash slots. I reach for it as a cache, rate limiter, leaderboard, session store, distributed lock, and lightweight queue."

Interview Explanation — 2 minutes

The fuller answer names the internals an interviewer is fishing for:

  • Execution model: one thread runs an event loop (epoll on Linux) that multiplexes client sockets. Commands are dequeued and executed serially, so there are no data races and no mutexes on the data. Redis 6+ added threaded I/O — extra threads only parse/write socket buffers; command execution stays single-threaded.
  • Data structures: each has an internal encoding that Redis switches based on size — small hashes are a listpack (was ziplist), large ones a real hashtable; small sorted sets are a listpack, large ones a skiplist plus hashtable. This gives O(1)/O(log n) with tiny memory for small objects.
  • Persistence: RDB is a point-in-time snapshot written by a forked child using copy-on-write; AOF logs every write and can fsync everysec (default) or always. Redis 7 ships a multi-part AOF + RDB preamble hybrid for fast restart and small files.
  • Replication: asynchronous, replicas serve reads; PSYNC allows partial resync from a backlog buffer after a blip instead of a full snapshot transfer.
  • HA & scale: Sentinel gives automatic failover with quorum on a single dataset; Redis Cluster shards data across 16384 slots (key hashed with CRC16 mod 16384), nodes gossip health, and clients follow MOVED/ASK redirects.
  • Atomicity toolkit: single commands are atomic; MULTI/EXEC batches them (no rollback); Lua EVAL runs a whole script atomically on the single thread — the go-to for read-modify-write.

Internal Working

  1. Accept & multiplex: the main thread runs aeMain(), an event loop over an epoll (Linux) / kqueue (BSD) file-descriptor set. Each connected client is a client struct with input/output buffers.
  2. Parse (RESP): bytes are parsed as the RESP protocol into an argv array. In Redis 6+, this parse and the reply write-back can be offloaded to I/O threads (io-threads 4), but the actual command still runs on the main thread.
  3. Lookup: the command name maps to a redisCommand in a dispatch table; the key is looked up in the per-database dict (an open-chaining hashtable of dictEntry). The dict does incremental rehashing: when load factor crosses ~1, it allocates a second table and migrates a few buckets per operation so no single command stalls.
  4. Execute: the command function mutates the value in place. Because only one command runs at a time, the mutation is atomic with no locking.
  5. Propagate: the write is appended to the AOF buffer (if enabled) and to the replication backlog / replica output buffers, then keyspace-notification pub/sub if subscribed.
  6. Reply: the RESP-encoded reply is queued on the client's output buffer and flushed by the loop (or an I/O thread).
  7. Background housekeeping: a serverCron timer (default 10 Hz, hz) runs active expiration (samples keys with TTL and deletes expired ones), triggers eviction when over maxmemory, resizes dicts, and starts RDB/AOF children.
  8. Expiration: two mechanisms — lazy (on access, if expired, delete and return nil) and active (serverCron samples 20 keys from the expires dict; if >25% were expired it repeats). This is probabilistic, so a key can sit expired-but-present until sampled or accessed.
Say this: "Single-threaded isn't a limitation, it's the design: no locks, deterministic atomicity, and cache-friendly execution. You scale out with more shards, not more threads per shard."

Why was this built?

Salvatore Sanfilippo built Redis in 2009 while scaling LLOOGG, a real-time web analytics tool. MySQL couldn't keep up with the write rate for a live "last N events" list. Memcached could cache but only stored opaque blobs — you couldn't push to a list, increment a counter atomically, or range-query a sorted set server-side; you had to read-modify-write over the network, which was racy and slow. Redis's insight: put data structures on the server so the operation happens next to the data, atomically. Before Redis, people bolted together Memcached for caching, a RDBMS row for counters (with row locks and contention), and cron jobs for leaderboards. Redis collapsed all of that into one sub-millisecond server.

Advantages

  • Latency: in-memory + O(1) hashing gives p50 ~50-100µs, p99 sub-millisecond for point ops.
  • Atomicity for free: single-threaded execution makes every command atomic; complex atomic logic via Lua.
  • Rich structures: sorted sets, HLL, bitmaps, streams — solve leaderboards, cardinality, and queues without app-side logic.
  • Throughput: a single instance sustains 100k-1M+ ops/sec depending on pipelining and command cost.
  • Operational maturity: replication, Sentinel, Cluster, managed offerings (ElastiCache, MemoryStore, Redis Enterprise).

Drawbacks

  • RAM cost: data must fit in memory (plus overhead + fork headroom); expensive per GB vs disk stores.
  • Async replication: failover can lose recent writes; not linearizable by default.
  • Fork spikes: RDB/AOF-rewrite forks the process; on a large heap the copy-on-write page faults cause latency blips and can OOM.
  • Single-thread ceiling: one expensive command (KEYS *, big SORT, large SUNIONSTORE) blocks the whole instance.
  • Cluster limits: multi-key ops must share a hash slot (hash tags); no cross-slot transactions.

Trade-offs

  • Durability vs latency: appendfsync always is durable per-write but ~1 order of magnitude slower; everysec risks losing ~1s of writes on crash but is fast.
  • Consistency vs availability: replicas serve stale reads (async); Cluster favors availability, so a minority partition stops serving its slots rather than diverging.
  • Memory vs CPU: compact listpack encodings save RAM but are O(n) to scan; upgrading to hashtable/skiplist costs memory for speed.
  • Snapshot vs log: RDB restarts fast and is compact but loses data since last save; AOF is more durable but larger and slower to load. Hybrid gets both.
  • Lock safety vs simplicity: a single-node SET NX PX lock is simple but unsafe on failover; Redlock adds nodes but is contested (Kleppmann's critique).

When NOT to use it

Watch out — anti-use-cases:
  • System of record needing strong durability — async replication + everysec fsync can lose writes. Use Postgres/DynamoDB.
  • Dataset far larger than RAM — you'll pay huge $$ or thrash eviction. Use a disk store or Aerospike.
  • Strong distributed coordination / leader election — use etcd/ZooKeeper (Raft), not Redlock.
  • Complex queries / joins / secondary indexes — Redis has no query planner. Use a real DB (or RediSearch module deliberately).
  • Huge durable event log with replay — Kafka beats Redis Streams past a point.
  • Storing giant values (multi-MB blobs) — big keys block the single thread and bloat replication. Use object storage.

Production Architecture

A typical production topology: app servers talk to a Redis Cluster of primary shards, each with 1-2 async replicas in separate availability zones. Sentinel is used instead when you run a single non-sharded dataset. Managed services (ElastiCache/MemoryStore) wrap this with automated failover and backups.

flowchart TD
  App["App servers"] --> LB["Smart client - slot map"]
  LB --> P1["Shard 1 primary - slots 0-5460"]
  LB --> P2["Shard 2 primary - slots 5461-10922"]
  LB --> P3["Shard 3 primary - slots 10923-16383"]
  P1 --> R1["Replica AZ-b"]
  P2 --> R2["Replica AZ-b"]
  P3 --> R3["Replica AZ-b"]
  P1 -. gossip .- P2
  P2 -. gossip .- P3
  P3 -. gossip .- P1

The client caches the slot-to-node map. On a MOVED redirect (slot permanently on another node) it refreshes the map; on ASK (slot mid-migration) it retries once on the target without caching. Primaries gossip over the cluster bus (port +10000) to detect failures; when a majority of primaries agree a node is down (PFAIL to FAIL), a replica is promoted.

Production Problems

  • Cache stampede / thundering herd: a hot key expires and thousands of requests miss and hit the DB simultaneously. Fix with a mutex/lock on rebuild, probabilistic early expiration, or serving stale-while-revalidate.
  • Hot key: one key (e.g. a celebrity's profile) gets millions of ops/sec, saturating one shard's single thread. Fix with client-side caching, local replicas, or key-splitting.
  • Big key: a single huge hash/list; operations on it block the loop and it makes migration/eviction lumpy. Fix by breaking into smaller keys.
  • Fork latency: BGSAVE on a 50 GB instance forks and COW page-copies spike latency and memory; can trigger OOM-killer without enough headroom.
  • Eviction storms: hitting maxmemory with noeviction returns errors on writes; with LRU it starts evicting hot data if undersized.
  • Synchronized TTLs: mass-expiry at the same second causes a miss cliff and CPU spike from active expiration.

Debugging Guide

# What is slow? enable + read the slowlog (microseconds)
redis-cli CONFIG SET slowlog-log-slower-than 10000
redis-cli SLOWLOG GET 10

# Live command sampling (careful, adds load)
redis-cli MONITOR | head

# Latency spikes (built-in monitor + doctor)
redis-cli --latency-history
redis-cli LATENCY DOCTOR
redis-cli LATENCY RESET

# Find hot keys / big keys WITHOUT blocking (samples, uses SCAN)
redis-cli --hotkeys
redis-cli --bigkeys
redis-cli --memkeys

# Never do KEYS * in prod — use SCAN with a cursor
redis-cli SCAN 0 MATCH "session:*" COUNT 100

# Memory breakdown & fragmentation
redis-cli INFO memory | grep -E "used_memory|fragmentation|maxmemory"
redis-cli MEMORY USAGE mykey
redis-cli MEMORY DOCTOR

# Replication + persistence health
redis-cli INFO replication
redis-cli INFO persistence | grep -E "rdb_last_bgsave_status|aof_last_write_status|loading"
Say this: "First thing I check is SLOWLOG and LATENCY DOCTOR. If latency is uniform it's usually fork/COW during BGSAVE or an O(n) command like KEYS or a big ZRANGEBYSCORE; if it's per-key it's a hot or big key, found with --hotkeys / --bigkeys."

Scaling

Vertical: bigger box (more RAM/faster CPU). One instance uses one core for commands, so vertical scaling hits a single-thread ceiling around a few hundred k ops/sec for non-trivial commands. Horizontal: Redis Cluster shards the keyspace into 16384 slots; add shards and reshard (move slots) to spread memory and CPU. Reads scale by adding replicas and enabling READONLY on the client.

flowchart LR
  K["key = user:42"] --> H["CRC16 mod 16384"]
  H --> S["slot 866"]
  S --> N["mapped to Shard 1"]
  N --> W["writes go to primary"]
  N --> RR["READONLY reads to replica"]
  • Hash tags: {user:42}:profile and {user:42}:cart hash on the {user:42} substring, so they land on the same slot — needed for multi-key ops (MGET, MULTI, Lua touching multiple keys) in Cluster.
  • Resharding: redis-cli --cluster reshard migrates slots key-by-key; clients see ASK redirects during migration.
  • Limits: up to ~1000 nodes recommended; 16384 slots caps practical shard count. Each shard is still single-threaded per command.

Security

  • AuthN: legacy requirepass; Redis 6+ ACLs (ACL SETUSER) give per-user command/key/channel permissions and passwords. Always disable the default user or set a strong password.
  • AuthZ: ACL rules like +@read ~cache:* -@dangerous restrict a user to read commands on a key pattern and block FLUSHALL/CONFIG/KEYS.
  • Encryption in transit: native TLS (tls-port, cert/key/ca config) since Redis 6. Terminate TLS on the server, not a sidecar, for real protection.
  • Encryption at rest: Redis doesn't encrypt RDB/AOF itself — rely on encrypted volumes (LUKS, EBS/KMS) or managed-service encryption.
  • Network isolation: bind to private interfaces, never expose 6379 to the internet, use security groups/VPC. Enable protected-mode.
  • Common CVEs / abuse: unauthenticated Redis on the internet has been used to write SSH keys / cron jobs via CONFIG SET dir + SAVE; Lua sandbox escapes have appeared. rename-command CONFIG "" / FLUSHALL "" to disable dangerous commands.
Watch out: the classic Redis compromise is an open instance where an attacker runs CONFIG SET dir /root/.ssh, CONFIG SET dbfilename authorized_keys, then SAVE. Firewall + ACL + protected-mode + renamed CONFIG closes it.

Performance

  • Point op latency: ~50-100µs p50, sub-ms p99 on the same host; add network RTT for remote clients.
  • Pipelining: batching N commands into one round trip turns N RTTs into 1 — throughput jumps 5-10x for chatty workloads. Use it instead of many sequential calls.
  • Connection reuse: use a pool; TCP + auth handshake per op destroys throughput. Watch out for connection storms from serverless.
  • Avoid O(n) on big collections: KEYS, SMEMBERS on a million-element set, LRANGE 0 -1 — all block the single thread. Use SCAN/SSCAN/HSCAN cursors and ranged reads.
  • Value size: keep values small; multi-MB values increase memory copies, replication bytes, and COW faults.
  • Tuning knobs: io-threads (parse/write parallelism), maxmemory-policy, maxmemory-samples 5 (LRU/LFU accuracy vs CPU), hz (background task frequency), activedefrag yes (online defrag when fragmentation high), lazyfree-lazy-eviction/expire yes (free big keys in a background thread to avoid blocking).
  • THP: disable Transparent Huge Pages — they cause large COW latency spikes during fork.

Common Mistakes

  • Running KEYS * in prod — O(n), blocks everything. Fix: SCAN.
  • No maxmemory / no eviction policy — instance grows until OOM-killed. Fix: set maxmemory + allkeys-lru/lfu.
  • Assuming MULTI/EXEC rolls back — it doesn't; a command that errors at runtime still lets the others run. Fix: validate first or use Lua.
  • Using Redis as a durable queue/DB and losing data on failover. Fix: understand async replication; use Streams with persistence + acks or a real broker.
  • Same TTL for everything → synchronized expiry cliff. Fix: add jitter (ttl + rand(0..10%)).
  • Non-atomic distributed lock (SETNX then EXPIRE) → crash between the two leaks a lock forever. Fix: single SET key val NX PX ms; release with a Lua compare-and-del.
  • Ignoring big keys until migration/eviction stalls. Fix: --bigkeys in CI, split large structures.
  • One giant connection or new connection per request. Fix: pooled, reused connections.

  2. If it's single-threaded, how does Redis 6 use threads?
    • Note: I/O threads parse/write sockets; command execution stays single-threaded.
  3. Walk me through what happens when a GET arrives.
    • Note: epoll → RESP parse → dict lookup → execute → reply buffer → flush.
  4. How does the main dict avoid stalling when it grows?
    • Note: incremental rehash — two tables, migrate a few buckets per op.
  5. How are TTLs actually enforced?
    • Note: lazy on access + active sampling (20 keys, repeat if >25% expired).
  6. Why does a sorted set need both a skiplist and a hashtable?
    • Note: skiplist for ordered range O(log n); hashtable for O(1) score lookup by member.
  7. Compare RDB vs AOF; which would you pick?
    • Note: RDB compact/fast-restart but loses data; AOF durable but big; hybrid in Redis 7.
  8. Explain copy-on-write during BGSAVE and its risk.
    • Note: fork shares pages; writes duplicate pages; heavy writes can double memory / OOM.
  9. Your instance hit maxmemory — what happens next?
    • Note: depends on policy — noeviction errors writes, allkeys-lru/lfu evict by sampled recency/frequency.
  10. How does approximate LRU work and why approximate?
    • Note: samples maxmemory-samples keys, evicts oldest of sample; true LRU needs a global list = too costly.
  11. How does Redis Cluster route a key?
    • Note: CRC16(key) mod 16384 → slot → node; MOVED/ASK redirects; hash tags for co-location.
  12. What can't you do across slots, and how do you work around it?
    • Note: no cross-slot multi-key/transactions; use hash tags to force same slot.
  13. How does failover happen in Cluster vs Sentinel?
    • Note: Cluster gossip PFAIL→FAIL + replica election by majority of primaries; Sentinel quorum votes a leader that promotes a replica.
  14. Can you lose data on failover? Why?
    • Note: yes — async replication, promoted replica may lack the last unacked writes.
  15. Is a Redis distributed lock safe? Discuss Redlock.
    • Note: single-node SET NX PX is best-effort; Redlock adds N nodes; Kleppmann critiques clock/GC-pause assumptions — use fencing tokens.
  16. How do you fix a cache stampede on a hot key?
    • Note: rebuild lock, probabilistic early expiry, stale-while-revalidate, TTL jitter.
  17. How would you find and fix a latency spike in prod?
    • Note: SLOWLOG, LATENCY DOCTOR; check BGSAVE fork, O(n) commands, big/hot keys, swap.
  18. How do you scale reads vs writes?
    • Note: reads via replicas + READONLY; writes via more shards (resharding slots).
  19. Does MULTI/EXEC give you rollback? What about WAIT?
    • Note: no rollback; WAIT blocks until N replicas ack, buying stronger (not guaranteed) durability.
  20. When would you not use Redis at all?
    • Note: system-of-record durability, data >> RAM, strong coordination, complex queries.

Common Cross Questions

  • After caching → they ask about cache patterns: cache-aside vs read-through vs write-through vs write-behind; invalidation; hit-ratio math. Angle: cache-aside is default; name TTL + jitter + stampede protection.
  • After persistence → durability & the CAP/PACELC pivot: where Redis sits (AP-ish, async). Angle: acknowledge you can lose recent writes; WAIT and AOF always tighten it at a latency cost.
  • After Cluster → consistent hashing & sharding: why 16384 slots (not consistent-hash ring), resharding, hot-shard rebalancing. Angle: slots decouple keys from nodes so you move slots not rehash everything.
  • After locks → consensus: Raft/Paxos, etcd/ZooKeeper, fencing tokens, split-brain. Angle: Redis locks aren't consensus; for correctness-critical locking use a consensus store.
  • After Streams → message queues: Kafka vs RabbitMQ vs SQS, consumer groups, at-least-once, dedup. Angle: Streams gives consumer groups + acks but isn't a durable log at Kafka scale.
  • After eviction → memory management: jemalloc, fragmentation, active-defrag, LFU vs LRU. Angle: fragmentation ratio and defrag; LFU better for skewed access.

Scenario 1 — Cache stampede takes down the database

SymptomsDB CPU spikes to 100% every hour on the minute; app p99 balloons; Redis hit ratio momentarily craters.
InvestigationCorrelate DB spike timing with cache TTLs; INFO stats shows expired_keys spike; all requests for one popular key miss simultaneously.
Root CausePopular keys were written with identical TTL, so they expired together; thousands of concurrent misses hit the DB (thundering herd).

Interview Answer"Classic stampede: synchronized TTLs meant a hot key's expiry sent all traffic to the DB. I fixed it with a rebuild mutex plus TTL jitter and stale-while-revalidate, so exactly one request repopulates while others serve slightly stale data."

Scenario 2 — Latency spikes every few minutes

SymptomsPeriodic p99 jumps from 0.5ms to 200ms+; timeouts on the client; ops/sec briefly dips.
InvestigationLATENCY DOCTOR flags fork; INFO persistence shows latest_fork_usec high and BGSAVE timing aligns with spikes; THP enabled.
Root CauseBGSAVE forks a multi-GB process; copy-on-write page faults plus Transparent Huge Pages make the fork and subsequent writes expensive.

Interview Answer"The spikes lined up with BGSAVE. Fork plus copy-on-write with THP on caused the stalls. I disabled THP, offloaded persistence to a replica, and left headroom for COW — spikes went away."

Scenario 3 — One shard is red-hot while others idle

SymptomsOne Cluster shard at 100% CPU, others at 10%; throughput capped; that shard's commands queue up.
Investigationredis-cli --hotkeys on the hot shard reveals a single key with millions of GETs (a celebrity/global config); it hashes to that shard's slot.
Root CauseHot key concentrates all traffic on one single-threaded shard; sharding doesn't help because it's one key.

Interview Answer"Sharding can't fix a single hot key since it lives on one thread. I added client-side/near caching for that key and, where writes allowed, split it into N shadow keys read at random to spread the load."

Scenario 4 — Writes suddenly start failing

SymptomsClients get OOM command not allowed when used memory > 'maxmemory'; reads fine, writes rejected.
InvestigationINFO memory shows used_memory at maxmemory; maxmemory-policy is noeviction; evicted_keys = 0.
Root CauseInstance filled up and the policy is noeviction, so it refuses writes rather than evict — often because someone stored data without TTLs.
SolutionImmediate: raise maxmemory or delete big keys. Proper: switch to allkeys-lru/allkeys-lfu if it's a cache, add TTLs, split big keys.

Interview Answer"It was maxmemory + noeviction — correct for a datastore, wrong for a cache. Data was written without TTLs and filled the heap. I set allkeys-lfu, added TTLs, and alerted at 80%."

Scenario 5 — Distributed lock let two workers run the same job

SymptomsA "run once" job executed twice; duplicate charges/emails; logs show two holders of the same lock key.
InvestigationLock acquired with SET lock 1 NX PX 30000; a GC pause / failover exceeded 30s; the lock expired and another worker grabbed it while the first was still running.
Root CauseRedis locks are time-bounded and best-effort; a process pause longer than the TTL, plus async-replicated failover, breaks mutual exclusion.
SolutionAdd fencing tokens (monotonic counter) so the protected resource rejects a stale holder; shorten work units; release with Lua CAS-delete; consider etcd for correctness-critical locks.
PreventionDesign idempotent jobs, use fencing tokens, don't rely on a single Redis lock for correctness (Redlock still can't beat clock/pause assumptions).
Interview Answer"The lock TTL expired during a GC pause, so two workers held it. Redis locks are best-effort; I added fencing tokens so the downstream rejects stale holders and made the job idempotent — and for anything that must be exactly-once I'd use a consensus store."

🎯 Deep-dive Q&A — model answers

Why is a single-threaded server faster than a multi-threaded one here?

For in-memory point operations the bottleneck isn't CPU, it's coordination. A single thread removes all locking, cache-line contention, and context-switch overhead, and keeps execution deterministic and CPU-cache-friendly. Every command is implicitly atomic. You'd only benefit from multiple threads if commands were CPU-heavy; instead Redis keeps them O(1)/O(log n) and scales out with shards. Redis 6 added I/O threads precisely because at very high throughput the syscall read/write and RESP parsing did become a bottleneck — but the data-touching code stays single-threaded to preserve the no-lock invariant.

Explain incremental rehashing and why it matters for tail latency.

The main keyspace is a dict with two hash tables, ht[0] and ht[1]. When the load factor crosses ~1, Redis allocates ht[1] at double size and sets a rehashidx. Instead of migrating all buckets at once (which on a large dict would freeze the server for seconds), each dictionary operation migrates a few buckets from ht[0] to ht[1], and serverCron does a time-boxed batch. During rehash, lookups check both tables and writes go to ht[1]. This amortizes the resize so no single command pays the O(n) cost — critical for keeping p99 flat as the dataset grows.

Walk through copy-on-write during BGSAVE and when it hurts.

BGSAVE calls fork(). The child shares the parent's physical pages read-only via the page tables. The child serializes a consistent snapshot while the parent keeps serving. When the parent writes to a shared page, the kernel traps, copies that 4KB page (or a huge page under THP), and gives the parent its own copy. If the write rate is high, many pages get duplicated, so memory can approach 2x the dataset — which is why you need fork headroom and why heavy-write instances OOM during snapshots. THP makes each COW copy 2MB instead of 4KB, amplifying both latency and memory, so you disable THP. Best practice: snapshot on a replica.

How does approximate LRU/LFU eviction actually work, and why not exact?

Exact LRU needs a doubly-linked list touched on every access to keep global recency order — extra memory per key and pointer churn on the hot path. Redis instead stores a 24-bit clock (LRU) or an 8-bit logarithmic counter (LFU) in each object header. On eviction it samples maxmemory-samples keys (default 5) and evicts the best candidate from the sample, keeping a small pool of good candidates across calls. Higher samples approach true LRU at more CPU. LFU uses a probabilistic counter that increments logarithmically and decays over time, so it tracks frequency, not just recency — better for skewed workloads where a rarely-but-recently accessed key shouldn't evict a frequently-hot one.

Why 16384 hash slots, and why CRC16 rather than a consistent-hash ring?

Slots decouple keys from nodes: a key maps to a fixed slot via CRC16(key) mod 16384, and slots are assigned to nodes. To rebalance you move slots between nodes without rehashing keys — resharding is just reassigning slot ownership and migrating those keys. 16384 was chosen because the cluster bus gossips a bitmap of each node's slots in heartbeats; 16384 bits is 2KB, small enough to send frequently, while still giving fine-enough granularity for up to ~1000 nodes. A pure consistent-hash ring would make multi-key locality (hash tags) and slot migration messier.

Does MULTI/EXEC give ACID, and what exactly happens on an error?

It gives Isolation and Atomicity-of-execution (commands run sequentially with nothing interleaved) but NOT rollback. Errors split into two kinds: a syntax/wrong-arity error detected at queue time aborts the whole transaction (EXEC returns an error, nothing runs). A runtime error — e.g. INCR on a string — is only discovered during EXEC; that one command fails but every other queued command still executes and is committed. There is no undo. For real read-modify-write atomicity with conditional logic you use WATCH (optimistic locking, EXEC returns nil if a watched key changed) or, more commonly, a Lua script which runs atomically and lets you branch on values.

How does PSYNC partial resynchronization work?

The primary keeps a fixed-size circular replication backlog and a replication offset, plus a replication ID. When a replica reconnects it sends PSYNC replid offset. If the replid matches and the requested offset is still within the backlog, the primary streams just the missing bytes (partial resync) — no full snapshot. If the offset has fallen out of the backlog or the replid changed (e.g. after a failover), it falls back to a full resync: BGSAVE (or diskless socket transfer) plus buffered commands. Sizing repl-backlog-size big enough to cover expected disconnect windows avoids expensive full resyncs on brief network blips.

Is Redlock safe? Summarize the debate.

Redlock acquires a lock on a majority of N independent Redis nodes with a TTL, computing remaining validity after network delays. Martin Kleppmann's critique: it relies on bounded clock drift and bounded process pauses, which don't hold — a GC pause or VM freeze longer than the TTL lets the lock expire while the holder still thinks it owns it, and NTP jumps break the timing math. His conclusion: for efficiency (avoid duplicate work) Redlock is fine; for correctness (mutual exclusion that must never be violated) you need fencing tokens — a monotonically increasing number checked by the resource — or a real consensus system. Antirez rebutted parts, but the practical takeaway is: add fencing tokens and make operations idempotent.

How would you build a rate limiter in Redis?

Simplest: fixed window — INCR user:api:{minute} with EXPIRE on first hit; reject over the limit. It's atomic but allows 2x burst at window edges. Better: sliding-window log using a sorted set — ZADD the timestamp, ZREMRANGEBYSCORE to drop old entries, ZCARD to count, all in one Lua script for atomicity. Best for smoothness: token bucket in Lua storing tokens + last-refill timestamp, refilling based on elapsed time. Put it in a Lua script so the read-check-write is atomic on the single thread; in Cluster, include the identity in a hash tag so all keys land on one slot.

What's the difference between listpack, quicklist, and skiplist and when do they matter?

A listpack (formerly ziplist) is a single contiguous, serialized blob of entries — extremely memory-efficient for small collections but O(n) to modify. A quicklist is a linked list of listpack nodes used by large lists, giving O(1) push/pop at ends while keeping memory compact. A skiplist is a probabilistic multi-level linked list giving O(log n) ordered operations, used by large sorted sets alongside a hashtable (member→score). Redis picks the encoding by size thresholds (e.g. zset-max-listpack-entries); small objects stay compact, large ones get the fast structure. This matters because a big collection accidentally kept as a listpack would be O(n), and iterating a huge structure blocks the single thread.

How do you achieve stronger durability, and what does WAIT do?

Layer the knobs: appendonly yes with appendfsync always makes each write durable to the local disk before ack (slow). WAIT numreplicas timeout blocks the client until the write has been acknowledged by that many replicas, giving you replicated durability on demand — but it's still not a distributed commit, and a timeout returns how many actually acked so you must handle partial success. Redis 7's multi-part AOF plus the RDB preamble speeds restart. Even with all of this, failover can lose writes that were acked locally but not yet replicated, so for true no-loss you combine WAIT with min-replica settings and accept the latency.

How do keyspace notifications and client-side caching work?

Keyspace notifications publish events (__keyspace@0__:mykey / __keyevent@0__:expired) via pub/sub when keys change, gated by notify-keyspace-events flags — useful for cache invalidation or expiry hooks (note pub/sub is fire-and-forget, no delivery guarantee). Client-side caching (RESP3 tracking, the "Redis as a near cache" feature) lets the client cache values locally; the server tracks which keys each client cached and pushes an invalidation message when they change, either in default mode (server remembers keys per client) or broadcast mode (client subscribes to key prefixes). This slashes round trips for hot read-mostly keys — the fix for a hot-key hotspot.

Why can memory fragmentation ratio be below 1, and why is that bad?

mem_fragmentation_ratio = RSS / used_memory. Above 1 is normal fragmentation (allocator overhead, freed-but-not-returned pages) — jemalloc holds freed memory in size classes rather than returning it to the OS. A ratio below 1 means the resident set is smaller than the logical memory Redis thinks it's using, which almost always means the OS has swapped Redis pages to disk. Swap is catastrophic for Redis: a page fault on a swapped page turns a microsecond operation into a millisecond+ disk read while blocking the single thread. The fix is to never let Redis swap (set memory limits, disable overcommit surprises) and to run activedefrag or restart to reclaim high fragmentation above ~1.5.

MOVED vs ASK redirection — what's the difference?

Both are Cluster redirects but mean different things. MOVED slot host:port means the slot has permanently moved to another node; the client should update its cached slot map and send all future requests for that slot there. ASK slot host:port is temporary — it appears while a slot is mid-migration: some keys have moved, some haven't. The client should send the specific request to the target node prefixed with an ASKING command, but must NOT update its slot map, because ownership hasn't officially transferred yet. Getting this wrong (caching on ASK) causes clients to hammer the wrong node during resharding.

How does HyperLogLog give cardinality in 12KB with ~0.81% error?

HLL hashes each element and uses the position of the leftmost 1-bit (number of leading zeros) as an estimator of magnitude — seeing a run of k zeros suggests roughly 2^k distinct items. To reduce variance it splits the hash into 16384 registers (buckets), each storing the max leading-zero count seen, then combines them with a harmonic mean and bias correction. Redis stores this in a 12KB dense representation (with a sparse form for small cardinalities). So PFADD is O(1), PFCOUNT returns an estimate with a standard error around 0.81%, and you can count billions of unique visitors in 12KB instead of storing every ID. The trade-off is you can't enumerate the members, only estimate the count.

Streams vs Lists vs Pub/Sub for queuing — how do you choose?

Pub/Sub is fire-and-forget with no persistence — a subscriber that's offline misses messages; use it for live fan-out where loss is acceptable. Lists (LPUSH/BRPOP) give a simple durable-ish work queue but no consumer groups, no acknowledgment, and once popped a message is gone (a crash mid-processing loses it). Streams are the real answer: an append-only log with IDs, consumer groups for load-balanced processing, per-message acknowledgment (XACK), and a pending-entries list so you can claim and reprocess messages a crashed consumer never acked (XPENDING/XCLAIM). Streams give at-least-once semantics. Past very high throughput or long retention with replay, Kafka is the better fit; Streams shines for moderate volumes where you already run Redis.
