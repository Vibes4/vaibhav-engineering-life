AWS: API Gateway, SQS, SNS & Event-Driven EY Sheet 05

The JD says "leveraging managed services and event-driven architectures" and lists API Gateway, SNS, SQS as primary skills. This is the highest-probability section on the whole sheet — if you prepare one AWS topic properly, prepare this one. The examiner wants to hear the words idempotency, dead-letter queue, at-least-once and backpressure come out of your mouth unprompted.

The line that wins this section: "My rule is: SQS when one consumer must do the work, SNS when many consumers must be told, EventBridge when I want routing and filtering decoupled from the producer, and Kinesis or MSK when I need ordered, replayable history. And because every one of these is at-least-once, consumers are idempotent by default — I treat idempotency as a design requirement, not a bug fix."

Choosing the right integration service

Subscribing Lambdas directly to SNS works but leaves you with SNS's retry semantics instead of a queue you can inspect and drain.

CertainSQS Standard vs FIFO — and how do you get exactly-once on Standard?

Standard: nearly unlimited throughput, best-effort ordering, at-least-once delivery. FIFO: strict ordering within a message group, provider-side deduplication over a 5-minute window, but throughput capped (300 msg/s, 3,000 with batching, higher with high-throughput mode) and ordering forces serial processing per group, which limits parallelism.

Exactly-once doesn't exist in distributed messaging — that's the answer they want to hear. What you build is at-least-once delivery plus idempotent processing, which is observably equivalent. Concretely: every message carries an idempotency key (a business key like orderId, or a producer-generated UUID). Before performing the side effect, the consumer does a conditional write to a dedup store — in DynamoDB, PutItem with attribute_not_exists(pk) and a TTL. If the condition fails, the message is a duplicate and is acknowledged without reprocessing. For non-idempotent effects like charging a card, the effect and the dedup record must be in the same transaction (DynamoDB TransactWriteItems, or the relational DB's own transaction) — otherwise there's a window where you charge and then crash before recording it.

I'd choose FIFO only when ordering is a genuine business requirement (e.g. account balance mutations for one account) and I'd scope the message group as narrowly as possible — MessageGroupId = accountId, not a single global group, so different accounts still process in parallel.

Depth probeExplain visibility timeout, and the bug it causes.

When a consumer receives a message, SQS doesn't delete it — it hides it for the visibility timeout. If the consumer deletes it within that window, it's gone. If not, the message becomes visible again and another consumer picks it up.

The bug: if processing takes longer than the visibility timeout, the message reappears while the first consumer is still working on it, so two workers process the same message concurrently — and the first one's eventual delete may even remove a message a second consumer is now holding. Symptoms are duplicate side effects and a queue that never drains because work is being redone.

Fixes: set the visibility timeout above your realistic p99 processing time (for Lambda, at least 6x the function timeout is the standard recommendation, since the event source mapping batches); call ChangeMessageVisibility to extend the lease for genuinely long jobs (a heartbeat); and cap it with maxReceiveCount so a message that keeps failing goes to the DLQ instead of looping forever.

CertainWhat is a dead-letter queue and how do you operate one?

A DLQ is a separate queue that receives messages which have been received maxReceiveCount times without being deleted — i.e. repeatedly failed. Its purpose is to stop a poison message (malformed payload, a record that triggers a bug) from blocking the queue forever and burning retry budget.

Operating it properly, which is what distinguishes a real answer:

  • Alarm on ApproximateNumberOfMessagesVisible > 0 on the DLQ. A DLQ nobody watches is a silent data-loss bucket. This is the single most common gap I'd flag in a review.
  • Set retention on the DLQ to the maximum (14 days) so you have time to investigate, and longer than the source queue's.
  • Triage, don't blind-redrive. Inspect a sample: is it a transient downstream outage (safe to redrive once the downstream is healthy), a data problem (fix the record or discard deliberately), or a code bug (deploy the fix first, then redrive)? SQS has a built-in redrive-to-source feature now.
  • For Lambda event source mappings, also use bisectBatchOnFunctionError and maxRecordAge/maxRetryAttempts, plus an on-failure destination — otherwise one bad record in a Kinesis/DynamoDB Stream batch stalls the entire shard until the record expires.
SQS is backing up and consumers can't keep up. What do you do?

First measure the right thing: ApproximateAgeOfOldestMessage is the metric that matters, not queue depth — depth tells you volume, age tells you how far behind you are against the SLA.

Then diagnose whether it's a throughput problem or a stuck problem. Stuck: consumers are erroring and messages keep reappearing (check DLQ growth and error rates). Throughput: consumers are succeeding but there aren't enough of them, or each one is too slow.

Levers, cheapest first: (1) increase consumer concurrency — Lambda event source mapping batch size and maximum concurrency, or the ECS service's desired count with auto-scaling driven by the queue-age metric, which is the correct scaling signal here. (2) Batch — process 10 messages per invocation instead of 1, and batch the downstream writes too; this is often a 5–10x win for free. (3) Find the actual bottleneck — usually it's a downstream database or third-party API, in which case adding consumers makes things worse, not better, and the honest answer is to rate-limit consumers to protect the downstream and accept the backlog. (4) If the work is genuinely too slow per message, split it into stages with a queue between them so the slow stage scales independently.

And the thing to say at the end: "A backing-up queue is doing its job — it's absorbing the spike instead of dropping requests. The question is whether the oldest-message age is inside the business SLA, not whether the depth is zero."

API Gateway

CertainREST API vs HTTP API vs ALB in front of Lambda — which and why?

HTTP API is my default for new work: roughly 70% cheaper than REST API, lower latency, and it covers what most services need — JWT authorizers, CORS, routing, stage variables.

REST API when I need features HTTP API doesn't have: request/response transformation via mapping templates, API keys and usage plans for partner throttling, request validation against a model, WAF integration, private APIs via VPC endpoints, caching, or Lambda authorizers with fine-grained IAM policy output.

ALB → Lambda when the traffic is high-volume and I just need routing without API-management features — ALB is cheaper at very high request volumes and I'm already paying for it for my container services. But I lose throttling, API keys, request validation and usage plans.

The framing: API Gateway is an API management product, not just a router. If I'm not using the management features, I'm paying for them for nothing.

How do you secure and throttle an API Gateway endpoint?

AuthN/AuthZ — pick one: IAM authorization for service-to-service or internal callers (SigV4-signed requests, no token management); a JWT authorizer validating tokens from Cognito or any OIDC provider for end users; or a Lambda authorizer when authorization logic is custom — and cache the authorizer result by token so you don't invoke it on every request.

Throttling — three layers: account-level limits, per-stage/per-method throttle settings (steady-state rate plus burst, implemented as a token bucket), and usage plans with API keys for per-client quotas when you're exposing the API to partners. Throttled requests get a 429, and the client is expected to back off — I'd document the Retry-After behaviour.

Plus: WAF in front for injection/bot rules and IP reputation, request validation against a JSON schema so malformed payloads never reach Lambda (cheaper and safer), mutual TLS for B2B, and a private API with a VPC endpoint when it should never be reachable from the internet at all. For end-user auth specifically, I'd avoid putting authorization logic in the handler when the gateway can reject the request before I pay for compute.

Depth probeDirect service integrations — when should API Gateway skip Lambda entirely?

API Gateway can call AWS services directly — put a message on SQS, write an item to DynamoDB, start a Step Functions execution — with no Lambda in the path. That removes a whole compute hop: no cold start, no Lambda cost, no code to maintain, and one fewer thing that can fail.

I'd use it for write-and-acknowledge endpoints: an ingest endpoint that validates the payload against a request model and drops it on SQS, returning 202 immediately, with the real processing happening asynchronously. That's a genuinely better design than a Lambda whose only job is sqs.sendMessage.

Where I wouldn't: when there's real business logic, when the transformation via VTL mapping templates becomes complex enough to be unreadable and untestable (VTL is miserable to debug and has no unit-test story), or when the response needs composing from multiple sources. The trade-off is honest — you trade Lambda cost and latency for logic that lives in a template nobody on the team wants to own.

Event-driven design

CertainHow do you guarantee that a database write and its event both happen?

This is the dual-write problem: if you write to the database and then publish to SNS/SQS as two separate operations, a crash in between leaves the system inconsistent — the order exists but nothing downstream knows, or you published an event for a write that rolled back. You cannot fix this with try/catch.

Two correct solutions:

  • Transactional outbox — inside the same database transaction, write the business row and a row to an outbox table. A separate relay process (polling the outbox, or a CDC stream) publishes those rows to the broker and marks them sent. Atomicity comes from the database transaction; delivery is at-least-once, so consumers are idempotent.
  • Change Data Capture — with DynamoDB this is nearly free: DynamoDB Streams is itself the outbox. A Lambda on the stream publishes the domain event. With RDS, DMS or Debezium reading the WAL/binlog does the same job.

And the thing to say for credibility: "Two-phase commit across a database and a message broker is the textbook answer and I'd avoid it — it couples availability of the two systems and the operational cost isn't worth it. Outbox plus idempotent consumers is the pattern I'd actually ship."

Orchestration vs choreography — and where do Step Functions fit?

Choreography: services emit events and react to each other's events; no central controller. Maximum decoupling, easy to add a consumer, but the end-to-end flow exists nowhere in the code — you can only reconstruct it from traces, which makes debugging "why didn't this order ship" genuinely hard. Good for loosely-related side effects: send an email, update a search index, bump an analytics counter.

Orchestration: a coordinator explicitly drives the steps. The flow is visible and testable, error handling and compensation are explicit, and you can see exactly where an execution stopped. The cost is coupling — the orchestrator knows about the participants.

Step Functions is managed orchestration: a state machine with built-in retries with exponential backoff, catch/error branches, parallel and Map states, timeouts, and a visual execution history that shows exactly which step failed with what input. That execution history is the reason I reach for it on business-critical multi-step flows — an auditable record per execution is worth a lot on a client engagement. Express workflows for high-volume short flows (cheap, at-least-once), Standard for long-running durable ones (up to a year, exactly-once state transitions).

My rule: orchestrate the core business transaction (order → payment → inventory → fulfilment, with compensations), choreograph the peripheral reactions.

Explain the saga pattern with a concrete compensation.

A saga replaces a distributed transaction with a sequence of local transactions, each with a compensating action that semantically undoes it. There's no global rollback, so the system passes through intermediate states that are visible — which you must design for.

Order example: Create order (pending) → Reserve inventory → Authorise payment → Capture payment → Mark order confirmed. If payment authorisation fails, the compensation runs backwards: release the inventory reservation, then mark the order failed and notify the customer.

The details that matter: compensations must be idempotent (they may run twice) and must be semantic, not literal — you don't un-send an email, you send a cancellation email; you don't un-charge a card, you issue a refund, which leaves a visible trace on the customer's statement. Some steps are genuinely uncompensatable, so you order the saga to do the reversible and most-likely-to-fail steps first and the irreversible ones last. And you need timeouts on every step, because the failure mode in production isn't "step returned an error", it's "step never returned".

How do you version events without breaking consumers?

Treat the event schema as a public API contract. Rules: only additive changes within a version — new optional fields are fine, removing or renaming a field or narrowing a type is a breaking change. Consumers must tolerate unknown fields rather than validating strictly and rejecting; that one discipline removes most breakage.

When you genuinely must break: publish both versions in parallel (OrderCreated.v1 and v2) for a deprecation window, migrate consumers one at a time, then retire v1 — the same expand/migrate/contract shape as a database migration. Carry a version and a schemaUrl or type field in the envelope so consumers can route. Use a registry — EventBridge Schema Registry or Confluent Schema Registry — so the contract is discoverable and can be enforced in CI rather than discovered in production. And keep a stable envelope (eventId, eventType, version, occurredAt, correlationId, payload) so routing and tracing never depend on payload internals.
