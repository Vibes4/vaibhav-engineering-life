MongoDB Mastery

MongoDB is a distributed document database: BSON documents in collections, WiredTiger as the storage engine, replica sets for HA/durability, and range/hash sharding for horizontal scale. This page is the senior-interview deep dive — internals, config knobs, real numbers, and the follow-up drill tree.

Interview Explanation — 30 seconds

Say this: "MongoDB stores schema-flexible BSON documents in collections. Durability and HA come from a replica set — one primary takes writes, secondaries replicate the oplog (a capped collection), and a Raft-like election picks a new primary in ~10-12s if the primary dies. The WiredTiger engine gives document-level concurrency, MVCC snapshots, and checkpoints every 60s backed by a journal WAL. You scale writes horizontally by sharding on a well-chosen shard key. The whole game is picking the shard key and the indexes right up front — get those wrong and you get hot shards, jumbo chunks, and collection scans."

Interview Explanation — 2 minutes

Structure the fuller answer around four layers:

  1. Data model: BSON documents (typed binary JSON — has ObjectId, Date, Decimal128, binary), max 16 MB per doc. You model by embedding (denormalize what's read together) vs referencing (normalize unbounded or independently-updated data). The document is the unit of atomicity.
  2. Storage engine — WiredTiger: B-tree per collection/index, document-level MVCC concurrency (writers don't block readers), an in-memory cache (default 50% of RAM − 1 GB), checkpoints every 60s that flush a consistent snapshot to disk, and a journal (WAL) that group-commits every ~50-100 ms so a crash loses at most that window. Snappy compression on data, prefix compression on indexes.
  3. Replication: A replica set (typically P + 2 S, or P + S + arbiter). Secondaries tail the primary's oplog (an idempotent, capped op log). Elections use a protocol version 1 (Raft-like) with terms and heartbeats every 2s; electionTimeoutMillis default 10s. You tune correctness with write concern (w:1, w:majority, j:true) and read concern (local, majority, linearizable) plus read preference.
  4. Sharding: mongos routers, config servers (a replica set holding the metadata/chunk map), and shards (each a replica set). Data is split into chunks by shard key; the balancer migrates chunks to keep shards even. Hashed vs ranged. Monotonic keys (_id, timestamp) create a hot shard.

Then name the levers: ESR index rule, covered queries, aggregation pipeline, and multi-document ACID transactions (4.0 on replica sets, 4.2 across shards, 60s default limit).

Internal Working

Path of a write

  1. Client sends insert/update to the primary (driver picks primary via topology monitoring).
  2. Query planner resolves the doc; WiredTiger takes a document-level intent lock and writes into its in-memory cache page (MVCC — creates a new version visible at the current snapshot).
  3. The operation is appended to the journal (WAL) in collection-*.wt-adjacent journal files; journal group-commit fsyncs every ~50 ms (or immediately if j:true is requested).
  4. A corresponding idempotent entry is written to the oplog (local.oplog.rs), a capped collection. Idempotent means an update like $inc is rewritten to a $set of the resulting value so replaying is safe.
  5. Secondaries tail the oplog via a long-poll getMore on a cursor, apply ops in parallel batches (by document id to preserve order), and advance their lastApplied optime.
  6. The write's w:majority acknowledgement returns only after a majority of voting members have persisted the op (tracked via replication heartbeats + optime).
  7. Every 60s WiredTiger writes a checkpoint: a consistent on-disk snapshot. After a checkpoint, journal older than the checkpoint can be reclaimed. On crash recovery, WiredTiger loads the last checkpoint and replays the journal forward.

Key data structures

  • B-tree — one per collection (clustered by internal RecordId) and one per index. Leaf pages hold documents/keys; WiredTiger uses copy-on-write pages.
  • Oplog — capped collection, fixed size (default 5% of free disk, min 990 MB, cap ~50 GB), FIFO ring. Its length in time is your replication safety window.
  • MVCC snapshots — read transactions see a point-in-time view; readConcern: "majority" reads the majority-committed snapshot.

Why was this built?

MongoDB (2009, 10gen) targeted the pain of forcing rapidly-evolving, hierarchical app objects into rigid relational tables. Before it, teams either:

  • ran an RDBMS and paid the object-relational impedance mismatch — ORMs, N-way joins to reassemble one screen's object, and migrations that locked tables;
  • bolted on memcached and manual sharding logic in the app to scale reads/writes;
  • used key-value stores that gave scale but no rich queries or secondary indexes.

MongoDB's bet: make the document (a whole aggregate) the unit of storage, indexing, and atomicity, give it secondary indexes and an expressive query language, and bake in replication + sharding so scale is an ops decision, not an app rewrite.

Advantages

  • Schema flexibility — ship features without blocking migrations; polymorphic documents.
  • Locality — read one aggregate in one seek; no joins for the common path.
  • Horizontal scale built-in — sharding + auto-balancing without app-side routing.
  • HA out of the box — replica set failover in ~10-12s, no external coordinator.
  • Rich queries + aggregation pipeline — closest to SQL among document stores; $lookup, $facet, window functions.
  • Document-level concurrency — WiredTiger MVCC means readers never block writers.
  • Tunable consistency/durability — per-operation write/read concern.

Drawbacks

  • 16 MB doc limit and the unbounded-array trap push you to bucketing/referencing.
  • Joins ($lookup) are expensive and can't use the foreign collection's index as efficiently as an RDBMS join.
  • Shard key is nearly immutable (resharding exists since 5.0 but is heavy) — a bad choice haunts you.
  • Transactions are costly — hold locks, 60s limit, and defeat much of the locality advantage.
  • No enforced schema by default — data drift unless you use JSON Schema validation.
  • Working set must fit RAM for good latency; cache eviction thrash kills p99.

Trade-offs

  • Consistency vs availability: w:majority + readConcern:majority gives no-rollback durability but ~2x write latency and a read lag; w:1 is fast but a failover can roll back unacked writes.
  • Durability vs latency: j:true forces a journal fsync per write (adds ~single-digit ms on SSD) vs riding the 50 ms group commit.
  • Embedding vs referencing: embedding = fast reads, atomic single-doc updates, but growth/duplication risk; referencing = normalized but needs $lookup or app-side joins.
  • Read scaling vs staleness: secondaryPreferred spreads reads but serves stale data (replication lag).
  • Hashed vs ranged shard key: hashed = even distribution, no hot shard, but kills range queries and scatter-gathers them; ranged = efficient range scans but risks hot chunks on monotonic keys.

When NOT to use it

Watch out: Reach for something else when — (1) your workload is inherently relational with many-to-many joins and cross-entity invariants (banking ledgers with complex constraints → Postgres); (2) you need true multi-region active-active writes with conflict resolution (→ Cassandra/Dynamo global tables); (3) it's a cache or ephemeral counter (→ Redis); (4) it's full-text search / relevance ranking as the primary need (→ Elasticsearch); (5) heavy OLAP / columnar analytics over billions of rows (→ ClickHouse/BigQuery); (6) you'll routinely store blobs > 16 MB (→ object storage + GridFS only if you must).

Production Architecture

A production sharded cluster: application drivers talk to mongos routers (stateless, often co-located or behind an LB). Routers consult config servers (a 3-node replica set holding the chunk-to-shard map) and route each query to the right shard(s). Each shard is itself a 3-node replica set spread across availability zones. The balancer runs on the config server primary and migrates chunks in the background.

Rules of thumb: 3 config servers, shards as 3-member replica sets across 3 AZs, at least 2 mongos for redundancy, and put a majority of each replica set in a primary region so a single-AZ loss keeps a majority alive.

Production Problems

  • Hot shard / monotonic key — sharding on _id or a timestamp sends all new writes to the max chunk on one shard; the balancer chases it forever.
  • Jumbo chunks — a chunk that can't split (all docs share one shard-key value) exceeds the max chunk size and becomes unmovable.
  • Replication lag — a slow secondary (I/O, index build, long-running op) falls behind; w:majority writes stall and stale reads worsen.
  • Cache eviction thrash — working set > WiredTiger cache → constant page eviction, disk reads, p99 spikes. Watch wiredTiger.cache dirty/eviction stats.
  • Collection scans (COLLSCAN) — a query without a supporting index scans everything; ESR-violating compound index doesn't get used.
  • Unbounded array growth — an $push-forever array grows the doc, causing frequent moves and eventually hitting 16 MB.
  • Oplog window too small — a secondary offline longer than the oplog window needs a full resync.
  • Election storms — flapping network causes repeated failovers; writes error with "not master".

Scaling

Vertical, then read, then shard

  1. Vertical: more RAM so the working set + indexes fit WiredTiger cache; NVMe SSD for journal/checkpoint I/O.
  2. Read scaling: add secondaries and route reads with secondaryPreferred (accept staleness) or use hidden/analytics nodes for reporting.
  3. Write scaling → sharding: the only way to scale writes past one primary. Choose a shard key that is high-cardinality, evenly distributed, and matches your query filter (so queries are targeted, not scatter-gather).
flowchart LR
  W["Write load rising"] --> V["Add RAM and SSD"]
  V --> R["Add secondaries for reads"]
  R --> SH["Shard the collection"]
  SH --> K1["Hashed key even spread"]
  SH --> K2["Ranged key range queries"]
  SH --> B["Balancer spreads chunks"]
  • Chunks default 128 MB; split automatically, migrated by the balancer to equalize chunk count per shard.
  • Compound shard key (e.g. {tenantId:1, orderDate:1}) avoids the monotonic hot-shard problem while keeping locality.
  • Zone sharding pins ranges to specific shards (data residency / tiered storage).
  • Resharding (5.0+) can change the key online but rewrites the whole collection — plan disk + time.
Watch out: A low-cardinality shard key (e.g. country for a mostly-one-country app) caps you at as many chunks as distinct values and creates unsplittable jumbo chunks. Cardinality is king.

Security

  • AuthN: SCRAM-SHA-256 (default), x.509 certs, LDAP/Kerberos (Enterprise), AWS IAM (Atlas). Always enable auth — an open 0.0.0.0 bind with no auth is the classic ransom-attack vector.
  • AuthZ: role-based access control — built-in roles (read, readWrite, dbAdmin, clusterAdmin) plus custom roles scoped per database/collection. Principle of least privilege for app users.
  • Encryption in transit: TLS/SSL for client↔server and intra-cluster (--tlsMode requireTLS).
  • Encryption at rest: WiredTiger native encryption (Enterprise/Atlas, AES-256) with KMIP/KMS-managed keys.
  • Client-Side Field Level Encryption (CSFLE) / Queryable Encryption: fields encrypted by the driver before they ever reach the server — the DB never sees plaintext PII.
  • Network isolation: bind to private subnets, VPC peering / PrivateLink, IP allowlists, no public exposure of 27017.
  • Common CVEs/mistakes: NoSQL injection via unsanitized query operators (e.g. passing {$gt:""} as a password field), default no-auth pre-3.6 binds, over-privileged app accounts.
Watch out: NoSQL injection — never pass raw request JSON straight into a query. {username: req.body.user} becomes {username: {$ne: null}} if the client sends an object. Cast to string / validate types.

Performance

  • Working set in RAM is the #1 lever. A cache miss to SSD turns a ~100 µs read into a ~100 µs-1 ms+ disk read; miss to spinning disk is catastrophic.
  • Indexes: follow the ESR rule for compound indexes — Equality fields first, then Sort, then Range. A covered query (all fields in the index, none from the doc) skips fetching documents entirely.
  • Concurrency tickets: WiredTiger historically capped concurrent read/write tickets (128 each); ticket exhaustion shows as queued ops. Modern versions auto-tune, but it's a real ceiling under storage saturation.
  • Write concern latency: w:1 ≈ local write time; w:majority adds a network round-trip to a majority (single-digit ms same-region, tens of ms cross-AZ); j:true adds a journal fsync.
  • $lookup executes as a nested loop — index the foreign key on the joined collection or it's O(n·m). Prefer embedding for hot joins.
  • Batch: bulkWrite / insertMany amortizes round-trips; ordered:false parallelizes.
  • Ballparks: indexed point read from cache ~sub-ms; well-indexed query a few ms; a single primary handles tens of thousands of simple ops/s; scale beyond by sharding.
Say this: "ESR — Equality, Sort, Range. If I put a range field before a sort field, the index can't serve the sort and Mongo does an in-memory sort, which blows up on large result sets (32 MB sort limit without an index)."

Common Mistakes

  • Monotonic shard key (_id/timestamp) → hot shard. Fix: hashed key or compound key with a high-cardinality prefix.
  • Compound index in wrong order → index unused for sort/filter. Fix: ESR rule; verify with explain.
  • Unbounded arrays ($push forever) → doc bloat + 16 MB wall. Fix: bucketing pattern or reference into a child collection.
  • Over-indexing → every write updates every index, slowing writes and eating RAM. Fix: drop unused via $indexStats.
  • Passing raw user JSON into queries → NoSQL injection. Fix: validate/cast types.
  • Assuming multi-doc atomicity without a transaction → partial updates. Fix: model as one doc, or use a transaction.
  • Reading from secondaries and being surprised by staleness. Fix: use causal consistency or read from primary for read-your-writes.
  • Undersized oplog → secondaries need full resync after brief downtime. Fix: size oplog for > maintenance window.
  • No connection pooling limits → connection storms exhaust the server. Fix: tune driver maxPoolSize.

Interview Follow-up Questions

  1. What's the difference between JSON and BSON, and why BSON?
    1. Answer pointer: BSON is binary, typed (ObjectId, Date, Decimal128, binary), length-prefixed for fast skipping, and traversable without full parse.
  2. Why is there a 16 MB document limit?
    1. Answer pointer: Bounds memory/network per doc, discourages unbounded growth; use GridFS or referencing for larger data.
  3. Walk me through what WiredTiger does on a single write.
    1. Answer pointer: Doc-level lock → cache page (MVCC) → journal WAL group-commit → oplog entry → checkpoint every 60s.
  4. How does crash recovery work? What can you lose?
    1. Answer pointer: Load last checkpoint, replay journal forward; lose at most the ~50 ms uncommitted journal window (0 if j:true).
  5. Explain the oplog. Why must its entries be idempotent?
    1. Answer pointer: Capped collection secondaries tail; idempotency (rewriting $inc to $set) makes replays safe on retry/resync.
  6. How does a primary election work and how long does it take?
    1. Answer pointer: PV1 Raft-like, terms + 2s heartbeats, electionTimeoutMillis 10s → new primary in ~10-12s; needs majority.
  7. Why do you need an odd number of voting members / an arbiter?
    1. Answer pointer: To break ties and always be able to form a majority; arbiter votes but holds no data.
  8. Difference between w:1, w:majority, and j:true?
    1. Answer pointer: Ack count vs durability; majority survives failover without rollback; j forces journal fsync.
  9. What can roll back, and when?
    1. Answer pointer: Writes acked at w:1 but not replicated to majority when the primary crashes → rolled back on rejoin.
  10. Explain read concern local vs majority vs linearizable.
    1. Answer pointer: Local may read uncommitted; majority reads durable snapshot; linearizable adds real-time ordering (primary only, slow).
  11. How do you get read-your-own-writes off a secondary?
    1. Answer pointer: Causal consistency (client session with afterClusterTime) or just read primary.
  12. How do you choose a shard key? What makes a bad one?
    1. Answer pointer: High cardinality, even distribution, query-aligned; bad = monotonic/low-cardinality → hot shard / jumbo chunks.
  13. Hashed vs ranged sharding — trade-off?
    1. Answer pointer: Hashed spreads evenly but scatter-gathers range queries; ranged is range-efficient but hot-shard prone.
  14. A shard is hot despite the balancer. Diagnose.
    1. Answer pointer: Monotonic key → all inserts on max chunk; check sh.status() for skew and jumbo chunks; consider hashed/compound key or resharding.
  15. Explain the ESR rule and covered queries.
    1. Answer pointer: Equality, Sort, Range order for compound index; covered = all needed fields in index, no doc fetch.
  16. How do multi-document transactions work and what do they cost?
    1. Answer pointer: Snapshot isolation over a session, 60s default limit, hold locks, WriteConflict retries; costly — prefer single-doc atomicity.
  17. Your p99 read latency spiked with no traffic change. Where do you look?
    1. Answer pointer: WiredTiger cache eviction/dirty %, page faults, working set > RAM, a new index build, or a COLLSCAN from a deployed query.
  18. How would you migrate a bad shard key in production?
    1. Answer pointer: Online resharding (5.0+) if feasible, else dump/reload into a new collection; plan double disk + downtime window.
  19. How do you enforce schema if you need it?
    1. Answer pointer: JSON Schema validators on the collection with validationLevel/validationAction.

Common Cross Questions

  • After replication: CAP theorem (Mongo is CP by default), Raft vs Paxos, quorum math, split-brain prevention — expect them to ask how majority prevents two primaries.
  • After sharding: consistent hashing vs range partitioning, hot partitions, rebalancing cost, scatter-gather queries — pivot to how Cassandra/Dynamo partition differently.
  • After WiredTiger: B-tree vs LSM-tree (RocksDB/Cassandra), write amplification, compaction, MVCC vs locking — be ready to contrast with Postgres MVCC and vacuum.
  • After indexes: query planner, index selectivity, when the planner picks the wrong index, plan cache, hints — and B-tree height/fanout math.
  • After transactions: isolation levels, snapshot isolation vs serializable, two-phase commit across shards, distributed transaction cost.
  • After consistency: read-your-writes, monotonic reads, linearizability vs eventual consistency, hybrid logical clocks / cluster time.
  • After schema design: normalization vs denormalization trade-offs, event sourcing/CQRS, outbox pattern for reliable events.

🎯 Deep-dive Q&A — model answers

Exactly how does WiredTiger guarantee durability across a crash, and where does the 50 ms come from?

WiredTiger keeps a write-ahead journal (WAL). Each write is buffered and journal records are flushed to disk on a group-commit cycle, by default every ~50 ms, unless the op requests j:true (immediate fsync) or the journal buffer fills. Separately, every 60s WiredTiger writes a checkpoint — a consistent copy-on-write snapshot of the B-trees to disk. On crash recovery, WiredTiger opens the last durable checkpoint and replays journal entries created after it, forward to the last fsynced record. So worst-case data loss without j:true is the last unsynced ~50 ms of journal; with j:true it's zero (for that node). Durability against node loss is a separate axis handled by write concern w:majority.

Why does w:majority plus readConcern:majority guarantee no rollbacks, and what's the latency cost?

A majority-acked write is on a majority of voting members, so any newly elected primary (which also needs a majority) is guaranteed to contain it — nothing acked at majority can be lost in a failover. readConcern:majority only returns data from the majority-committed snapshot, so reads never expose writes that could later roll back. Cost: the write waits for a network round-trip to a majority of members — single-digit ms same-region, tens of ms cross-AZ — roughly 2x the w:1 latency, and the majority snapshot lags the latest optime slightly so majority reads see marginally stale data.

Give the precise ESR rule and show why a range-before-sort index fails.

For a compound index serving a query, order fields as Equality → Sort → Range. Equality fields pin the index to a single value prefix; the sort field then lets the index return already-ordered results; range fields last narrow within that. If you put a range field before the sort field, the index entries within the range are ordered by the range field, not the sort field, so Mongo can't stream them in sort order — it does a blocking in-memory sort, which is capped at 32 MB (without allowDiskUse) and fails or spills on large result sets. Verify with explain: a good plan shows the sort satisfied by the index (no SORT stage).

Walk through a MongoDB primary election step by step.

Protocol Version 1 (Raft-like). Members exchange heartbeats every 2s. If a secondary misses heartbeats for electionTimeoutMillis (default 10s), it increments the term and calls for votes. Each member votes at most once per term and only for a candidate whose oplog is at least as fresh as its own. A candidate that wins a majority of votes becomes primary for that term, immediately catching writes; stale members that had unreplicated writes roll them back on rejoin. Priority settings bias which node wins; a member with priority:0 can't be primary. End-to-end a clean failover is typically ~10-12s. Arbiters vote but store no data, purely to reach a majority in even-membership sets.

How do multi-document transactions actually work internally, and why the 60s limit?

A transaction runs inside a client session using WiredTiger snapshot isolation: at start it pins a snapshot (an MVCC read view) and buffers writes, taking document locks as it writes. Conflicting concurrent writes cause a WriteConflict which the driver can retry (transient-transaction-error retry). On commit it becomes an atomic apply, replicated as a single oplog entry group (an applyOps) and honoring the transaction's write concern. On sharded clusters (4.2+) it's coordinated two-phase commit across participating shards. The default transactionLifetimeLimitSeconds is 60s because a long-running transaction pins a snapshot, which prevents WiredTiger from evicting old versions — holding it too long causes cache pressure and blocks checkpointing. So keep transactions short; prefer single-document atomicity (Mongo guarantees a single doc update is atomic) whenever the model allows.

When would embedding hurt you, and how does the bucketing pattern fix unbounded arrays?

Embedding hurts when the embedded data is unbounded (e.g. every sensor reading pushed into one device doc) or updated independently at high frequency — the doc grows, forcing rewrites/moves, and eventually hits 16 MB. Bucketing fixes this by capping each doc: instead of one doc per device with a giant array, you create bucket docs holding, say, 200 readings each ({deviceId, startTs, count, readings:[...]}), rolling to a new bucket when full. This keeps docs small and bounded, keeps time-locality for range reads, and dramatically reduces index entries versus one-doc-per-reading. MongoDB's native time-series collections automate exactly this bucketing under the hood.

What's the difference between hashed and ranged sharding at the query level?

Ranged sharding partitions the key space into contiguous ranges (chunks), so a range query like createdAt between A and B is targeted to the few shards owning that range — efficient. But a monotonic key means all new inserts land in the top range on one shard (hot shard). Hashed sharding applies a hash to the key so consecutive values scatter across shards — great even write distribution, no hot shard — but a range query can no longer be localized, so it becomes a scatter-gather to all shards and merge. Point queries on the exact key are fine either way. The compound-key trick (high-cardinality prefix + time) often gives distribution without fully sacrificing range locality.

How do you diagnose a query that's suddenly slow?

Run db.coll.find(...).explain("executionStats"). Check the winning plan stage: IXSCAN good, COLLSCAN bad. Compare totalDocsExamined vs nReturned — near 1:1 is efficient; a big ratio means the index is missing or non-selective. Look for a blocking SORT stage (index doesn't cover the sort). Check totalKeysExamined for over-broad index scans. Cross-reference the profiler (system.profile) for frequency, db.currentOp() for a blocking op, and $indexStats to see if the intended index is even used. If the planner chose the wrong index, pin it with .hint() and investigate plan-cache staleness.

What is causal consistency and when do you need it?

Causal consistency guarantees that operations that are causally related are seen in order — specifically read-your-writes, monotonic reads/writes, and writes-follow-reads — even when reading from secondaries. It's implemented with cluster time / hybrid logical clocks: a client session tracks the operationTime of its last op, and subsequent reads specify afterClusterTime so a secondary waits until it has applied at least up to that time before answering. You need it when you scale reads to secondaries but still require a user to see their own just-made write — without it, a read routed to a lagging secondary could miss it. The alternative is simply reading from the primary.

Why can a jumbo chunk form and how do you resolve it?

The balancer splits chunks and migrates them to equalize count. A chunk can only be split at shard-key value boundaries. If a huge number of documents share the exact same shard-key value (low cardinality), that chunk can't be split below one key value; once it exceeds the max chunk size it's flagged jumbo and the balancer refuses to move it (moving would be too large/slow). It then sits on one shard causing imbalance. Resolution: the real fix is a higher-cardinality shard key (reshard), or a compound key that adds a distinguishing field. Short-term you can manually clear the jumbo flag and force a move if the chunk is actually movable, but that's a band-aid.

How does MongoDB avoid split-brain (two primaries)?

Elections require a strict majority of voting members, and each member grants at most one vote per term. Since two disjoint majorities of the same set can't exist, only one candidate can win a given term, so at most one primary exists per term. If a primary is network-partitioned into the minority side, it can't confirm it still has majority support (heartbeats fail) and steps itself down to secondary — it stops accepting writes. Combined with terms increasing monotonically, a stale primary that rejoins sees a higher term and yields, rolling back any writes that never reached the new majority.

What's the working-set-in-RAM rule and how do you measure if you've blown it?

MongoDB is fast when the frequently-accessed documents and their indexes fit in the WiredTiger cache (default 50% of RAM minus 1 GB). When the working set exceeds cache, WiredTiger must evict pages and re-read from disk, turning sub-ms cache hits into disk reads and spiking p99. Measure via serverStatus().wiredTiger.cache: watch "bytes currently in the cache" vs "maximum bytes configured", "unmodified pages evicted" and "pages evicted by application threads" (app-thread eviction means you're behind), and OS page-fault / disk-read rates. Rising eviction with rising disk IOPS and iowait is the signature. Fixes: more RAM, fewer/smaller indexes, TTL-archive cold data, or shard to divide the working set.

Explain index intersection and why a single compound index usually beats it.

Index intersection lets the planner use two separate single-field indexes for one query, scanning both and intersecting the matching record ids. It's a fallback that helps ad-hoc queries, but it's usually slower than a purpose-built compound index because it examines more keys, can't serve a sort from the intersection, and can't produce a covered query. A single compound index ordered by ESR scans one contiguous range, can satisfy the sort, and can cover the query (no doc fetch). So for known hot query shapes you design a compound index; intersection is for the long tail you didn't index specifically.

What does a $lookup cost and how do you make it acceptable?

$lookup is executed as a nested-loop join: for each input document from the pipeline, it runs a query against the foreign collection. If the foreign collection's join field isn't indexed, each lookup is a COLLSCAN and the whole thing is O(n·m) — deadly. To make it acceptable: (1) index the foreign field so each lookup is an IXSCAN; (2) reduce the left-side cardinality with $match/$limit before the $lookup; (3) prefer embedding for hot, always-together reads so no join is needed at all. Even indexed, cross-collection joins on large data are far more expensive than an RDBMS hash/merge join, so treat frequent $lookup as a modeling smell.

How would you size and monitor the oplog, and why does it matter?

The oplog is a capped collection; its size in bytes determines how much time of operations it retains, which is your replication safety window. If a secondary is offline (or lagging) longer than the oplog window, the ops it needs have been overwritten and it must do a full initial resync — expensive and slow on large data. Size it (via replSetResizeOplog) so the window comfortably exceeds your longest expected maintenance/downtime — often 24-72h. Monitor with db.getReplicationInfo() (time span) and alert when the window drops below a few hours or when secondary lag approaches the window.

Give the concrete NoSQL-injection failure and the fix.

Consider login code db.users.findOne({user: req.body.user, pass: req.body.pass}). If the client sends JSON {"user":"admin","pass":{"$ne":null}}, the query becomes {user:"admin", pass:{$ne:null}}, matching admin regardless of password. Operators like $ne, $gt, $regex injected as object values subvert the query. Fix: validate/cast inputs to their expected primitive types (ensure pass is a string), reject objects where scalars are expected, use schema validation at the API layer, and never pass raw request bodies straight into query filters. Parameterize by explicitly constructing the query from typed fields.
