Components & Props React

A component is a function from props to a description of UI. That is the entire contract — and the reason React scales: if a component is a pure function, you can reason about it, test it, memoize it, render it on a server, replay it, and render it twice without consequence.

Props are that function's arguments. They are read-only, they flow strictly downward, and the discipline around them (purity, composition, no mutation) is what separates a codebase that stays debuggable from one that does not.

Props are read-only arguments

function Greeting({ name, greeting = 'Hello' }) {
  return <h1>{greeting}, {name}!</h1>;
}
<Greeting name="Ada" />   // → Greeting({ name: 'Ada' })

A component must never write to its props. React does not deep-freeze the props object, so mutation silently "works" and then fails in ways that are hard to trace:

function Row({ user }) {
  user.name = user.name.toUpperCase();   // ❌ mutates the PARENT's object
  return <td>{user.name}</td>;
}
  • The parent's state object now differs from what the parent last set, so the parent's own render output changes without any setState.
  • The reference did not change, so React.memo, useMemo and dependency arrays all conclude "nothing changed" and skip work.
  • Rendering twice (StrictMode, concurrent re-render, a replayed render) applies the transformation twice — ADA then ADA, but a count + 1 becomes count + 2.

The correct shape is: derive a local value during render, and to change data, call a callback the owner passed down.

Note: "One-way data flow" is enforced by convention, not by the runtime. React tells you nothing when you break it — which is exactly why interviewers ask about it.

children and composition

children is just a prop whose value happens to be whatever you nested between the tags. It can be an element, a string, an array — or a function.

function Card({ title, children, footer }) {
  return (
    <section className="card">
      <h3>{title}</h3>
      <div className="body">{children}</div>
      {footer && <footer>{footer}</footer>}
    </section>
  );
}

<Card title="Billing" footer={<SaveButton />}>
  <InvoiceTable rows={rows} />
</Card>

Two things worth naming: multiple slots (any prop can take an element, so footer, icon, header are all "children" by another name), and the fact that Card knows nothing about InvoiceTable. It renders a hole.

Slots kill prop drilling

Prop drilling usually appears because a middle component creates the deep child and therefore must be handed its data. If the top component creates the element and passes it down as children, the middle layer never sees the data at all:

// ❌ Layout must accept `user` only to forward it two levels
<Layout user={user} />

// ✅ Layout accepts an opaque child; `user` never enters Layout's props
<Layout><Sidebar><Profile user={user} /></Sidebar></Layout>
Senior tip: Reach for composition before Context. "Lift the element, not the data" removes most drilling with zero runtime cost and no re-render fan-out, whereas Context re-renders every consumer on every value change.

Composition over inheritance

React has no component inheritance and the docs recommend against simulating it. There is no extends BaseButton pattern that works well, because a subclass has to know its parent's render internals to override them — the classic fragile-base-class problem.

A variant of a componentSubclass and overrideProps (variant="danger")
A shell with variable contentTemplate methodchildren / slot props
Shared behaviourBase-class methodsA custom hook
A specialised componentSubclassA component that renders the generic one with fixed props
 
// "specialisation" in React is just a function calling another function
const DangerButton = (props) => <Button {...props} variant="danger" />;
Note: Shared logic goes in a custom hook; shared markup goes in a component; shared structure goes in children. Those three cover everything inheritance was used for, without the coupling.

Defaults, spreading, and prop APIs

// ✅ destructuring defaults — the modern way
function Button({ variant = 'primary', size = 'md', disabled = false, ...rest }) {
  return <button className={`btn ${variant} ${size}`} disabled={disabled} {...rest} />;
}

Button.defaultProps is deprecated for function components (React 18.3 warns; React 19 removed support) — it still exists for classes. Use default values in the parameter destructuring.

Spreading {...rest}: when it helps and when it hurts

  • Good: leaf wrappers over a DOM element, where forwarding aria-*, data-*, type, onFocus etc. is the point. Spread before your own props if the caller must not override them, after if they should be able to.
  • Bad: <Child {...props} /> through several layers. The component's real API becomes invisible, TypeScript stops helping, dead props travel forever, and typos land in the DOM as unknown-attribute warnings.
  • Order matters: <input {...rest} value={v} /> means value always wins; swapping them lets a caller silently break the component.
Gotcha: Spreading an object built inline ({...{ style: {...} }}) or passing an inline object/array/arrow prop creates a new reference every render, defeating React.memo on the child. That is a real cost only when the child is expensive or the list is long — measure before you memoize.

Presentational vs container components

The 2015 split (a "container" fetches and holds state, a "presentational" component only takes props and renders) was a workaround for class components having no way to share stateful logic. Hooks made the split largely obsolete — Dan Abramov, who popularised the pattern, has said so.

What survives is the useful half:

  • Keep components that touch the network or global state shallow and few; a custom hook (useInvoices()) is the modern "container".
  • Keep pure, prop-driven components for anything you want to reuse, storybook, or snapshot-test.
  • Do not create a wrapper file per component out of ceremony. Split when a component has two reasons to change, not because a pattern says so.

Purity, and what StrictMode catches

React requires render to be pure: given the same props and state it must return the same JSX, and it must not touch anything outside its own scope while rendering.

Forbidden during render: mutating props, state, or module-level variables; writing to the DOM; calling fetch; starting timers; Math.random()/Date.now() where the value is compared across renders; calling a setter of another component.

let renderCount = 0;                 // ❌ module-level mutation

function Item({ item }) {
  renderCount++;                     // ❌ side effect during render
  item.seen = true;                  // ❌ mutating a prop
  return <li>{item.title} ({renderCount})</li>;
}

In development, <StrictMode> deliberately calls your component function twice and double-invokes effects (mount → unmount → mount). A pure component produces identical output both times and nobody notices; an impure one changes on the second call, which is the point — it surfaces the bug on your machine instead of in production, where concurrent rendering can render, discard, and re-render a component at any time.

Gotcha: StrictMode's double render happens in development only, and React deliberately suppresses duplicate console.logs in the doubled pass, so people conclude "it only rendered once". Run index.js in this folder to see exactly how an impure component diverges between call 1 and call 2.

Typing props, naming, and when to split

type Variant = 'primary' | 'danger';

interface ButtonProps extends React.ComponentPropsWithoutRef<'button'> {
  variant?: Variant;               // optional with a default
  loading?: boolean;
  children: React.ReactNode;       // required content
  onConfirm?: (id: string) => void;
}

export function Button({ variant = 'primary', loading = false, children, ...rest }: ButtonProps) { … }
  • Extend ComponentPropsWithoutRef<'button'> so every native attribute is typed for free — better than redeclaring onClick by hand.
  • React.ReactNode for anything renderable; React.ReactElement only when you truly require a single element.
  • Prefer a union of literals over string; the compiler then enforces your design system.
  • React.FC is out of favour: it adds an implicit children (removed in React 18 types) and complicates generics. Type the props parameter instead.

Conventions and splitting

  • PascalCase components, camelCase props, on* for callbacks the child calls, handle* for the parent's implementation, is/has for booleans.
  • One exported component per file, file named after it; colocate its sub-parts, hook, and test in the same folder.
  • Split when: a chunk of JSX gets its own name in conversation, a piece needs independent state, or a subtree re-renders far more often than its siblings. Do not split merely because a file crossed a line count — a 200-line component with one job beats five files with one job between them.

🎯 Interview questions

Why are props read-only?

A component is a function of its props; mutating them makes render impure, so the same inputs stop producing the same output. Practically, the parent's data changes behind its back, the reference stays identical so memoization and dependency arrays miss it, and a second render (StrictMode or a concurrent re-render) applies the change twice.

How do you avoid prop drilling without Context?

Composition: let the component that owns the data create the deep element and pass it down as children or a slot prop. The intermediate layers accept an opaque node and never learn about the data. No re-render fan-out, and the component API stays honest.

Why does React favour composition over inheritance?

Inheritance couples a child to its parent's internals and offers nothing React needs: variants are props, variable content is children, shared logic is a custom hook, and specialisation is a component that renders the generic one with fixed props. There is no supported inheritance mechanism for components.

What does StrictMode actually do, and why?

In development only, it double-invokes component functions, initialisers and updaters, and mounts → unmounts → remounts each component so effects run twice. This surfaces impure render logic and missing effect cleanup on your machine, because concurrent React may render a component and throw the result away at any time.

Is defaultProps still the way to set defaults?

No. It is deprecated for function components (warned in 18.3, removed in 19) and remains only for classes. Use destructuring defaults in the parameter list, which is also better for TypeScript inference.

What are the downsides of {...rest} spreading?

It hides the component's real API, weakens type checking, lets unknown props reach the DOM as warnings, and can silently override your own props depending on spread order. It is right for thin wrappers over a DOM element that should forward native attributes, and wrong as a way to pass data through several layers.

Are presentational/container components still relevant?

Mostly not — the split existed because classes could not share stateful logic. Custom hooks do that now. The surviving guidance is to keep data-fetching shallow (in hooks) and keep reusable UI pure and prop-driven, rather than mechanically creating a container per component.
