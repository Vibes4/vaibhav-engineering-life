Data Fetching React

React has no data-fetching layer. useEffect + fetch is not a pattern the React team recommends — it is the lowest-level escape hatch, and writing it correctly means handling race conditions, cancellation, a proper state machine, deduplication, caching, revalidation and retries by hand. That list is the entire reason React Query, SWR and RSC exist.

The interview version of this topic is: name what the naive version gets wrong, fix the race condition two different ways, explain waterfalls, and explain why you would not hand-roll a cache.

The naive pattern, and everything it misses

function User({ id }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch(`/api/users/${id}`)
      .then(r => r.json())
      .then(setUser);
  }, [id]);
}
  • Race condition: change id quickly and a slow earlier response can land after a fast later one, leaving the wrong user on screen.
  • No cleanup: the setUser may run after unmount, and nothing aborts the in-flight request.
  • No error handling: fetch does not reject on 404 or 500 — only on network failure. You must check res.ok yourself.
  • No loading state, so the UI cannot distinguish "loading" from "loaded, empty".
  • No cache, no dedupe: two components asking for the same user make two requests; navigating away and back refetches from scratch.
  • Waterfall: the effect runs only after the component mounts and paints, so nested components fetch in sequence.

Race conditions — the classic bug

Requests are not guaranteed to resolve in the order they were fired. Type "a", then "ab": if the request for "a" takes 900ms and "ab" takes 100ms, the results for "a" arrive last and overwrite the fresher data. The UI now shows stale results with a fresh query in the box.

Fix 1 — the ignore flag in cleanup

useEffect(() => {
  let ignore = false;                        // scoped to THIS effect run
  fetch(`/api/search?q=${q}`)
    .then(r => r.json())
    .then(data => { if (!ignore) setResults(data); });
  return () => { ignore = true; };           // runs before the next effect and on unmount
}, [q]);

The cleanup runs before the next effect, so an outdated response finds ignore === true and quietly does nothing. This is the fix in the official React docs. It does not cancel the request — it just stops it from being applied.

Fix 2 — AbortController

useEffect(() => {
  const ctrl = new AbortController();
  fetch(url, { signal: ctrl.signal })
    .then(r => { if (!r.ok) throw new Error(r.status); return r.json(); })
    .then(setData)
    .catch(e => { if (e.name !== 'AbortError') setError(e); });   // ignore our own abort
  return () => ctrl.abort();
}, [url]);
Senior tip: both fixes are correct; they solve different halves. ignore guarantees you never apply a stale result. AbortController additionally frees the connection and stops server work — the one that matters for expensive queries and mobile data. In production use both, or use a library that does.

One status, not three booleans

// ❌ 8 combinations, most of them impossible
const [loading, setLoading] = useState(false);
const [error, setError]     = useState(null);
const [data, setData]       = useState(null);

// ✅ a state machine: idle → loading → success | error
const [state, dispatch] = useReducer(reducer, { status: 'idle', data: null, error: null });

Three booleans let you render "loading" and "error" at the same time, or forget to clear the previous error on a retry. A single status string makes those states unrepresentable — and it is exactly what React Query exposes (isPending/isError/isSuccess are derived from one internal status).

StrictMode's double fetch is a symptom, not a bug

In development, <StrictMode> mounts, unmounts and remounts every component, so effects run twice and you see two requests. This is deliberate: it surfaces effects that are not cleanup-safe. If the double fetch causes a visible problem, your effect is missing a cleanup — the same missing cleanup that produces the race condition above.

Gotcha: never "fix" it by adding a useRef guard like if (didFetch.current) return;. That silences the warning while leaving the real bug (no cancellation, no dedupe) in place, and it does not run in production anyway — StrictMode's double-invoke is development-only.

Waterfalls vs parallel fetching

A waterfall is requests that run in sequence when they could have run at once. React makes it easy to create one accidentally, because a child's effect cannot start until the parent has rendered — and a parent that renders a spinner while loading never renders the child at all.

// ❌ waterfall: Profile fetches, renders, only THEN Posts mounts and fetches
function Profile({ id }) {
  const user = useUser(id);
  if (!user) return <Spinner />;         // Posts does not exist yet
  return <Posts userId={user.id} />;
}

// ✅ independent requests start together
const [user, posts] = await Promise.all([fetchUser(id), fetchPosts(id)]);
  • Genuine dependency (you need the user's id before you can fetch their posts) — a waterfall is unavoidable; consider a single endpoint or a server-side join instead.
  • Accidental dependency (both only needed the route param) — hoist both requests to the same level and run them with Promise.all, parallel queries, or a route loader.
  • Promise.allSettled when one failure should not sink the others; Promise.all rejects on the first failure.

Caching, deduplication and stale-while-revalidate

Three behaviours you will otherwise rewrite badly in every project:

  • Deduplication: five components mount at once asking for the same key → one network request, five subscribers. Implemented by storing the in-flight promise in the cache, not just the result.
  • Caching: a key already fetched renders instantly from memory instead of flashing a spinner.
  • Stale-while-revalidate: serve the cached value immediately, refetch in the background, update when it lands. The UI is never blank and never permanently stale.

A correct implementation also needs: cache invalidation, garbage collection of unused keys, refetch on window focus and reconnect, retry with backoff, pagination, and per-key subscriber notification. That is a library, not a hook you write in an afternoon.

const { data, isPending, error, refetch } = useQuery({
  queryKey: ['user', id],                    // the cache key — deps array for the cache
  queryFn: ({ signal }) => fetchUser(id, { signal }),
  staleTime: 60_000,                         // how long a value is served without refetching
});

const mutation = useMutation({
  mutationFn: updateUser,
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['user', id] }),
});

On top of that: useInfiniteQuery for pagination, retries with exponential backoff by default, and optimistic updates — apply the change locally, roll back in onError, invalidate in onSettled.

Note: the request itself is a one-liner. What you are buying is the cache and its lifecycle. Answering "why React Query?" with "so I don't write useEffect" is shallow; answering with dedupe, SWR, invalidation and retries is not.

Suspense, and moving fetching out of the component

<Suspense fallback={...}> inverts loading state: instead of each component rendering its own if (isLoading), a component suspends and the nearest boundary above shows one fallback for the whole region. Combined with an error boundary, the happy path in your component has no branches at all.

<ErrorBoundary fallback={<Failed />}>
  <Suspense fallback={<Skeleton />}>
    <Profile id={id} />      {/* renders as if data were already there */}
  </Suspense>
</ErrorBoundary>

Suspense for data requires a data source that integrates with it — React Query's useSuspenseQuery, Relay, or a framework. React 19 also adds the use() hook, which can read a promise and suspend; the promise must come from a cache or from the server, not be created during render.

Framework-specific, and worth labelling as such: React Server Components and framework loaders (Next.js App Router server components, React Router / Remix loader functions) move fetching out of the component lifecycle entirely. The data is fetched on the server, in parallel, before render — which structurally eliminates client waterfalls, the race condition, and the loading-state plumbing. Say this is framework territory, not core React.

Errors and retries

  • fetch only rejects on network failure — always check res.ok and throw yourself, or every 500 becomes a successful render of an error page's JSON.
  • Retry only idempotent requests (GET), with exponential backoff and jitter, and a cap. Never blindly retry a POST that may have charged a card.
  • Distinguish an aborted request (e.name === 'AbortError') from a real failure — showing "Something went wrong" because the user typed another character is a common bug.
  • Error boundaries catch render-phase errors, not rejected promises in an effect. Either set error state and render it, or use a library that rethrows during render so a boundary can catch it.
  • Keep the previous data visible while refetching (placeholderData: keepPreviousData) so pagination does not flash empty.

🎯 Interview questions

Describe the race condition in useEffect + fetch and fix it.

Responses can resolve out of order, so a slow earlier request can overwrite a fast later one with stale data. Fix by setting a let ignore = false in the effect and returning a cleanup that flips it, checking it before setState; or by aborting the previous request with an AbortController in cleanup. The flag guarantees stale data is never applied; the abort additionally cancels the work.

Why does my component fetch twice in development?

StrictMode intentionally mounts, unmounts and remounts components so effects run twice, surfacing effects that lack cleanup. It is development-only. The right response is to add the cleanup (ignore flag or abort), not a ref guard that hides the symptom.

What is a request waterfall and how do you avoid it?

Requests running sequentially that could have run in parallel — typically because a child component only mounts after the parent's data arrives. Hoist independent requests to the same level and use Promise.all or parallel queries, or fetch on the server via a route loader / RSC. Only a genuine data dependency justifies a waterfall.

Why not just write your own cache?

Because "a cache" really means keyed storage, in-flight deduplication, stale-while-revalidate, invalidation after mutations, garbage collection, refetch on focus and reconnect, retries with backoff, and per-key subscriptions. Getting all of that right and keeping it right is a library's job; React Query, SWR and RTK Query already do it.

Why is one status better than isLoading/isError/isSuccess?

Three booleans allow eight combinations, most of them impossible, and make it easy to forget to clear an error on retry. One status string ('idle' | 'loading' | 'success' | 'error') makes invalid states unrepresentable and the render logic a single switch.

How does Suspense change data fetching?

It moves the loading state from inside the component to a boundary above it: the component renders as if the data were present and suspends if it is not, and the nearest <Suspense> shows one fallback for the region. It needs a Suspense-aware data source (useSuspenseQuery, Relay, a framework, or React 19's use() reading a cached promise), and pairs with an error boundary for failures.

Does fetch reject on a 500?

No. It resolves; only network-level failures reject. You must check res.ok and throw, otherwise error responses are treated as successful data. This is the single most common data-fetching bug in code reviews.
