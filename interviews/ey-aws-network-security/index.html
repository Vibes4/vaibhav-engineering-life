AWS: VPC, IAM & Security EY Sheet 04

The JD lists VPC, IAM, Security Groups under primary skills. This is where application developers most often get exposed, because you can build a lot on AWS without ever designing a network. Expect at least two networking questions and one IAM question; "trace a request from the internet to the database" is the single most common shape.

The line that wins this section: "My default VPC layout is three tiers across at least two AZs: public subnets holding only the load balancer and NAT gateways, private subnets for compute, and isolated subnets for data with no route to the internet at all. Nothing except the ALB has a public IP, service-to-service access is expressed as security-group-to-security-group rules rather than CIDRs, and workloads get credentials from IAM roles — there are no long-lived access keys anywhere in the estate."

VPC & networking

CertainTrace a packet from a user's browser to a private RDS instance.

Step by step — this is the answer to memorise:

  1. Browser resolves the domain via Route 53 (possibly to a CloudFront edge first, which terminates TLS at the edge and forwards to the origin).
  2. DNS returns the ALB's public addresses. The ALB sits in public subnets — subnets whose route table has 0.0.0.0/0 → Internet Gateway. Its security group allows 443 inbound from the world.
  3. TLS terminates at the ALB (certificate from ACM). The ALB evaluates listener rules and picks a healthy target.
  4. The ALB opens a connection to an app task/instance in a private subnet. That target's security group allows the app port from the ALB's security group — not from a CIDR. There's no public IP on the app tier.
  5. The app resolves the RDS endpoint to a private IP and connects on 5432. The RDS security group allows 5432 from the app's security group only. The DB sits in isolated subnets with no route to an IGW or NAT.
  6. Return traffic flows back without explicit rules because security groups are stateful.
  7. If the app needs to call an external API, its subnet's default route points at a NAT Gateway in a public subnet, which source-NATs the traffic out through the Internet Gateway. Inbound connections from the internet to the app are still impossible.

The one-sentence summary to close on: "The only thing with a public IP is the load balancer, and every hop is expressed as security-group references so the rules survive IP changes."

CertainSecurity Group vs NACL — give a case where you actually need a NACL.

Security groups are stateful, attach to an ENI (instance, task, Lambda, RDS), and are allow-only — there is no deny rule. Return traffic is automatic. NACLs are stateless, attach to a subnet, are evaluated in rule-number order, and support both allow and deny.

You need a NACL when you need something the SG model cannot express: an explicit deny, or a subnet-wide control. Concretely — blocking a specific malicious CIDR at the subnet edge during an incident, or enforcing that a quarantine/DMZ subnet can never reach the data subnet regardless of what security groups anyone later creates. It's a blast-radius and defence-in-depth tool.

The gotcha to volunteer: because NACLs are stateless you must explicitly allow the ephemeral port range (1024–65535) for return traffic. Forgetting that produces the classic "the security group allows it but connections just hang" bug. In practice SGs do 95% of the work and I'd resist adding NACL complexity without a specific reason.

Why is one NAT Gateway both a cost problem and an availability problem?

Availability: a NAT Gateway lives in exactly one AZ. If every private subnet routes 0.0.0.0/0 to that one NAT and its AZ has an event, private instances in every AZ lose outbound internet — package pulls, third-party API calls, licence checks all fail, even though the instances themselves are healthy. The fix is one NAT Gateway per AZ, with each private subnet's route table pointing at the NAT in its own AZ.

Cost: NAT Gateways charge an hourly rate plus a per-GB data processing fee on top of normal egress, and routing cross-AZ to reach a single NAT adds inter-AZ transfer charges. It's one of the top surprise line items on AWS bills. The big lever: put VPC gateway endpoints for S3 and DynamoDB in place — they're free and route that traffic off the NAT entirely. For other AWS services, interface endpoints (PrivateLink) cost per hour but are usually still cheaper than NAT processing at volume, and they keep traffic off the public internet, which is a security win too.

Depth probeHow do you plan CIDR ranges, and what goes wrong if you don't?

I'd size the VPC generously — a /16 gives 65,536 addresses and costs nothing — then carve per-AZ subnets, typically /20 or /24 per tier per AZ. AWS reserves 5 addresses in every subnet (network, VPC router, DNS, future use, broadcast), so a /28 gives you 11 usable, not 16.

What goes wrong when you don't plan: (1) Overlapping CIDRs. If two VPCs use 10.0.0.0/16 you cannot peer them, ever — and you'll discover this the day the client wants to connect a newly acquired business unit or a Direct Connect link to on-prem. Overlap is the single most expensive networking mistake because the fix is re-addressing a live environment. (2) Subnets too small. EKS in particular burns IPs fast because every pod gets a VPC IP with the default CNI; a /24 per subnet runs out at a few hundred pods. (3) You can add secondary CIDRs to a VPC later, which softens the pain, but you cannot resize an existing subnet.

On a consulting engagement I'd ask for the client's IP allocation standard on day one and register ranges centrally, because the VPC I build has to coexist with everything else they own.

VPC peering vs Transit Gateway vs PrivateLink.

Peering — a one-to-one private link between two VPCs. Simple, no bandwidth bottleneck, no extra hourly cost beyond data transfer. But it's non-transitive (A–B and B–C does not give A–C) so N VPCs need N(N−1)/2 connections, and CIDRs must not overlap. Fine for two or three VPCs.

Transit Gateway — a hub-and-spoke router. Every VPC, VPN and Direct Connect attaches once and routing is centralised with route tables per attachment. This is the answer for any real enterprise estate — which, at EY, is the normal case. Costs an hourly attachment fee plus per-GB processing.

PrivateLink / VPC endpoint services — exposes a single service (not a whole network) into a consumer VPC via an interface ENI. One-way, no route table changes, and crucially CIDRs may overlap because there's no network-level routing. This is how you consume AWS services privately and how SaaS vendors expose products to customer VPCs. When a client says "we need to connect to a partner but our IP ranges collide", PrivateLink is the answer.

IAM & identity

CertainExplain IAM roles vs users, and how an EC2 instance or Lambda gets credentials.

An IAM user is a long-lived identity with long-lived credentials. In a well-run account there should be almost none — humans federate in through SSO/OIDC and get temporary credentials. A role has no permanent credentials; it's assumed, and assuming it returns short-lived credentials from STS (an access key, secret, and session token, default 1 hour).

A role has two policies that people conflate: the trust policy says who may assume it, and the permissions policy says what the session can do.

For EC2: you attach an instance profile wrapping the role; the Instance Metadata Service at 169.254.169.254 serves time-limited credentials, and the SDK's default credential provider chain finds them and refreshes automatically before expiry. Always use IMDSv2 (session-token based), because IMDSv1's simple GET is what made SSRF vulnerabilities into full credential theft — the 2019 Capital One breach is the canonical example. For Lambda: the execution role's credentials arrive as environment variables, rotated by the service. For ECS: task roles are served over a link-local endpoint, and you should use task roles rather than instance roles so tasks on the same host don't share permissions.

The punchline: there is never a reason to bake an access key into an AMI, a container image, or a config file.

Depth probeHow is an IAM request actually evaluated?

Order of evaluation: (1) an explicit Deny anywhere always wins and ends the decision. (2) Service Control Policies at the Organizations level act as a ceiling — if an SCP doesn't allow it, nothing below can. (3) Resource-based policies (bucket policy, KMS key policy, SQS queue policy) and identity-based policies are evaluated together; for same-account access, an allow in either can suffice, but for cross-account access you need an allow on both sides. (4) Permission boundaries cap what an identity-based policy can grant. (5) Session policies narrow further. (6) Default is deny.

Practical consequence I'd give: when someone says "my policy allows it but I'm getting AccessDenied", the checklist is — is there an explicit deny, is an SCP blocking it, is this cross-account (needing both sides), is there a permission boundary, and is there a KMS key policy in the path (S3 with SSE-KMS needs kms:Decrypt, not just s3:GetObject, and that's the most common one).

How do you enforce least privilege across an organisation without blocking developers?

Guardrails plus self-service, not a central team approving every policy — that model doesn't scale and gets routed around.

  • SCPs as organisation-wide guardrails: deny disabling CloudTrail or GuardDuty, deny regions you don't operate in, deny making S3 buckets public, deny deleting KMS keys.
  • Permission boundaries on roles developers can create, so teams self-serve roles for their workloads but can never exceed the boundary.
  • Start broad, then tighten with evidence — begin from managed job-function policies, then use IAM Access Analyzer to generate least-privilege policies from actual CloudTrail activity. Guessing at least privilege up front produces either over-grants or a week of AccessDenied tickets.
  • ABAC — tag-based access (aws:PrincipalTag/team matching aws:ResourceTag/team) so one policy scales across many teams instead of one policy per team.
  • No long-lived keys — SSO for humans, roles for workloads, OIDC federation for CI/CD so the pipeline assumes a role instead of holding a secret.
  • Account separation as the strongest boundary: separate AWS accounts per environment, so a mistake in dev cannot touch prod at all.
What is the confused deputy problem, and how does ExternalId fix it?

You let a third-party SaaS assume a role in your account, so their role ARN is in your trust policy. But that SaaS uses the same identity to serve all its customers. An attacker who is also their customer can ask the SaaS to act on "their" account and supply your account ID — the SaaS, being confused about whose behalf it's acting, assumes your role. The deputy has been confused into misusing its authority.

ExternalId fixes it: you give the vendor a secret string unique to your tenancy, they must pass it on the AssumeRole call, and your trust policy requires sts:ExternalId to match. The attacker doesn't know your ExternalId, so they can't get the SaaS to assume your role. It binds the trust relationship to your specific tenant rather than to the vendor as a whole.

How do you manage application secrets on AWS?

Secrets Manager or SSM Parameter Store (SecureString), never environment variables committed to a repo and never in the IaC templates.

Parameter Store is cheaper and fine for config and low-churn secrets. Secrets Manager costs per secret per month but adds automatic rotation with native integration for RDS — it can rotate the database password and update the secret without an outage — plus cross-region replication and resource policies. For a database credential I'd pay for Secrets Manager specifically to get rotation; for a feature flag or an endpoint URL, Parameter Store.

Operational points: encrypt with a customer-managed KMS key so you control who can decrypt and get an audit trail; fetch at startup and cache in memory rather than calling on every request (API throttling is real and it's a latency cost); give each service an IAM policy scoped to its own secret path, not secretsmanager:GetSecretValue on *; and remember that a value injected into a Lambda environment variable is visible to anyone with lambda:GetFunctionConfiguration, so genuinely sensitive values should be fetched at runtime.

A developer accidentally committed AWS keys to a public repo. What do you do?

In order, and speed matters more than elegance:

  1. Deactivate the key immediately — don't delete first, deactivate, so you can still investigate. Assume it was scraped within seconds; public-repo scanning is automated.
  2. Rotate — issue new credentials to whatever legitimately needed them, or better, replace the key with a role so it can't happen again.
  3. Investigate blast radius — CloudTrail for every API call made by that access key ID, looking especially for IAM changes (new users, new keys, policy attachments), EC2 launches in unusual regions (crypto mining is the standard payload), S3 access, and any attempt to disable logging.
  4. Contain — delete anything the attacker created, check for backdoor IAM users and roles, check GuardDuty findings.
  5. Purge and notify — the key is in git history, so removing it from HEAD is not enough; the repo history must be rewritten or the repo treated as permanently compromised. Notify security, and follow the client's incident process.
  6. Prevent — this is the part they're listening for: pre-commit secret scanning (gitleaks/trufflehog), GitHub push protection, an SCP blocking key creation, and migrating CI to OIDC federation so there is no long-lived key to leak.
