SSR, Hydration & Server Components React

Client-side rendering ships an empty <div id="root"> and asks the browser to build the page from scratch. Everything on this page is an answer to the cost of that: send HTML first (SSR), send it at build time (SSG), stream it in pieces (streaming SSR), or stop sending the component's JavaScript altogether (React Server Components).

The through-line is where a component runs and what the client has to download before the page works. Get that straight and the rest — hydration mismatches, 'use client', Server Actions — follows.

They are not exclusive: a real app renders the marketing pages statically, the product pages with ISR, the account area with SSR, and the internal dashboard as pure CSR. Pick per route, not per app.

Note: SSG and ISR are framework features (Next.js, Remix/React Router framework mode, Astro, Gatsby), not React APIs. React itself gives you renderToPipeableStream, renderToReadableStream, renderToString and hydrateRoot; everything else is build-time orchestration on top.

Hydration: HTML first, then React takes over

SSR sends a fully-formed HTML document. The user sees content immediately — but it is inert: no onClick, no state. Hydration is the client pass where React runs the same component tree, builds its fiber tree, and adopts the existing DOM nodes instead of creating new ones, attaching event listeners as it goes.

// server
import { renderToPipeableStream } from 'react-dom/server';
// client
import { hydrateRoot } from 'react-dom/client';
hydrateRoot(document.getElementById('root'), <App />);   // NOT createRoot().render()
flowchart LR
  S["Server renders HTML"] --> N["Browser paints content - not interactive"]
  N --> J["JS bundle downloads"]
  J --> H["hydrateRoot walks the tree"]
  H --> I["Listeners attached - page is interactive"]

The gap between "paints" and "interactive" is the uncanny valley of SSR: the page looks ready and ignores clicks. That gap is why the size of your client bundle still matters even with perfect SSR — and it is the problem streaming and RSC attack from two different angles.

Hydration mismatches

Hydration assumes the client's first render produces the same tree the server produced. When it does not, React warns and (since 18) discards the mismatched subtree and re-renders it on the client — losing the SSR benefit exactly where it went wrong. The usual culprits are all forms of non-determinism:

  • Date.now(), new Date() rendered directly — the server's clock is never the client's.
  • Math.random(), crypto.randomUUID(), or a non-deterministic id generator (use useId, which is SSR-safe by design).
  • Locale and timezone formatting — toLocaleDateString() on a UTC server vs a user in Mumbai renders different text.
  • window, localStorage, navigator, matchMedia read during render — undefined on the server, so the branches differ.
  • Invalid HTML nesting — a <div> inside a <p>, or a <p> inside a <p>. The browser silently repairs the markup, so the DOM no longer matches what React sent.
  • Browser extensions injecting attributes or nodes into the body (Grammarly, password managers, translation tools) — a real and famously confusing cause.
// ❌ different on server and client
<p>Rendered at {new Date().toLocaleTimeString()}</p>

// ✅ render nothing time-dependent until after hydration
const [now, setNow] = useState(null);
useEffect(() => setNow(new Date()), []);       // effects run only on the client
return <p>{now ? now.toLocaleTimeString() : '—'}</p>;

// ✅ deliberate, one-node-deep escape hatch
<time dateTime={iso} suppressHydrationWarning>{formatted}</time>
Gotcha: suppressHydrationWarning silences the warning for that element's text/attributes only — it does not fix the mismatch, and it does not apply to children deeper in the tree. It is right for a timestamp you know differs, and wrong as a way to make a warning go away. React 19 improved the diagnostics: you get a diff of server vs client output instead of a generic message.

Streaming SSR and selective hydration

Classic renderToString is all-or-nothing: one slow query holds the entire HTML response hostage, so TTFB equals your slowest data dependency. renderToPipeableStream (Node) and renderToReadableStream (Web streams / edge) instead flush HTML as it becomes ready, using <Suspense> as the boundary marker.

<Layout>
  <Nav />                                    {/* fast — flushed immediately */}
  <Suspense fallback={<ReviewsSkeleton />}>
    <Reviews />                              {/* slow — streamed in later */}
  </Suspense>
</Layout>

const { pipe, abort } = renderToPipeableStream(<App />, {
  bootstrapScripts: ['/main.js'],
  onShellReady()  { res.status(200).setHeader('Content-Type', 'text/html'); pipe(res); },
  onShellError()  { res.status(500).send('<h1>Server error</h1>'); },
});
  1. React renders down to the first <Suspense> boundary and flushes that shell, with the fallback in place. The user has pixels.
  2. When Reviews's data resolves, React streams an extra HTML chunk plus a tiny inline script that swaps it in place of the fallback — no client render needed.
  3. Selective hydration: boundaries hydrate independently as their code arrives, and React prioritises the boundary the user just clicked — it records the event, hydrates that subtree first, and replays the event. Slow parts of the page no longer block interactivity elsewhere.
Senior tip: Every <Suspense> boundary is simultaneously a streaming flush point, a hydration unit and an error/loading boundary. Place them where the page has a natural "this part can arrive late" seam — a comments list, a recommendation rail — not around the primary content.

React Server Components

RSC is a different axis from SSR. SSR renders your client components to HTML once, then ships their JS anyway so they can hydrate. A Server Component runs only on the server and its code is never sent to the browser at all — the client receives a serialized description of the rendered output (the RSC payload), not the component.

// app/posts/page.jsx  — a Server Component (the default in the Next.js App Router)
import db from '@/lib/db';
import fs from 'node:fs/promises';

export default async function Posts({ searchParams }) {
  const posts = await db.post.findMany({ take: 20 });   // direct DB access, no API route
  const banner = await fs.readFile('./banner.md', 'utf8');
  return (
    <section>
      <Markdown source={banner} />      {/* the markdown lib stays on the server */}
      {posts.map((p) => <Post key={p.id} {...p} />)}
    </section>
  );
}

The wins: heavy dependencies (markdown renderers, syntax highlighters, date libraries, ORMs) stop counting against the bundle; data fetching happens next to the database with no waterfall and no public API surface; secrets stay server-side by construction. The cost: no interactivity, and today RSC needs a framework/bundler integration to work — you cannot bolt it onto a plain Vite SPA.

The 'use client' boundary and composition

'use client' at the top of a file marks the boundary where the server tree hands off to the browser. The critical rule: everything that file imports becomes client code too, transitively. One 'use client' at the top of your layout drags the whole app into the bundle.

'use client';                       // must be the first line of the file
import { useState } from 'react';
export function Accordion({ title, children }) {
  const [open, setOpen] = useState(false);
  return (
    <div>
      <button onClick={() => setOpen(o => !o)}>{title}</button>
      {open && children}            {/* children may be SERVER-rendered content */}
    </div>
  );
}

Composition is the escape hatch. A client component cannot import a server component, but it can render one passed in as children (or any prop) — because the parent server component already rendered it to a payload before handing it over:

// app/page.jsx — Server Component
export default async function Page() {
  const doc = await db.doc.find();
  return (
    <Accordion title="Details">
      <ServerRenderedDoc doc={doc} />   {/* stays on the server, zero JS shipped */}
    </Accordion>
  );
}
  • Props crossing the boundary must be serializable: no functions, no class instances, no Date-in-a-Map exotica. (Server Actions are the one exception — a function reference that serializes to an endpoint id.)
  • Push 'use client' as far down as possible: make the button interactive, not the page.
  • A client component still gets server-rendered to HTML for the initial load — "client" means "also runs in the browser", not "not rendered on the server".
Gotcha: Server Components are not "SSR with a new name". SSR is about producing HTML; RSC is about which components' code ever reaches the browser. A page can be SSR'd with zero server components, or use RSC in a framework that also streams SSR — which is what Next.js App Router does.

Server Actions ('use server')

If Server Components solved reading, Server Actions solve writing. An async function marked 'use server' can be passed to a form or called from a client component; React serializes the call to an HTTP request, runs the function on the server, and revalidates the affected data — no hand-written API route, no fetch, no client-side request state.

'use server';                                   // file-level, or first line inside the function
export async function addComment(formData) {
  const text = formData.get('text');
  await db.comment.create({ data: { text } });
  revalidatePath('/posts');                     // Next.js-specific cache invalidation
}

// used directly as a form action — works before JS loads
<form action={addComment}>
  <input name="text" /><button>Post</button>
</form>

React 19 ships the client-side half: useActionState (pending/result/error state for an action), useFormStatus (a child can read whether its parent form is submitting), and useOptimistic (show the comment instantly, roll back if the action fails). Security note: a Server Action is a public HTTP endpoint. Authenticate and validate inside every one of them — the fact that it is only called from an admin page proves nothing.

Where Next.js fits, and when plain CSR still wins

The Next.js App Router is the mainstream production home for all of the above, and it is worth naming which parts are React and which are Next:

  • React: Server Components, 'use client'/'use server', <Suspense>, streaming renderers, hydrateRoot, useActionState/useOptimistic.
  • Next.js: file-system routing, server components by default, loading.js/error.js (which compile to Suspense and error boundaries), generateStaticParams, ISR and revalidatePath/revalidateTag, the extended fetch cache, middleware and edge runtime.

Other RSC-capable stacks exist (React Router v7 framework mode, Waku, and Vite's RSC plugin), but the bundler integration is unavoidable: RSC needs a build that can split the module graph into server and client halves and a runtime that can serialize the tree.

Senior tip: Plain CSR is still the correct answer for an app behind a login where every page is user-specific and no crawler will ever see it — an internal admin console, an analytics dashboard, a trading terminal. SEO is irrelevant, the shell caches on a CDN forever, there is no server render to pay for, and you skip hydration, RSC boundary rules and the whole class of mismatch bugs. Choose SSR/RSC because the content is public, large, or first-paint-critical — not because it is the newest thing.

🎯 Interview questions

What is hydration, and what causes a hydration mismatch?

Hydration is the client pass where React re-renders the tree that the server already turned into HTML, adopts the existing DOM nodes instead of recreating them, and attaches event listeners. A mismatch happens when the client's first render differs from the server output — Date.now(), Math.random(), locale/timezone formatting, reading window/localStorage during render, invalid HTML nesting the browser repairs, or extensions injecting DOM. React warns and re-renders the affected subtree on the client, wasting the SSR work.

How do you fix a value that is genuinely different on server and client?

Render a stable placeholder on the first pass and set the real value in useEffect, which only runs on the client — so both server and first client render agree. For a single node you know will differ (a formatted timestamp) suppressHydrationWarning is the sanctioned escape hatch, but it only covers that element's own text/attributes, not its subtree, and it silences rather than fixes.

What does streaming SSR give you that renderToString does not?

renderToString blocks the whole response on the slowest data dependency. renderToPipeableStream flushes the shell as soon as it is ready and streams each <Suspense> boundary's HTML when its data resolves, so first paint is decoupled from slow data. It also enables selective hydration: boundaries hydrate independently, and React prioritises the one the user interacted with, replaying the recorded event.

How are Server Components different from SSR?

SSR renders client components to HTML for the first response, then still ships their JavaScript so they can hydrate. A Server Component runs only on the server and its code is never sent — the client receives a serialized render output. So SSR improves first paint; RSC removes bundle weight and lets components read the database or filesystem directly. They compose: the Next.js App Router streams SSR of an RSC tree.

What can a Server Component not do?

No useState/useReducer/useEffect, no event handlers, no browser APIs, no re-rendering in response to interaction — it runs once per request. Anything interactive goes below a 'use client' boundary. In exchange it can be async and await data directly in its body.

What does 'use client' actually do, and why does its placement matter?

It marks the boundary between the server tree and the client bundle. Everything the file imports becomes client code transitively, so a 'use client' high in the tree pulls the whole app into the bundle. Push it to the smallest interactive leaf. A client component cannot import a server component, but it can render one passed as children, since the server rendered it before handing it over — and props crossing the boundary must be serializable.

When would you deliberately choose plain CSR today?

An authenticated, highly interactive app no crawler will ever see — an internal dashboard or admin console. SEO and first-paint-for-strangers are non-issues, the shell is a CDN-cached static file, there is no per-request server cost, and you avoid hydration mismatches and RSC boundary constraints entirely. Reach for SSR/SSG/RSC when content is public, large, or first-paint-critical.
