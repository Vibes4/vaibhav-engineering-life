Microservices, APIs & Resiliency EY Sheet 07

The JD asks for "scalable, resilient, and secure microservices", "RESTful APIs with strong focus on performance, observability, and fault tolerance", and "monolith-to-microservices" modernization. This sheet is the architecture-judgement half of the round — separate from the AWS-service half. The most valuable thing you can demonstrate here is knowing when not to use microservices.

The line that wins this section: "Microservices are an organisational solution before they're a technical one — they let independent teams deploy independently. If you don't have that problem, you're buying distributed-systems complexity with no return. I've seen more damage from a premature split than from a well-modularised monolith."

Decomposition & boundaries

CertainHow do you decide service boundaries?

By business capability and data ownership, not by technical layer. A service owns a bounded context — Orders, Payments, Inventory — and owns its data exclusively. The test I apply: can this service be deployed without coordinating a release with another team? If two services always ship together, they're one service wearing a costume.

Practical heuristics: draw the boundary where the language changes (a "customer" in Billing is a different concept from a "customer" in Support — that's a context boundary). Follow team ownership, because Conway's Law will win anyway. Watch transaction boundaries: if an invariant must hold atomically across two candidate services, that's a strong signal they belong together, because the alternative is a saga and eventual consistency that the business may not accept.

Anti-patterns I'd name: splitting by technical layer (an "API service", a "database service") which gives you a distributed monolith with network calls where function calls used to be; splitting so finely that a single user action fans out to twelve synchronous calls; and sharing a database between services, which recreates coupling invisibly — the schema becomes a public API nobody can change.

CertainHow would you break a monolith into microservices?

Strangler fig, incrementally, never a big-bang rewrite. The steps:

  1. Don't start with code — start with a seam. Put a routing layer (ALB or API Gateway) in front of the monolith so every request passes through a point you control. Nothing changes behaviourally, but now you can redirect traffic per-route.
  2. Pick the first capability deliberately. Good first candidates: something with a clear boundary, low coupling to the rest, and a real reason to move — it scales differently, it changes often, or it's owned by a team blocked by the monolith's release train. A bad first candidate is the most business-critical module.
  3. Extract the code first, the data second. Move the logic into a new service that still reads the monolith's database (or calls back into it), so you validate the boundary before doing the hard part.
  4. Then split the data. This is the genuinely hard step and where most migrations stall. Identify foreign keys crossing the new boundary and replace them with API calls or replicated read models. Dual-write or CDC during transition, verify with reconciliation jobs, then cut over.
  5. Shift traffic gradually — route 1%, then 10%, then 100%, with the ability to route back instantly. Run both paths in parallel and compare outputs where you can.
  6. Delete the old code. The step everyone skips. A migration that leaves the monolith's version in place has doubled the maintenance cost and achieved nothing.

What I'd add as the consulting answer: "I'd also ask whether the client needs this at all. Often the actual pain is deployment speed or test-suite duration, and a modular monolith with a fixed CI pipeline delivers most of the benefit for a fraction of the risk. Recommending not to migrate is sometimes the right call, and saying so early builds more trust than agreeing to everything."

What are the 7 Rs of cloud migration?

Retire (switch it off — always check, a surprising share of an estate is unused), Retain (leave it on-prem for now, because of latency, licensing or regulation), Rehost (lift-and-shift onto EC2 — fastest, no cloud benefits), Relocate (move VMware workloads wholesale), Replatform (lift-and-reshape — e.g. move the database to RDS and the app to containers without rewriting it; usually the best effort-to-benefit ratio), Repurchase (drop it for a SaaS product), Refactor/Re-architect (rewrite cloud-native — highest cost, highest benefit, only justified when the business case is strong).

The judgement to add: most real programmes are a portfolio. I'd rehost the long tail to hit a data-centre exit deadline, replatform the mid-tier, and refactor only the two or three systems where the cloud-native benefit is genuinely worth the spend. Refactoring everything is how migration programmes run three years late.

API design

CertainHow do you version a REST API, and what counts as a breaking change?

Breaking: removing or renaming a field, changing a type, adding a required request field, tightening validation, changing an error code's meaning, changing default behaviour. Non-breaking: adding an optional request field, adding a response field (provided clients ignore unknown fields), adding a new endpoint, adding a new optional query parameter.

Versioning approaches: URI path (/v1/orders) — ugly to purists but unambiguous, cacheable, trivially routable at the gateway, and instantly visible in logs. It's what I'd pick for a client-facing API. Header / media-type versioning is cleaner in principle but harder to debug, easy for clients to get wrong, and complicates caching.

The operational half of the answer, which matters more than the syntax: version only when you must, run old and new in parallel with a published deprecation window, instrument per-version usage so you know who is still on v1 before you turn it off, and communicate with Deprecation/Sunset headers. The most common real failure isn't picking the wrong versioning scheme — it's turning off v1 without knowing who was still calling it.

Design a well-behaved REST API — what do you insist on?
  • Resources as nouns, HTTP verbs for actions. POST /orders, GET /orders/{id}, not POST /createOrder.
  • Correct status codes — 201 with a Location header on create, 202 for accepted-async, 400 vs 422 for malformed vs semantically invalid, 401 vs 403 for unauthenticated vs unauthorised, 409 for conflict, 429 with Retry-After for throttling. Returning 200 with {"error": ...} is the thing I'd reject in review.
  • Idempotency — PUT and DELETE are idempotent by spec; POST isn't, so accept an Idempotency-Key header on anything that creates money or side effects, store the key with the response, and replay the stored response on a retry.
  • Cursor pagination, not offset — OFFSET 100000 forces the database to scan and discard 100,000 rows, and results shift under the client when data is inserted. Cursor (keyset) pagination is stable and O(1).
  • Consistent error envelope — a machine-readable code, a human message, field-level details, and the correlationId so a user can quote it to support and you can find the exact trace.
  • Filtering, sorting, sparse fieldsets as query params with an allow-list, never interpolated into SQL.
  • OpenAPI spec as the contract, ideally generated from code or used to generate it, published, and validated in CI.
REST vs gRPC vs GraphQL for service-to-service calls.

REST/JSON — universal, debuggable with curl, cacheable by HTTP infrastructure, zero client tooling required. Default for public and partner APIs and perfectly fine internally.

gRPC — HTTP/2, binary protobuf, generated clients, streaming in both directions, and a schema that's enforced rather than documented. Meaningfully faster and smaller on the wire. Right for chatty internal service-to-service traffic where latency matters. Costs: not browser-native without a proxy, harder to inspect, and you now own protobuf schema evolution and a codegen step in CI.

GraphQL — solves the client-driven over/under-fetching problem, which is a real pain for mobile clients hitting many services. I'd use it as a gateway for varied front-end clients, not as the protocol between backend services. Its costs are real: N+1 resolver problems needing DataLoader, caching that HTTP can't help with, query-complexity attacks needing depth limiting, and authorisation that has to be enforced per-field.

Resiliency & observability

CertainHow do you stop one failing service from taking down the system?

Cascading failure is the default behaviour of a distributed system unless you design against it. The countermeasures:

  • Timeouts everywhere. The root cause of most cascades is an unbounded wait: service A's threads/connections all sit waiting on slow service B, so A stops answering anyone. Timeouts must be shorter than the caller's timeout, and budgeted across the chain.
  • Circuit breaker. After a failure threshold, open the circuit and fail fast for a cooling period, then half-open to test recovery. This protects the caller from the callee's latency and gives the callee headroom to recover instead of being hammered while it's already struggling.
  • Bulkheads. Isolate resources per dependency — separate connection pools, separate thread pools, separate Lambda reserved concurrency — so exhaustion in one path can't starve the others.
  • Retries with backoff and jitter, and a retry budget. Naive retries amplify load exactly when the system is weakest; jitter de-synchronises the herd, and a budget (cap retries at, say, 10% of traffic) prevents retry storms.
  • Load shedding and rate limiting. Rejecting 10% of requests with a fast 429 is strictly better than degrading 100% into timeouts.
  • Graceful degradation. Serve a stale cached response, hide the recommendations widget, queue the write for later — decide in advance what a degraded-but-useful version of each feature looks like.
  • Async by default. The strongest form of isolation: if the interaction can be a queued message instead of a synchronous call, the downstream being down becomes a backlog rather than an outage.
CertainWhat does observability mean for a microservices platform?

Three signals, and the distinction from "monitoring" is that monitoring answers questions you knew to ask, observability lets you ask new ones.

  • Metrics — cheap, aggregated, good for alerting and dashboards. I care about the RED metrics per service (Rate, Errors, Duration) and USE for resources (Utilisation, Saturation, Errors). Alert on percentiles, never averages — an average of 200 ms can hide a p99 of 8 seconds, and the p99 is somebody's actual experience.
  • Logs — structured JSON, not string concatenation, so they're queryable. Every log line carries the correlation/trace ID, the service name, and the user or tenant. Sampled at high volume, with error logs never sampled out.
  • Traces — the one that makes microservices debuggable. A trace ID propagates through every hop (W3C traceparent header), so you can see that a 3-second request spent 2.7 seconds in one downstream call. In Node I'd propagate context with AsyncLocalStorage and instrument with OpenTelemetry, exporting to X-Ray or whatever the client already runs — vendor-neutral instrumentation matters because on a consulting engagement the backend is the client's choice, not mine.

Then the layer above: SLIs and SLOs. Define what "working" means numerically (99.9% of requests under 300 ms), alert on error-budget burn rate rather than on every individual spike, and make dashboards that answer "is the user experience broken", not "is CPU at 70%". Alerting on symptoms rather than causes is what keeps on-call sustainable.

Depth probeHow do you do a zero-downtime deployment?

The deployment strategy and the application both have to cooperate.

Strategies: Rolling — replace instances gradually; cheapest, but two versions run simultaneously so the code must be backward-compatible. Blue/green — stand up the full new environment, switch the load balancer, keep the old one warm for instant rollback; costs double infrastructure briefly but gives the fastest, most certain rollback. Canary — route a small percentage to the new version, watch error rate and latency, then ramp; best risk control, needs good metrics and automated rollback to be worth the complexity.

The application requirements people forget: health checks that distinguish liveness (is the process alive) from readiness (can it serve traffic yet — dependencies connected, caches warm), so the load balancer doesn't send traffic to a booting instance. Graceful shutdown on SIGTERM: stop accepting new connections, finish in-flight requests, drain from the target group, then exit — without this, every deploy drops the requests in flight. Backward-compatible database migrations (expand/migrate/contract), because during a rolling deploy old and new code both hit the same schema. And feature flags to separate deploy from release, so shipping code and enabling behaviour are two independent decisions and the rollback is a flag flip rather than a redeploy.

Where do you put caching, and how do you invalidate it?

Layers, from the user inward: browser (Cache-Control/ETag), CDN (CloudFront for static and cacheable API responses), API/application cache (Redis/ElastiCache), database (query cache, materialised views, DAX for DynamoDB), and in-process (fastest, but per-instance so it's inconsistent across a fleet — fine for config, dangerous for user data).

Patterns: cache-aside (read cache, miss → read DB → populate) is the default and keeps the cache optional; write-through keeps the cache fresh at write cost; write-behind is fast but can lose data. Invalidation: TTL-based is simple and self-healing (and I'd start there); event-based invalidation is accurate but you must handle the message being lost; versioned keys (user:123:v7) sidestep deletion entirely.

Failure modes worth naming: stampede/thundering herd when a hot key expires and a thousand requests all miss simultaneously — fix with a lock or single-flight so one request repopulates while others wait, or probabilistic early expiry. Cache penetration from repeated misses on keys that don't exist — cache the negative result briefly. And always design so that the cache being completely empty degrades performance rather than causing an outage; if the system can't survive a cold cache, the cache is load-bearing infrastructure and needs to be treated as such.
