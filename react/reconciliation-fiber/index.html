Reconciliation & Fiber React

Reconciliation is how React turns "here is what the UI should look like now" into "here are the specific DOM mutations to perform". You describe the whole tree on every render; React diffs the new element tree against the previous one and commits only the differences.

Fiber is the data structure and scheduler that does this work. Rewritten in React 16, it turned reconciliation from one uninterruptible recursive call into a queue of small units of work that can be paused, prioritised, abandoned and restarted — which is what makes concurrent features like useTransition and Suspense possible at all.

The honest claim about the virtual DOM

The virtual DOM is a tree of plain JS objects ({ type, props, key }) that React builds when your components run. Diffing it is extra work compared with writing to the DOM directly — hand-written imperative DOM code will always be faster than React if you write it perfectly.

What the virtual DOM actually buys you:

  • A declarative programming model. You write UI as a function of state and never touch a node by hand; the whole class of "the DOM and my model drifted apart" bugs disappears.
  • Batching. Many state updates collapse into one diff and one coordinated set of mutations, instead of N separate layout-triggering writes.
  • Minimal, ordered mutations. React computes the set of changes before touching anything, so it avoids repeated layout thrashing.
  • A platform-independent target. The same reconciler drives react-dom, React Native and custom renderers.
Gotcha: "the virtual DOM is faster than the DOM" is a comparison error and a red flag in interviews. It is faster than naive re-rendering (blowing away and rebuilding innerHTML), and it is fast enough while being far easier to reason about. That is the real pitch.

The two heuristics that make diffing O(n)

Optimally diffing two arbitrary trees is O(n³). React refuses to pay that and instead assumes two things that are almost always true of real UIs, giving O(n):

1. Different element type ⇒ tear down the whole subtree

If the type at a position changes — div → span, or ProfileA → ProfileB — React does not try to match children. It unmounts the old subtree (running cleanup and componentWillUnmount), destroys all of its state and refs, and mounts the new one from scratch.

{isEditing ? <EditForm value={v} /> : <ReadOnly value={v} />}
// toggling this destroys the whole subtree each way — scroll position, focus,
// uncontrolled input values and any local state are gone.

The same trap hides in a component defined inside another component: the function identity is new on every render, so the type differs, so React remounts it every time.

// ❌ new function identity per render → remount + state loss + focus loss, every keystroke
function Page() {
  function Row() { … }
  return <Row />;
}

2. Same type ⇒ keep the instance, update props

Same type at the same position means React keeps the existing DOM node and fiber, updates only the attributes that changed, and preserves state, refs and effects. This is why toggling a class on an element is cheap and why a component keeps its useState across prop changes.

Keys: identity across renders

Inside a list, position is not identity. A key tells React "this is the same logical child as before, even if it moved". Without keys (or with index keys) React matches children by position.

old: [a, b, c]        new: [c, a, b]        // one item moved to the front

index keys : slot 0 was "a" now "c" → patch, slot 1 patch, slot 2 patch  (3 updates)
stable ids : c matched to c, a to a, b to b → ONE move                    (1 move)

The extra patches are the cheap part of the damage. The expensive part is that state travels with the key: if row "a" had a half-typed input, an open menu or a focused field, an index key hands that state to whatever item now occupies index 0.

Key choiceVerdict
Stable domain id (item.id)Correct default
Array indexOnly for a static list that is never reordered, inserted into, filtered or sorted
Math.random() / uuid() in renderNever — remounts every child on every render
Composite (`${type}-${id}`)Fine when ids are only unique per group
Senior tip: keys are scoped to their sibling list, not globally, and they are consumed by React — props.key is not readable inside the component. Flip the trick around and key becomes a deliberate reset: changing key={userId} on a form remounts it with fresh state.

Fiber: work as a linked list, not a call stack

Before React 16 the "stack reconciler" recursed through the tree synchronously. Once started, it could not stop — a big update blocked the main thread and dropped frames, with no way to say "the user just typed, handle that first".

A fiber is a plain object representing one unit of work for one element. Fibers form a tree via three pointers — child, sibling, return (parent) — so React can walk the tree with a loop and an explicit cursor rather than the JS call stack. That means it can stop between any two fibers, keep the cursor, hand the thread back to the browser, and resume later.

fiber = {
  tag, type, key,          // what this is
  stateNode,               // the DOM node or class instance
  child, sibling, return,  // tree traversal without recursion
  pendingProps, memoizedProps, memoizedState,   // the hook list lives here
  flags,                   // Placement / Update / Deletion effect tags
  lanes,                   // priority of pending work
  alternate,               // the other tree — see double buffering
}

Work proceeds as beginWork going down (render the component, create child fibers) and completeWork coming back up (build/prepare DOM nodes, bubble effect flags to the parent). Between any two units, React checks whether its time slice has expired.

Why "no side effects in render" is a hard rule: a render can be discarded or replayed. If you mutate a module variable, fire analytics or write to a ref during render, it happens an unpredictable number of times. StrictMode double-invokes components in development precisely to surface this.

Commit is split into three sub-phases: before mutation (snapshots, e.g. getSnapshotBeforeUpdate), mutation (insert/update/delete DOM, detach old refs), and layout (attach refs, run useLayoutEffect synchronously before paint). Passive effects (useEffect) are flushed after paint, which is why they never block the frame — and why measuring layout in useEffect can show a flicker where useLayoutEffect would not.

Double buffering: current and work-in-progress

React keeps two fiber trees. current is what is on screen. During a render React builds a workInProgress tree, reusing fibers from current where possible via the alternate pointer that links each pair.

  • An abandoned render simply drops the WIP tree — current was never touched, so the screen never showed a half-finished state.
  • Commit ends with a single pointer swap: the finished WIP tree becomes current. That is why commit is atomic.
  • The two trees are recycled between renders instead of being allocated fresh, which keeps GC pressure down.

Concurrent rendering: lanes and time slicing

Every update is tagged with a lane — a bitmask priority. Discrete input (click, keypress) gets a sync lane; the default lane covers ordinary updates; transitions get a lower lane; offscreen/idle work is lowest. The scheduler always works on the highest-priority pending lane, and entangles lanes that must not be split apart.

Time slicing: for non-sync work React renders a few fibers, checks shouldYield() against a ~5 ms budget, and if the budget is gone it yields to the browser via a MessageChannel task, so input and paint get a turn. It then resumes at the fiber it stopped on. If a higher-priority update arrives mid-render, the in-progress tree is thrown away and rendering restarts at the new priority.

How this powers useTransition

const [isPending, startTransition] = useTransition();

function onChange(e) {
  setQuery(e.target.value);                       // sync lane: the input updates now
  startTransition(() => setResults(filter(e.target.value)));  // transition lane: interruptible
}

The typed character commits in the next frame. The expensive results render at transition priority and can be interrupted and restarted by the next keystroke — so no frame is blocked and stale results are never shown. useDeferredValue is the same mechanism with a value instead of a setter. Without Fiber's interruptible render phase, neither could exist.

Note: concurrent features do not make rendering faster. They reorder when work happens. A single 400 ms component render is still 400 ms and still blocks a frame — time slicing only helps when the work is spread across many fibers.

Hydration and mismatches

Server rendering ships HTML; hydration then walks the existing DOM with hydrateRoot, builds the fiber tree, and attaches events and state without re-creating nodes. It expects the client's first render to produce exactly the server markup.

  • Common causes of a mismatch: Date.now()/Math.random() in render, locale or timezone formatting, reading window/localStorage, browser extensions mutating the DOM, and invalid nesting such as a <div> inside a <p> which the parser silently rewrites.
  • React 18 recovers from a mismatch by discarding the server HTML for that subtree and client-rendering it — correct, but you lose the SSR benefit and get a console error. React 19 reports mismatches with a much clearer diff.
  • Deliberate escape hatches: suppressHydrationWarning for a single unavoidable node (a timestamp), or render the client-only value in an effect after mount.
  • Selective hydration: with streaming SSR, Suspense boundaries hydrate independently and React prioritises the boundary the user just interacted with — another thing only interruptible rendering makes possible.

🎯 Interview questions

Is the virtual DOM faster than the real DOM?

No — it is additional work on top of the DOM. It wins by enabling a declarative model, batching many updates into one coordinated set of mutations, and computing a minimal ordered diff before touching anything. It is faster than naive full re-rendering and fast enough in practice, while removing an entire class of manual-DOM-sync bugs.

How does React get O(n) diffing?

Two heuristics instead of a general tree-diff. First, elements of different types produce different trees, so a type change tears down the subtree and rebuilds it rather than trying to match children. Second, keys let the developer declare which children are stable across renders, so sibling lists are matched by identity rather than searched. A general optimal diff would be O(n³).

What breaks when you use the array index as a key?

Keys are identity across renders. With index keys, inserting or reordering makes React match old index 0 to new index 0, so it patches every row's props instead of moving one node, and — the real bug — component state, uncontrolled input values, focus and refs stay attached to the position rather than the item. The half-typed comment ends up on the wrong row.

What is a fiber, and what did it change?

A fiber is a plain object representing one unit of work for one element, linked to its child, sibling and parent. Because the tree is walked with a loop over these pointers rather than the JS call stack, React can pause between units, yield to the browser, resume, reprioritise or discard work. The pre-16 stack reconciler recursed synchronously and could not be interrupted.

Why are side effects forbidden during render?

The render phase is interruptible: React may throw a partial render away and restart it, or render a component twice at different priorities, so anything you do there can happen zero, one or many times. Effects belong in the commit phase (useEffect/useLayoutEffect). StrictMode double-invokes components in development to make impure renders fail loudly.

What is double buffering in React?

React maintains two fiber trees linked by alternate: current (on screen) and workInProgress (being built). Discarding an interrupted render just drops the WIP tree, so the user never sees a partial UI, and commit is a single pointer swap making it atomic. The trees are recycled rather than reallocated.

How does useTransition relate to Fiber?

startTransition tags its updates with a low-priority lane. The scheduler renders that work in slices, yielding roughly every 5 ms, and abandons and restarts it whenever a higher-priority update such as a keystroke arrives. The urgent update commits first; the expensive one catches up. This depends entirely on the render phase being interruptible, which is what Fiber provides.

What causes a hydration mismatch?

The client's first render producing different markup than the server sent — random or time-based values, locale/timezone formatting, reading browser-only APIs during render, invalid HTML nesting that the parser rewrites, or extensions mutating the DOM. React 18 falls back to client-rendering that subtree, losing the SSR benefit. Fix by making the first render deterministic, deferring the client-only value to an effect, or using suppressHydrationWarning for a single unavoidable node.
