Observability Mastery

Observability is the property that lets you ask arbitrary new questions about a running system from its telemetry — without shipping new code — so you can debug the failures you never anticipated. It is built on high-cardinality, high-dimensionality data across three pillars: metrics, logs, and traces.

Interview Explanation — 30 seconds

Say this: "Monitoring answers known-unknowns — I pre-decide the dashboard and alert on thresholds I already thought of. Observability lets me answer unknown-unknowns: I emit wide, high-cardinality events and can slice them by user, region, build SHA, or endpoint at query time to explain a novel failure. Three pillars — metrics for cheap aggregate trends, structured logs for detailed events, distributed traces for causality across services — all stitched by a shared trace ID so I can pivot metric → trace → log and cut MTTR."

Interview Explanation — 2 minutes

The control-theory root: a system is observable if you can infer its internal state from its outputs. In practice that means emitting enough telemetry that a novel question ("why is p99 latency 3s only for Android users in Mumbai on build 4a2f?") is answerable from stored data alone.

  • Metrics — numeric time series, pre-aggregated, cheap to store (a few bytes/sample). Types: counter (monotonic, use rate()), gauge (up/down), histogram (bucketed, server computes percentiles via histogram_quantile), summary (client-computed quantiles, not aggregatable). Great for trends and alerting, terrible for high cardinality.
  • Logs — discrete events, ideally structured JSON with levels and a trace_id. Rich but expensive; sampled and retention-capped. Aggregated in ELK/OpenSearch or Loki (index labels only).
  • Traces — a tree of spans across services, tied by W3C traceparent context propagation. Show causality and where latency actually goes. OpenTelemetry SDK + Collector + OTLP is the standard; backends are Jaeger/Tempo/Grafana.

On top: SLIs/SLOs/error budgets drive alerting via multi-window multi-burn-rate rules, and you alert on symptoms (the four golden signals: latency, traffic, errors, saturation) not causes. Exemplars link a metric bucket directly to a sample trace, so a latency spike on a dashboard is one click from the exact slow request.

Internal Working

  1. Instrumentation. Code emits telemetry via an SDK. Auto-instrumentation monkey-patches libraries (HTTP client/server, DB drivers, gRPC) to create spans and metrics; manual instrumentation adds custom spans and business attributes.
  2. Context creation. On an inbound request with no context, the SDK generates a 16-byte trace_id and 8-byte span_id, builds a root span, and stores it in a context object (Node.js AsyncLocalStorage, Java ThreadLocal / Context).
  3. Propagation. Outbound calls inject traceparent: 00-{trace_id}-{span_id}-{flags} and tracestate headers (W3C Trace Context). The downstream service extracts them and makes its root span a child — this is how the tree links across process boundaries.
  4. Metric aggregation. Counters/gauges/histograms live in-process. A histogram increments the bucket le (less-than-or-equal) counter plus _sum and _count. Prometheus later computes histogram_quantile(0.99, rate(http_req_bucket[5m])) by interpolating within buckets.
  5. Collection. Prometheus pulls /metrics every scrape_interval (typically 15s) from targets found via service discovery (Kubernetes SD, Consul, EC2). Traces/logs are pushed over OTLP/gRPC to an OpenTelemetry Collector.
  6. Processing/sampling. The Collector batches, enriches (adds k8s resource attributes), and samples. Head-based sampling decides at the root; tail-based sampling buffers a whole trace and keeps it if any span errored or was slow.
  7. Storage. Metrics → TSDB (Prometheus/Mimir/Thanos) with delta-of-delta + XOR compression (~1.3 bytes/sample). Traces → Tempo/Jaeger (object storage, indexed by trace_id). Logs → Loki (label index + compressed chunks) or Elasticsearch (inverted index).
  8. Correlation & query. Grafana/PromQL/LogQL/TraceQL query the stores. Exemplars and shared trace_id let you pivot: alert fires on a metric → jump to exemplar trace → open the error log line by trace_id.

Why was this built?

In monoliths, a single stack trace and one host's logs explained almost any failure. Microservices broke that: one user request fans out to 20+ services across pods that are rescheduled every few minutes, so there is no single log file and no single stack trace. Aggregate CPU dashboards ("the box is fine") coexisted with users seeing 500s.

  • Before: Nagios/Zabbix host checks, grep over SSH, per-service Munin graphs, and static threshold alerts that fired on causes ("CPU > 80%") producing pager fatigue.
  • The shift: Google's Dapper (2010) introduced distributed tracing; Prometheus (2012, ex-Borgmon) brought dimensional metrics + pull; the SRE book codified SLOs/error budgets; Honeycomb popularized high-cardinality wide events. OpenTelemetry (2019, merging OpenTracing + OpenCensus) unified the SDKs and wire format so instrumentation is vendor-neutral.

Advantages

  • Answer unknown-unknowns at query time — no redeploy to add a new breakdown dimension.
  • MTTR collapse — metric → exemplar trace → log pivot turns a 2-hour hunt into minutes.
  • Vendor neutrality via OpenTelemetry: instrument once, export to Prometheus/Tempo/Datadog/Honeycomb without code changes.
  • SLO-driven ops — error budgets convert reliability into a shared, quantified decision instead of gut feel.
  • High cardinality lets you isolate the one bad tenant, build, or region among millions.

Drawbacks

  • Cost. Telemetry can rival or exceed compute cost; logs and high-cardinality metrics are the usual budget-eaters.
  • Cardinality explosion. One unbounded label (user_id, URL with IDs) multiplies time series and can OOM Prometheus.
  • Sampling trade-off. Traces are usually sampled, so the one failing request you need may not be stored (mitigated by tail-based sampling).
  • Instrumentation drift. Inconsistent attribute names across teams make cross-service queries painful.
  • Alert fatigue. Too many cause-based alerts train engineers to ignore the pager.

When NOT to use it

Watch out: Don't put unbounded values (user_id, request_id, raw URLs, timestamps, full emails) in metric labels — that's a cardinality bomb; put them in trace/log attributes instead. Don't run full tail-based sampling on a low-traffic single service — head-based at 100% is simpler. Don't build a bespoke agent-based tracing framework when OpenTelemetry auto-instrumentation covers your stack. Don't alert on every cause (CPU, memory, GC); alert on user-facing symptoms tied to SLOs. Don't log at DEBUG in prod for high-QPS paths — it will dominate your bill and can add latency.

Production Architecture

A typical Kubernetes deployment: apps auto-instrumented with OTel SDKs push OTLP to a per-node Collector agent (DaemonSet), which forwards to a gateway Collector pool that does tail-based sampling and fan-out. Metrics are scraped by Prometheus (or pushed via OTLP to Mimir); traces go to Tempo; logs to Loki. Grafana is the single query pane, wiring exemplars and trace_id links across all three.

flowchart LR
  App["App pods with OTel SDK"] -->|OTLP| Agent["Collector agent DaemonSet"]
  Agent -->|OTLP| GW["Collector gateway pool"]
  Prom["Prometheus"] -->|scrape metrics| App
  GW -->|traces| Tempo["Tempo traces"]
  GW -->|logs| Loki["Loki logs"]
  Prom --> Mimir["Mimir long term TSDB"]
  Grafana["Grafana"] --> Mimir
  Grafana --> Tempo
  Grafana --> Loki
  Alert["Alertmanager"] --> Prom

The gateway Collector is the sampling and enrichment choke point: it buffers spans per trace_id, applies tail policies (keep-on-error, latency threshold, probabilistic base rate), attaches k8s resource attributes, and drops noisy telemetry before it hits paid storage. Prometheus stays pull for scrape-health signals; everything else is push.

Production Problems

  • Cardinality blow-up: a new label with per-request values takes Prometheus from 1M to 50M series, RSS spikes, OOMKilled, alerting goes blind during an incident.
  • Broken trace propagation: one service (often a legacy or third-party hop) drops traceparent, so traces fragment into disconnected halves and you can't follow the request.
  • Collector backpressure: trace volume exceeds gateway throughput; OTLP queue fills, spans are dropped silently, and you lose exactly the incident traffic.
  • Log cost runaway: a DEBUG line in a hot loop or a stack trace on every request 10x's log volume and blows the retention budget overnight.
  • Clock skew: unsynced node clocks make child spans appear to start before parents; trace waterfalls look nonsensical.

Scaling

Metrics scale via federation and sharding: Prometheus stays single-node per shard, then Thanos/Mimir/Cortex provide global query, long-term object storage, downsampling, and horizontal ingest. Traces scale by pushing sampling to a stateless gateway tier and storing in object storage (Tempo). Logs scale by indexing only labels (Loki) instead of full text.

flowchart TD
  A["App fleet"] --> B1["Prometheus shard 1"]
  A --> B2["Prometheus shard 2"]
  B1 --> C["Thanos or Mimir query layer"]
  B2 --> C
  C --> D["Object storage S3 with downsampling"]
  C --> E["Grafana global view"]
  • Vertical first: Prometheus handles millions of series on one box before you shard.
  • Functional sharding: split scrape jobs by team/namespace via hashmod relabeling.
  • Downsampling: keep raw for 15d, 5m-resolution for 90d, 1h for a year — cuts storage 10-100x.
  • Collector autoscaling: HPA the gateway pool on queue size and CPU; tail sampling needs enough RAM to buffer full traces.

Security

  • PII leakage: emails, tokens, card numbers end up in logs/span attributes. Mitigate with Collector redaction/attributes processors and log scrubbers; enforce in review.
  • Transport: OTLP over TLS/mTLS; Prometheus scrape with bearer tokens or mTLS; never expose /metrics publicly (it leaks internal topology and versions).
  • Multi-tenancy: enforce tenant isolation (Mimir/Loki X-Scope-OrgID) so one team can't query another's data.
  • Access control: RBAC on Grafana; traces can contain sensitive request payloads.
  • DoS via cardinality: a malicious or buggy client can inflate labels — enforce label limits and rate-limit ingest.

Performance

  • Instrumentation overhead: OTel SDK adds ~1-5% CPU with auto-instrumentation; a span is on the order of hundreds of ns to create in-process. Batch exporters, don't block the request path.
  • Cardinality is the dominant cost: Prometheus memory ≈ ~3KB per active series; 5M series ≈ ~15GB+ RSS. Cut it by dropping high-card labels via relabeling.
  • Scrape tuning: 15s interval is standard; drop to 30-60s for large fleets. scrape_timeout must be < interval.
  • Histogram buckets: too many buckets = cardinality × buckets; native/exponential histograms (Prometheus 2.40+) give better resolution at lower cost.
  • Log throughput: async, batched, non-blocking log appenders; structured JSON serialization is cheaper to parse downstream than regex over free text.
  • Sampling for throughput: at 100k+ traces/s, tail sampling to ~1-10% keeps storage sane while preserving all errors.
Say this: "The number I watch is active series and RSS on Prometheus, and dropped_spans on the Collector. Those two tell me if observability itself is about to fail during an incident."

Common Mistakes

  • High-cardinality metric labels. Fix: move IDs to trace/log attributes; keep metric labels bounded (status, method, route template not raw path).
  • Alerting on causes, not symptoms. Fix: alert on golden signals + SLO burn; make CPU/memory diagnostic dashboards, not pages.
  • Unstructured logs. Fix: JSON with consistent keys and a trace_id on every line.
  • Averages instead of percentiles. Fix: histograms + histogram_quantile; the mean hides the tail.
  • Head sampling that drops errors. Fix: tail-based keep-on-error policy.
  • No trace_id in logs. Fix: inject it via logging framework MDC/formatter so you can pivot trace ↔ log.
  • Summary metrics across replicas. Fix: never average quantiles; use histograms which aggregate correctly.

🎯 Deep-dive Q&A — model answers

Walk me through exactly what happens from a metric alert to root cause.

Alertmanager fires on an SLO burn-rate rule computed from a histogram (e.g. histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) breaching target). I open the Grafana panel; the p99 spike has an exemplar — a dot carrying a trace_id — so I click straight into Tempo and see the waterfall. The slow span is a DB call in service C. I take that trace_id and query Loki {service="C"} | trace_id="..." to find the log line with the actual statement and error. If the span shows CPU-bound time with no clear cause, I pull the continuous profile for that pod's window and read the flame graph. Metric → trace → log → profile: minutes, not hours.

Why can't you average two services' summary quantiles, and what do you do instead?

A summary computes quantiles client-side over a sliding window; the p99 of instance A and p99 of instance B have no mathematical relationship to the p99 of the combined stream — averaging them is statistically meaningless. Histograms store per-bucket counts, which are additive: sum the buckets across instances, then apply histogram_quantile on the aggregate. That's why fleet-wide percentiles require histograms. The cost is you must pick buckets up front (or use native/exponential histograms for automatic resolution).

Design a tail-based sampling policy for a payments service.

Keep 100% of traces with any error span, 100% above a latency threshold (say p99 target), and a low probabilistic base rate (1-5%) for the healthy majority. Add a policy to always keep specific high-value routes (settlement, refund). Buffer at the gateway Collector keyed by trace_id with a decision window (e.g. 5-10s) long enough for all spans to arrive. Size Collector RAM for peak in-flight traces × avg spans × span size. The point: you can throw away boring successful traffic but never the failures or slow requests, and you keep enough baseline to compute unbiased latency stats.

How do you set up multi-window multi-burn-rate alerts for a 99.9% SLO?

99.9% over 30 days = 0.1% error budget ≈ 43 minutes. A burn rate of 1 exhausts the budget exactly in 30 days. Page on fast burn: 14.4x over a 1h window AND a 5m short window (the short window prevents flapping and makes it recover fast) — that burns 2% of budget in an hour. Add a slow burn ticket: ~6x over 6h, and ~1x over 3d. Two severities: fast burn pages immediately (something is badly broken), slow burn opens a ticket (steady degradation). Requiring both a long and short window cuts false positives and false negatives.

Your Prometheus is at 8M series and climbing. Walk me through the fix.

First, find the offender: topk(10, count by (__name__)({__name__=~".+"})) and count by (job)(...). Usually one label is unbounded. Immediate mitigation: metric_relabel_configs with labeldrop/labelkeep to strip it at scrape time, and per-target sample_limit. Structural fix: change instrumentation to use route templates not raw paths, move IDs to trace attributes, adopt native histograms to cut bucket cardinality. Long term: functional shard across multiple Prometheus by namespace and put Thanos/Mimir in front for global query and downsampled long-term storage. Guardrail: alert on prometheus_tsdb_head_series growth and add CI cardinality checks.

Explain W3C Trace Context on the wire, byte by byte.

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01. Fields: version (00), 16-byte trace-id (32 hex), 8-byte parent span-id (16 hex), 1-byte trace-flags (01 = sampled). tracestate carries vendor-specific key-value pairs to survive multi-vendor hops. The receiving SDK extracts, sets its new span's parent to the incoming span-id, keeps the trace-id, and re-injects with its own span-id on the next outbound call. If a hop doesn't forward these headers, the trace fragments — that's the number-one cause of broken waterfalls.

When would you choose Loki over Elasticsearch, and what do you give up?

Loki indexes only labels and stores compressed log chunks in object storage, so ingestion and storage are cheap and it pairs naturally with Prometheus labels. You give up full-text inverted-index search speed — LogQL brute-force scans chunks matching the label selector, which is slower for needle-in-haystack queries over huge volumes. Choose Loki when logs are high-volume, cost-sensitive, and you mostly filter by known labels (namespace, service, trace_id). Choose Elasticsearch/OpenSearch when you need fast arbitrary full-text search and complex aggregations and can pay for the index.

How does continuous profiling complement tracing?

A trace tells you span X took 400ms; it rarely tells you why the CPU was busy inside it. Continuous profiling (pprof, Parca, Pyroscope, Grafana Phlare) samples stacks always-on at low overhead (~1-2%) and produces flame graphs you can slice to the incident window and even the pod. You see the exact function eating CPU or allocating. The frontier is linking a span to its profile via span context, so from a slow span you jump to the flame graph of that request. It closes the last gap: trace says where, profile says which line of code.

How do you keep observability alive when the thing you're observing is falling over?

Isolation: telemetry infra runs in a separate failure domain (own nodes/cluster), so an app outage doesn't take Prometheus with it. Non-blocking exporters and bounded queues so the app degrades telemetry, not requests, under load. Local Collector agents buffer and retry so a gateway blip doesn't lose data. Alert on the observability stack itself (up, head_series, dropped_spans) so you know when you're flying blind. And keep a minimal always-on low-cardinality metric set that survives even when high-card debugging telemetry is shed.

What's the difference between auto and manual instrumentation, and where's the boundary?

Auto-instrumentation hooks known libraries (HTTP, gRPC, DB drivers, message queues) via bytecode agents (Java) or monkey-patching (Node/Python) to emit spans and metrics with zero code changes. It gets you the request skeleton for free. Manual instrumentation adds business-meaningful spans and attributes — order_id, tenant, payment_method, cache hit/miss — which is what makes traces answer real questions. The rule: auto for plumbing, manual for domain semantics. Without manual attributes your traces show where time went but not which business case, so debugging stays coarse.

Why is the pull model useful beyond just scraping numbers?

Pull gives you a free liveness signal — the up metric per target — so a target that vanishes is instantly detectable, unlike push where silence is ambiguous (dead vs idle). Service discovery (kubernetes_sd, consul) means new pods are scraped automatically and relabeling normalizes their labels. It also centralizes scrape config and rate control on the monitoring side, so a runaway app can't flood you. The gap is short-lived jobs and serverless that die before a scrape — for those you push to a Pushgateway or use OTLP.

An exemplar links a metric to a trace — how is it stored and surfaced?

When recording a histogram observation, the SDK can attach the current trace_id as an exemplar to the specific bucket. Prometheus stores exemplars in a separate, size-limited store (they're not full samples). Grafana renders them as clickable dots on the graph at the timestamp/value, each carrying the trace_id that Grafana turns into a deep link to Tempo/Jaeger. So a latency spike on a panel is literally one click from a representative slow trace — that's the single biggest MTTR lever because it removes the "now go find a matching trace" step.

How do you observe an async / event-driven flow where there's no synchronous call chain?

Context must travel through the message, not an HTTP header. Inject traceparent into message metadata/headers (Kafka record headers, SQS message attributes) on produce, and extract on consume to create a span linked to the producer. Because it's async, use span links rather than strict parent-child for fan-out/batch consumers, so one consumer span can reference many producing traces. Watch for long queue dwell — model it as a span or a gap between producer and consumer spans so latency in the broker is visible, not hidden.

Give me the cost-reduction playbook when the observability bill is out of control.

Attack in order of $/value. 1) Logs: sample non-error logs, drop DEBUG in prod, cut retention on low-value streams, move to label-indexed storage. 2) Metric cardinality: drop unbounded labels, aggregate away unused dimensions with recording rules, use native histograms. 3) Traces: tail-sample to keep errors + slow + a small baseline, drop the boring successful bulk. 4) Downsample old metrics (raw 15d, 5m 90d, 1h 1y). 5) Right-size retention per pillar to how far back you actually query. Always keep a cheap always-on core (SLO metrics) untouched so cost cuts never blind you to user pain.

What breaks if node clocks are skewed, and how do you detect it?

Span timestamps are set locally per service; if node clocks drift, a child span can appear to start before its parent or spans overlap impossibly, making waterfalls unreadable and duration math wrong. Metrics get misaligned buckets and rate() can produce spikes/negatives. Detect via NTP offset monitoring (node_timex_offset_seconds) and alert on drift > a few ms; in traces, watch for negative or nonsensical span gaps. Fix: enforce NTP/chrony on all nodes; some backends clamp child start to parent start as a band-aid but the real fix is clock sync.

How do RED and USE differ and when do you use each?

RED is request-centric — Rate, Errors, Duration — applied per service/endpoint; it's what users feel and what your SLOs are built on, so it drives alerting. USE is resource-centric — Utilization, Saturation, Errors — applied per resource (CPU, disk, queue, connection pool); it's diagnostic, telling you why RED went bad. In an incident: RED alert says "checkout p99 is breaching"; USE dashboards then reveal the DB connection pool is saturated. Alert on RED (symptoms), diagnose with USE (causes).
