Kubernetes Mastery

Kubernetes is a declarative container orchestrator: you write the desired state into etcd via the API server, and an army of controllers runs level-triggered reconciliation loops to drive the cluster's actual state toward it — rescheduling Pods, programming iptables/IPVS, attaching volumes, and scaling replicas without you touching a node.

Interview Explanation — 30 seconds

Say this: "Kubernetes is a control loop over a distributed key-value store. You POST desired state (Deployments, Services) to the kube-apiserver, which persists it to etcd — the single source of truth backed by Raft. Controllers watch etcd and reconcile: the Deployment controller creates a ReplicaSet, the ReplicaSet controller creates Pods, the scheduler binds each Pod to a node, and the kubelet on that node tells the container runtime to start it. Everything is level-triggered, so if a node dies the controllers just re-reconcile and reschedule. Networking is handled by CNI for pod IPs and kube-proxy programming iptables/IPVS for Services."

Interview Explanation — 2 minutes

At the SDE3/Staff level I frame Kubernetes around four ideas:

  1. Declarative + reconciliation. You never issue imperative "start 3 containers" commands. You declare "I want 3 replicas" in a spec. Controllers continuously diff desired vs actual (.spec vs .status) and act. This is level-triggered, not edge-triggered — a missed event is self-healing on the next resync (default informer resync is periodic; the watch stream is the fast path).
  2. The control plane. kube-apiserver is the only component that talks to etcd; everything else talks to the apiserver. etcd holds all cluster state and uses Raft for consensus (leader + majority quorum). The scheduler assigns Pods to nodes; the controller-manager runs ~30 built-in controllers (Deployment, ReplicaSet, Node, Endpoint, Job...); the cloud-controller-manager talks to the cloud provider for LoadBalancers, routes and node lifecycle.
  3. The node plane. kubelet is the node agent — it watches for Pods bound to its node, calls the container runtime over CRI (containerd/CRI-O), runs probes, and reports status. kube-proxy programs iptables/IPVS so a ClusterIP virtual IP load-balances to healthy pod IPs. The CNI plugin (Calico, Cilium, flannel) gives each Pod a routable IP.
  4. The workload API. Pods are the atom; ReplicaSets keep N copies alive; Deployments manage rolling updates over ReplicaSets; StatefulSets give stable identity + ordered rollout; DaemonSets run one pod per node; Jobs/CronJobs run to completion. Services + EndpointSlices provide stable virtual IPs and DNS in front of ephemeral pods.
Say this: "The mental model that impresses interviewers is: desired state in etcd, actual state on nodes, controllers close the gap forever. Self-healing is just reconciliation you never turned off."

Internal Working

Walk through what happens when you run kubectl apply -f deployment.yaml with 3 replicas:

  1. Client → apiserver. kubectl does a TLS mutual-auth POST to kube-apiserver. The request passes through the chain: authentication (client cert / OIDC / SA token) → authorization (RBAC) → mutating admission webhooks → schema validation → validating admission webhooks.
  2. Persist to etcd. The Deployment object is serialized (protobuf internally) and written to etcd under a key like /registry/deployments/<ns>/<name>. etcd replicates via Raft — the write only returns after a quorum of members has it in their log (fsync to WAL).
  3. Deployment controller reconciles. It watches Deployments via a long-lived watch (HTTP/2 stream backed by etcd's watch). Seeing a new Deployment, it creates a ReplicaSet with a pod-template hash label.
  4. ReplicaSet controller reconciles. It sees a ReplicaSet wanting 3 replicas but 0 existing, so it creates 3 Pod objects with nodeName empty (unscheduled).
  5. Scheduler binds. The scheduler watches for Pods with empty .spec.nodeName. For each it runs the filter phase (predicates: resource fit, node selectors, taints/tolerations, affinity) then the score phase (spread, least/most-allocated) and issues a Binding (a write of .spec.nodeName back to the apiserver).
  6. kubelet starts the pod. The kubelet on the chosen node watches Pods bound to it. It calls the CRI runtime: pull image → create the pod sandbox (pause container holding the network namespace) → invoke the CNI plugin to allocate an IP and wire veth/routes → start init containers → start app containers. Volumes are attached/mounted first via CSI.
  7. Probes & status. kubelet runs startup → readiness → liveness probes and PATCHes Pod .status back to the apiserver.
  8. Endpoints wire up. The EndpointSlice controller sees a Ready pod matching a Service selector and adds its IP to an EndpointSlice. kube-proxy on every node watches EndpointSlices and rewrites iptables/IPVS rules so the Service ClusterIP now DNATs to the new pod IP.
Watch out: Only the apiserver writes to etcd. If someone tells you "the scheduler writes the binding to etcd," correct it — the scheduler POSTs a Binding to the apiserver, which persists it. This single-writer design is why the apiserver is the scaling bottleneck, not etcd directly.

The reconciliation loop, concretely

for {
  desired := informer.Get(key)        // from watch cache, not etcd directly
  actual  := listActualChildren(key)
  diff    := desired - actual
  if diff &gt; 0 { create(diff) }         // level-triggered: act on state, not events
  if diff &lt; 0 { delete(-diff) }
  // errors -&gt; requeue with rate-limited exponential backoff
}

Why was this built?

Before Kubernetes (2014, from Google's internal Borg), operators ran containers/VMs with hand-rolled tooling:

  • Manual placement: "server-27 runs the payment service" in a spreadsheet. A node dying meant a pager and a human re-placing workloads.
  • Config management sprawl: Puppet/Chef/Ansible describing how to converge each box imperatively, fragile and order-dependent.
  • Bespoke autoscaling and LB: custom scripts poking HAProxy configs and cloud APIs.
  • Docker alone had no orchestration: docker run on one host; no rescheduling, no service discovery, no rollout strategy.

Kubernetes generalized Borg's lesson: express intent declaratively, let control loops maintain it, and treat machines as fungible cattle. It made self-healing, rolling updates, and horizontal scaling first-class primitives instead of runbooks.

Advantages

  • Self-healing: crashed pods restart, dead-node pods reschedule, all via reconciliation — no human in the loop.
  • Declarative + GitOps-friendly: the entire cluster is data; Argo CD/Flux diff Git against live state.
  • Portable API: the same manifests run on EKS, GKE, AKS, on-prem.
  • Bin-packing: the scheduler packs pods by requests, raising node utilization vs one-service-per-VM.
  • Extensible: CRDs + custom controllers/operators extend the API without forking core.
  • Batteries included: service discovery, rollouts, secrets, RBAC, autoscaling, storage abstraction all in one API.

Drawbacks

  • Operational complexity: etcd tuning, upgrades, CNI/CSI choices, cert rotation — a real ops burden (managed control planes mitigate but don't erase it).
  • Steep learning curve: hundreds of API objects; failure modes (CrashLoopBackOff, Pending, Evicted) require deep knowledge.
  • Networking is hard: overlay vs native routing, MTU issues, DNS latency, NetworkPolicy debugging.
  • etcd is a hard scaling ceiling: ~8GB practical DB size, watch/write pressure, and it must stay low-latency.
  • Not for stateful-heavy from day one: databases need careful StatefulSet + storage + backup design; many teams keep DBs off-cluster.
  • Cost: control plane + idle headroom + observability overhead.

Trade-offs

  • Consistency vs availability (etcd): etcd is CP (Raft). If it loses quorum, writes stop — the control plane freezes, but running pods keep serving (kubelet/kube-proxy run off local state). K8s deliberately chooses consistency of desired state over control-plane availability.
  • Requests vs limits: setting limits==requests gives Guaranteed QoS and predictable latency but wastes headroom; overcommitting (limits > requests) raises density but risks OOMKills and CPU throttling.
  • Rollout speed vs safety: high maxSurge/maxUnavailable deploys fast but risks capacity dips; low values are safe but slow.
  • Level-triggered latency: reconciliation is robust to lost events but adds latency vs edge-triggered; resync periods trade freshness for apiserver load.
  • Pod density vs blast radius: big nodes bin-pack better but a node failure/drain hits more pods; PodDisruptionBudgets + topology spread bound this.

When NOT to use it

Watch out — anti-use-cases:
  • 1–3 simple services, one cloud, small team: Cloud Run / ECS Fargate / a couple of VMs is cheaper and far less ops.
  • Pure event-driven spiky workloads: Lambda/serverless beats an always-on cluster.
  • A single big stateful DB: use the managed offering (RDS/Cloud SQL); don't run your primary OLTP DB in K8s unless you have a strong operator + SRE team.
  • Hard real-time / ultra-low-latency kernel-bypass workloads: the network/scheduling overhead fights you; bare metal + tuning wins.
  • No platform/ops capacity: without someone owning upgrades, etcd, and CNI, a self-managed cluster becomes an incident generator.

Production Architecture

A realistic HA topology: 3 (or 5) control-plane nodes for etcd quorum, worker node pools spread across AZs, a cloud load balancer fronting the apiservers, an Ingress controller for L7, and CNI/CSI plugins on every node.

Key points to narrate:

  • etcd quorum: 3 members tolerate 1 failure, 5 tolerate 2. Never run 2 or 4 (even numbers give no extra fault tolerance and worsen write latency). Put etcd on fast disks (NVMe); wal_fsync latency is the killer metric.
  • apiserver is stateless and sits behind the LB — scale horizontally; all state lives in etcd.
  • Node pools by AZ + topology spread constraints so a zone loss doesn't take a whole service down.
  • Ingress (nginx/Contour/Gateway API) terminates TLS and does host/path routing to Services.

Production Problems

  • etcd disk latency / fragmentation: slow fsync spikes apiserver p99, causes leader elections and cascading timeouts. Needs regular etcdctl defrag and compaction.
  • CrashLoopBackOff storms: a bad deploy where the app exits on start; exponential backoff (10s→20s→...→300s cap) makes recovery slow even after a fix.
  • OOMKilled pods: memory limit too low or a leak; kernel OOM killer (cgroup) kills the container, exit code 137.
  • PVC stuck Pending: WaitForFirstConsumer means the PV binds only after scheduling; a StorageClass mismatch or zone constraint leaves it hung.
  • DNS latency/failures: CoreDNS overloaded or the old musl/ndots:5 5-lookup problem inflates latency; NodeLocal DNSCache fixes it.
  • IP exhaustion: pod CIDR too small for the node count; new pods stuck ContainerCreating with CNI "no IP available".
  • Node NotReady / disk pressure evictions: kubelet evicts pods under memory/disk pressure; batch evictions cause request drops if PDBs are missing.
  • Rollout deadlock: new ReplicaSet pods never go Ready (bad readiness probe/config), Deployment stuck progressDeadlineExceeded.

Debugging Guide

# What's wrong and why (events at the bottom are gold)
kubectl describe pod &lt;pod&gt; -n &lt;ns&gt;
kubectl get events -n &lt;ns&gt; --sort-by=.lastTimestamp

# Logs incl. previous crashed container
kubectl logs &lt;pod&gt; -c &lt;container&gt; --previous

# CrashLoopBackOff: check exit code + reason
kubectl get pod &lt;pod&gt; -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'

# OOMKilled shows reason=OOMKilled, exitCode 137; check limits vs usage
kubectl top pod &lt;pod&gt; -n &lt;ns&gt;

# Pending: why can't it schedule?  (Events: FailedScheduling ...)
kubectl describe pod &lt;pod&gt; | grep -A5 Events

# ImagePullBackOff: registry/auth/tag
kubectl describe pod &lt;pod&gt; | grep -i -E 'pull|image'

# PVC stuck Pending
kubectl get pvc,pv,storageclass
kubectl describe pvc &lt;pvc&gt;

# Service has no endpoints? selector mismatch or no Ready pods
kubectl get endpointslices -l kubernetes.io/service-name=&lt;svc&gt;

# Control-plane / etcd health
kubectl get --raw='/readyz?verbose'
ETCDCTL_API=3 etcdctl endpoint status --write-out=table

# Live debug into a distroless pod
kubectl debug -it &lt;pod&gt; --image=busybox --target=&lt;container&gt;

Scaling

Three orthogonal autoscalers plus manual sharding of the control plane:

  • HPA (Horizontal Pod Autoscaler): scales replica count on CPU/memory or custom/external metrics. Formula: desired = ceil(current * (currentMetric / targetMetric)). Has a stabilization window (default 300s scale-down) to avoid flapping.
  • VPA (Vertical Pod Autoscaler): right-sizes requests/limits; recreates pods to apply. Don't run VPA and HPA on the same CPU metric — they fight.
  • Cluster Autoscaler / Karpenter: adds/removes nodes when pods are Pending for lack of capacity, or consolidates underused nodes. Karpenter provisions right-sized nodes directly from the cloud API, much faster than ASG-based CA.
  • Control-plane scaling: apiserver scales horizontally (stateless); etcd does NOT scale writes by adding members (more members = slower Raft). Scale etcd vertically (CPU/NVMe) and by keeping the DB small (compaction/defrag).

Watch out: HPA can't help if pods can't schedule — you need Cluster Autoscaler/Karpenter behind it, and it can't help if the bottleneck is a downstream DB. Also HPA needs resources.requests set or CPU-target HPA does nothing.

Security

  • AuthN: client certs, OIDC (SSO), or ServiceAccount JWT tokens (now bound, audience-scoped, short-lived projected tokens). No static passwords.
  • AuthZ: RBAC — Role/ClusterRole + RoleBinding/ClusterRoleBinding. Least privilege; never bind ServiceAccounts to cluster-admin.
  • Admission control: Pod Security Admission (restricted/baseline/privileged), OPA Gatekeeper/Kyverno for policy (no privileged, no hostPath, required labels).
  • Secrets: base64 in etcd is NOT encryption — enable EncryptionConfiguration (KMS-backed) so etcd stores ciphertext; use external secret stores (Vault, cloud KMS) for real rotation.
  • Network: default-deny NetworkPolicies (Calico/Cilium) — pods are flat/open by default. Encrypt in transit with mTLS (service mesh: Istio/Linkerd) and TLS at Ingress.
  • Node/workload hardening: drop capabilities, runAsNonRoot, read-only root FS, seccomp profiles, no host network/PID unless required.
  • Common CVE classes: over-privileged ServiceAccount tokens auto-mounted into every pod (set automountServiceAccountToken: false); container escapes via privileged pods/hostPath; exposed kubelet/etcd ports; supply-chain (unsigned images — use Sigstore/cosign + admission verification).

Performance

  • etcd is the latency floor. Every write blocks on Raft quorum + WAL fsync. NVMe (<10ms fsync) vs spinning disk is the difference between a healthy and a flapping control plane.
  • apiserver throughput: tune --max-requests-inflight / --max-mutating-requests-inflight and enable API Priority and Fairness (APF) so a chatty controller can't starve kubelets. Watch cache serves reads without hitting etcd.
  • kube-proxy iptables vs IPVS: iptables rule evaluation is O(n) in Services — a few thousand Services makes rule reload and packet matching slow. IPVS uses hash tables (O(1) lookup) and scales to tens of thousands of Services; Cilium eBPF bypasses kube-proxy entirely.
  • CPU limits cause throttling: CFS quota throttles even when the node has spare CPU, adding tail latency. Many teams drop CPU limits (keep requests) for latency-sensitive services.
  • DNS: ndots:5 triggers up to 5 lookups for external names; use fully-qualified names or NodeLocal DNSCache to cut p99.
  • Scheduler throughput: ~100s of pods/sec; percentage-of-nodes-to-score tuning trades placement quality for speed on big clusters.
  • Image pulls: the slowest part of pod start; use small images, layer caching, and pre-pulled images / imagePullPolicy: IfNotPresent.

Interview Follow-up Questions

  1. What is a Pod and why not schedule containers directly?
    1. Answer pointer: Pod is the scheduling atom — shared network namespace + volumes; sidecars co-locate.
  2. Difference between a Deployment and a ReplicaSet?
    1. Pointer: Deployment manages ReplicaSets to enable rolling updates/rollback; you rarely touch RS directly.
  3. How does a rolling update actually work — what do maxSurge/maxUnavailable control?
    1. Pointer: New RS scales up by maxSurge, old scales down respecting maxUnavailable; gated on readiness.
  4. What guarantees does a StatefulSet give that a Deployment doesn't?
    1. Pointer: Stable network identity (pod-0..n via headless svc), ordered create/delete, per-pod PVC.
  5. Walk me through what happens from kubectl apply to a running container.
    1. Pointer: apiserver→etcd→Deployment ctrl→RS ctrl→scheduler bind→kubelet→CRI→CNI→probes→endpoints.
  6. Why is etcd the source of truth and what consistency model does it use?
    1. Pointer: Raft, quorum writes, linearizable reads; CP system; only apiserver writes to it.
  7. What happens to running workloads if the entire control plane goes down?
    1. Pointer: Existing pods keep running (kubelet/kube-proxy off local state); no new scheduling/healing until it recovers.
  8. How does a Service get traffic to a pod — what does kube-proxy do?
    1. Pointer: ClusterIP virtual IP; kube-proxy programs iptables/IPVS DNAT to EndpointSlice pod IPs.
  9. iptables vs IPVS mode — when does it matter?
    1. Pointer: iptables O(n) rules; IPVS hash O(1) — matters at thousands of Services; eBPF (Cilium) bypasses proxy.
  10. Difference between liveness, readiness, and startup probes?
    1. Pointer: Liveness→restart; readiness→remove from endpoints; startup→gate the other two during boot.
  11. Explain QoS classes and how they affect eviction.
    1. Pointer: Guaranteed (limits==requests) evicted last; Burstable next; BestEffort (no requests) first.
  12. Why would a PVC be stuck Pending?
    1. Pointer: WaitForFirstConsumer + no scheduled pod, no matching StorageClass, zone/access-mode mismatch, no provisioner.
  13. How does the HPA decide replica count, and what breaks it?
    1. Pointer: ratio formula on metric; breaks without requests set, without metrics-server, or when downstream is the bottleneck.
  14. A pod is OOMKilled repeatedly — how do you root-cause vs just raising the limit?
    1. Pointer: Check RSS trend (leak?), heap profile, working set vs limit; raise limit only if legitimately sized.
  15. How do you guarantee availability during a node upgrade/drain?
    1. Pointer: PodDisruptionBudget minAvailable + topology spread + surge; drain respects PDB.
  16. How does the scheduler choose a node — filter vs score?
    1. Pointer: Filter (predicates: fit, taints, affinity), then score (spread, allocation), pick highest, Binding.
  17. How would you debug 5% of requests to a Service failing intermittently?
    1. Pointer: Stale endpoints, one bad pod passing readiness, kube-proxy sync lag, conntrack table full.
  18. etcd is at 7.5GB and apiserver p99 is climbing — what do you do?
    1. Pointer: Compact + defrag, find high-churn resources (events!), raise quota carefully, check disk fsync.
  19. How do you stop a noisy controller from starving kubelet heartbeats on the apiserver?
    1. Pointer: API Priority and Fairness — flow schemas/priority levels isolate and rate-limit.
  20. Design multi-region K8s — what's hard?
    1. Pointer: etcd can't span high-latency regions; use cluster-per-region + global LB + GitOps + data replication.

  • After Services → networking: "How does DNS work (CoreDNS)?", "What's a NetworkPolicy and default behavior?", "Explain CNI and pod-to-pod routing across nodes." Angle: flat pod network, CoreDNS service records, default-allow until you add policies.

  • After Deployments → CI/CD: "How do canary/blue-green work?", "GitOps with Argo/Flux", "how do you roll back?" Angle: progressive delivery, declarative reconciliation of Git.
  • After probes/QoS → reliability: "How do you set SLOs?", "graceful shutdown / preStop / terminationGracePeriod", "PDBs and disruption budgets." Angle: connection draining, SIGTERM handling.

Production Scenarios

Incident 1 — Deploy causes cluster-wide CrashLoopBackOff

SymptomsNew version pods restart every ~30s→300s; error rate spikes; old pods gone.
Investigationkubectl logs --previous shows a DB migration failing on boot; describe shows exit code 1, Back-off restarting.
Root CauseApp runs migration at startup; migration incompatible with running old replicas; container exits.
Solutionkubectl rollout undo deployment/x to previous ReplicaSet; move migrations to a pre-deploy Job/init container with proper gating.
PreventionReadiness-gated rollout, low maxUnavailable, progressDeadlineSeconds, canary + smoke tests, backward-compatible migrations.
Interview Answer"App crashed on boot from a bad migration; backoff made it look stuck. I rolled back to the prior ReplicaSet instantly since K8s keeps it, then decoupled migrations from app start behind a Job."

Incident 2 — Pods stuck Pending after a traffic spike

SymptomsHPA scaled replicas to 40 but half are Pending; latency high, users see 503s.
Investigationdescribe pod → FailedScheduling: 0/12 nodes available: insufficient cpu; Cluster Autoscaler logs show scale-up blocked by quota.
Root CauseCloud account CPU quota / no spare node capacity; CA couldn't add nodes fast enough.
SolutionRaise cloud quota, pre-provision warm nodes (over-provisioning pause pods / Karpenter), lower per-pod requests to fit.
PreventionHeadroom via low-priority placeholder pods, Karpenter for fast provisioning, capacity alerts, load-test peaks.
Interview Answer"HPA did its job but there were no nodes — autoscaling is only as fast as node provisioning. I added warm capacity via low-priority pause pods and switched to Karpenter for sub-minute node launches."

🎯 Deep-dive Q&A — model answers

Why is Kubernetes reconciliation "level-triggered" and not "edge-triggered", and why does it matter?

Edge-triggered systems act on events ("pod deleted"): if you miss the event, you're permanently out of sync. Kubernetes controllers are level-triggered — each loop reads the current desired state and current actual state and computes the diff, regardless of what events fired. Watches are just an optimization to wake the loop quickly; periodic informer resyncs (and the ability to relist) guarantee correctness even if events are lost or the controller restarts. This is why K8s self-heals: a controller that was down for 10 minutes just relists on startup and reconciles reality to spec. The cost is latency and extra apiserver load from relists, which is why resync periods and watch caches are tuned carefully.

Only the apiserver talks to etcd. Why that design, and what's the consequence?

Centralizing etcd access behind the apiserver gives one place for authN/authZ, admission control, validation, versioning/conversion between API versions, and the watch cache. Components never need etcd credentials or to understand storage encoding. The consequence: the apiserver is the scaling chokepoint and single logical writer. It scales horizontally (stateless, all identical), but every mutating write ultimately serializes through etcd's Raft. This also means you protect etcd by protecting the apiserver — API Priority and Fairness, rate limits, and watch caches (reads served from memory) are how you keep a runaway controller from taking etcd down.

Explain QoS classes precisely and how they interact with the OOM killer and eviction.

Three classes derived from requests/limits: Guaranteed (every container has memory and CPU limit == request), Burstable (at least one request set but not equal to limits), BestEffort (no requests/limits). Under node memory pressure the kubelet evicts BestEffort first, then Burstable exceeding requests, and Guaranteed last. Separately, the Linux OOM killer uses oom_score_adj values that K8s sets by QoS: BestEffort pods get the most kill-favorable score, Guaranteed the least. Note the OOM killer is per-cgroup for limit-exceeding containers (exit 137) and can fire even when the node has free memory if a container hits its own memory limit. This is why latency-critical services should be Guaranteed for memory and why "no requests set" is dangerous.

Why can a PVC be stuck Pending with a healthy StorageClass?

The most common reason is volumeBindingMode: WaitForFirstConsumer: the PV is intentionally not provisioned until a pod using the PVC is scheduled, so the volume lands in the same zone as the pod. If the pod itself can't schedule (no capacity, taints, affinity), the PVC stays Pending forever — you must fix scheduling first. Other causes: no CSI provisioner running for that StorageClass, requested access mode unsupported (e.g. RWX on a block device that only does RWO), a zone constraint where no node in the required zone has capacity, or exceeding a storage quota. Debug with kubectl describe pvc (events name the provisioner error) and check the pod's FailedScheduling events in tandem.

Liveness vs readiness vs startup — give a failure mode caused by conflating them.

Readiness controls endpoint membership (fail = removed from Service, no restart). Liveness controls restarts (fail = kill+restart container). Startup gates both during boot. Classic incident: a team sets liveness to hit /health which also checks the database. The DB has a transient blip; every pod fails liveness simultaneously and gets killed, turning a 10-second DB hiccup into a cluster-wide CrashLoopBackOff and a full outage. The fix: liveness should only check "is this process wedged/deadlocked" (cheap, local), readiness checks dependencies (so a DB blip removes pods from rotation but doesn't kill them), and a startupProbe covers slow boot so liveness doesn't fire mid-initialization.

Walk through exactly how kube-proxy in iptables mode routes a ClusterIP request, and why IPVS scales better.

For each Service, kube-proxy writes a chain that matches the ClusterIP:port and uses iptables statistic (random probability) modules to DNAT to one of the backend pod IPs from the EndpointSlices, then conntrack tracks the connection. The problem: iptables is a linear ruleset — adding thousands of Services and endpoints means huge rule tables, O(n) matching per packet, and multi-second rule reloads on every endpoint change, which spikes CPU and delays convergence. IPVS mode uses the kernel's in-kernel hash-table load balancer: O(1) lookup, incremental updates, and multiple LB algorithms (rr, lc, etc.). At thousands of Services IPVS is dramatically faster; eBPF-based dataplanes (Cilium) go further by replacing kube-proxy entirely with eBPF maps and doing DNAT at the socket/XDP layer.

How does a Deployment rolling update actually sequence, and how do maxSurge/maxUnavailable bound it?

The Deployment controller creates a new ReplicaSet (identified by a pod-template hash). It then scales the new RS up and the old RS down in a loop, respecting two constraints computed against desired replicas: maxSurge caps how many pods above desired can exist (extra capacity created first), and maxUnavailable caps how many below desired can be unready at once. With defaults (25%/25%) on 4 replicas it can run up to 5 pods and keep at least 3 available. Crucially, a new pod only counts toward progress when its readiness probe passes, so a bad readiness config stalls the rollout until progressDeadlineSeconds marks it failed. maxSurge=0 means truly zero extra capacity (needs spare headroom pattern), maxUnavailable=0 means never dip below desired (needs surge). You tune these for capacity vs speed vs safety.

What actually differs in a StatefulSet, and when is it wrong to use one?

StatefulSet gives: stable, ordinal pod names (web-0..web-n) backed by a headless Service for stable DNS per pod; ordered, sequential creation and reverse-order deletion (0 before 1, with readiness gating each step by default); and per-pod PersistentVolumeClaims via volumeClaimTemplates that survive rescheduling and reattach to the same pod ordinal. This is essential for clustered stateful systems (Kafka, ZooKeeper, Cassandra, primary/replica DBs) that need stable identity and their own durable disk. It's wrong for stateless web apps — the ordered rollout is slower and the stable-identity machinery buys you nothing. It's also not a magic DB operator: it won't handle backups, failover promotion, or reconfiguration — that's what a dedicated operator (e.g. a Postgres operator) adds on top.

The whole control plane is down for 20 minutes. What still works and what doesn't?

Data plane keeps running: existing pods keep serving because kubelet runs them from its local pod cache and kube-proxy already programmed iptables/IPVS, and CoreDNS pods keep resolving. What stops: no new scheduling, no self-healing (a pod that crashes won't be recreated by controllers, though kubelet still restarts containers within an existing pod per restartPolicy), no rollouts, no scaling, no Service endpoint updates (so if pods churn, stale endpoints linger), and kubectl is dead. This is the CP-over-availability trade-off: K8s would rather stop changing state than risk making inconsistent decisions without etcd quorum. It's why you run 3–5 etcd members across failure domains and treat control-plane HA seriously.

Design autoscaling for a service with sharp 10x meal-time spikes. What are the failure modes?

Layer three things: HPA on a leading metric (CPU or, better, requests-per-second/queue-depth via custom metrics) with a short scale-up stabilization and longer scale-down to avoid flapping; Cluster Autoscaler or Karpenter behind it so Pending pods trigger fast node provisioning; and warm headroom via low-priority "pause" pods that get preempted when real pods need the space, hiding node-launch latency. Failure modes: (1) HPA scales pods but no nodes exist and CA is slow → Pending → 503s (fix with warm capacity/Karpenter); (2) requests not set → CPU-target HPA is a no-op; (3) scaling the app but the DB/connection pool is the real bottleneck → you just move the queue; (4) scale-down too aggressive → thrashing and dropped connections. Always load-test the actual peak and pre-scale on a schedule if spikes are predictable (cron-based HPA).

etcd DB hit 7.8GB and the control plane is degrading. Precise remediation?

etcd keeps a multi-version history; without compaction the DB grows and every write's B-tree/fsync gets slower, and there's a ~8GB hard-ish quota after which etcd goes read-only (NOSPACE alarm). Steps: (1) trigger compaction to drop old revisions (etcdctl compact <rev> or auto-compaction), (2) etcdctl defrag each member to reclaim freed space on disk (do it one member at a time — defrag blocks that member), (3) disarm the NOSPACE alarm after, (4) find the churn source — usually Events (give them a short TTL or a separate etcd), or a controller hot-looping writes, (5) verify disk is NVMe and fsync p99 <10ms. Long term: alert on DB size at ~6GB, enable auto-compaction (e.g. periodic/revision), run a dedicated etcd for events, and use APF to throttle chatty clients.

How do taints/tolerations, node affinity, and topology spread differ — and when do you use each?

Taints/tolerations are repulsion from the node side: a tainted node repels all pods except those that tolerate it (e.g. dedicate GPU nodes, or the control-plane taint). Node affinity/nodeSelector is attraction from the pod side: "schedule me on nodes with label disktype=ssd" (required or preferred). Pod affinity/anti-affinity place pods relative to other pods (co-locate with cache, or spread away from same-app pods). topologySpreadConstraints evenly distribute pods across a topology domain (zones/nodes) with a maxSkew, which is the modern, cheaper way to get AZ balance than anti-affinity. Rule of thumb: taints to reserve nodes, affinity to require capabilities, topology spread for availability distribution. They compose in the scheduler's filter/score phases.

Base64 Secrets aren't encryption. How do you actually secure secrets at rest and in use?

By default Secrets are stored in etcd base64-encoded (trivially reversible) and mounted into pods. To secure at rest: enable an EncryptionConfiguration on the apiserver with a KMS provider so etcd stores AEAD-encrypted values, keyed by a cloud KMS/HSM (envelope encryption), and rotate the KEK. For rotation and least exposure, use an external secret manager (Vault, AWS/GCP secret manager) via the CSI Secrets Store driver or External Secrets Operator so secrets are pulled just-in-time and rotated centrally rather than living statically in etcd. In use: set automountServiceAccountToken: false where not needed, restrict who can get secrets via RBAC (reading a Secret is often equivalent to owning the credential), avoid dumping secrets into env vars/logs, and use short-lived bound ServiceAccount tokens instead of long-lived ones.

Explain the endpoint-removal race during pod shutdown and the correct graceful-shutdown pattern.

When a pod is deleted, two things happen concurrently and asynchronously: (1) the endpoint controllers remove its IP from EndpointSlices and kube-proxy reprograms iptables — but this propagates across all nodes with some delay; (2) the kubelet sends SIGTERM to the container. If the app exits immediately on SIGTERM, it stops accepting connections while some nodes still route to it → connection refused/resets. The fix: add a preStop hook (e.g. sleep 5–10) so the container keeps serving during the deregistration window, handle SIGTERM by first flipping readiness to false and draining in-flight requests before exiting, and set terminationGracePeriodSeconds longer than your max request time. Order matters: fail readiness → wait for deregistration → stop accepting new → drain → exit.

How does CNI actually give a pod an IP, and what causes "no IP available" ContainerCreating hangs?

When kubelet creates the pod sandbox (the pause container that owns the network namespace), it invokes the CNI plugin binary with ADD. The plugin (Calico, Cilium, flannel, or a cloud CNI like AWS VPC CNI) allocates an IP from the pod CIDR/IPAM pool, creates a veth pair linking the pod netns to the host, and programs routes so the IP is reachable cluster-wide (overlay via VXLAN/IPIP, or native routing/BGP). "No IP available" happens when the IPAM pool is exhausted: e.g. AWS VPC CNI assigns real VPC IPs limited by ENI/instance type, or a per-node pod CIDR (/24 = 254 IPs) is too small for --max-pods. Symptoms are pods stuck ContainerCreating with CNI errors in kubelet logs. Fixes: larger CIDRs, prefix delegation (AWS), fewer pods per node, or a different IPAM mode.

Multi-region Kubernetes: why can't one cluster span regions, and what's the right pattern?

etcd is the blocker: Raft requires a quorum write on every mutation, and cross-region RTT (tens of ms) added to every write cripples control-plane latency and destabilizes leader elections. etcd is designed for LAN/single-region (or multi-AZ within a region, ~1-2ms). So you don't stretch a cluster across regions. The pattern is cluster-per-region (or per-AZ-group): each region has its own independent control plane and etcd, workloads deployed identically via GitOps (Argo/Flux) from one repo, a global load balancer (GeoDNS/anycast) routing users to the nearest healthy region, and data replicated at the datastore layer (not by K8s) — e.g. multi-region DB, async replication, or CRDTs. Tools like Cluster API, Fleet, or Karmada help manage many clusters. The trade-off is you now own cross-cluster consistency yourself, which is exactly where the real distributed-systems work lives.
