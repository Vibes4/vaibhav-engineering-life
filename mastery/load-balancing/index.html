Load Balancing & Proxies Mastery

A load balancer is a traffic director that spreads connections or requests across a fleet so no single box melts and dead boxes stop getting traffic. This page pushes past "round-robin across servers" into L4 vs L7 internals, Maglev consistent hashing, power-of-two-choices, health-check-induced cascades, retry storms, connection draining, and the proxy taxonomy (forward / reverse / gateway / sidecar) that Staff interviewers keep drilling.

Interview Explanation — 30 seconds

Say this: "A load balancer distributes incoming traffic across a pool of backends to maximize throughput, minimize latency, and survive individual failures. There are two layers: L4 balances at the transport level — it forwards TCP/UDP by IP:port, is protocol-agnostic and blazing fast, but can't see HTTP. L7 terminates the connection, parses HTTP, and routes by host, path, or header, does TLS termination, retries and sticky sessions — richer but more CPU and latency. It picks a backend with an algorithm (round-robin, least-connections, consistent hashing, power-of-two-choices), removes unhealthy nodes via active or passive health checks, and drains connections gracefully on deploy so no in-flight request is killed."

Interview Explanation — 2 minutes

The fuller answer names the internals an interviewer is fishing for:

  • Layer split: L4 operates on TCP/UDP — it sees only the 5-tuple (src IP, src port, dst IP, dst port, protocol). It forwards packets via NAT (rewrite dst IP, both directions flow through the LB) or DSR/direct-server-return (LB rewrites only the inbound path; backend replies directly to the client, so the LB never sees the response — huge for asymmetric traffic like video). L7 terminates TCP, reads the HTTP request line and headers, and can route by Host, path prefix, method, cookie, or JWT claim; it owns TLS, HTTP/2 multiplexing, retries, rewrites, and buffering.
  • Algorithms: round-robin and weighted RR (weight by CPU/capacity), least-connections and least-response-time (EWMA of latency), IP-hash / consistent hashing (for cache affinity and stateful routing, minimizes remap on scale change), and power-of-two-choices — pick two random backends, send to the less loaded — which gets near-optimal load spread without the herding problem of global least-connections.
  • Health checks: active probes (HTTP /healthz or TCP connect on an interval, with unhealthy/healthy thresholds and slow-start on recovery) plus passive outlier detection (eject a host after N consecutive 5xx or timeouts on real traffic).
  • Resiliency toolkit: retry budgets (cap retries at e.g. 20% of requests so a retry storm can't 3x load), jittered exponential backoff, circuit breaking, outlier ejection, deadline/timeout propagation, and load shedding under overload.
  • Global vs local: GSLB / anycast / Global Accelerator route users to the nearest healthy region (DNS or BGP anycast); a local LB spreads within a datacenter. Google's Maglev is a software L4 LB that uses consistent hashing plus ECMP from routers and connection tracking to survive re-hashing.
  • Proxy taxonomy: forward proxy (client-side egress), reverse proxy (server-side, the LB itself), API gateway (reverse proxy + auth + rate limit + routing), and sidecar (Envoy per-pod, the service-mesh data plane).

Internal Working

Trace one request through an L7 reverse proxy (Envoy/NGINX style):

  1. Accept: the listener socket accepts a connection off the kernel accept queue (sized by somaxconn + the app's backlog). The FD count is bounded by ulimit -n; a busy LB needs 100k+ FDs.
  2. TLS handshake (if terminating): ClientHello → certificate → key exchange. Session tickets / session IDs let repeat clients resume without a full handshake. This is the CPU hot spot — ECDSA certs are ~5-10x cheaper than RSA-2048 to sign.
  3. Parse: read the request line and headers into a structured request. For HTTP/2 the LB demultiplexes streams over one connection; for HTTP/1.1 it uses keepalive to reuse connections.
  4. Route match: match against a route table — virtual host by Host header + SNI, then longest-prefix or regex path match, then header/weight predicates. This produces a cluster (upstream pool).
  5. Endpoint selection: run the load-balancing policy over healthy endpoints in the cluster — round-robin cursor, least-request via P2C, or ring-hash / Maglev table for consistent hashing. Ejected outliers are skipped.
  6. Connection pooling: grab an idle upstream connection from the per-endpoint pool or open a new one (respecting max_connections, max_pending_requests circuit-breaker limits).
  7. Forward + timeouts: proxy the request with a per-try timeout and an overall route timeout; the remaining deadline is propagated downstream (e.g. gRPC grpc-timeout header).
  8. Response handling: on 5xx/timeout/connect-failure, consult the retry policy + retry budget; otherwise stream the response back (DSR skips this for L4). Update passive-health counters and EWMA latency.
  9. Draining on shutdown: on deploy, the endpoint is marked draining — new requests stop, in-flight ones finish, then the connection closes after drain-timeout.
Say this: "The load balancer is a state machine over a route table and an endpoint pool. Health checks decide the pool membership; the algorithm decides which member; circuit breakers and retry budgets decide whether to even try."

Consistent hashing — the K/N remap problem

Naive hash(key) % N remaps almost every key when N changes (add one node, ~all keys move). Consistent hashing places nodes and keys on a hash ring; adding/removing a node only remaps ~1/N of keys. Virtual nodes (each physical node gets ~100-200 ring positions) smooth out the otherwise lumpy distribution. Maglev builds a fixed lookup table (size ~65537, a prime) via a permutation algorithm so lookups are O(1) and disruption on node change is minimal.

Why was this built?

Before load balancers, you scaled vertically — one bigger server — until you hit a ceiling and a single point of failure. Early horizontal attempts used DNS round-robin: return multiple A records and let clients pick. It "works" but has no health awareness (dead IPs still returned), caching means TTLs pin clients to a box for minutes, and there's zero connection-level balancing. Then came hardware appliances (F5 BIG-IP, Citrix NetScaler) — expensive, vertically scaled boxes doing L4/L7 in ASICs. The cloud era pushed load balancing into software (HAProxy, NGINX, Envoy) and into the network fabric (Google Maglev, AWS NLB/ALB) so it scales horizontally with ECMP and commodity servers instead of a $50k appliance.

Advantages

  • Horizontal scale + HA: add backends without client changes; dead backends removed automatically.
  • Zero-downtime deploys: connection draining + rolling restarts behind a stable VIP.
  • TLS offload: terminate once at the edge; backends speak cheap HTTP internally (or re-encrypt for zero-trust).
  • Traffic control: canary weights, blue-green, header-based routing, rate limiting, WAF at L7.
  • Observability choke point: centralized metrics, access logs, and tracing headers injected in one place.

Drawbacks

  • Single point of failure if not itself redundant — you now need to make the LB HA (active-active, ECMP, floating VIP).
  • Extra hop + latency — L7 adds parse/buffer/TLS cost (often 1-5 ms; TLS handshake tens of ms cold).
  • State/affinity headaches — sticky sessions break clean stateless scaling and rebalancing.
  • Failure amplifier — a bad health check or retry policy can turn a small blip into a fleet-wide cascade.
  • Config complexity — route tables, timeouts, circuit breakers, and cert rotation are their own operational surface.

When NOT to use it

Watch out: Don't reach for a heavy L7 LB when:
  • You have a single backend or trivial traffic — you've added a SPOF and a hop for nothing.
  • You need true end-to-end encryption with no middlebox seeing plaintext — use L4 passthrough, not L7 termination.
  • Latency budget is microseconds (HFT, some RPC) — an L7 proxy hop can blow the budget; use client-side LB or L4/DSR.
  • You're balancing long-lived stateful connections that must pin to one node (WebSocket to in-memory game state) without external state — stickiness will bite you on rebalance/deploy.
  • Traffic is naturally partitioned by key and clients can route themselves (consistent-hash client-side) — an intermediary just adds a hop.

Production Architecture

A typical multi-tier production topology: BGP anycast / GSLB steers users to the nearest region; an L4 layer (ECMP + Maglev-style) fans packets to a fleet of L7 proxies that terminate TLS and route by path to service clusters, each fronted by health-checked endpoints. Envoy sidecars handle service-to-service inside the mesh.

flowchart TD
  U["Users worldwide"] --> DNS["GSLB or Anycast VIP"]
  DNS --> L4["L4 fleet ECMP plus Maglev"]
  L4 --> P1["L7 proxy A"]
  L4 --> P2["L7 proxy B"]
  P1 --> SVC["Service cluster"]
  P2 --> SVC
  SVC --> S1["Backend 1 healthy"]
  SVC --> S2["Backend 2 healthy"]
  SVC --> S3["Backend 3 draining"]
  HC["Health checker"] -.probe.-> S1
  HC -.probe.-> S2
  HC -.eject.-> S3

The L4 tier is stateless and scales by adding hosts behind the same anycast VIP — routers ECMP-hash the 5-tuple across them. Maglev's connection tracking keeps existing flows pinned to the same L7 proxy even when the L4 set changes, avoiding mid-connection resets. The L7 tier owns TLS certs, route tables, and circuit breakers; it's where canary weights and WAF rules live.

Production Problems

  • Retry storms / metastable failure: a latency blip causes clients to retry, retries triple load, backends slow further, more retries — the system stays collapsed even after the original trigger is gone. Fix: retry budgets + circuit breakers + jitter.
  • Health-check induced cascade: too-aggressive checks eject a slow-but-alive node, dumping its load on peers, which then trip the same threshold — the whole fleet ejects itself. Fix: eject a bounded percentage (outlier max_ejection_percent), panic mode.
  • Thundering herd on failover: a region fails, all its traffic lands on the standby at once; cold caches + cold connection pools + JIT warmup overwhelm it.
  • Sticky-session hot spots: one whale tenant's session pins to one backend and saturates it while peers idle.
  • Connection pool exhaustion: LB→backend keepalive pool caps at max_connections; a slow backend fills the pool and requests queue in max_pending_requests then fail fast.
  • TLS CPU saturation: handshake storms (no session resumption) peg cores; p99 spikes.

Scaling

The LB tier itself scales horizontally: put multiple L4 nodes behind one anycast VIP and let routers ECMP-hash flows across them; add L7 proxies behind the L4 tier. The bottleneck moves from a single box to the aggregate NIC/PPS and the crypto cores. Autoscale L7 proxies on connection count + CPU; keep L4 stateless so scaling it never resets flows (with connection tracking).

flowchart LR
  R["Edge routers"] -->|ECMP hash 5-tuple| M1["Maglev node 1"]
  R --> M2["Maglev node 2"]
  R --> M3["Maglev node 3"]
  M1 -->|consistent hash| B["Backend pool"]
  M2 --> B
  M3 --> B
  B --> A["Autoscaler adds pods on CPU and rq load"]
  • Scale-out knobs: more proxy replicas, more crypto cores (offload TLS to AES-NI/QAT), bigger connection pools.
  • Vertical: raise somaxconn, nofile (FD limit), net.ipv4.ip_local_port_range (ephemeral ports for upstream conns), tune tcp_tw_reuse.
  • Warmup: slow-start ramps traffic to newly healthy nodes over a window so cold caches/JIT don't get slammed.

Security

  • TLS termination is a trust boundary: plaintext exists inside the LB — restrict who can read logs/heap; re-encrypt to backends (mTLS) for zero-trust.
  • DDoS / SYN floods: anycast to absorb, SYN cookies (net.ipv4.tcp_syncookies), connection rate limits, and a WAF at L7.
  • Header spoofing: the LB must overwrite (not append) X-Forwarded-For/X-Real-IP from untrusted clients, else attackers forge source IPs.
  • Request smuggling: mismatched Content-Length vs Transfer-Encoding parsing between LB and backend — normalize and reject ambiguous framing.
  • Cert management: automate rotation (ACME), disable weak ciphers/TLS 1.0/1.1, enforce OCSP stapling.
  • Sticky-session cookies must be signed/encrypted so a client can't rewrite them to target a specific backend.

Performance

  • L7 proxy overhead: typically adds ~0.5-3 ms per hop for parse + route + buffer; keep it out of ultra-low-latency paths.
  • TLS handshake: full handshake ~1 RTT (TLS 1.3) plus signing cost; resumption/0-RTT avoids the round trip. RSA-2048 sign is the CPU hog — ECDSA P-256 is ~5-10x cheaper; use AES-NI for bulk.
  • Connection reuse: upstream keepalive + HTTP/2 multiplexing cut connection setup cost dramatically; without it you burn ephemeral ports and hit ip_local_port_range (~28k default) limits.
  • Buffering: L7 buffering (NGINX proxy_buffering on) protects slow-client-slow-backend but adds memory + latency; disable for streaming.
  • Kernel limits to tune: somaxconn (accept queue, raise to 65535), tcp_max_syn_backlog, nofile (1M+), tcp_tw_reuse for high TIME_WAIT churn.
  • Throughput: a single Maglev/NLB node moves millions of PPS via DSR; an L7 proxy is limited by crypto + syscall overhead — tens to low-hundreds of k RPS per core class.

Common Mistakes

  • Retries without a budget → retry storm. Fix: cap retries (e.g. Envoy retry budget 20%), add jitter, retry only idempotent + retriable statuses.
  • Health check hits / or a DB-heavy path → a slow dependency fails the check and ejects healthy app instances. Fix: shallow /healthz (liveness) vs deep /readyz.
  • No connection draining → deploys kill in-flight requests (client 502s). Fix: drain + preStop hook + graceful shutdown.
  • Sticky sessions as the primary scaling model → hot spots + broken rebalance. Fix: externalize session state (Redis).
  • Ejecting too many hosts → cascade. Fix: max_ejection_percent + panic mode (route to all if too few healthy).
  • Timeouts not propagated → LB waits full timeout on a request the client already abandoned. Fix: deadline propagation.
  • somaxconn/backlog too small → silent SYN drops under burst. Fix: raise both kernel and app backlog together.
  • Same timeout at every layer → inner retries stack past outer timeout. Fix: shrinking timeout budget per layer.

Interview Follow-up Questions

  1. What's the difference between L4 and L7 load balancing?
    1. L4 = transport, 5-tuple, protocol-agnostic, fast, no HTTP; L7 = HTTP-aware, routes by host/path/header, TLS, retries.
  2. How does DSR differ from NAT?
    1. NAT: both directions through LB; DSR: backend replies directly to client, LB only on ingress — great for asymmetric egress.
  3. Why is hash % N bad and what fixes it?
    1. Remaps ~all keys on N change; consistent hashing + virtual nodes remaps only ~1/N.
  4. Why is power-of-two-choices better than pure least-connections at scale?
    1. Global least-conn needs shared state and causes herding onto one "least" node; P2C picks 2 random + lesser — near-optimal, no herding, no global state.
  5. Active vs passive health checks?
    1. Active = synthetic probe on interval; passive = outlier detection on real traffic (eject after N 5xx/timeouts).
  6. What is a retry storm and how do you prevent it?
    1. Retries amplify load during a blip → metastable collapse; prevent with retry budgets, jitter, circuit breakers.
  7. What is metastable failure?
    1. System stays collapsed even after trigger removed because a sustaining feedback loop (retries) persists; needs load shedding to break.
  8. How does connection draining work on deploy?
    1. Mark endpoint draining → no new requests → let in-flight finish → close after drain-timeout.
  9. How do health checks cause cascades?
    1. Ejecting a slow node dumps load on peers that then trip too; bound with max_ejection_percent + panic mode.
  10. Sticky sessions — mechanism and downside?
    1. Cookie or source-IP affinity; downside = hot spots, broken rebalance, deploy pain. Externalize state instead.
  11. TLS termination vs passthrough vs re-encryption?
    1. Terminate = LB decrypts (observability, cheap backends); passthrough = E2E, LB blind; re-encrypt = decrypt+re-encrypt for zero-trust.
  12. What is slow-start on recovery?
    1. Ramp traffic to a newly healthy node over a window so cold caches/pools don't get slammed.
  13. How does GSLB/anycast pick a region?
    1. DNS-based geo/latency steering, or BGP anycast where routers route the shared IP to nearest site.
  14. What's deadline propagation and why does it matter?
    1. Pass remaining time budget downstream so no hop works on an abandoned request; prevents wasted work + stacked timeouts.
  15. How does Maglev survive re-hashing when nodes change?
    1. Consistent-hash lookup table + connection tracking pins existing flows to the same backend despite table changes.
  16. Forward proxy vs reverse proxy vs API gateway vs sidecar?
    1. Forward = client egress; reverse = server-side entry; gateway = reverse + auth/rate-limit/routing; sidecar = per-pod Envoy in a mesh.
  17. How do you make the LB itself HA?
    1. Active-active behind anycast VIP + ECMP, or floating VIP with VRRP/keepalived failover.
  18. What kernel knobs matter under high connection load?
    1. somaxconn, tcp_max_syn_backlog, nofile (FDs), ip_local_port_range, tcp_tw_reuse.
  19. How do you canary with a load balancer?
    1. Weighted routing (e.g. 1% to new cluster) or header-based routing; watch error/latency, then ramp.
  20. Why can't L4 do TLS termination or path routing?
    1. It never parses the application payload — it forwards packets by 5-tuple; TLS/HTTP live above L4.

🎯 Deep-dive Q&A — model answers

Walk me through exactly what NAT vs DSR rewrite at L4.

In NAT mode the LB rewrites the destination IP (and often source, SNAT) on the inbound packet so the backend sees the LB or client; the return packet must traverse the LB again to reverse the translation, so the LB is on both legs. In DSR (direct server return), the LB leaves the destination IP as the VIP and forwards the frame to the backend (e.g. via MAC rewrite or IP-in-IP/GRE tunnel); the backend is configured with the VIP on a loopback and replies directly to the client, source-IP = VIP. The LB never sees the response. DSR wins for asymmetric, high-egress workloads (video, downloads) because the response bytes bypass the LB entirely, but it can't do L7 things and needs backend loopback config + ARP suppression.

Why does power-of-two-choices beat both random and global least-connections?

Pure random gives O(log n / log log n) max load imbalance — some node gets unlucky and piles up. Global least-connections needs a synchronized view of every node's load; at scale that view is stale and multiple balancers all pick the same "least" node simultaneously (herding), overshooting it. P2C samples two nodes at random and sends to the lesser of the two — this exponentially improves the max-load bound to O(log log n) with no global coordination and no herding, because the two-sample comparison self-corrects locally. Envoy's default LEAST_REQUEST is P2C for exactly this reason.

Design a retry policy that can't cause a storm.

Retry only idempotent methods and retriable outcomes (connect-failure, 503 with Retry-After, gateway timeout — never a 400/409/business error). Cap attempts (1 retry, maybe 2). Enforce a retry budget: total retries ≤ X% (e.g. 20%) of active requests over a window — once exceeded, retries are disabled, converting a storm into fail-fast. Add full jitter to backoff so retries don't synchronize. Propagate the deadline so a retry that can't finish in the remaining budget is never issued. Pair with a circuit breaker so a persistently failing upstream is skipped entirely.

How does Maglev keep a flow on the same backend when the LB set changes?

Two layers. Routers ECMP-hash the 5-tuple across Maglev nodes — if a Maglev node dies, ECMP re-hashes and some flows land on a different Maglev node. That new node might select a different backend, which would reset the connection. Maglev solves this with (a) a consistent-hash lookup table built by a permutation algorithm so the same 5-tuple maps to the same backend on any node that shares the same backend set, and (b) per-flow connection tracking so an established flow sticks to its chosen backend even if the table changes. The combination means backend or Maglev churn disrupts only a small fraction of flows.

You have to route by JWT tenant claim to a per-tenant shard. L4 or L7, and how?

Must be L7 — the claim is inside the TLS-encrypted HTTP body/header, invisible to L4. Terminate TLS at the proxy, parse the Authorization bearer token, extract the tenant claim, and use it as the hash key into a consistent-hash ring (ring-hash / Maglev LB policy in Envoy) whose members are the shard backends. Consistent hashing keeps a tenant pinned to its shard and remaps only ~1/N tenants when shards change. Validate the JWT signature at the edge so a client can't forge the routing key, and cache the decode to avoid per-request crypto cost.

What's the difference between liveness and readiness, and why does the LB care?

Liveness answers "is this process wedged and should it be restarted?" — it must be shallow and dependency-free, or a slow DB triggers pointless restarts. Readiness answers "should this instance receive traffic right now?" — it can gate on warm caches, open pools, or migration completion. The LB routes only to ready endpoints. Conflating them is the classic cascade: a deep health check that touches a shared dependency fails on every instance at once, the LB ejects the entire fleet, and you get a total outage from a partial dependency slowdown. Keep them separate and cap ejection percentage.

Explain metastable failure and how load shedding escapes it.

A metastable failure is a stable-bad equilibrium: some trigger (latency blip, cache flush) pushes the system into overload, and a sustaining effect — usually retries or queue buildup — keeps it overloaded even after the trigger is gone. Goodput drops while offered load stays high. You can't wait it out because the feedback loop is self-reinforcing. Load shedding breaks it: reject a fraction of requests fast (429/503) so backends get below the saturation threshold, drain queues, and recover; then you ramp load back. The key insight is that reducing accepted load increases successful throughput while collapsed — counterintuitive but necessary.

How do you do zero-downtime deploys behind an LB, precisely?

Rolling: for each instance — (1) flip readiness to NotReady so the LB stops sending new requests; (2) wait for the discovery/EDS change to propagate (a preStop sleep of a few seconds, because removal isn't instantaneous); (3) stop accepting new connections but let in-flight requests complete (graceful shutdown handler on SIGTERM); (4) close idle keepalive connections with a GOAWAY/Connection: close; (5) exit before terminationGracePeriodSeconds. The grace period must exceed drain time or the orchestrator SIGKILLs mid-request. Combine with maxSurge/maxUnavailable so capacity never dips below demand.

Consistent hashing distributes unevenly — why, and what's the fix?

With few nodes placed once on the ring, the arc each node owns varies wildly — one node might own 40% of the ring by luck, creating a hot spot. The fix is virtual nodes (replicas): each physical node is hashed to ~100-200 ring positions, so the law of large numbers smooths ownership to near-1/N with low variance. Maglev takes a different route — it builds a fixed-size table (a prime like 65537) by interleaving each backend's preference permutation, guaranteeing near-perfect balance and O(1) lookup while keeping disruption minimal on membership change. Trade-off: more vnodes = smoother but more memory and slower ring rebuild.

When would you choose TLS passthrough over termination?

Passthrough (L4, SNI-based routing without decrypting) when: end-to-end encryption is a hard requirement and no middlebox may see plaintext (regulatory, or the backend does client-cert mTLS the LB can't proxy); when you want the LB to stay dumb and cheap; or when the backend must terminate TLS itself for protocol reasons. You lose L7 routing, retries, and observability of the payload — you can still route on the SNI hostname from the ClientHello, which is cleartext. If you need both E2E crypto and L7 features, use re-encryption: terminate, inspect, then open a fresh TLS connection to the backend (double crypto cost, but zero-trust internal + full L7).

How does deadline propagation prevent wasted work?

The client sets an overall deadline (say 2s). Each hop passes the remaining budget downstream (gRPC does this natively via the grpc-timeout header; you can carry it in a custom header for HTTP). A downstream service that receives 50ms remaining knows not to start a 500ms query — it fails fast instead of doing work whose result will be discarded when the client has already timed out. Without propagation, every layer uses its own fixed timeout, so an abandoned request keeps consuming DB connections and CPU up and down the tree — a major amplifier during overload. It also stops nested retries from exceeding the outer deadline.

Your L7 proxy is CPU-bound. What's eating it and how do you fix it?

Usually TLS. Profile: if it's asymmetric crypto (handshakes), the fix is session resumption (tickets/IDs) and 0-RTT to avoid full handshakes, plus switching RSA-2048 certs to ECDSA P-256 (5-10x cheaper signatures). If it's bulk symmetric crypto, ensure AES-NI is used (or offload to QAT). Beyond TLS: HTTP/1.1 without keepalive burns connection setup — enable pooling and HTTP/2. Excessive header manipulation, large access-log formatting, and per-request Lua/WASM filters also cost. Scale out proxy replicas since the tier is stateless, and pin to cores / disable HT contention for crypto workloads.

Difference between an API gateway and a plain reverse proxy?

A reverse proxy terminates and forwards — routing, TLS, load balancing, caching. An API gateway is a reverse proxy plus application-level concerns: authentication/authorization (validate JWT/API keys), rate limiting and quotas, request/response transformation, protocol translation (REST↔gRPC), API composition/aggregation, and per-consumer analytics/billing. It's the single managed entry point for an API product. The line blurs — Envoy can be either depending on filters enabled. Interview framing: "gateway = reverse proxy + policy + product concerns; if all I need is LB and TLS, a reverse proxy is enough and cheaper."

How does outlier detection differ from active health checks, and how do they interact?

Active health checks send synthetic probes on a fixed interval and require consecutive successes/failures to flip state — good for detecting a dead process but blind to partial or intermittent failure between probes. Outlier detection (passive) watches real traffic: after N consecutive 5xx or gateway failures, or when a host's error rate deviates from the pool, it ejects the host for a base duration that grows with repeat ejections (exponential). They complement each other — active for coarse liveness, passive for "serving errors right now." Both must respect max_ejection_percent so they can't eject the whole pool, and passive ejection should have a floor (panic mode) to avoid cascade.

What kernel-level tuning does a high-traffic LB need and why?

net.core.somaxconn and the app's listen backlog (both, the smaller wins) — sizes the accept queue so bursts don't drop SYN-ACKed connections (watch ListenOverflows). net.ipv4.tcp_max_syn_backlog for the half-open queue under SYN load, with tcp_syncookies for flood resistance. nofile (ulimit -n) to 1M+ because every client and upstream connection is an FD. net.ipv4.ip_local_port_range widened because each upstream connection consumes an ephemeral port; tcp_tw_reuse to recycle TIME_WAIT sockets. tcp_fin_timeout lower to release closed conns faster. On the NIC: RSS/RPS to spread interrupts across cores, and enough rx/tx ring buffers.

A newly added backend gets slammed and its p99 spikes right after joining. Why and fix?

Cold start: the instance joins the pool at full weight instantly, but its caches are empty, its connection pools to dependencies aren't warm, and a JIT runtime (JVM) hasn't compiled hot paths — so it's temporarily slow, yet least-connections/round-robin sends it a full share (or more, since it has zero active connections, least-conn actually favors it). The fix is slow-start: ramp the new host's traffic weight linearly over a warmup window (e.g. Envoy slow_start_window) so it gets a trickle first, warms up, then reaches full weight. Also pre-warm caches and pools in the readiness gate so it doesn't go Ready until it can actually serve.
