Component Patterns React

Patterns are answers to "how do I share this?" — shared logic, shared state, shared control over a DOM node. React has cycled through mixins, higher-order components, render props and now hooks for logic reuse, and each generation was invented to fix the previous one's composition problems.

A senior answer names the pattern, the problem it solves, and the concrete cost of using it. Three of these — error boundaries, portals and forwardRef — are not stylistic choices at all; they are the only supported way to do the thing they do.

Error boundaries — still class-only

A rendering error anywhere in the tree unmounts the entire React root by default (React 16+ chose a blank screen over a corrupted UI). An error boundary catches errors from its subtree and renders a fallback instead. There is still no hook equivalent: this is the one place you must write a class.

class ErrorBoundary extends React.Component {
  state = { error: null };

  static getDerivedStateFromError(error) {   // render phase: return the fallback state
    return { error };
  }
  componentDidCatch(error, info) {           // commit phase: side effects belong here
    logToSentry(error, info.componentStack);
  }
  render() {
    if (this.state.error) return this.props.fallback ?? <p>Something went wrong.</p>;
    return this.props.children;
  }
}

Two methods, two jobs: getDerivedStateFromError is static and pure, and decides what to render; componentDidCatch is where you log, because it runs after commit.

What error boundaries do NOT catch

Not caughtWhy / what to do
Event handlersThey run outside the render/commit cycle — use try/catch
Async code (setTimeout, promises, fetch)The stack has left React — catch it and put the error in state, then throw it during render if you want the boundary
Server-side renderingBoundaries are a client-render mechanism; handle SSR errors in the framework
Errors thrown by the boundary itselfThey propagate to the next boundary above — so never let the fallback throw
Senior tip: placement is the whole design. One boundary at the root gives a whole-app crash screen; boundaries per route give a broken page inside working chrome; boundaries per widget keep the dashboard alive when one chart fails. Ship at least route-level, plus one around any third-party or user-generated content, and give the fallback a "retry" that resets by changing a key.

react-error-boundary is the pragmatic library wrapper: <ErrorBoundary FallbackComponent={Fallback} onReset={…} onError={…}>, plus useErrorBoundary() whose showBoundary(err) lets async code hand an error to the nearest boundary — the missing hook, effectively.

Portals — render elsewhere, stay in the tree

createPortal(children, domNode) renders children into a DOM node outside the parent's DOM hierarchy, while keeping them in the same React tree.

import { createPortal } from 'react-dom';

function Modal({ children, onClose }) {
  return createPortal(
    <div className="overlay" onClick={onClose}>{children}</div>,
    document.body
  );
}

Use it whenever a child must visually escape its parent: modals, tooltips, dropdowns and toasts trapped by an ancestor's overflow: hidden, transform, or a stacking context that makes z-index unwinnable.

The detail interviewers ask for: events from a portal bubble up the React tree, not the DOM tree. A click inside a portal rendered into document.body still fires the onClick of the JSX parent that rendered the portal. Context, error boundaries and Suspense all reach into portals for the same reason. Convenient for a dropdown inside a form; a surprise for "click outside to close" logic, which must account for the portal content not being a DOM descendant.

HOCs and render props — the two pre-hooks answers

Higher-order component

A function that takes a component and returns a new one with extra props injected: withRouter, connect, withTheme.

function withWindowSize(Wrapped) {
  return function WithWindowSize(props) {
    const size = useWindowSize();
    return <Wrapped {...props} size={size} />;
  };
}
  • Wrapper hell. withRouter(connect(...)(withTheme(Comp))) — five anonymous layers in DevTools, and a real cost in tree depth.
  • Prop collisions. Two HOCs both injecting data: one silently wins, and TypeScript will not always save you.
  • Where does this prop come from? Nothing in the component's source says.
  • Refs do not pass through — a ref lands on the wrapper unless you add forwardRef.
  • Statics are lost — Comp.defaultProps, Comp.getLayout etc. need hoist-non-react-statics.
  • Never create an HOC inside render — new type every render, so the subtree remounts every time.

Render prop

Pass a function as a prop (often children) and let the component call it with the data it manages.

<WindowSize>{size => <Chart width={size.width} />}</WindowSize>

It fixes prop collisions and makes the data source explicit, but composing several is the "callback pyramid":

<Auth>{user =>
  <Theme>{theme =>
    <WindowSize>{size =>
      <Dashboard user={user} theme={theme} size={size} />
    }</WindowSize>}</Theme>}</Auth>

Custom hooks — the modern replacement for both

The same logic, with no wrapper component and no nesting:

function useWindowSize() {
  const [size, setSize] = useState(() => ({ width: window.innerWidth }));
  useEffect(() => {
    const on = () => setSize({ width: window.innerWidth });
    window.addEventListener('resize', on);
    return () => window.removeEventListener('resize', on);
  }, []);
  return size;
}

function Dashboard() {
  const user  = useAuth();
  const theme = useTheme();
  const size  = useWindowSize();       // flat, explicit, renameable, no collisions
  …
}

Note: hooks share logic, not markup. When the thing you want to reuse is rendering structure with a hole in it, a render prop or a children-as-function API is still the right tool — that is why TanStack Table, virtualizers and chart libraries expose headless hooks plus render-prop escape hatches. Also note each caller of a hook gets its own independent state; nothing is shared unless the hook reads a context or an external store.

Compound components

A parent and a family of children that share state implicitly through context, so the consumer writes markup instead of wiring props:

<Tabs defaultValue="billing">
  <TabList>
    <Tab value="profile">Profile</Tab>
    <Tab value="billing">Billing</Tab>
  </TabList>
  <TabPanel value="billing">…</TabPanel>
</Tabs>

const TabsCtx = createContext(null);
function Tabs({ defaultValue, children }) {
  const [active, setActive] = useState(defaultValue);
  const value = useMemo(() => ({ active, setActive }), [active]);
  return <TabsCtx.Provider value={value}>{children}</TabsCtx.Provider>;
}
function Tab({ value, children }) {
  const { active, setActive } = useContext(TabsCtx);   // no props threaded from Tabs
  return <button aria-selected={active === value} onClick={() => setActive(value)}>{children}</button>;
}
  • Worth it for reusable UI primitives with several arrangements — tabs, accordions, menus, selects, dialogs. It is why Radix and Headless UI are shaped this way.
  • Not worth it for a one-off widget with a fixed layout: a config prop such as <Tabs items={items} /> is simpler and easier to type.
  • Throw a clear error when the context is null — "useTabs must be used within <Tabs>" — instead of letting a child crash on undefined.
  • Do not use React.Children.map + cloneElement to inject props; it breaks the moment a child is wrapped in a div or another component. Context works at any depth.

Controlled, uncontrolled, and supporting both

  • Controlled: the parent owns the value and passes value + onChange. Needed for validation on every keystroke, formatting/masking, dependent fields, or disabling submit.
  • Uncontrolled: the DOM owns the value; you pass defaultValue and read it via a ref or on submit through FormData. Fewer renders, less code, and what React 19's form actions encourage.

Reusable components usually support both, exactly like <input> itself. The trick is to keep internal state and let a supplied prop win:

function useControllable({ value, defaultValue, onChange }) {
  const [internal, setInternal] = useState(defaultValue);
  const isControlled = value !== undefined;             // undefined, not null
  const current = isControlled ? value : internal;
  const set = (next) => {
    if (!isControlled) setInternal(next);               // controlled: parent is the source of truth
    onChange?.(next);
  };
  return [current, set];
}
Gotcha: switching an input between controlled and uncontrolled mid-life triggers React's classic warning. It happens when value starts as undefined from an unloaded fetch — use value={data?.name ?? ''}, or key the form on the loaded id so it mounts fresh.

Providers, forwardRef, and key as a reset

The provider pattern

Wrap a context, its state and its actions in one component and expose a hook, so consumers never touch createContext directly:

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const value = useMemo(() => ({ user, login, logout }), [user]);   // memo or every consumer re-renders
  return <AuthCtx.Provider value={value}>{children}</AuthCtx.Provider>;
}
export const useAuth = () => {
  const ctx = useContext(AuthCtx);
  if (!ctx) throw new Error('useAuth must be used inside <AuthProvider>');
  return ctx;
};

Split a fast-changing value from a stable one into two contexts (state vs dispatch) so consumers of the stable half do not re-render.

forwardRef

Function components have no instance, so a ref passed to one is dropped. forwardRef lets a component expose an inner DOM node — required for focus management, scrolling, measurement, and any design-system input.

const Input = forwardRef(function Input(props, ref) {
  return <input ref={ref} {...props} />;
});
// React 19: forwardRef is no longer needed — ref arrives as a normal prop
function Input({ ref, ...props }) { return <input ref={ref} {...props} />; }

useImperativeHandle(ref, () => ({ focus, clear }), []) narrows what you expose to a few methods instead of the raw node — use it sparingly, since imperative APIs are the exception in React.

key as a deliberate remount

<ProfileForm key={userId} user={user} />      // switching user resets every field
<ErrorBoundary key={attempt}>…</ErrorBoundary> // bump attempt to retry after a crash

Changing a key unmounts and remounts, giving fresh state, fresh refs and re-run effects. It is the idiomatic reset — far cleaner than an effect that syncs props into state. The cost is real: everything in that subtree is destroyed and rebuilt, so do not put a changing key on an expensive tree.

🎯 Interview questions

Why must an error boundary be a class?

There is no hook equivalent of getDerivedStateFromError / componentDidCatch; React has not shipped one. In practice you write one class (or use react-error-boundary) and use it everywhere. Note it only catches errors thrown during render, in lifecycles and in constructors of its subtree — not event handlers, async callbacks, SSR, or errors thrown by the boundary itself.

How do you get an async error into a boundary?

Catch it where it happens and put it in state, then throw it during the next render — if (error) throw error; — so it goes through the render phase the boundary can see. react-error-boundary's useErrorBoundary().showBoundary(err) packages exactly that.

Where do events from a portal bubble?

Up the React tree, not the DOM tree. The portal's children are DOM children of wherever you mounted them (often document.body), but React's synthetic event system propagates along the component hierarchy, so the JSX parent's onClick still fires. Context and error boundaries cross portals for the same reason. It surprises click-outside handlers, which test DOM containment.

What problems do custom hooks solve that HOCs did not?

No wrapper components, so no tree depth and no unreadable DevTools nesting; no injected-prop name collisions, since the caller names the variable; the source of every value is visible in the component body; composing three concerns is three flat lines instead of nested wrappers; and typing is natural. HOCs additionally drop refs and static properties unless you handle both by hand.

When is a render prop still the right answer?

When what you are sharing is rendering structure rather than logic — the component controls a shape and needs the consumer to fill a hole, as in headless table, list-virtualizer and chart libraries. Hooks share behaviour; they cannot hand you a slot in someone else's markup.

How would you design a component that is both controlled and uncontrolled?

Keep internal state seeded from defaultValue, treat value !== undefined as "controlled", read from the prop when controlled and from state otherwise, and always call onChange. Never write to internal state while controlled, or the two sources of truth drift. Do not let a component flip modes mid-life — that produces React's controlled/uncontrolled warning.

What are compound components and what do they cost?

A parent that owns state and shares it with a family of children through context, so the consumer composes markup instead of passing props — <Tabs><Tab/></Tabs>. You gain a flexible, arrangement-agnostic API; you pay in more exported pieces, an implicit dependency children must be inside the parent (throw a clear error if the context is missing), and a harder-to-type surface. Worth it for reusable primitives, overkill for a one-off widget.

When is changing key the right tool?

When you want a full reset: a form that must clear when the selected record changes, a retry after an error boundary caught, or re-running mount effects. It unmounts and remounts the subtree, so state, refs and effects all start over — cheaper to reason about than syncing props into state in an effect, but expensive if the subtree is large.
