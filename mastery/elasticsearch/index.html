Elasticsearch Mastery

Elasticsearch is a distributed, near-real-time search and analytics engine built on top of Apache Lucene. You throw JSON documents at it, it builds an inverted index (term → list of documents), and it answers full-text, structured, geo, and aggregation queries in milliseconds across billions of documents by sharding the data and fanning queries out to every shard in parallel. This page covers the core concepts, the full CRUD query surface with real request bodies, and — the part everyone gets wrong in interviews — pagination: the three types, why deep from/size is a trap, and how search_after + Point-in-Time does it correctly.

Interview Explanation — 30 seconds

Say this: "Elasticsearch is a distributed document store and search engine on top of Lucene. Documents are JSON, grouped into an index, which is split into shards (each a self-contained Lucene index) and replicated for HA. On write it analyzes text into terms and stores them in an inverted index; on read a coordinating node scatters the query to every shard, each returns its top matches ranked by BM25 relevance, and the coordinator gathers and merges them. It's near-real-time — writes become searchable after a refresh, ~1 second by default. I use it for full-text search, log/observability analytics, and faceted filtering."

Core concepts / building blocks

ConceptWhat it is
DocumentA single JSON object — the unit of indexing and search. Has an _id and lives in an index.
IndexA logical collection of documents with a shared mapping (like a table, but schema-flexible). Physically split into shards.
MappingThe schema: field names → types (text, keyword, integer, date, geo_point, nested…) and how each is analyzed/indexed.
Shard (primary)A self-contained Lucene index holding a subset of the documents. An index is split into N primary shards at creation (can't change without reindex).
Replica shardA copy of a primary on another node — provides HA (failover) and extra read throughput. Configurable and changeable any time.
Node / ClusterA node is one ES process; a cluster is nodes sharing data. Roles: master (cluster state), data (holds shards), coordinating (routes queries), ingest.
Inverted indexThe core structure: for every term, the sorted list of documents containing it (a postings list) — turns "which docs contain 'search'?" into an O(1) lookup + list scan.
AnalyzerThe text pipeline at index & query time: character filters → tokenizer → token filters (lowercase, stop-words, stemming). text fields are analyzed; keyword fields are stored verbatim.
SegmentAn immutable Lucene file a refresh flushes to. Searches hit all segments; a background merge consolidates them. Immutability is why deletes are just tombstones.

Interview Explanation — 2 minutes

  • Write path: a document is routed to a shard by hash(_id) % number_of_primary_shards, written to the in-memory buffer + a translog (durability), then a periodic refresh (default 1s) turns the buffer into a searchable segment — this is why ES is "near-real-time", not real-time.
  • Analysis: a text field like "Fast Searching" becomes terms [fast, search] (lowercased, stemmed) via an analyzer, and each term points back to the doc in the inverted index. A keyword field stays "Fast Searching" verbatim for exact match/sort/aggregation.
  • Read path: any node can be the coordinating node. It fans the query to one copy of each shard (query phase → each returns top-K doc IDs + scores), merges/sorts, then a fetch phase pulls the actual _source for the final K. This scatter-gather is the key to understanding pagination cost.
  • Relevance: scored with BM25 by default (term frequency ↑ score, but saturating; rarer terms weigh more via IDF; longer docs are penalized). Filters (yes/no) skip scoring and are cacheable.
  • Consistency model: per-document CRUD is strongly consistent and versioned (optimistic concurrency via _seq_no/_primary_term); search is eventually-visible (after refresh). It is not a transactional store — no multi-document ACID.

Cluster architecture (scatter-gather)

flowchart TD
  C["Client"] --> CO["Coordinating node"]
  CO -->|query phase| S0["Shard 0 (primary)"]
  CO -->|query phase| S1["Shard 1 (replica)"]
  CO -->|query phase| S2["Shard 2 (primary)"]
  S0 -->|top-K ids + scores| CO
  S1 -->|top-K ids + scores| CO
  S2 -->|top-K ids + scores| CO
  CO -->|merge + sort, then fetch _source| C

The coordinating node asks each shard for its own top from + size hits, then merges. Remember this: every shard must produce from + size results even if you only want page 500 — that is the entire reason deep offset pagination is expensive.

CRUD — Create (index a document)

First, create an index with an explicit mapping (recommended in production over dynamic mapping):

PUT /products
{
  "settings": { "number_of_shards": 3, "number_of_replicas": 1 },
  "mappings": {
    "properties": {
      "name":     { "type": "text" },
      "sku":      { "type": "keyword" },
      "price":    { "type": "scaled_float", "scaling_factor": 100 },
      "in_stock": { "type": "boolean" },
      "created":  { "type": "date" },
      "tags":     { "type": "keyword" }
    }
  }
}

Index (write) a document — three variants:

# Explicit id, "index" = create-or-replace (idempotent on _id)
PUT /products/_doc/1
{ "name": "Wireless Mouse", "sku": "WM-100", "price": 24.99, "in_stock": true, "created": "2024-01-05", "tags": ["mouse","wireless"] }

# Auto-generated id (POST, no id)
POST /products/_doc
{ "name": "Mechanical Keyboard", "sku": "KB-200", "price": 79.00, "in_stock": true }

# create ONLY — fails with 409 if the id already exists (safe insert)
PUT /products/_create/1
{ "name": "..." }
index vs create: PUT _doc/{id} (op "index") overwrites; PUT _create/{id} refuses to overwrite. Use _create when a duplicate write must not clobber existing data.

CRUD — Read

# Get one document by id (real-time — bypasses refresh, reads the translog)
GET /products/_doc/1

# Get many by id in one round trip
GET /products/_mget
{ "ids": ["1", "2", "3"] }

# Search: full-text match (analyzed) vs exact term (not analyzed)
GET /products/_search
{ "query": { "match": { "name": "wireless mouse" } } }

GET /products/_search
{ "query": { "term": { "sku": "WM-100" } } }   # term = exact, on keyword fields

# Bool query: must (score) + filter (no score, cached) + must_not + should
GET /products/_search
{
  "query": {
    "bool": {
      "must":     [ { "match": { "name": "keyboard" } } ],
      "filter":   [ { "term": { "in_stock": true } },
                    { "range": { "price": { "gte": 20, "lte": 100 } } } ],
      "must_not": [ { "term": { "tags": "refurbished" } } ],
      "should":   [ { "term": { "tags": "wireless" } } ]
    }
  }
}
query vs filter context: clauses in must/should run in query context and compute a relevance _score. Clauses in filter/must_not run in filter context — a yes/no decision, no scoring, and the result bitset is cached. Put everything that's a hard yes/no (status, date range, ownership) in filter; it's faster and cache-friendly.

CRUD — Update

# Partial update — merge fields (read-modify-reindex under the hood; docs are immutable)
POST /products/_update/1
{ "doc": { "price": 22.49, "in_stock": false } }

# Upsert — update if present, otherwise insert the "upsert" body
POST /products/_update/1
{ "doc": { "price": 22.49 }, "upsert": { "name": "Wireless Mouse", "price": 22.49 } }

# Scripted update — e.g. atomic counter increment
POST /products/_update/1
{ "script": { "source": "ctx._source.views += params.n", "params": { "n": 1 } } }

# Optimistic concurrency: only apply if the doc hasn't changed since you read it
PUT /products/_doc/1?if_seq_no=42&if_primary_term=1
{ "name": "Wireless Mouse v2", "price": 22.49 }

# Update many by query
POST /products/_update_by_query
{ "query": { "term": { "tags": "clearance" } },
  "script": { "source": "ctx._source.price *= 0.8" } }
Watch out: there is no in-place edit. A partial update fetches the doc, applies the change, and re-indexes a whole new version (the old one becomes a tombstone until segment merge). High-frequency updates to the same doc are an anti-pattern — model hot counters in Redis, not ES.

CRUD — Delete

# Delete one by id (creates a tombstone; space reclaimed on merge)
DELETE /products/_doc/1

# Delete many by query
POST /products/_delete_by_query
{ "query": { "range": { "created": { "lt": "2020-01-01" } } } }

# Drop the whole index
DELETE /products

CRUD — Bulk (the throughput API)

Never index documents one HTTP request at a time in production. The Bulk API takes newline-delimited JSON (NDJSON): an action line, then (for index/create/update) a source line. One round trip, many ops.

POST /_bulk
{ "index":  { "_index": "products", "_id": "1" } }
{ "name": "Wireless Mouse", "price": 24.99 }
{ "update": { "_index": "products", "_id": "1" } }
{ "doc": { "price": 19.99 } }
{ "delete": { "_index": "products", "_id": "2" } }
Say this: "Batch with Bulk — a few MB or ~1–5k docs per request — and index without an _id when you can, so ES auto-generates one and skips the read-before-write dedupe check."

Pagination — the three types

This is the highest-signal Elasticsearch interview topic. There are three ways to page, and choosing wrong is a real production outage.

TypeMechanismGood forCost / limit
Offset — from / sizeSkip from, take size. Each shard returns from+size hits to the coordinator.Shallow paging: jump-to-page UIs, first few pages.Capped at index.max_result_window = 10 000. Cost grows O(from+size) per shard — deep pages blow up heap.
Cursor / keyset — search_after"Give me results after this sort value." Stateless cursor = the sort values of the last hit.Deep pagination, infinite scroll, "next page" flows. The correct default for > a few pages.No jump-to-arbitrary-page; needs a deterministic total sort (with a tiebreaker). Pair with a PIT for consistency.
Snapshot — scrollFreezes a snapshot of the index and streams batches via a scroll_id.Bulk export / reindex of an entire result set (offline jobs).Stateful & heavy (holds segments open); not for live user pagination. Superseded by PIT + search_after.

1. Offset pagination — from / size

GET /products/_search
{ "from": 20, "size": 10, "sort": [ { "price": "asc" } ],
  "query": { "match_all": {} } }

Page 3 with page size 10 → from:20, size:10. Simple, supports random page access. But to return page 501 (from:5000), each of the N shards must build and ship 5010 hits to the coordinator, which then sorts ~N×5010 and discards all but 10. That's why from + size is hard-capped at max_result_window (10 000) — beyond it you get an error, by design.

Gotcha: raising max_result_window to "fix" a deep-pagination error is the classic mistake — it just moves the OOM further out. Past ~page 1000 you must switch to search_after.

2. Keyset pagination — search_after (the right way to go deep)

Instead of an offset, you remember the sort values of the last row you saw and ask for everything after it. Cost is constant per page regardless of depth. It requires a total, deterministic sort — always add a unique tiebreaker so ties never drop or duplicate rows.

# Page 1 — normal search, note the sort tiebreaker (_shard_doc / _id)
GET /products/_search
{
  "size": 10,
  "sort": [ { "price": "asc" }, { "_id": "asc" } ],
  "query": { "term": { "in_stock": true } }
}
# → each hit has a "sort" array, e.g. the last hit: "sort": [24.99, "WM-100"]

# Page 2 — pass the last hit's sort values as search_after
GET /products/_search
{
  "size": 10,
  "sort": [ { "price": "asc" }, { "_id": "asc" } ],
  "search_after": [24.99, "WM-100"],
  "query": { "term": { "in_stock": true } }
}
Why a tiebreaker? If you sort only by price and 50 products cost 24.99, the cursor [24.99] is ambiguous — you'd skip or repeat rows at the boundary. Adding _id (or _shard_doc under a PIT) makes every sort key unique, so the cursor points at exactly one row.

3. Complex / consistent deep pagination — PIT + search_after

search_after alone runs against the live index — if documents are inserted/deleted between pages, rows can shift. A Point-in-Time (PIT) freezes a consistent view so the whole pagination sees one snapshot. This is the modern replacement for the scroll API.

# 1) Open a PIT (returns an id); keep_alive is how long the view lives
POST /products/_pit?keep_alive=2m
# → { "id": "46ToAwMDaWR5B..." }

# 2) First page — NOTE: no index in the URL; the pit carries it.
#    Use _shard_doc as the efficient, unique tiebreaker (only valid with a PIT).
GET /_search
{
  "size": 10,
  "query": { "term": { "in_stock": true } },
  "pit": { "id": "46ToAwMDaWR5B...", "keep_alive": "2m" },
  "sort": [ { "price": "asc" }, { "_shard_doc": "asc" } ],
  "track_total_hits": false
}

# 3) Next page — feed back the LAST hit's sort array AND the (possibly refreshed) pit id
GET /_search
{
  "size": 10,
  "query": { "term": { "in_stock": true } },
  "pit": { "id": "46ToAwMDaWR5B...", "keep_alive": "2m" },
  "sort": [ { "price": "asc" }, { "_shard_doc": "asc" } ],
  "search_after": [24.99, 421]
}

# 4) When done, close it to free resources
DELETE /_pit
{ "id": "46ToAwMDaWR5B..." }
Two performance flags: set "track_total_hits": false so ES stops counting the exact total after 10k (counting all matches is expensive and you rarely need it while deep-paging); and prefer _shard_doc as the tiebreaker under a PIT — it's a cheap, globally-unique, monotonic doc counter.

Bonus: paginating aggregations — composite + after

from/size don't page buckets. To page through millions of aggregation buckets (e.g. every SKU's sales) use a composite aggregation and feed its after_key back like a cursor:

GET /products/_search
{ "size": 0,
  "aggs": { "by_tag": { "composite": {
      "size": 100,
      "sources": [ { "tag": { "terms": { "field": "tags" } } } ],
      "after": { "tag": "wireless" }      // ← cursor from the previous response's after_key
  } } } }

Types of pagination — how to choose

  • Offset (from/size) → shallow, jump-to-page. Same idea as SQL LIMIT/OFFSET. Simple, but O(offset) and capped at 10k.
  • Keyset / cursor (search_after) → deep paging & infinite scroll. Same idea as SQL "keyset pagination" (WHERE (price,id) > (?, ?) ORDER BY price,id). Constant cost per page, no arbitrary jumps.
  • Snapshot (scroll) → one-shot full export in a batch job. Consistent but stateful/heavy; don't use for user-facing UIs.
  • PIT + search_after → deep paging that must be consistent across pages (report exports, "download all matching"). The recommended modern approach; replaces scroll.
  • Composite after_key → paging aggregation buckets, not documents.
Rule of thumb: first few pages of a UI → from/size. Anything that can go deep, infinite-scroll, or export → search_after (add a PIT if consistency matters). Reach for scroll only for legacy batch jobs.

Why was this built?

Shay Banon created Elasticsearch (2010) to put a distributed, JSON/REST, horizontally-scalable layer over Apache Lucene. Lucene is a brilliant single-machine search library but has no clustering, no sharding, no REST API, and no easy scale-out. Databases at the time did full-text search poorly (LIKE '%x%' can't use a B-tree; MySQL FULLTEXT was limited and didn't scale). Elasticsearch made Lucene distributed and developer-friendly, and became the backbone of the ELK/Elastic Stack for logging and observability.

Advantages

  • Full-text relevance: analyzers, stemming, fuzziness, synonyms, BM25 scoring out of the box.
  • Horizontal scale: shard + replicate across nodes; queries fan out in parallel.
  • Rich queries: full-text, structured filters, geo, nested/parent-child, aggregations, and kNN vector search in one engine.
  • Near-real-time: writes searchable within ~1s; great for logs/metrics dashboards.
  • Ecosystem: Kibana, Beats, Logstash, ingest pipelines — the de-facto observability stack.

Drawbacks / When NOT to use it

Anti-use-cases:
  • System of record / transactions — no multi-doc ACID, eventual visibility, and reindex-on-update. Keep the source of truth in a real DB and index into ES.
  • Frequent updates to the same document — every update reindexes the whole doc. Use Redis/DB for hot counters.
  • Deep random-access pagination for huge result sets via from/size — use search_after; don't fight the 10k window.
  • Tiny datasets — a Postgres index is simpler and cheaper than running a cluster.
  • Strong consistency / joins across documents — ES denormalizes; there are no real joins (only limited nested/parent-child).

Trade-offs & production concerns

  • Shard count is (mostly) fixed: primary shard count is set at index creation and needs a reindex to change. Too few = hot shards; too many = overhead. Aim for ~10–50 GB per shard.
  • Refresh interval: default 1s. Increasing it (e.g. 30s) during heavy bulk loads boosts indexing throughput at the cost of search freshness.
  • Mapping explosion: dynamic mapping on arbitrary JSON keys can create thousands of fields and blow up the cluster state. Disable dynamic mapping or use flattened fields for unbounded keys.
  • text vs keyword: you can't sort/aggregate on an analyzed text field — you need a keyword sub-field (the standard field.keyword multi-field pattern).
  • Deep pagination heap pressure: big from or huge size across many shards is a top cause of circuit-breaker OOMs.

🎯 Deep-dive Q&A — model answers

What actually is an inverted index?

It's a map from term → sorted list of document ids containing that term (the postings list), often with term frequencies and positions. To answer "which docs contain 'search'?" you look up the term and get the doc list directly, instead of scanning every document (a "forward" index would be doc → its words). Combined with the analyzer that normalizes text into terms at index time, this is what makes full-text search fast. Boolean queries intersect/union postings lists; phrase queries also use the stored positions.

Why is Elasticsearch "near-real-time" and not real-time?

A write goes into an in-memory buffer plus the translog (for durability), but it isn't searchable until a refresh turns the buffer into a new immutable Lucene segment — by default every 1 second. So there's a sub-second lag between indexing and searchability. GET-by-id is the exception: it's real-time because it can read the translog directly. You can force ?refresh=true on a write for immediate visibility, but doing it per-request kills throughput by creating tiny segments.

Explain the difference between match and term.

match is a full-text query: it runs the search string through the same analyzer as the field, so "Wireless Mouse" becomes [wireless, mouse] and matches analyzed text fields. term is an exact, non-analyzed lookup of a single token — use it on keyword fields (ids, statuses, tags). A classic bug is running term against a text field: the field was lowercased/stemmed at index time but your term value wasn't analyzed, so it silently matches nothing.

Walk through what happens on a search request, and where pagination cost comes from.

A coordinating node receives the query and fans it to one copy (primary or replica) of every shard — the query phase. Each shard runs the query locally and returns the ids + sort/score of its own top from + size hits. The coordinator merges all of those, sorts globally, and keeps the window it needs; then the fetch phase pulls the _source for just the final size docs. The cost of deep offset pagination is right there: to serve from:9990, size:10, every shard ships 10 000 hits to the coordinator, which sorts N×10 000 and throws almost all away — that's O(from+size) per shard and why the 10k max_result_window exists.

You need to export 5 million matching documents. How do you paginate?

Not with from/size — you'd hit the 10k window and OOM the heap. Open a Point-in-Time for a consistent snapshot, then loop with search_after, sorting on a unique key (e.g. _shard_doc), passing each page's last sort array as the next search_after, with track_total_hits:false and a reasonable size (say 1000). Close the PIT at the end. (The older scroll API also works for a one-shot export but is heavier and now discouraged in favor of PIT + search_after.)

Why does search_after require a tiebreaker, and what's the risk without one?

search_after is "resume after this exact sort position." If the sort isn't unique — say you sort only by price and many docs share a price — the cursor value is ambiguous at the boundary between pages, so rows with the boundary value can be skipped or returned twice. Adding a globally-unique tiebreaker (_id, or _shard_doc under a PIT) makes every document's sort key unique, so the cursor identifies exactly one row and paging is lossless.

Why can't I sort or aggregate on my text field?

Analyzed text fields are tokenized into multiple terms and stored in the inverted index, not as a single sortable value, and they don't have doc values (the columnar structure ES uses for sort/aggregation) by default. So ES refuses to sort/aggregate on them (or warns and needs fielddata, which is memory-hungry). The standard fix is a multi-field: index the field as text for search AND as field.keyword (a keyword sub-field) for exact sort/aggregation.

How does optimistic concurrency control work in ES?

Every document carries _seq_no (a per-shard monotonically increasing write counter) and _primary_term (bumped on primary failover). When you read a doc you get both; on write you pass if_seq_no and if_primary_term. ES applies the write only if they still match — otherwise it returns a 409 conflict, meaning someone else wrote in between. This gives you compare-and-swap semantics for concurrent updates without locks (the older version-based approach is deprecated in favor of seq_no/primary_term).

How would you size shards, and why does it matter for pagination?

Target roughly 10–50 GB per shard and keep shard count proportional to data and query parallelism — too many small shards waste heap on cluster state and per-shard overhead; too few create hot shards. It matters for pagination because every query fans out to every shard and each returns from+size hits: more shards means more partial results to merge at the coordinator, so deep offset pagination gets more expensive as shard count grows. Right-sizing shards plus using search_after keeps the coordinator's merge cheap.

How do you keep Elasticsearch in sync with your primary database?

Treat ES as a derived read model, never the source of truth. Common patterns: (1) dual-write from the app (simple but risky — the two can diverge on partial failure); (2) transactional outbox + a CDC pipeline (Debezium reading the DB's change log → Kafka → an indexer into ES) which is the robust, at-least-once approach; (3) periodic reindex jobs for backfills. Make the indexer idempotent (index by primary key) so replays are safe, and reindex into a new index behind an alias for zero-downtime mapping changes.
