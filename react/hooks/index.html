Hooks: Rules, Refs & Memoization React

Hooks let a function component have state, effects and context without a class — and, more importantly, let stateful logic be extracted and reused. Before hooks, sharing behaviour meant higher-order components and render props, which wrapped the tree in layers of anonymous components that showed up in the profiler and the devtools as "wrapper hell" while making the data flow untraceable.

A custom hook is just a function that calls other hooks. That single idea replaces the entire HOC/render-prop pattern, and it composes: hooks call hooks call hooks, with no extra components in the tree.

The Rules of Hooks, and the real reason for them

  1. Only call hooks at the top level — never inside conditions, loops, nested functions, or after an early return.
  2. Only call hooks from React function components or other custom hooks.

These are not stylistic. React stores a component's hooks in an ordered list attached to that component's fiber, and matches each call to its slot by call order — there are no names or keys involved. The internal model is essentially:

// render 1        slots: [ 0:'Ada', 1:0,   2:effect ]
const [name]  = useState('Ada');   // slot 0
const [count] = useState(0);       // slot 1
useEffect(...);                    // slot 2

Skip a call on a later render and every subsequent hook shifts down one slot, so useState hands back another hook's value — often of the wrong type, sometimes without throwing:

// ❌ conditional hook
if (isLoggedIn) {
  const [name] = useState('Ada');  // slot 0 only on SOME renders
}
const [count] = useState(0);       // slot 0 or slot 1 depending on the branch → corrupt

React can often detect the change in hook count and throw "Rendered fewer hooks than expected", but when the counts happen to match it silently returns the wrong value. Enforce it with eslint-plugin-react-hooks: rules-of-hooks catches the ordering violations and exhaustive-deps catches lying dependency arrays.

Senior tip: the correct pattern is to call the hook unconditionally and make the value conditional: useEffect(() => { if (!enabled) return; … }, [enabled]). Put the condition inside the hook, never around it.

useRef: a mutable box that does not re-render

const ref = useRef(initial) returns the same object { current: initial } on every render. Writing ref.current = x mutates it in place: the value survives re-renders, and changing it triggers no render at all.

It has exactly two jobs:

  • A DOM handle. <input ref={inputRef} /> then inputRef.current.focus() — focus, scroll position, measurements, and controlling non-React widgets.
  • Instance-like storage. Values the render output does not depend on: a timer id, a previous value, a "has submitted" flag, a websocket, a mutable counter.
Gotcha: do not read or write ref.current during render (initializing it lazily on the first render is the accepted exception). Render must be pure so React can re-run, discard or replay it under concurrent rendering; a ref read during render makes the output depend on hidden mutable state. Touch refs in event handlers and effects — that is what "escape hatch" means.

And if the UI must change when the value changes, it is state, not a ref: a ref update is invisible to React, so the screen simply will not update.

useMemo and useCallback

const filtered = useMemo(() => items.filter(matches), [items, query]);   // caches a VALUE
const onPick   = useCallback((id) => select(id), [select]);              // caches a FUNCTION
// useCallback(fn, deps) === useMemo(() => fn, deps)

Both cache across renders keyed by a dependency array compared with Object.is. Neither is free: you pay an extra closure, an array allocation and a comparison on every render, plus the memory held by the cached value, in exchange for skipping the computation when deps match.

Memoization is also a hint, not a guarantee: React may discard cached values (for example to free memory), so your code must stay correct if the factory re-runs. Never put a side effect or a "run once" flag inside useMemo.

The real job is referential stability

People reach for useMemo hoping for raw speed. In practice the compute saved is usually microseconds. What actually matters is the identity of the returned object or function, because identity feeds:

  • React.memo children — a new function prop every render defeats the memo entirely, making the wrapper pure overhead.
  • Dependency arrays of useEffect/useMemo/useCallback — an unstable value re-fires the effect every render.
  • Context values — a fresh { user, login } object re-renders every consumer on every provider render.
// a new object each render → every consumer of this context re-renders
<AuthCtx.Provider value={{ user, login }}>

// stable while its inputs are stable
const value = useMemo(() => ({ user, login }), [user, login]);
<AuthCtx.Provider value={value}>

When memoizing is premature

  • The child is not wrapped in React.memo and the value is not in a dependency array — then the memo buys nothing.
  • The computation is cheap (a small map, a string concat, arithmetic). Wrapping it costs more than it saves.
  • You have not profiled. Measure with the React DevTools Profiler; a re-render is not automatically a performance problem.
Senior tip: the honest answer to "should I memoize everything?" is: fix the structure first (move state down, lift content up as children, split components), and note that the React Compiler in React 19 auto-memoizes, which is expected to make most hand-written useMemo/useCallback unnecessary. Where it is not enabled, memoize deliberately at the boundaries — memoized children, context values, expensive derivations.

Custom hooks: sharing logic, not state

A custom hook is any function whose name starts with use and which calls other hooks. The naming convention is what tells React, the linter and human readers that the Rules of Hooks apply to it.

function useLocalStorage(key, initial) {
  const [value, setValue] = useState(() => {
    const raw = localStorage.getItem(key);          // lazy init: read storage once
    return raw ? JSON.parse(raw) : initial;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));   // sync to an external system
  }, [key, value]);

  return [value, setValue];
}
function useDebounced(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);      // cleanup cancels the superseded timer
  }, [value, delay]);
  return debounced;
}
The key insight: custom hooks share logic, not state. Each call site runs the hook body again and gets its own independent slots, exactly like calling useState twice in one component. Two components using useLocalStorage do not observe each other's value in memory. To share state you need lifted state, context, or an external store.

Composition

function useSearch(query) {
  const debounced = useDebounced(query, 300);   // hooks calling hooks
  const [results, setResults] = useState([]);
  useEffect(() => {
    let ignore = false;
    search(debounced).then(r => { if (!ignore) setResults(r); });
    return () => { ignore = true; };
  }, [debounced]);
  return results;
}

Good custom hooks are named after what they do, wrap a concrete concern (useOnlineStatus, useInterval, useChatRoom), and hide an effect behind a declarative value. A hook named useEffectOnce or a bag of unrelated logic named useUtils is a smell.

🎯 Interview questions

Why can't hooks be called conditionally?

React keeps a per-component list of hook slots and matches each call to its slot purely by call order — there are no names. A skipped or extra call shifts every later hook by one slot, so a hook receives another hook's state. React sometimes throws "Rendered fewer hooks than expected"; when the counts coincide it silently returns the wrong value.

What is the difference between useRef and useState?

Both survive re-renders; only state triggers one. A ref is a stable mutable box you write in place, used for DOM handles and instance-like values the render output does not depend on. If changing the value should update the screen, it must be state.

Why shouldn't you read or write a ref during render?

Render must be pure and repeatable — React may re-run, abandon or replay it under concurrent rendering. A ref read during render makes the output depend on hidden mutable state, producing inconsistent UI. Read and write refs in event handlers and effects. Lazy initialization on the first render is the accepted exception.

useMemo vs useCallback?

useMemo caches the result of calling a function; useCallback caches the function itself. useCallback(fn, deps) is exactly useMemo(() => fn, deps). Both compare deps with Object.is.

Is memoizing everything a good default?

No. Each one costs a closure, an allocation and a comparison every render, and memoization is a hint React may discard. Its real value is referential stability for React.memo children, dependency arrays and context values. Fix component structure first, profile before optimizing — and React 19's compiler auto-memoizes, removing most manual cases.

Do two components using the same custom hook share state?

No. A custom hook shares logic, not state: every call site executes the hook body with its own set of hook slots. Sharing state requires lifting it up, context, or an external store.

Why do custom hooks have to start with use?

It is a convention React's tooling relies on: the linter uses the prefix to decide where the Rules of Hooks apply and to check dependency arrays, and readers use it to know the function is stateful and must be called at the top level.
