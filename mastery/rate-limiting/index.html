Rate Limiting & Resiliency Mastery

Rate limiting decides who gets to call you and how often; resiliency decides what your service does when its dependencies misbehave. Together they are the two halves of "keep the system up under load and failure." This page pushes past "use a token bucket" into Redis Lua atomicity, sliding-window sorted sets, circuit-breaker state machines, full-jitter backoff math, deadline propagation, and the incidents that actually get asked about at Staff level.

Interview Explanation — 30 seconds

Say this: "Rate limiting protects a service from being overwhelmed by capping request rate per caller — usually with a token bucket or sliding window keyed on user, API key, or IP, enforced at the edge and backed by a shared Redis counter for cross-instance accuracy. When you exceed the limit you get a 429 with a Retry-After header. Resiliency is the flip side: it's how the caller survives a slow or failing dependency — timeouts and deadlines so you never wait forever, retries with exponential backoff and full jitter so you don't stampede, circuit breakers to stop hammering a dead dependency, bulkheads to isolate pools, and load shedding plus graceful degradation so you drop low-priority work instead of falling over. Idempotency keys make the retries safe."

Interview Explanation — 2 minutes

The fuller answer separates the two concerns and names the internals an interviewer is fishing for.

  • Algorithms: Fixed window is a single counter per window — cheap but suffers boundary bursts (2x the limit across a window edge). Sliding window log stores every timestamp in a sorted set — exact but memory-heavy. Sliding window counter interpolates the previous and current window — cheap approximation, the industry default. Token bucket allows bursts up to the bucket size and refills at the sustained rate. Leaky bucket smooths output to a constant rate regardless of input burst.
  • Distributed enforcement: per-instance counters drift and let N instances each admit the full limit, so you centralize state in Redis. The atomic move is a Lua script that does check-and-decrement in one round trip, or INCR+EXPIRE for fixed window, or a sorted set with ZADD/ZREMRANGEBYSCORE for a true sliding window.
  • Identifying the caller: API key > user ID > IP. IP is a trap — NAT and mobile carriers put thousands of users behind one IP, and X-Forwarded-For is client-spoofable unless you trust only the last proxy hop.
  • Responses: HTTP 429, Retry-After, and the X-RateLimit-Limit / Remaining / Reset headers so well-behaved clients self-throttle.
  • Resiliency patterns: timeouts and deadline propagation (a budget that shrinks as it flows through the call chain), retries with exponential backoff + full jitter, circuit breaker (closed → open → half-open), bulkheads, load shedding / admission control, backpressure via bounded queues, graceful degradation with fallbacks, and hedged requests to cut tail latency.
  • Placement: coarse limits and DDoS shielding at the edge/gateway; fine-grained per-tenant and per-endpoint limits at the service. Resiliency lives in the caller (client-side library or sidecar/service mesh).

Internal Working

Token bucket (the workhorse)

  1. State per key: tokens (current count) and last_refill (timestamp). Stored as a Redis hash.
  2. On request, compute elapsed time now - last_refill, add elapsed * refill_rate tokens, cap at capacity (the burst size).
  3. If tokens >= cost, subtract cost, allow, write back state. Else reject with 429 and compute Retry-After = (cost - tokens) / refill_rate.
  4. The whole read-modify-write MUST be atomic across instances — do it in a Lua script so no two instances race the same bucket.
-- token_bucket.lua  KEYS[1]=bucket  ARGV: now, rate, capacity, cost
local st = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(st[1]) or tonumber(ARGV[3])
local ts     = tonumber(st[2]) or tonumber(ARGV[1])
local rate, cap, cost = tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local delta = math.max(0, tonumber(ARGV[1]) - ts)
tokens = math.min(cap, tokens + delta * rate)
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[1])
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
return { allowed and 1 or 0, tokens }

Sliding window log with a Redis sorted set

  1. Each request adds a member scored by timestamp: ZADD key now now.
  2. Evict everything older than the window: ZREMRANGEBYSCORE key 0 (now-window).
  3. Count survivors: ZCARD key. If > limit, reject. Set a TTL so idle keys die.
  4. Exact to the millisecond, but memory is O(limit) per key — a 10k/min limit stores 10k members per active caller.

Sliding window counter (approximation)

  1. Keep two fixed-window counters: current and previous window.
  2. Estimated rate = current + previous * (1 - elapsed_fraction_of_current_window).
  3. Two integers per key, no per-request storage — this is what most API gateways ship by default.

Circuit breaker state machine

  1. Closed: calls pass through; a rolling window counts failures. When failure ratio crosses the threshold (e.g. >50% over the last 20 calls), trip to Open.
  2. Open: fail fast immediately (no call to the dependency) for reset_timeout (e.g. 30s). This is what stops retry storms from crushing a recovering service.
  3. Half-open: after the timeout, allow a small number of trial requests. If they succeed, close; if any fail, re-open and reset the timer.
Watch out: A naive breaker keyed on a raw failure count trips on low-traffic endpoints from a couple of blips. Use a ratio over a rolling window plus a minimum-volume threshold (don't evaluate until you've seen, say, 20 requests).

Why was this built?

Before rate limiting, a single misbehaving client — a runaway cron, a scraping bot, a buggy retry loop — could consume all of a service's capacity and take it down for everyone (the "noisy neighbor" and thundering-herd problems). Operators tried to cope with over-provisioning, IP blocklists, and manual firewall rules, all reactive and coarse.

On the resiliency side, early distributed systems used unbounded synchronous calls with no timeouts. One slow dependency would exhaust every thread waiting on it, which cascaded: the caller became slow, its callers piled up, and the failure propagated up the stack until the whole system was down — a cascading failure. Netflix's 2011–2012 outages drove the creation of Hystrix (circuit breakers + bulkheads + fallbacks), which codified these patterns. AWS's "Timeouts, retries and backoff with jitter" and Google's SRE book (deadlines, load shedding) turned them into industry standards.

Advantages

  • Protects capacity: caps worst-case load so one caller can't starve the rest — the core fairness guarantee.
  • Prevents cascading failure: breakers + timeouts + bulkheads stop a single slow dependency from taking down the whole call graph.
  • Monetization & tiering: quotas map directly to plans (free vs pro vs enterprise).
  • Predictable tail latency: timeouts and hedged requests bound p99 instead of letting it drift to the slowest replica.
  • Graceful degradation: shed low-priority traffic first, keep the money path alive.
  • Backpressure signal: 429 + Retry-After tells clients to slow down instead of retrying blindly.

Drawbacks

  • Shared-counter latency & coupling: a central Redis adds a network hop to every request and becomes a availability dependency of the whole fleet.
  • Approximation vs cost trade-off: exact limiting is memory-heavy; cheap limiting is approximate.
  • Retry amplification: naive retries multiply load exactly when the system is already struggling.
  • Breaker false trips: a badly tuned breaker fails healthy requests; a lax one never protects anything.
  • Operational complexity: deadlines, budgets, jitter, and half-open trials are subtle and easy to get wrong.
  • Client identity is hard: IP-based limiting punishes NAT'd users; header-based identity can be spoofed.

Trade-offs

  • Local vs global limits: local (per-instance) counters are fast and need no network but drift — N instances each admit the full limit, so effective global limit ≈ N × configured. Global (shared Redis) is accurate but adds latency and a dependency. Hybrid: local token buckets synced periodically, or allocate each instance a slice of the global budget.
  • Accuracy vs memory vs cost: sliding log (exact, heavy) ↔ sliding counter (approx, cheap).
  • Fail-open vs fail-closed: if Redis is down, do you allow all traffic (fail-open, availability first) or reject all (fail-closed, protection first)? Most public APIs fail open with a local fallback limiter.
  • Retries vs load: more retries improve success rate for transient errors but amplify load during real outages — bounded by circuit breakers and retry budgets.
  • Timeout tightness: tight timeouts free threads fast but cause false failures on slow-but-fine requests; loose timeouts tie up resources.
  • Edge vs service enforcement: edge is cheap and blocks abuse early but lacks business context; service-level knows the tenant/cost but has already paid for connection handling.

When NOT to use it

Watch out: Don't reach for these when they add more risk than they remove:
  • Internal, trusted, low-fanout calls with capacity headroom — a rate limiter there just adds a Redis dependency and a failure mode for no protection benefit.
  • Retries on non-idempotent writes without an idempotency key — you'll double-charge, double-ship, or duplicate records. Fix idempotency first.
  • Circuit breakers on a dependency you can't fall back from — tripping open just converts slow errors into fast errors with no recovery; sometimes you must wait.
  • Rate limiting purely by IP for a mobile/consumer app — carrier NAT means one IP = thousands of users; you'll throttle innocent people.
  • Retries inside a request that also has an upstream deadline without honoring the remaining budget — you'll blow the caller's deadline retrying work that's already doomed.

Production Architecture

A typical topology puts coarse DDoS/volumetric protection and per-IP limits at the CDN/edge, per-API-key and per-tenant limits at the API gateway (backed by a shared Redis cluster with a local fallback), and per-endpoint resiliency (breakers, bulkheads, deadlines) inside each service or its mesh sidecar. Deadlines are injected at the gateway and propagated downstream so the whole call tree shares one budget.

  • Edge: Cloudflare/CloudFront + WAF absorbs volumetric attacks before they cost you compute.
  • Gateway: Envoy/Kong/APIGee runs the token-bucket or sliding-window logic, calling a Redis cluster; if Redis is unreachable it degrades to a per-pod local limiter (fail-open with a cap).
  • Service: resilience4j / Hystrix / Polly / a mesh (Istio, Linkerd) wraps outbound calls with timeouts, breakers, bulkheads, and retries.
  • Deadline propagation: gRPC deadlines or a X-Request-Deadline header flow downstream; each hop subtracts its own latency and refuses to start work that can't finish in time.

Production Problems

  • Retry storm / thundering herd: a dependency blips, every client retries at the same instant, and the synchronized wave keeps it down. Fix: full jitter + circuit breakers + retry budgets.
  • Redis hot key: a single global limiter key (e.g. per-endpoint, not per-user) funnels all traffic to one Redis shard's slot. Fix: shard the key or use per-caller keys.
  • Counter drift under partition: Redis cluster failover loses the last few INCRs; limits briefly loosen or reset.
  • Breaker flapping: a marginal dependency oscillates open/closed, causing intermittent 503s. Fix: hysteresis, longer reset timeout, higher half-open threshold.
  • Deadline not propagated: service A times out at 1s but calls B which retries for 3s — wasted work on an already-abandoned request.
  • Fail-open cascade: Redis outage flips every gateway to fail-open simultaneously, and the now-unlimited traffic overwhelms the backend.

Debugging Guide

  • Inspect a limiter key: redis-cli HGETALL rl:user:123 or redis-cli ZRANGE rl:user:123 0 -1 WITHSCORES for sliding-log.
  • Find hot slots: redis-cli --hotkeys and redis-cli INFO keyspace; watch redis-cli --latency and --latency-history.
  • Live command stream (careful in prod): redis-cli MONITOR | grep 'EVALSHA'.
  • Confirm 429 shape: curl -i https://api/... and check Retry-After, X-RateLimit-*.
  • Breaker state: expose resilience4j.circuitbreaker.state / Hystrix stream; grep logs for CircuitBreakerOpenException.
  • Retry amplification: compare inbound RPS to outbound RPS on the failing dependency — a >1 ratio means retries are amplifying.
  • Deadline violations: trace with OpenTelemetry; look for spans killed by DEADLINE_EXCEEDED and check whether children ran past the parent deadline.
  • Thread/connection pool exhaustion: check pool active vs max, queue depth, and rejection counts — the classic bulkhead signal.

Scaling

The limiter's own state store is the scaling bottleneck. Options in order of scale: (1) local in-memory limiter — infinite scale, no accuracy; (2) shared Redis single instance — accurate, ~100k+ ops/s, one shard; (3) Redis Cluster — shard keys by caller so load spreads across slots; (4) two-tier — local token buckets that periodically reconcile a slice of the global budget, cutting Redis traffic by the sync ratio.

flowchart TD
  REQ["Incoming request"] --> L1["Local bucket per pod"]
  L1 -->|"budget available"| PASS["Allow immediately"]
  L1 -->|"local budget low"| SYNC["Fetch slice from global"]
  SYNC --> REDIS["Redis global budget"]
  REDIS -->|"granted N tokens"| L1
  REDIS -->|"exhausted"| REJECT["429 Too Many Requests"]
  • Key sharding: per-user keys naturally distribute; avoid a single global key that hot-spots one slot.
  • Pipeline / EVALSHA: ship the Lua script once, call by SHA to avoid resending it; pipeline batches to cut round trips.
  • Two-tier budgeting: each pod leases M tokens from Redis and serves locally until depleted — trades a little accuracy for a huge drop in Redis QPS.
  • Cell-based / approximate: partition callers into cells with independent limiters to bound blast radius and store.

Security

  • X-Forwarded-For spoofing: a client can inject fake XFF entries. Trust only the value your own trusted proxy appends (the rightmost hop), or use a platform-set header like CF-Connecting-IP. Never key limits off a client-controllable header.
  • NAT / shared IP fairness: IP limiting throttles legitimate users behind carrier-grade NAT; prefer authenticated identity (API key / user ID) and reserve IP limits for unauthenticated endpoints.
  • Limiter as DoS target: if the limiter itself is expensive (sliding log with huge windows), an attacker can exhaust Redis memory. Cap window size and set TTLs.
  • Enumeration via 429 vs 401: different responses for known vs unknown keys can leak validity — keep the limiter response uniform.
  • Retry-After as an oracle: don't leak exact internal capacity; round Retry-After.
  • Distributed / L7 DDoS: per-key limits don't stop a botnet with many keys — layer with WAF, challenge (CAPTCHA/JS), and anomaly detection.
  • Idempotency key replay: scope keys per user and expire them so a stolen key can't be replayed indefinitely.

Performance

  • Limiter overhead: a local token bucket is a few nanoseconds; a Redis round trip is ~0.3–2ms same-AZ, which dominates the check. Two-tier design amortizes this to near-zero for most requests.
  • Lua atomicity cost: the script runs on Redis's single thread — keep it O(1); a sliding-log ZREMRANGEBYSCORE is O(log N + M) where M is evicted members, so it can spike CPU on large windows.
  • Memory: sliding log = O(limit) members per active key; token bucket = 2 fields; sliding counter = 2 ints. At 1M active users a 10k-limit sliding log is billions of members — don't.
  • Timeout tuning: set per-dependency timeouts near p99.9 of healthy latency, not an arbitrary round number — too tight causes false failures, too loose ties up threads.
  • Hedged requests: fire a second request after p95 latency; caps tail at the cost of ~5% extra load. Google's BigTable/Spanner use this to crush p99.
  • Backoff math (full jitter): sleep = random(0, min(cap, base * 2^attempt)). Full jitter beats "equal jitter" and fixed backoff at decorrelating clients — AWS's measurements show it minimizes both completion time and competing load.
  • Connection pool sizing: pool size ≈ target throughput × latency (Little's Law); undersized pools serialize, oversized pools remove backpressure and let overload propagate.
// full jitter exponential backoff
const base = 100, cap = 20000;   // ms
function delay(attempt) {
  const exp = Math.min(cap, base * 2 ** attempt);
  return Math.random() * exp;      // uniform 0..exp
}

Common Mistakes

  • Fixed window with high limits: boundary burst lets 2x through. Fix: sliding window counter.
  • Per-instance counters believed to be global: effective limit = N × configured. Fix: shared store or divide budget by instance count.
  • Non-atomic check-then-decrement: two instances both read "1 left" and both allow. Fix: Lua / atomic INCR.
  • Retries without a circuit breaker or budget: retry storm. Fix: breaker + retry budget (cap retries to ~10% of requests).
  • Retrying non-idempotent operations: duplicate side effects. Fix: idempotency keys.
  • No jitter on backoff: synchronized retry waves. Fix: full jitter.
  • Timeout longer than the caller's deadline: wasted work. Fix: propagate and honor the deadline budget.
  • Retrying on 4xx (except 429): a 400 will never succeed on retry. Fix: retry only 429/503/network errors.
  • One global limiter key: Redis hot slot. Fix: key per caller.
  • Breaker on request count not ratio: trips on low traffic. Fix: ratio + minimum volume.
  • Fail-closed on limiter outage for a public API: total outage from a Redis blip. Fix: fail-open with a local cap.

Interview Follow-up Questions

  1. What's the difference between rate limiting, throttling, and shaping?
    1. Limiting rejects over-limit; throttling delays/slows; shaping (leaky bucket) buffers to a constant output rate.
  2. Walk me through the boundary-burst problem in fixed window.
    1. Limit N in window W; N at the end of one window + N at the start of the next = 2N in ~W. Sliding window fixes it.
  3. How do you make the check-and-decrement atomic across instances?
    1. Single Redis Lua script (runs on the single thread) or atomic INCR with EXPIRE; never read-then-write in the app.
  4. Sliding log vs sliding counter — when do you accept the approximation?
    1. Log is exact but O(limit) memory; counter is 2 ints with small edge error — use counter unless exactness is contractual.
  5. Token bucket vs leaky bucket?
    1. Token allows bursts up to capacity then throttles to refill rate; leaky bucket enforces constant output, no burst.
  6. How do you identify the caller, and what breaks?
    1. API key > user ID > IP; IP breaks under NAT and XFF spoofing — trust only the proxy-appended hop.
  7. What do you return when limited?
    1. 429 + Retry-After + X-RateLimit-Limit/Remaining/Reset so clients self-throttle.
  8. Redis is down — fail open or closed?
    1. Public API: fail open with a local per-pod cap. Protection-critical: fail closed. State the trade explicitly.
  9. Local vs global limits — what's the drift?
    1. N instances each admit the full limit → effective ≈ N×. Divide the budget or centralize; two-tier reconciles periodically.
  10. Explain the circuit breaker states and transitions.
    1. Closed (count failures) → Open (fail fast for reset_timeout) → Half-open (trial requests) → Closed or back to Open.
  11. Why jitter on retries, and which jitter?
    1. Decorrelates synchronized clients to avoid retry waves; full jitter (random 0..exp) minimizes both latency and competing load.
  12. What's a retry budget and why?
    1. Cap retries to a fraction (~10%) of requests so retries can't amplify load during a broad outage.
  13. What is deadline propagation?
    1. A shrinking time budget passed downstream; each hop subtracts its latency and refuses work that can't finish in time.
  14. What are bulkheads?
    1. Isolated thread/connection pools per dependency so one saturated dep can't exhaust shared resources.
  15. How does load shedding decide what to drop?
    1. By request criticality/priority — drop low-priority (recommendations) first, keep the money path; admission control at the front.
  16. What are hedged requests and their cost?
    1. Fire a duplicate after p95, take the first response; cuts tail latency at ~5% extra load. Cancel the loser.
  17. Why do retries need idempotency keys?
    1. So a retried write is deduplicated server-side and doesn't double-charge/double-create.
  18. Where do you enforce — edge or service?
    1. Coarse/DDoS at edge, fine-grained per-tenant/endpoint at service; often both layers.
  19. How do you rate limit by cost, not count?
    1. Assign each endpoint a token cost; heavy queries deduct more from the same bucket (Atlassian/GitHub GraphQL model).
  20. How do you prevent a breaker from flapping?
    1. Ratio over a rolling window + minimum volume + longer reset timeout + gradual half-open ramp (hysteresis).

Common Cross Questions

  • Redis internals: "Why is a Lua script atomic?" → single-threaded execution, script runs to completion before any other command. Expect follow-ups on EVALSHA, cluster slots, and CROSSSLOT errors on multi-key scripts.
  • Distributed consensus / clocks: "How do sliding windows behave under clock skew across instances?" → use server-side Redis time (TIME) not app clocks; NTP skew corrupts timestamp-based windows.
  • Load balancing: "How does this interact with autoscaling?" → per-instance limits must divide by live instance count or you loosen the global limit as you scale out.
  • Microservices & mesh: "Would you do this in code or the sidecar?" → mesh (Envoy) gives language-agnostic breakers/retries/limits; library gives finer business context.
  • Queues & backpressure: "Rate limiting vs a bounded queue?" → limiting rejects at the door; a bounded queue buffers then rejects (reject vs block); both are backpressure mechanisms.
  • Idempotency & exactly-once: "How do you dedupe retries?" → idempotency key + a store of seen keys with a TTL; ties into exactly-once semantics discussion.
  • Observability: "How do you tell retries from real traffic?" → tag retries with an attempt header/count; compare inbound vs outbound RPS on the dependency.

Production Scenarios

Retry storm takes down a recovering service

SymptomsDependency has a 5s blip, then can't recover; its RPS stays pinned at 4x normal even after the root cause is fixed.
InvestigationCompare inbound vs outbound RPS (ratio ~4). Traces show every client retrying 3x with fixed 1s backoff, synchronized. No breaker.
Root CauseBlind retries with no jitter and no circuit breaker; the synchronized retry wave keeps the dependency saturated.
SolutionAdd circuit breaker (trip open at 50% failures) to fail fast, full-jitter backoff, and a retry budget capping retries to 10%.
PreventionStandardize the resilient client library across services; alert on retry_ratio > 0.3.
Interview Answer"Retries without a breaker amplify load during the exact window you need to shed it. I add fail-fast breakers, full jitter, and a retry budget so the dependency can recover."

Rate limiter loosens 8x after autoscaling

SymptomsAfter scaling from 5 to 40 pods during a sale, a client that should get 1000 rpm is doing ~8000 rpm; backend overloads.
InvestigationLimiter is in-memory per pod. 40 pods each enforce 1000 → effective 40,000. Confirmed by summing per-pod counters.
Root CausePer-instance local limiting mistaken for a global limit; no shared state.
SolutionMove to shared Redis limiter (Lua token bucket keyed per user), or two-tier with a global budget leased to pods.
PreventionLoad test the limiter at target replica count; assert effective global limit in integration tests.
Interview Answer"Local counters don't compose — N pods means N× the limit. Either centralize the counter in Redis or divide the budget by live replica count."

Deadline not propagated wastes capacity

SymptomsGateway times out user requests at 1s, but backend CPU stays pegged doing work no one is waiting for.
InvestigationTraces show service B retrying a DB call for 3s on requests whose parent span was already cancelled at 1s.
Root CauseDeadline set at the edge wasn't propagated; downstream had its own longer timeout and no cancellation.
SolutionPropagate gRPC deadline / X-Request-Deadline header; each hop checks remaining budget and aborts doomed work; wire context cancellation.
PreventionEnforce deadline propagation in the RPC framework; alert on deadline_exceeded and orphaned-work spans.
Interview Answer"Without deadline propagation, downstream services burn CPU on abandoned requests. I pass a shrinking budget and cancel work that can't finish in time."

Duplicate charges from payment retries

SymptomsSupport reports customers double-charged during a period of elevated payment-API latency.
InvestigationClient timed out at 2s and retried; the original request had actually succeeded server-side. No idempotency key.
Root CauseRetrying a non-idempotent write with no dedupe — the retry created a second charge.
SolutionRequire an idempotency key per charge; server stores key→result with a TTL and returns the original result on replay.
PreventionMake idempotency keys mandatory on all mutating endpoints; test the retry-after-success path.
Interview Answer"Retries are only safe if the operation is idempotent. For payments I require an idempotency key so a retry returns the original result instead of charging again."

🎯 Deep-dive Q&A — model answers

Design a distributed rate limiter for 1000 req/min per API key across 50 gateway pods.

Centralize state in Redis so pods share one view. Use a token bucket in a Lua script keyed rl:{apiKey} — the hash tag isn't needed unless multi-key; per-key naturally spreads across cluster slots. Script does refill (elapsed × rate, capped at capacity=burst), check tokens >= cost, decrement, PEXPIRE. To cut Redis QPS at scale, go two-tier: each pod leases a slice (e.g. 20 tokens) from Redis and serves locally until depleted, then re-leases — trades bounded over-admission for a big drop in round trips. Return 429 + Retry-After = (cost−tokens)/rate. Fail open with a local per-pod cap if Redis is unreachable. Use Redis server TIME for the timestamp to avoid app clock skew.

Why is full jitter mathematically better than fixed or "equal" jitter?

Fixed backoff keeps all clients that failed at the same instant synchronized — they all wake at t+base, t+2base, hammering in waves. Equal jitter (base·2^n/2 + rand(0, base·2^n/2)) still clusters around the midpoint. Full jitter (rand(0, min(cap, base·2^n))) spreads clients uniformly across the whole interval, maximally decorrelating them. AWS's simulations showed full jitter minimizes both total completion time and the number of competing calls hitting the server, because the uniform spread flattens the load spike better than any scheme with a non-zero lower bound.

How do you build a true sliding window in Redis, and what's the cost?

Sorted set per key. On each request: ZREMRANGEBYSCORE key 0 (now-window) to evict old, ZADD key now member (member must be unique — use now + a counter to avoid collisions), ZCARD key to count, PEXPIRE. Wrap all of it in one Lua script for atomicity. It's exact to the millisecond. Cost: memory is O(limit) members per active key — a 10k/min limit stores up to 10k members per caller, so at millions of callers it's billions of members. CPU: ZREMRANGEBYSCORE is O(log N + M) for M evicted. For high limits, prefer the sliding-window-counter approximation (two integers, interpolated) instead.

Explain the circuit breaker tuning knobs and how you'd pick them.

Failure-rate threshold (e.g. 50%): fraction of failures in the rolling window that trips Open. Minimum-number-of-calls (e.g. 20): don't evaluate the ratio until you've seen enough volume — prevents tripping on a single blip on low-traffic endpoints. Sliding-window size (count- or time-based). reset_timeout / wait-duration-in-open (e.g. 30s): how long to fail fast before probing. permitted-calls-in-half-open (e.g. 5): trial requests; if they succeed, close. Slow-call threshold treats slow-but-successful calls as failures (e.g. >2s counts). Pick the threshold from your dependency's normal error rate + margin, reset_timeout from its typical recovery time, and add hysteresis (longer timeout, higher half-open bar) to stop flapping on marginal deps.

What breaks when you rate limit by IP, and what do you do instead?

Carrier-grade NAT and corporate proxies put thousands of distinct users behind one IP, so a per-IP limit throttles innocents and lets a single abuser behind a unique IP through untouched. X-Forwarded-For is client-spoofable — an attacker prepends fake entries to dodge limits; you must trust only the value your own trusted proxy appends (rightmost hop) or a platform header like CF-Connecting-IP. The fix: rate limit authenticated traffic by API key / user ID, and reserve IP limits for unauthenticated endpoints (login, signup) where you additionally layer WAF and challenge mechanisms. For login specifically, limit by (IP + username) tuple to slow both credential stuffing and targeted attacks.

Fail-open vs fail-closed when the limiter's Redis is down — how do you decide?

It's an availability-vs-protection call and depends on what the limiter guards. A public API where the backend can absorb a short spike should fail open — a Redis blip shouldn't 503 all customers — but with a local per-pod cap so "open" isn't literally unlimited. A limiter protecting a fragile or expensive resource (a payment switch, a small DB) should fail closed, because unbounded traffic would be worse than rejecting. The dangerous middle case is fail-open cascading: every gateway flips open simultaneously and the now-unlimited flood overwhelms a backend that was only surviving because of the limiter. Mitigate with the local fallback cap and by making Redis itself HA (cluster + replicas) so the failure is rare.

How does deadline propagation actually work in a call tree?

The entrypoint sets an absolute deadline (now + budget), not a relative timeout. It passes that deadline downstream — gRPC does it natively via the deadline in call metadata; over HTTP you send X-Request-Deadline or a remaining-ms header. Each hop computes remaining = deadline - now, uses min(remaining, its own timeout) for its calls, and refuses to even start work if remaining is below a floor (fail fast with DEADLINE_EXCEEDED). Critically, cancellation propagates: when the parent's context is cancelled (client gave up), children observe it and abort, freeing threads and DB work. Without this, a service keeps grinding on requests nobody is waiting for — wasted capacity exactly during overload.

What's a bulkhead and how is it different from a circuit breaker?

A bulkhead isolates resources: you give each downstream dependency its own thread pool or connection-pool/semaphore with a max concurrency, so if dependency A goes slow and its pool fills, calls to A get rejected but dependencies B and C keep their own pools and stay healthy. It prevents one slow dep from exhausting a shared pool and stalling everything (the classic cascading failure). A circuit breaker is temporal — it stops calling a dependency that's failing over time. They're complementary: the bulkhead contains the blast radius of a slow dep right now; the breaker stops calling a dead dep and gives it room to recover. Netflix Hystrix shipped both together.

How do hedged (or tied) requests reduce tail latency, and what's the risk?

For a read you can safely duplicate, send the request to one replica; if no response by, say, the p95 latency, send a second copy to another replica and take whichever returns first, cancelling the loser. Because it's rare for two independent replicas to both be slow, this collapses p99 toward p50 at only ~5% extra requests (you only hedge the slow tail). "Tied" requests go further: send both immediately but have them cancel each other once one starts executing, so you don't do double work. Risks: it amplifies load if your hedge trigger is too aggressive (hedging everything doubles traffic), and it's only safe for idempotent reads — never hedge a non-idempotent write. Google uses this in BigTable/Spanner.

Rate limiting by request cost instead of count — how and why?

Not all requests are equal: a paginated list of 1 item and a report scanning a million rows shouldn't each cost "1." Assign each endpoint (or each query, for GraphQL) a token cost proportional to its work, and deduct that cost from the caller's token bucket. GitHub's GraphQL API and Atlassian do exactly this — a complex query might cost 50 points against a 5000-point hourly budget. It gives fair protection: a caller can make many cheap calls or few expensive ones, but can't hide an expensive operation behind a low request count. Implementation: the limiter computes cost before or after execution (post-execution needs a reservation + reconcile), then the Lua decrement uses that cost as ARGV.

Why aren't per-instance in-memory limiters enough, and when are they actually fine?

They drift: with N instances each enforcing limit L, the effective global limit is up to N×L because instances don't share state, and it changes as you autoscale. They're fine when (a) you only need approximate protection and can divide L by expected instance count, (b) traffic is evenly load-balanced so each instance sees ~1/N, or (c) you use them as the fast local tier of a two-tier design that reconciles against a global Redis budget. They're the right first line even in distributed setups because they're free (no network) and absorb the common case — you only touch Redis when the local budget runs low, cutting central QPS dramatically.

Retries, timeouts, and breakers all interact — give me the correct layering.

Innermost: a per-attempt timeout near the dependency's healthy p99.9. Around retries: retry only on retryable errors (timeout, 503, 429-with-Retry-After, connection reset — never 4xx except 429), with full-jitter exponential backoff, a bounded max attempts, and a retry budget capping total retries to ~10% of requests. Around that: a circuit breaker that trips on failure ratio so retries stop entirely when the dep is down. Enclosing everything: an overall deadline/budget for the whole operation so retries + backoff can never exceed what the caller is willing to wait — each retry checks remaining budget before sleeping/attempting. And every retried write carries an idempotency key. The order matters: the breaker short-circuits before you spend retry budget, and the deadline caps the whole thing.

How do load shedding and admission control decide what to drop under overload?

You tag requests with a criticality/priority (e.g. CRITICAL_PLUS for checkout, CRITICAL for core reads, SHEDDABLE for recommendations/prefetch). When a server detects overload — rising queue depth, latency past SLO, CPU saturation — it sheds from the lowest priority up, rejecting SHEDDABLE traffic first with a fast 503 so the money path keeps its capacity. Admission control does this at the front door before work is queued, so you don't spend resources on requests you'll drop. Adaptive versions (Netflix concurrency-limits, Google's approach) measure the server's actual capacity via latency gradient (like TCP Vegas) and adjust the concurrency limit dynamically rather than using a fixed threshold. The key insight: under overload, serving fewer requests well beats serving all requests badly (or crashing).

Reject vs block for backpressure with a bounded queue — which and why?

A bounded queue is your backpressure buffer. When it fills you choose: block the producer (backpressure propagates upstream, producer slows) or reject immediately (fast fail, producer decides what to do). For synchronous request/response you almost always reject — blocking ties up the caller's thread and the caller has a deadline anyway; a fast 503/429 lets it shed or retry elsewhere. Blocking is appropriate in internal pipelines where the producer can genuinely slow down (e.g. a Kafka consumer that just stops polling) and you want lossless flow control. The anti-pattern is an unbounded queue — it hides the overload, grows until OOM, and adds latency to every request (queue wait) with no ceiling. Always bound it and set the bound so max queue wait stays under the timeout budget.

Your 429 rate is spiking but real traffic is flat — how do you debug it?

First confirm it's real limiting not a misconfig: check limiter_fail_open_rate (if Redis flapped, some pods may be mis-counting) and whether a recent deploy changed limit config. Pull the top limited keys — is it one caller (a broken client retry loop hammering you) or broad? If one caller, check their retry behavior: a client retrying on 429 without honoring Retry-After creates a feedback loop that inflates the 429 count. Check whether autoscaling changed instance count on a per-instance limiter (effective limit shifted). Inspect a sample key's state (HGETALL/ZCARD) to verify the counter matches reality — a clock-skew bug or non-unique sorted-set members can corrupt counts. Correlate with limiter_redis_latency: if Redis got slow, some checks may be timing out and being counted wrong. The usual culprit is a client ignoring Retry-After and retry-storming your limiter.

How would you rate limit a GraphQL API where one query can be arbitrarily expensive?

Count-based limiting is meaningless — one query can request the entire object graph. Use query complexity analysis: statically compute a cost from the query AST before execution (each field a weight, list fields multiply by the requested/estimated page size, nesting compounds), reject queries over a max complexity outright, and deduct the computed cost from a token-bucket budget per caller. Also enforce max depth to stop deeply nested recursive queries, and require pagination limits (no unbounded lists). Optionally do post-execution reconciliation if actual cost diverged from the estimate. GitHub's GraphQL API is the canonical example — a 5000-point/hour budget where each query's cost is computed from its shape. This is cost-based token-bucket limiting applied to a variable-cost interface.
