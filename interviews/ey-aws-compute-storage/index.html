AWS: Compute & Storage EY Sheet 02

The JD names EC2, EKS, Lambda for compute and S3 for storage. Expect 6–10 questions here. The examiner is checking one thing above all: can you choose between them and defend the choice? Nobody is impressed that you know Lambda has a 15-minute timeout; they are impressed when you say why that timeout pushed you to Step Functions on a specific job.

The line that wins this section: "I pick compute by traffic shape and operational appetite. Spiky, event-driven, bursty, with idle periods → Lambda, because I pay nothing at idle and scale is free. Steady high-throughput with long-lived connections → containers on ECS/Fargate or EKS. Legacy, licensed, or needing OS-level control → EC2. The cost crossover between Lambda and always-on Fargate usually lands somewhere around 30–50% sustained utilisation."

Compute: Lambda

CertainLambda vs EC2 vs ECS/Fargate vs EKS — how do you choose?

I choose on four axes: traffic shape, runtime duration, operational surface, and cost at steady state.

  • Lambda — event-driven, spiky or low-duty-cycle work. Zero cost at idle, scales per-request automatically, no servers to patch. Costs: cold starts, 15-minute hard cap, 10 GB memory ceiling, no long-lived connections (bad for WebSockets or a chatty DB pool), and per-invocation pricing that becomes expensive under sustained high QPS.
  • ECS on Fargate — my default for steady HTTP services. Containers without managing nodes; no cold start; long-lived connections and in-process caching work normally. Less control than EC2, cheaper ops than EKS.
  • EKS — when the organisation has standardised on Kubernetes, needs portability across clouds or on-prem, or needs the K8s ecosystem (operators, service mesh, Helm-based GitOps). The cost is a real operational surface: cluster upgrades, node groups, add-on lifecycle, and an ongoing control-plane fee. I don't reach for EKS for three services.
  • EC2 — OS-level control, licensed software, GPU/specialised instances, or lift-and-shift of something that isn't containerised yet. You own patching, AMI hygiene and scaling policy.

The honest summary: if it fits Lambda, use Lambda; if it needs to be always-on, use Fargate; use EKS when the org already has it; use EC2 when you genuinely need the box.

CertainExplain a Lambda cold start. How do you reduce it?

On invoke, Lambda looks for a warm execution environment (a Firecracker microVM). If none exists it creates one: download/unpack the deployment package, boot the microVM, start the runtime, then run your module-level init code — then the handler. That whole prefix is the cold start, typically tens of milliseconds to a couple of seconds depending on runtime and package size. Node.js is one of the faster runtimes here.

Mitigations, roughly in the order I'd apply them:

  • Shrink the package — bundle and tree-shake (esbuild), don't ship the whole SDK, don't ship dev dependencies. Package size directly drives download time.
  • Move work out of the handler — but be careful which way. Initialising the SDK client and the DB connection at module scope means it happens once per environment and is reused across invocations; that's good. Doing heavy work at module scope that only some invocations need is bad.
  • Raise memory — memory and CPU are allocated together, so more memory means faster init and faster execution. Often 512 MB is cheaper per request than 128 MB because duration falls more than price rises. That's counterintuitive and worth saying out loud.
  • Provisioned concurrency — pre-initialises N environments so those invocations skip the cold start entirely. You pay for them idle, so I scale it on a schedule around known peaks rather than leaving it flat.
  • Avoid VPC-attached Lambdas unless needed — this used to add seconds. Since Hyperplane ENIs it's largely fixed, but a Lambda that doesn't need VPC resources shouldn't be in a VPC.

The framing that matters: cold starts are a tail-latency problem, not an average problem. If the SLO is on p99 and traffic is steady, cold starts may be irrelevant. I'd measure before paying for provisioned concurrency.

Depth probeReserved vs provisioned concurrency vs account concurrency.

Three different things that sound alike:

  • Account concurrency — the region-wide ceiling on simultaneous executions across all functions. Default 1,000, raisable by support ticket.
  • Reserved concurrency — carves a guaranteed slice out of that ceiling for one function and caps that function at it. Two uses: protect a critical function from being starved by a noisy neighbour, and protect a downstream (say an RDS instance with 100 connections) from being hammered by unbounded Lambda scaling. Reserved instances still cold-start.
  • Provisioned concurrency — pre-warms N environments so they're initialised and waiting. Kills cold starts; you pay whether or not they're used.

Real setups combine them: reserved concurrency to bound blast radius on the database, provisioned concurrency with scheduled scaling for the morning peak.

What breaks when a Lambda talks to RDS, and how do you fix it?

Connection exhaustion. Lambda scales to hundreds or thousands of concurrent environments; each one opens its own connection, and RDS has a hard max_connections. At scale you don't get slow — you get too many connections errors and a cascading outage.

Fixes, in order: (1) RDS Proxy, which pools and multiplexes connections on Lambda's behalf and also handles failover more gracefully than a raw connection; (2) reserved concurrency on the function to hard-cap how many environments can exist; (3) create the connection at module scope so it's reused across invocations in the same environment, and never open/close per invocation; (4) question the design — if a workload needs a big relational connection pool and steady throughput, a Fargate service with a proper pool is often the more honest answer than Lambda plus a proxy.

Lambda is timing out at 15 minutes on a batch job. What now?

15 minutes is a hard wall, so the answer is never "raise the timeout". Options: (1) Split the work — fan out with a coordinator Lambda that writes chunks to SQS and many workers that each process a chunk. (2) Step Functions — model it as a state machine with Map state for parallel iteration, which also gives you retries, error branches and visibility per step; Standard workflows run up to a year. (3) Move the compute — if it's genuinely one long CPU-bound job that can't be chunked, it belongs on ECS/Fargate as a task or on AWS Batch, not on Lambda. I'd pick based on whether the work is parallelisable (SQS fan-out), a sequence of steps (Step Functions), or indivisible and long (Fargate/Batch).

Compute: EC2, Auto Scaling & containers

CertainHow does an Auto Scaling Group keep a service healthy?

An ASG maintains a desired count across the AZs and subnets you give it, using a launch template (AMI, instance type, security groups, IAM instance profile, user-data). It replaces instances that fail health checks — either EC2 status checks (is the VM alive) or, better, ELB health checks (does the application respond on /health). That distinction matters: a process that has deadlocked still passes EC2 status checks, so if you don't wire ELB health checks to the ASG it will happily keep a hung instance in service.

Scaling policies: target tracking is the default I reach for (keep average CPU at 50%, or keep ALB requests-per-target at N) because it's self-tuning; step scaling for when you need different responses at different breach magnitudes; scheduled for known daily patterns. I also set a cooldown / warm-up so the group doesn't thrash while new instances are still booting, and I spread across at least two AZs so an AZ failure halves capacity rather than removing it.

Spot vs On-Demand vs Reserved / Savings Plans.

On-Demand — full price, no commitment, use for unpredictable or short-lived workloads and as the baseline you measure savings against. Reserved Instances / Savings Plans — commit to 1 or 3 years for roughly 40–72% off; Savings Plans are the modern choice because they're flexible across instance family and even across Lambda/Fargate (Compute Savings Plans), where classic RIs pin you harder. Spot — up to ~90% off spare capacity, but AWS can reclaim the instance with a two-minute warning.

The rule I apply: cover the steady baseline with Savings Plans, absorb the predictable peak with On-Demand, and run interruption-tolerant work on Spot — batch jobs, CI runners, stateless web tier behind a load balancer with enough diversification across instance types that a reclaim in one pool doesn't take the service down. Never put a stateful singleton on Spot.

Depth probeECS Fargate vs EKS — argue both sides for a 12-service platform.

For Fargate: no node fleet to patch or upgrade, task-level IAM roles are trivially clean, security groups attach per task, the mental model is small enough that any backend engineer can operate it. For 12 services with a normal HTTP/async shape, Fargate gets you to production faster and the ongoing ops cost is close to zero.

For EKS: if the client has already standardised on Kubernetes, fighting that is a losing battle — you'd be the one bespoke platform in the estate. EKS also wins when you need portability (multi-cloud or on-prem parity), the operator ecosystem, service mesh, or fine-grained scheduling and bin-packing that Fargate's per-task pricing makes expensive.

My actual recommendation at 12 services with no existing K8s investment is Fargate, and I'd say so plainly — but in consulting the deciding input is usually the client's existing platform team, not the service count.

Storage: S3

CertainS3 storage classes and lifecycle — how do you use them to cut cost?

Classes by access pattern: Standard (frequent), Intelligent-Tiering (unknown or changing patterns — it moves objects automatically for a small monitoring fee, and it's my default when I can't characterise access), Standard-IA / One Zone-IA (infrequent but needs fast retrieval; IA has a 30-day minimum and a per-GB retrieval charge), Glacier Instant / Flexible / Deep Archive (archival, retrieval from milliseconds to hours, Deep Archive being the cheapest and slowest).

The lever is a lifecycle policy: e.g. logs go Standard → IA at 30 days → Glacier Flexible at 90 → expire at 400. Two gotchas I'd mention: IA and Glacier have minimum storage durations, so transitioning millions of tiny short-lived objects costs more than leaving them in Standard; and there's a per-object transition request charge, so lifecycle rules on huge numbers of small objects need a size filter. Also: enable a lifecycle rule to abort incomplete multipart uploads — orphaned parts are invisible in the console but billed, and they're one of the most common silent S3 costs.

How do you let a browser upload a 2 GB file to S3 without proxying it through your API?

Pre-signed URLs, and for 2 GB specifically, pre-signed multipart upload. Flow: the client calls my API; the API authenticates and authorises the user, then calls CreateMultipartUpload and returns pre-signed URLs for each part; the browser PUTs parts directly to S3 in parallel; the client tells my API it's done and the API calls CompleteMultipartUpload. The file never touches my compute, so I'm not paying for the bandwidth twice or holding a Lambda open for the duration.

Controls I'd put on it: short expiry on the URLs (minutes), a content-length range condition so someone can't upload 500 GB with a URL minted for 2 GB, server-side encryption enforced by bucket policy, upload into a quarantine prefix and only move to the served prefix after validation, and a lifecycle rule to abort incomplete multipart uploads after 7 days. Post-processing is triggered by an S3 event → SQS → worker, not synchronously.

Depth probeIs S3 strongly consistent? What was the old failure mode?

Yes — since December 2020 S3 provides strong read-after-write consistency for all operations: a GET or LIST after a successful PUT or DELETE always reflects the latest state, at no extra cost and no latency penalty. Before that, new-object PUTs were read-after-write consistent but overwrites and deletes were eventually consistent, which produced the classic bugs: a GET right after an overwrite returning stale bytes, or a LIST not yet showing a just-written key. Teams worked around it with retry loops and DynamoDB-based index tables.

What's still not true: there are no multi-object atomic operations. If two writers overwrite the same key concurrently, it's last-writer-wins — you need conditional writes (If-Match on ETag) or an external lock/DB if you care. And S3 is object storage, not a filesystem: no partial in-place updates, no rename (a rename is a copy plus a delete).

How do you secure an S3 bucket properly?

Layered, and I'd list them as layers because that's what "defence in depth" actually means here:

  • Block Public Access on at account level and bucket level unless the bucket is genuinely a public website. This alone prevents the most common breach.
  • Bucket policy + IAM — least privilege, scoped to prefixes, not s3:* on *. Access is the intersection of the identity policy and the resource policy.
  • Encryption — SSE-S3 by default, SSE-KMS when you need key-level audit trails and separate key permissions (note the KMS request cost at high volume, and use bucket keys to cut it). Deny unencrypted PUTs via bucket policy.
  • Enforce TLS — bucket policy denying requests where aws:SecureTransport is false.
  • Versioning + MFA delete / Object Lock for anything that ransomware or a bad script could wipe.
  • VPC gateway endpoint so traffic from private subnets reaches S3 without traversing a NAT Gateway — this is a security and a cost win.
  • Access logging / CloudTrail data events so you can answer "who read this" after an incident. Plus IAM Access Analyzer to catch buckets exposed cross-account.
EBS vs EFS vs S3 vs instance store — one line each and when each wins.

S3 — object storage over HTTP, effectively infinite, 11 nines durability, cheap. For files, backups, static assets, data lake. Not a filesystem; no partial writes.

EBS — network-attached block device for one instance (multi-attach exists but is niche), persists independently of the instance, snapshot-able, replicated within a single AZ. For OS volumes and single-node databases. gp3 lets you provision IOPS and throughput independently of size, which is usually cheaper than over-sizing a gp2 volume to get IOPS.

EFS — managed NFS, POSIX semantics, shared by many instances across AZs, elastic. For shared content and lift-and-shift apps that expect a shared filesystem. Higher latency and much higher cost per GB than EBS or S3, so it's the answer when you truly need shared POSIX, not a default.

Instance store — physically attached NVMe on the host. Fastest by a distance, and ephemeral — gone on stop or host failure. For scratch, caches, shuffle spill, or distributed databases that replicate durability at the cluster layer.
