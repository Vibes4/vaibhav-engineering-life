Rate Limiter — Requirements Exercise

Design brief: Design a service that limits how many requests a client can make to an API within a given time window.

Functional Requirements

  • The system must reject or throttle requests from a client once a configured request quota for a time window is exceeded.
  • Operators can define limits per API key, per user, and per client IP address.
  • Operators can configure different limits for different API endpoints or route groups.
  • The system must return a clear response indicating a request was rate-limited, distinct from other errors.
  • Responses must communicate the remaining quota, the applicable limit, and when the quota resets.
  • Operators can configure limits with different granularities (per second, per minute, per hour, per day).
  • The system must allow limit rules to be updated at runtime without restarting dependent services.
  • The system must support tiered limits so that premium clients receive higher quotas than free clients.
  • Operators can define burst allowances above the steady-state rate for short spikes.
  • The system must be usable by multiple independent services sharing the same limiting infrastructure.
  • Operators can view metrics on how often clients are being throttled.

Non-Functional Requirements

  • The rate-limit decision must add no more than 5 ms of latency per request (p99).
  • The system must handle 1 million rate-limit checks per second across the fleet.
  • Availability target of 99.99%; the limiter must not become a single point of failure for the APIs it protects.
  • Limit counters must be accurate enough that clients are not throttled significantly below or above their configured quota.
  • Limits must be enforced consistently across many distributed API server instances.
  • The system must degrade gracefully: if the limiter is unavailable, a configurable fail-open or fail-closed policy applies.
  • Memory and storage footprint per tracked client must remain small enough to track millions of clients cost-effectively.
  • Configuration changes to limits should take effect within seconds across the fleet.

Assumptions & Out of Scope

  • Assume clients are already authenticated and carry an identifiable API key or user identity.
  • Billing and monetization of quota tiers are out of scope.
  • Assume the limiter runs alongside existing API gateways or services rather than as the primary auth layer.
  • DDoS mitigation at the network layer is excluded; this focuses on application-level request limiting.
