Networking Mastery

The wire underneath every distributed system: how bytes cross the planet through TCP, TLS, HTTP, DNS and load balancers, and where the milliseconds and the outages actually come from.

Interview Explanation — 30 seconds

Say this: "Networking is the layered stack that moves a request from a client to a server and back. IP routes packets, TCP turns them into a reliable ordered byte stream with a 3-way handshake plus flow and congestion control, TLS encrypts that stream and proves server identity via certificates, and HTTP frames the actual request. DNS resolves the name to an IP first, and a load balancer picks the backend. My mental model when debugging is: name resolution → TCP connect → TLS handshake → HTTP round trip, and I know which metric and which tool to reach for at each layer."

Interview Explanation — 2 minutes

The OSI model has seven layers but in practice you reason with the four-layer TCP/IP model: Link (Ethernet/Wi-Fi), Internet (IP, routing, BGP), Transport (TCP/UDP), and Application (HTTP, DNS, TLS as a shim between transport and app).

  • TCP gives a reliable, ordered, byte-stream connection. It opens with SYN → SYN-ACK → ACK (1 RTT before data), tracks bytes with 32-bit sequence numbers, does flow control with a receiver-advertised window, and congestion control with a sender-side congestion window that grows via slow start then AIMD (or CUBIC/BBR).
  • TLS layers on top: an asymmetric handshake (certificate + key exchange) establishes a symmetric session key, then all data is AES-GCM or ChaCha20. TLS 1.3 cut the handshake to 1 RTT and added 0-RTT resumption. The cert chain roots in a trusted CA; SNI tells the server which cert to present; ALPN negotiates HTTP/2 vs HTTP/1.1.
  • HTTP evolved to kill head-of-line blocking: 1.1 has one request in flight per connection (keep-alive reuses the socket), HTTP/2 multiplexes many streams over one TCP connection with HPACK header compression, HTTP/3 moves to QUIC over UDP to remove TCP-level HOL blocking entirely.
  • DNS resolves names via recursive resolvers hitting authoritative servers; records (A/AAAA/CNAME/SRV/TXT) are cached by TTL; anycast + GSLB give geographic routing and failover.
  • Load balancing is L4 (transport, fast, connection-level) or L7 (HTTP-aware, routing/retries/TLS termination), with algorithms like round-robin, least-connections, and consistent hashing, plus health checks and connection draining.

The unifying constraint is the latency budget: one cross-continent RTT is ~80-150 ms, and every handshake round trip multiplies it, which is why we pool connections, resume TLS, and push content to CDN edges.

Internal Working

TCP connection lifecycle

  1. Resolve: app calls getaddrinfo(); DNS returns an IP.
  2. Connect (3-way handshake): client sends SYN with initial sequence number (ISN, randomized to prevent spoofing) and its receive window + options (MSS, window scale, SACK-permitted, timestamps). Server replies SYN-ACK with its own ISN. Client sends ACK. Connection is ESTABLISHED after 1 RTT.
  3. Data transfer: each segment carries a sequence number = byte offset; receiver ACKs the next expected byte (cumulative ACK), with SACK filling holes. The kernel maintains send and receive socket buffers.
  4. Flow control: receiver advertises rwnd (bytes it can buffer). Sender never has more than min(rwnd, cwnd) unacked bytes in flight. A stalled reader shrinks rwnd to 0 (zero-window), sender probes with window updates.
  5. Congestion control: sender keeps cwnd. Slow start doubles cwnd each RTT until ssthresh; then congestion avoidance (AIMD) grows by ~1 MSS/RTT. On loss (3 dup ACKs) it halves cwnd (fast recovery); on timeout (RTO) it drops to 1 and restarts slow start. CUBIC uses a cubic growth curve for high bandwidth-delay networks; BBR models bottleneck bandwidth + RTT instead of reacting to loss.
  6. Teardown: FIN/ACK each direction. The active closer enters TIME_WAIT for 2×MSL (~60 s on Linux) to absorb stray retransmits — this is what causes port exhaustion under high connection churn.

TLS 1.3 handshake internals

  1. Client sends ClientHello with supported cipher suites, a key share (X25519 ephemeral public key), SNI, and ALPN list.
  2. Server replies ServerHello with its key share, certificate, and a Finished — both sides now derive the shared secret via ECDHE and switch to symmetric encryption. Data flows after 1 RTT.
  3. On resumption, a PSK ticket from a prior session enables 0-RTT: client sends early data with the first flight (at the cost of replay risk for that data).

Why was this built?

Before packet switching, telecom used circuit switching — a dedicated physical path per call, wasteful and fragile. ARPANET introduced packet switching so links could be shared and routed around failures. TCP/IP (1974, Cerf & Kahn) split concerns: IP does best-effort routing, TCP adds reliability on top, so the network core stays dumb and the endpoints stay smart (the end-to-end principle).

  • Before DNS (1983): a single HOSTS.TXT file distributed by SRI — didn't scale past a few thousand hosts.
  • Before TLS: plaintext HTTP; anyone on-path could read/modify. SSL (Netscape, 1994) → TLS 1.0 (1999) → 1.3 (2018).
  • Before HTTP/2: HTTP/1.1 needed 6+ parallel TCP connections per origin to hide HOL blocking; SPDY/HTTP/2 fixed it with multiplexing.

Advantages

  • Layering: each layer is independently upgradable — you can swap CUBIC for BBR without touching apps.
  • Reliability without app effort: TCP hides loss, reordering, duplication.
  • Security is now default: TLS 1.3 + modern ciphers give forward secrecy; a stolen server key can't decrypt captured past traffic.
  • Multiplexing: HTTP/2/3 amortize one handshake across hundreds of streams.
  • Global scale: DNS + anycast + CDN move content within ~10-30 ms of most users.

Drawbacks

  • Handshake tax: TCP + TLS = 2-3 RTTs before first byte; brutal on high-latency links.
  • Head-of-line blocking: one lost TCP segment stalls all HTTP/2 streams on that connection.
  • TIME_WAIT / port exhaustion: ~64K ephemeral ports per source IP:dest tuple; connection churn starves them.
  • DNS caching lag: TTL means failover and config changes propagate slowly and unevenly.
  • Opaqueness: TLS encryption hides payloads from middleboxes, complicating debugging and DPI.

Trade-offs

  • Latency vs reliability: TCP retransmits guarantee delivery but add tail latency; UDP drops the guarantee for speed.
  • Throughput vs fairness: BBR grabs more bandwidth and can starve CUBIC flows sharing a bottleneck.
  • Security vs performance: mutual TLS adds a client-cert round trip and CPU; 0-RTT adds a replay-attack surface.
  • Nagle vs delayed ACK: Nagle coalesces small writes to save packets but combined with delayed ACK can add ~40 ms stalls — disable with TCP_NODELAY for request/response protocols.
  • DNS TTL: low TTL = fast failover but more query load and resolver cost; high TTL = cheap but slow to change.
  • TLS termination location: terminate at edge = simpler certs + cheaper backends but plaintext inside the mesh; end-to-end mTLS = zero-trust but more CPU and cert management.

When NOT to use it

Watch out: Don't reach for TCP when microsecond tail latency matters and you can tolerate loss — real-time media, telemetry, and multiplayer games belong on UDP/QUIC. Don't put an L7 load balancer in front of a pure bulk-throughput or non-HTTP workload — you pay TLS-termination CPU and parsing latency for routing features you don't use; use L4/DSR. Don't rely on DNS TTL for fast failover (clients and resolvers ignore low TTLs) — use anycast/health-checked VIPs. Don't enable HTTP/2 for large uploads over lossy links where a single loss stalls every stream — HTTP/3 or parallel HTTP/1.1 connections can beat it.

Production Architecture

A typical global request path: the client resolves an anycast DNS name to the nearest edge PoP, TLS terminates at the CDN/edge, and requests fan into an L7 load balancer that routes to a health-checked backend pool, with an L4 layer for raw ingress.

flowchart LR
  U["User"] --> DNS["Anycast DNS GSLB"]
  DNS --> EDGE["CDN edge PoP TLS 1.3"]
  EDGE -->|cache miss| L4["L4 LB ingress"]
  L4 --> L7["L7 LB routing and retries"]
  L7 --> B1["Backend pod A"]
  L7 --> B2["Backend pod B"]
  L7 --> B3["Backend pod C"]
  B1 --> DB["Primary datastore"]

The edge absorbs TLS handshakes and caches static assets; the L4 layer gives fast, protocol-agnostic ingress and DDoS scrubbing; the L7 layer does path/host routing, per-route retries, circuit breaking, and connection draining on deploy. Health checks at both LB layers eject unhealthy pods within seconds.

Production Problems

  • Ephemeral port exhaustion on a service making many short-lived outbound calls — TIME_WAIT piles up; fix with connection pooling / keep-alive and SO_REUSEADDR.
  • Retry storms: an L7 LB retrying failed requests amplifies load during a partial outage (metastable failure).
  • TLS cert expiry: the classic 3 AM page — a leaf or intermediate expires and every client fails handshake.
  • MTU/PMTU black holes: an ICMP-filtering middlebox drops "fragmentation needed", so large packets vanish and connections hang after the handshake.
  • DNS TTL stampede: TTL expires simultaneously across many clients, spiking authoritative query load.
  • Nagle + delayed-ACK 40 ms stalls in chatty RPC over TCP.
  • Slow-start on new connections: cold connections underperform; connection reuse and pacing matter.

Scaling

Networking scales horizontally: add PoPs (anycast pulls users to the nearest), shard traffic across LB pools, and use consistent hashing so stateful backends remap minimally when the fleet changes.

flowchart TD
  C["Clients worldwide"] --> A["Anycast VIP"]
  A --> P1["PoP US East"]
  A --> P2["PoP EU West"]
  A --> P3["PoP AP South"]
  P1 --> H1["Consistent hash ring"]
  H1 --> N1["Node 1"]
  H1 --> N2["Node 2"]
  H1 --> N3["Node 3"]
  • Vertical limits: a single L7 proxy saturates on TLS handshakes (CPU) or connection count (memory/fds) — tune somaxconn, file descriptor limits, and offload TLS to hardware/NIC.
  • Horizontal: DSR (direct server return) and Maglev-style consistent hashing let L4 LBs scale to millions of connections; ECMP spreads flows across LB instances at the router.
  • Bandwidth-delay product: to fill a 1 Gbps link at 100 ms RTT you need ~12.5 MB of in-flight data — enable window scaling and large socket buffers or throughput caps at the window size.

Security

  • Encryption in transit: TLS 1.3 only, disable TLS 1.0/1.1, prefer AEAD ciphers (AES-GCM, ChaCha20-Poly1305) with ECDHE for forward secrecy.
  • Identity: server certs chain to a trusted CA; validate hostname (SNI), expiry, revocation (OCSP stapling). mTLS for service-to-service zero-trust — both sides present certs.
  • Network isolation: private subnets, security groups/NACLs, no public IPs on backends; egress via NAT gateway only.
  • Common attacks: SYN flood (mitigate with SYN cookies), amplification/reflection (UDP DNS/NTP — rate-limit, BCP38 anti-spoofing), MITM/downgrade (HSTS, disable renegotiation), DNS cache poisoning (DNSSEC, random source ports/query IDs), 0-RTT replay (only for idempotent requests).
  • DDoS: anycast disperses volumetric attacks across PoPs; scrubbing centers filter L3/L4; WAF handles L7.

Performance

  • Latency floor: ~1 ms per 100 km one-way (speed of light in fiber ~200,000 km/s). US↔EU ≈ 70-90 ms RTT; can't beat physics — put compute near users.
  • Handshake cost: TCP=1 RTT, TLS 1.2=2 RTT, TLS 1.3=1 RTT, 0-RTT=0. Every avoided round trip saves one RTT of first-byte latency.
  • Bottlenecks: TLS handshakes (CPU-bound, ~thousands/core/s), connection setup (pool it), slow start (reuse connections), congestion window (BBR beats CUBIC on lossy long-fat networks).
  • Tuning: TCP_NODELAY for RPC, keep-alive + connection pools, HTTP/2 to multiplex, net.ipv4.tcp_tw_reuse, increase net.core.somaxconn and tcp_max_syn_backlog, enable window scaling, tune tcp_rmem/wmem, enable TLS session resumption + OCSP stapling.

Common Mistakes

  • New TCP connection per request → handshake + slow start every time. Fix: keep-alive and connection pooling.
  • Ignoring TIME_WAIT on the client side → port exhaustion. Fix: pool connections; the server (passive close) shouldn't be the one accumulating TIME_WAIT.
  • Leaving Nagle on for small request/response → 40 ms delayed-ACK stalls. Fix: TCP_NODELAY.
  • Relying on low DNS TTL for failover → clients cache anyway. Fix: anycast / health-checked VIP.
  • Terminating TLS but not re-encrypting internally in a "zero-trust" claim → plaintext east-west traffic. Fix: mTLS in the mesh.
  • Unbounded retries at the LB → retry storm. Fix: retry budgets, jittered backoff, circuit breakers.
  • Forgetting cert-chain intermediates → works in browser (which caches intermediates) but fails for API clients. Fix: serve the full chain.

🎯 Deep-dive Q&A — model answers

Why are TCP initial sequence numbers randomized?

If ISNs were predictable, an off-path attacker could forge segments with valid sequence numbers to inject data or reset connections (blind spoofing/RST attacks). RFC 6528 specifies deriving the ISN from a per-connection hash of the 4-tuple plus a secret and a clock, so ISNs are unpredictable to outsiders but still monotonically increasing enough to avoid wrapping ambiguity with old segments (PAWS uses timestamps for that).

Explain exactly how cwnd, ssthresh, and rwnd interact to bound in-flight data.

The sender may have at most min(cwnd, rwnd) unacknowledged bytes outstanding. rwnd is set by the receiver's advertised window (flow control). cwnd is the sender's estimate of network capacity. In slow start cwnd grows exponentially (≈ doubling per RTT) until it reaches ssthresh, then congestion avoidance grows it ~1 MSS per RTT (AIMD additive increase). On 3 duplicate ACKs, ssthresh = cwnd/2 and cwnd = ssthresh (fast recovery, multiplicative decrease). On RTO timeout, ssthresh = cwnd/2 but cwnd resets to 1 MSS and slow start restarts. The receiver never overflows because rwnd caps everything.

How does BBR differ fundamentally from loss-based congestion control?

Loss-based algorithms (Reno, CUBIC) treat packet loss as the congestion signal and back off on it — but on modern networks loss often comes from bufferbloat or wireless noise, not true congestion, so they either underutilize or fill buffers. BBR instead continuously estimates the bottleneck bandwidth (max delivery rate) and the minimum RTT (propagation delay), and paces sending at bandwidth×RTT — the actual bandwidth-delay product — keeping buffers nearly empty. This gives high throughput with low latency on long-fat and lossy links. The downside is unfairness: BBR can crowd out CUBIC flows at a shared bottleneck because it doesn't yield on loss.

Walk through why TLS 1.3 is 1-RTT while 1.2 was 2-RTT.

In TLS 1.2 the client sends ClientHello, the server responds with ServerHello + certificate + ServerKeyExchange + ServerHelloDone (RTT 1), then the client sends ClientKeyExchange + ChangeCipherSpec + Finished, and only after the server's Finished (RTT 2) can application data flow. TLS 1.3 removes the negotiation round trip by having the client speculatively include its ECDHE key share in the ClientHello for the groups it supports. The server picks one, sends its key share + encrypted cert + Finished in the ServerHello flight, and both sides can derive the handshake secret — so application data flows after 1 RTT. Resumption via PSK enables 0-RTT early data.

Why is symmetric encryption used for the bulk of a TLS session if asymmetric is "more secure"?

Asymmetric (public-key) crypto like RSA/ECDHE is ~100-1000x slower than symmetric AES and unsuitable for encrypting megabytes of data. So TLS uses asymmetric operations only during the handshake to authenticate the server and securely agree on a shared secret (via ECDHE), then derives a symmetric session key (AES-GCM/ChaCha20) for all bulk data. This is the hybrid cryptosystem: asymmetric for key establishment and authentication, symmetric for throughput. Forward secrecy comes from using ephemeral DH keys that are discarded after the session.

Precisely, what causes HTTP/2 head-of-line blocking and how does HTTP/3 fix it?

HTTP/2 multiplexes many logical streams over a single TCP connection. TCP delivers a strictly ordered byte stream, so if one segment is lost, the kernel holds back all subsequently received bytes — including those belonging to other HTTP/2 streams — until the retransmit arrives. So HTTP/2 solved application-layer HOL blocking but not transport-layer. HTTP/3 runs over QUIC (on UDP), which implements independent streams: loss on one stream only stalls that stream, others deliver immediately. QUIC also integrates TLS 1.3 into the transport handshake (1-RTT or 0-RTT) and supports connection migration across IP changes via connection IDs.

Explain the full chain-of-trust validation a client performs on a server cert.

The server presents its leaf cert plus intermediates. The client: (1) builds a chain from the leaf up to a root in its local trust store, verifying each cert's signature was made by the next cert's private key; (2) checks each cert's validity period (notBefore/notAfter); (3) checks the leaf's Subject Alternative Name matches the hostname (SNI); (4) checks key usage/extended key usage (serverAuth); (5) checks revocation via CRL or OCSP (ideally stapled). If any link fails — expired intermediate, missing chain, hostname mismatch, untrusted root — the handshake aborts. Browsers cache intermediates so they can succeed where a bare API client fails, which is why you must serve the full chain.

How does anycast actually route a user to the nearest PoP, and how is failover instant?

The same IP prefix is announced from multiple physical locations via BGP. Internet routers select the best path to that prefix using BGP attributes (AS-path length, local pref), which usually maps to the topologically nearest PoP. Packets to that IP land at whichever PoP the routing fabric prefers. For failover, a PoP simply withdraws its BGP announcement (or health-check automation does), and routers reconverge to the next-best PoP within seconds — no DNS change and no client TTL involved. It also disperses DDoS: attack traffic is absorbed across all PoPs rather than concentrated.

Consistent hashing: why K/N keys move and how do virtual nodes help?

Nodes and keys are hashed onto a ring; a key is served by the next node clockwise. When a node is added or removed, only the keys between it and its predecessor remap — approximately K/N keys for N nodes — versus a plain modulo hash where changing N remaps nearly everything. The problem is uneven distribution and load imbalance when a node leaves (its whole range dumps onto one neighbor). Virtual nodes fix this: each physical node is placed at many points on the ring, so its key range is spread across the ring and remapping is smooth. Used in Dynamo, Cassandra, Maglev, and memcached clients.

What is the bandwidth-delay product and why does it cap single-flow throughput?

BDP = bandwidth × RTT = the amount of data that can be "in flight" on the link at once. To fully utilize a link, the sender must have at least BDP bytes unacknowledged, which is bounded by the TCP window (min of cwnd and rwnd). If the window is smaller than BDP, the sender stalls waiting for ACKs and can't fill the pipe. Example: 1 Gbps × 100 ms = 12.5 MB — you need a 12.5 MB window. The classic 64 KB window (without scaling) caps you at ~5 Mbps on that path. Fix: TCP window scaling (RFC 1323) and large socket buffers (tcp_rmem/tcp_wmem).

Why does TIME_WAIT live on the active closer, and how does it cause port exhaustion?

The endpoint that sends the first FIN (active close) enters TIME_WAIT for 2×MSL (~60 s on Linux) after the connection closes. This ensures (a) delayed/duplicate segments from this connection expire before the same 4-tuple could be reused, and (b) if the final ACK is lost, the peer's retransmitted FIN can still be answered. Each TIME_WAIT socket holds its 4-tuple. A client opening many short-lived connections to the same server IP:port burns through the ~28K default ephemeral port range quickly, causing "cannot assign requested address". Fixes: connection pooling/keep-alive (best), tcp_tw_reuse (safe with timestamps for outbound), widen ip_local_port_range, or make the server the active closer.

L4 vs L7 load balancer — what can each see and do?

An L4 LB operates on IP:port and TCP/UDP — it forwards or NATs connections without looking at payload, so it's fast, protocol-agnostic, and can do Direct Server Return (response bypasses the LB). It can't route by URL or terminate TLS. An L7 LB terminates the connection, parses HTTP (and usually TLS), so it can route by host/path/header, do retries, rewrites, sticky sessions, rate limiting, and observability — at the cost of TLS-termination CPU and added latency, and it must handle both client-side and backend-side connections. Common pattern: L4 for ingress/DDoS/throughput, L7 behind it for smart routing.

How do SYN cookies defend against SYN floods without breaking legitimate connections?

Normally a SYN allocates a half-open connection entry in the SYN backlog; a flood of spoofed SYNs fills it and drops real clients. With SYN cookies, when the backlog is full the server does not allocate state — it encodes the connection parameters (MSS, timestamp, a hash of the 4-tuple + secret) into the ISN it puts in the SYN-ACK. If a real client responds with the ACK, that ACK carries seq = cookie+1, so the server reconstructs and validates the state from the cookie alone and builds the connection then. Spoofed SYNs never complete, so they cost nothing. The trade-off is that some TCP options can't be preserved, so it's used only under attack.

How does OCSP stapling improve on plain OCSP?

Plain OCSP requires the client to contact the CA's OCSP responder to check whether a cert is revoked, which adds latency, leaks browsing to the CA, and fails open if the responder is down (soft-fail = weak security). OCSP stapling has the server periodically fetch a signed, time-stamped OCSP response from the CA and "staple" it into the TLS handshake. The client gets revocation proof without a separate round trip, the CA doesn't see the client, and it scales because thousands of clients reuse one stapled response. OCSP Must-Staple in the cert forces the server to staple, closing the soft-fail gap.

How does connection draining work during a zero-downtime deploy?

When a backend is marked for removal, the LB stops sending it new connections but lets in-flight requests complete up to a drain timeout. In Kubernetes: the pod gets marked NotReady (removed from Service endpoints), receives SIGTERM, and a preStop hook plus terminationGracePeriodSeconds gives it time to finish active requests before SIGKILL. The app should stop accepting new work, finish outstanding requests, and close keep-alive connections with a Connection: close. Combined with a readiness probe gating pool entry on the new pods, you get overlap with no dropped requests. The drain timeout must exceed the longest expected request.

Why can 0-RTT data be replayed, and what's the correct mitigation?

0-RTT early data is sent with the first flight using a pre-shared key from a prior session, before the server has proven liveness for this specific handshake. An attacker who captures that encrypted early-data packet can resend it, and the server may process it again — because there's no fresh server nonce in the exchange yet to bind it to a single handshake. Mitigation: only allow 0-RTT for idempotent, safe requests (GET without side effects); implement anti-replay windows / single-use session tickets at the server; and never expose non-idempotent operations (payments, writes) to early data. Many stacks disable 0-RTT for anything but idempotent GETs by default.
