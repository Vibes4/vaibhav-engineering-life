JSX & Rendering React

JSX is not HTML and not a template language — it is syntax sugar for a function call. A build step (Babel, SWC, TypeScript, esbuild) rewrites every tag into a call that returns a plain, immutable JavaScript object describing what should be on screen. React reads those objects; the browser never sees JSX.

Almost every JSX confusion — why class is className, why {0 && ...} prints a zero, why keys exist — dissolves once you can see the object the tag compiles to.

What JSX compiles to

The classic transform produced React.createElement, which is why React had to be in scope in every file:

<button className="primary" onClick={save}>Save</button>

// classic transform
React.createElement('button', { className: 'primary', onClick: save }, 'Save');

Since React 17 the automatic runtime is the default. The compiler injects an import for you, so no import React is needed just for JSX:

import { jsx as _jsx } from 'react/jsx-runtime';
_jsx('button', { className: 'primary', onClick: save, children: 'Save' });

Note the shape difference: in the automatic runtime children is a normal prop, and key is passed separately (_jsx(type, props, key)) because it is metadata for the reconciler, not data for the component.

Lowercase tags become strings ('button' → a host element); capitalised tags become a reference to the function itself (Button → the component). That is why components must be capitalised — a lowercase <button /> would be sent to the DOM as an unknown tag.

Note: Because JSX is just expressions, <A /> is a value. You can store it in a variable, put it in an array, return it from a ternary, or pass it as a prop — that last one is the whole basis of the slots pattern.

Elements are descriptions, not DOM nodes

A React element is roughly this frozen object:

{
  $$typeof: Symbol(react.element),   // guards against JSON-injection XSS
  type: 'button',                    // string = host tag, function = component
  key: null,
  props: { className: 'primary', children: 'Save' },
  ref: null
}

Creating one is cheap and does nothing: no DOM is touched, no component function is called. React calls the component later, during render, and reconciles the result. Keep three words distinct:

TermWhat it is
ComponentThe function itself: function Button(props) { ... }
ElementA description of one usage: <Button label="Save" /> → a plain object
InstanceThe mounted fiber React keeps in the tree, holding state, hooks and DOM refs. You never touch it in function components.
Gotcha: Elements are immutable. You cannot mutate element.props to change a rendered UI — you describe a new element instead. (React.cloneElement exists for the rare case of injecting props into children, and is a smell in most new code.)

Conditional rendering, and the 0 bug

{isLoggedIn ? <Dashboard /> : <Login />}      {/* either/or */}
{error && <Banner text={error} />}            {/* render or nothing */}
if (!user) return null;                        {/* early return, cleanest for whole-component cases */}

React renders null, undefined, true and false as nothing. It renders numbers and strings as text. Those two rules collide in the most famous JSX bug:

// ❌ when items is empty, `items.length` is 0 — a NUMBER, not false.
// `0 && x` evaluates to 0, and React happily prints "0" on the page.
{items.length && <List items={items} />}

// ✅ coerce to a real boolean, or use a ternary
{items.length > 0 && <List items={items} />}
{items.length ? <List items={items} /> : null}
Gotcha: The same trap bites with empty strings in some engines and with NaN. Rule of thumb: the left side of && in JSX must be a boolean, never a length, count or id.

Lists and the meaning of key

You render a list by mapping data to elements. key is not a prop the component receives — it is a hint to the reconciler about identity across renders:

{todos.map(todo => <TodoRow key={todo.id} todo={todo} />)}

Without keys React matches children by position. With keys it matches by key, so a reordered or spliced list moves existing instances instead of rewriting their contents.

Why the array index is usually wrong

The state React preserves lives on the instance, matched by key. With key={index}, deleting the first row does not delete an instance — every row shifts up one key, so React thinks row 0's props changed and keeps row 0's local state:

// rows: [{id:'a'}, {id:'b'}, {id:'c'}], each with its own <input> text
// user types "hello" into row a, then deletes row a

key={index}  → keys 0,1,2 become 0,1. React reuses instance#0 for b.
               b now shows "hello" — a's DOM state attached to the wrong row.
key={id}     → keys a,b,c become b,c. React UNMOUNTS a and moves b, c.
               State follows the data. Correct.
  • Keys must be stable (same item ⇒ same key across renders), unique among siblings (not globally), and derived from the data, not the render.
  • Never use Math.random() or Date.now() — a new key every render remounts everything, destroying state, focus and DOM.
  • The index is acceptable when the list is static, never reordered, never filtered, and its items hold no state or DOM focus.
  • To force a remount deliberately, change the key: <Form key={userId} /> resets all its state when the user changes.
Senior tip: "Keys tell React which item is which; the index tells React which slot is which. They only agree while the list never changes shape." Run index.js in this folder to see the wrong-row state migration printed as patch operations.

Fragments, whitespace and text rules

A component returns one node. <>...</> (shorthand for <React.Fragment>) groups children without adding a wrapper div — essential inside flex/grid layouts, tables and lists where a stray element breaks CSS or HTML validity.

// the shorthand cannot take a key; use the long form inside a map
{rows.map(r => (
  <React.Fragment key={r.id}>
    <dt>{r.term}</dt>
    <dd>{r.def}</dd>
  </React.Fragment>
))}
  • Rendered: strings, numbers, arrays of elements.
  • Rendered as nothing: null, undefined, true, false, empty arrays.
  • Throws: a plain object as a child ("Objects are not valid as a React child") — the usual cause is forgetting .name, or accidentally rendering a Promise.
  • Whitespace: JSX trims leading/trailing whitespace on a line and collapses blank lines. To force a space between two elements use {' '} or &nbsp;.

Escaping and dangerouslySetInnerHTML

React escapes every string it renders before inserting it, so {'<img src=x onerror=alert(1)>'} shows up as visible text, never as markup. That default is why XSS is rare in React apps.

The one deliberate hole is verbose on purpose:

<div dangerouslySetInnerHTML={{ __html: userHtml }} />
  • It bypasses escaping entirely — any <script>, onerror or javascript: URL in userHtml executes with your origin's privileges.
  • Only ever pass HTML you sanitised server-side or with DOMPurify, and only when you truly need rich text (a CMS body, sanitised markdown).
  • Children and dangerouslySetInnerHTML are mutually exclusive on the same element.
Gotcha: Escaping is not React's only XSS surface. <a href={userUrl}> still allows javascript: (React 16+ warns, but validate the protocol yourself), and spreading unvalidated objects into props can inject event handlers. $$typeof being a Symbol is what stops server JSON from being mistaken for an element.

🎯 Interview questions

What does JSX compile to, and what changed in React 17?

Each tag becomes a function call returning a plain object. Classically React.createElement(type, props, ...children), which required React in scope. The automatic runtime introduced in 17 compiles to _jsx(type, props, key) imported from react/jsx-runtime, with children as a normal prop, so the import is no longer needed.

Difference between an element, a component and an instance?

The component is the function. An element is an immutable plain object describing one usage of it ({type, props, key}) — creating it does nothing. The instance is the mounted fiber React keeps internally, holding hook state and DOM references.

Why does {items.length && <List />} print a 0?

&& returns its left operand when falsy, so an empty array yields the number 0. React renders false/null/undefined as nothing but renders numbers as text. Use items.length > 0 && ... or a ternary.

What is key for, and why not the array index?

It gives each child a stable identity so the reconciler can match elements across renders by identity instead of position, moving instances rather than rewriting them. With an index key, inserting or deleting shifts every subsequent key, so React reuses the wrong instance and its state, focus and DOM stay with the wrong row.

Does key arrive as a prop?

No. It is stripped by React and consumed by the reconciler (in the automatic runtime it is a separate argument to _jsx). If a child needs the id, pass it again explicitly as its own prop.

When are Fragments required?

Whenever you need to return multiple siblings without a wrapper element: table rows inside a tbody, dt/dd pairs, and direct children of a flex or grid container where an extra div would break layout. Use the long <React.Fragment key=...> form inside a map, since <> takes no key.

How does React protect against XSS, and how do you defeat it?

Every rendered string is escaped, so injected markup becomes text; the $$typeof Symbol on elements also prevents raw JSON from being treated as an element. You defeat it with dangerouslySetInnerHTML, which must only receive sanitised HTML (DOMPurify or server-side sanitisation), and by putting unvalidated user URLs into href/src.
