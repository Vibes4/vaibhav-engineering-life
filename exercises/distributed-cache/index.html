Distributed Cache — Requirements Exercise

Design brief: Design a distributed in-memory caching service that application clients use to store and retrieve key-value data across many nodes.

Functional Requirements

  • Clients can set, get, and delete values by key.
  • The system must support per-key time-to-live (TTL) with automatic expiration.
  • Clients can set a value conditionally (e.g. only if absent) to support simple coordination.
  • The system must support atomic increment and decrement operations on numeric values.
  • The system must distribute keys across many nodes so total capacity exceeds a single machine.
  • The system must automatically rebalance keys when nodes are added or removed.
  • The system must apply an eviction policy when memory is full.
  • Clients can batch multiple get or set operations in a single request.
  • The system must expose operational metrics such as hit ratio, latency, and memory usage.
  • The system must support optional replication of keys for read scaling and failover.
  • Administrators can flush a namespace or the entire cache.

Non-Functional Requirements

  • Serve 10M+ operations per second across the cluster at peak.
  • Read and write latency must be under 1 ms at p99 within a data center.
  • The cluster must scale horizontally to hundreds of nodes and tens of terabytes of aggregate memory.
  • Availability target of 99.99%; loss of any single node must not take down the service.
  • Cached data is treated as non-durable and best-effort; loss on restart is acceptable.
  • Values may be eventually consistent across replicas; bounded staleness is acceptable.
  • Adding or removing a node must move only a small fraction of keys to limit disruption.
  • Access must be restricted to authorized services within the network, with optional encryption in transit.
  • Memory overhead per entry should be minimal to maximize effective cache capacity per dollar.

Assumptions & Out of Scope

  • Assume the cache is a look-aside cache; the source of truth lives in backing databases owned by callers.
  • Assume clients are trusted internal services within a private network.
  • Persistent durability, snapshots to disk, and point-in-time recovery are out of scope.
  • Complex query, secondary indexes, and range scans are excluded; access is by key only.
  • Cross-region active-active replication is out of scope for this exercise.
