React Overview React

React is a library for describing user interfaces as a function of state. You never tell the browser how to change; you describe what the screen should look like for the current data, and React works out the minimal set of DOM operations to get there. That single inversion — UI = f(state) — is the whole idea, and everything else (the virtual DOM, hooks, reconciliation, concurrency) is machinery in service of it.

It is deliberately not a framework. React ships a component model and a renderer, and stops. Routing, data fetching, global state and forms are left to an ecosystem — a design decision with real consequences for how you architect an app.

Imperative DOM vs declarative UI

With raw DOM (or jQuery), you own every transition. You must remember which nodes are affected by which change, and update all of them, in the right order, from every code path:

// imperative: you describe the TRANSITION
function addTodo(text) {
  const li = document.createElement('li');
  li.textContent = text;
  list.appendChild(li);
  counter.textContent = list.children.length;   // easy to forget
}
function removeTodo(li) {
  li.remove();
  // ...and here someone forgot to update `counter`  → the bug
}

The bug class is structural: N states × M update paths means every new feature multiplies the places that can drift out of sync. React removes the transition entirely — you re-describe the whole UI from the current state and let the library compute the transition:

// declarative: you describe the RESULT
function TodoList({ todos }) {
  return (
    <div>
      <ul>{todos.map(t => <li key={t.id}>{t.text}</li>)}</ul>
      <p>{todos.length} items</p>
    </div>
  );
}
Senior tip: The counter cannot go stale, because there is no code path that updates the list without also re-deriving the count. Declarative UI trades a small constant cost (re-describe everything) for the elimination of an entire bug family.

The component model and one-way data flow

A component is a function from props to a description of UI. Components compose into a tree; data enters at the top and flows down through props, while events flow up through callbacks. There is no two-way binding and no observable magic.

Why this matters at a senior level: when a value on screen is wrong, there is exactly one place it could have come from — the prop chain above it. You walk up the tree until you find the owner of that state. In a two-way-binding system any of N watchers could have written the value, and the debugging cost grows with the size of the app rather than the depth of the tree.

Note: "Single source of truth" is a consequence, not a slogan. Each piece of state has exactly one owner; everyone else receives a read-only copy through props.

The virtual DOM — what it actually buys you

Rendering a component produces a tree of plain JavaScript objects (React elements), not DOM nodes. React keeps the previous tree, compares it to the new one (reconciliation), and applies only the differences to the real DOM.

The honest version of the story, which interviewers are listening for:

  • The virtual DOM is not faster than hand-written DOM code. Optimal imperative updates will always beat diffing — you are adding a diff pass that a human writing the minimal mutation does not pay.
  • It is faster than naive re-rendering (innerHTML = template(state)), which destroys focus, scroll position, selection and input state.
  • What it really buys is predictability and batching. You get to write "re-render everything" code and still get a small, coalesced set of mutations, applied once per commit rather than once per setState.
  • It also decouples React from the DOM entirely, which is why react-native, react-three-fiber and custom renderers exist at all.
Gotcha: "React is fast because of the virtual DOM" is a red flag answer. React is fast enough because diffing is cheap relative to layout and paint, and it is maintainable because you never write the transition. Signals-based frameworks (Solid, Svelte 5) skip the VDOM and update the DOM directly — proof the VDOM is a means, not the point.

The modern baseline (React 18 / 19)

  • Function components + hooks are the default. Classes are legacy. The only thing you cannot yet do with a function component is an error boundary (componentDidCatch / getDerivedStateFromError), so those stay classes — or you use react-error-boundary.
  • React 18 introduced createRoot, automatic batching everywhere (promises, timeouts, native handlers — not just event handlers), StrictMode double-invoking renders and effects in development, and concurrent features: useTransition, useDeferredValue, streaming SSR with Suspense.
  • React 19 adds Actions and useActionState, useOptimistic, use(), ref as a regular prop (no forwardRef needed), and stabilizes the Server Components model. The React Compiler (auto-memoization) is shipping separately and makes most manual useMemo/useCallback unnecessary over time.
  • RSC is a framework-level feature. Server Components need a bundler + router integration; in practice that means Next.js App Router or React Router / Waku. Plain create-react-app-style SPAs do not have them (and CRA is deprecated — the docs now point at Vite or a framework).

The senior framing is not "which is better" but who owns the architecture decisions. Angular decides for you and upgrades the whole stack in lockstep — excellent for large orgs, constraining for product teams. React hands you the decisions and the maintenance of the choices you made; a five-year-old React app is usually an archaeology of the state library that was fashionable each year.

When React is the wrong tool

  • Mostly-static content sites — a marketing site, docs, or a blog. Astro or a plain static generator ships zero JS by default; React ships a runtime and then hydrates markup the user could have had instantly.
  • A tiny widget on an existing server-rendered page — a date picker on a Rails/Django page does not justify ~45 KB of runtime. Web components or a few dozen lines of vanilla JS win.
  • Extremely high-frequency updates — 60fps canvas, charting with thousands of points, spreadsheets. Let React own the shell and drop to imperative code (canvas, WebGL, direct refs) inside it.
  • Hard SEO/latency budgets with a small team — you end up needing SSR, which means adopting a framework anyway; decide that upfront rather than retrofitting it.
Senior tip: The strongest signal for React is lots of interactive state that changes over time. If your page is 95% content and 5% interaction, you are paying React's cost for the 95%.

🎯 Interview questions

Is React a framework or a library, and why does the distinction matter?

A library: it renders components and manages updates, and nothing else. Routing, data fetching, global state, forms and build tooling are your choices. That means flexibility and a stack you must curate and maintain yourself, versus Angular where those decisions come pre-made and version together.

Is the virtual DOM faster than direct DOM manipulation?

No. Optimal hand-written DOM updates beat diffing. The VDOM is faster than naive full re-rendering and, more importantly, it buys predictability and batching: you write "describe everything from state" code and React coalesces it into one minimal commit. It also abstracts the host, enabling React Native and other renderers.

What does one-way data flow give you concretely?

Traceability. Any value on screen came from props passed by an ancestor, so debugging is a walk up a single chain to the state's owner. With two-way binding, any watcher could have written the value, so the search space is the whole app rather than one path.

Do you still need class components?

Only for error boundaries, which have no hook equivalent — getDerivedStateFromError and componentDidCatch are class-only. Most teams use react-error-boundary so they never write a class. Everything else is function components with hooks.

What did React 18 actually change for an app author?

createRoot instead of ReactDOM.render; automatic batching extended to promises, timeouts and native handlers; StrictMode double-invoking renders and effects in development to surface impurity and missing cleanup; and opt-in concurrent features (useTransition, useDeferredValue, Suspense-based streaming SSR).

When would you argue against using React?

Content-dominant sites where shipping a runtime and hydrating is pure overhead (use Astro or static HTML); a single small widget inside an existing server-rendered app; and render loops at animation frequency, where you keep React for the shell and go imperative (canvas/WebGL/refs) for the hot path.

Why is Context not a substitute for a state library?

Context is a distribution mechanism with no selector layer: any change to the provider's value re-renders every consumer, no matter which slice it reads. Stores like Zustand or Redux subscribe per-selector so only affected components re-render. Context is right for stable values (theme, locale, the store handle itself).
