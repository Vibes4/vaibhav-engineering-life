Concurrency & Async Mastery

Concurrency is about structure — dealing with many things at once — while parallelism is about execution — doing many things at once. This page pushes past "use async/await" into the event loop phases, libuv's thread pool, race conditions and the Coffman deadlock conditions, optimistic vs pessimistic locking, MVCC isolation anomalies, distributed locks with fencing tokens, and the war-stories (double-charged payments, lost counter increments, cache stampedes) that separate an SDE2 from a Staff answer.

Interview Explanation — 30 seconds

Say this: "Concurrency is structuring a program so independent tasks make progress without blocking each other; parallelism is literally running them on multiple cores at the same instant. You can be concurrent on one core. Node.js runs your JavaScript single-threaded on an event loop, offloading blocking I/O to libuv's thread pool and the OS, so one thread juggles tens of thousands of sockets. The moment shared mutable state is touched by two flows at once, you get a race condition — you fix it with a critical section guarded by a lock, an atomic compare-and-swap, or by pushing the invariant into the database with a conditional UPDATE or SELECT FOR UPDATE. The hard part is never the happy path — it's deadlock, lost updates, and idempotency under retries."

Interview Explanation — 2 minutes

At senior level I frame it in four layers:

  • Execution model. Three ways to overlap work: multiple processes (isolated address spaces, IPC, expensive context switch ~1-10µs), multiple threads (shared address space, cheap switch, but shared mutable memory = the danger zone), and async I/O on a single thread (the event loop) where the CPU never blocks on a socket — it registers interest with epoll/kqueue/IOCP and gets woken on readiness.
  • Node.js specifics. One JS thread, one event loop (libuv). Each loop iteration walks fixed phases: timers → pending callbacks → poll → check (setImmediate) → close. Between every phase (and after each macrotask) the microtask queues drain: process.nextTick first, then the Promise/microtask queue. CPU-bound work blocks the loop and stalls every connection — you move it to worker_threads, cluster, or an external service. Blocking file/DNS/crypto calls run on libuv's thread pool (default 4, tunable via UV_THREADPOOL_SIZE).
  • Correctness under sharing. A race condition is when the result depends on interleaving; the classic is read-modify-write (x = x + 1) which is three non-atomic steps. You protect the critical section with a mutex, or make the whole operation atomic (CAS, atomic counter), or serialize it in the database. TOCTOU (time-of-check to time-of-use) bugs are the same disease across a gap.
  • Coordination hazards. Deadlock (four Coffman conditions must all hold), livelock, starvation, priority inversion. In distributed systems the same problems reappear as distributed locks (Redis Redlock, ZooKeeper/etcd ephemeral nodes) plus the extra evils of partial failure and clock skew — which is why fencing tokens matter.

Then I'd name the two big concurrency-control philosophies: pessimistic (lock first, then work — SELECT ... FOR UPDATE) wins under high contention; optimistic (work, then check nobody changed it — version column CAS) wins under low contention and avoids holding locks across round-trips.

Internal Working

The Node.js event loop, step by step

  1. Bootstrap. V8 compiles and runs your top-level script synchronously. Any fs.readFile, timer, or socket you register is handed to libuv, which stores callbacks in per-phase queues.
  2. Timers phase. libuv checks a min-heap of timers; callbacks whose threshold elapsed run. setTimeout(fn, 0) is really "≥1ms, next timers phase".
  3. Pending callbacks. Deferred system-level callbacks (e.g. some TCP errors like ECONNREFUSED).
  4. Poll phase. The heart. libuv calls epoll_wait (Linux) / kqueue (BSD/macOS) / IOCP (Windows) and blocks here for I/O until either an event fires or the next timer is due. Ready I/O callbacks execute here.
  5. Check phase. setImmediate callbacks run — designed to fire right after poll.
  6. Close callbacks. socket.on('close') etc.
  7. Microtask drain. After each macrotask callback and between phases, Node empties the process.nextTick queue (highest priority) then the Promise microtask queue. A tight recursive nextTick can starve the loop forever.

libuv thread pool

  1. Truly-async kernel primitives (network sockets) use epoll directly — no thread needed.
  2. APIs with no portable async syscall — fs.*, dns.lookup (getaddrinfo), crypto.pbkdf2/randomBytes, zlib — are dispatched to a fixed pool of worker threads (default 4). Set UV_THREADPOOL_SIZE (max 1024) before the process spins up the pool.
  3. If all 4 threads are busy on slow crypto, your fs.readFile queues behind them even though the disk is idle — a classic "why is my I/O slow" mystery.

Race condition & critical section mechanics

  1. Two flows execute balance = balance - amount. Machine code: LOAD, SUB, STORE. Interleave two LOADs before either STORE → one update is lost.
  2. A mutex makes the LOAD-SUB-STORE a critical section: only the lock holder enters; others block. Under the hood a mutex is itself built on an atomic instruction (lock cmpxchg / test-and-set) plus a futex to park waiters in the kernel.
  3. Atomic / CAS avoids the lock: CAS(addr, expected, new) succeeds only if memory still equals expected; loop and retry on failure. This is lock-free and the basis of optimistic concurrency.

Why was this built?

Before async I/O, servers used thread-per-connection (Apache prefork/worker). Each connection = a thread with an ~1-8 MB stack; at 10k connections you're spending gigabytes of RAM and drowning in context switches — the C10k problem. The kernel scheduler thrashes and most threads are just parked waiting on a socket read.

Event-driven servers (nginx, then Node.js on libuv) flipped the model: one thread, non-blocking sockets, and a readiness notification syscall (select → poll → epoll). Now one thread services tens of thousands of idle-ish connections because it only wakes for sockets that actually have data. Node made this ergonomic for application developers by exposing it as callbacks/promises rather than raw reactor loops.

On the data side, before proper concurrency control people used table locks or "last write wins" and quietly corrupted balances. MVCC (invented conceptually in the late 1970s, productionized by Postgres/Oracle/InnoDB) let readers not block writers, which unlocked high-throughput OLTP.

Advantages

  • Event loop: massive connection concurrency on tiny memory; no per-request thread stack; no lock contention in your JS because there's one thread — you never race on plain JS variables within a single process.
  • Async/await: non-blocking code that reads sequentially; error propagation via try/catch; composable with Promise.all/allSettled.
  • Optimistic concurrency: no lock held across the user's think-time; scales reads; lock-free means no deadlock.
  • Worker threads: real parallelism for CPU work with SharedArrayBuffer zero-copy sharing when you need it.

Drawbacks

  • One CPU-bound function (JSON.parse of a 50 MB body, sync bcrypt, a regex catastrophe) freezes the entire event loop — every request, including health checks, stalls.
  • Single JS thread means one process uses one core; you need cluster/PM2 to use all cores.
  • Async stack traces are shallow/confusing without --async-stack-traces; "callback hell" and unhandled rejections crash processes.
  • Optimistic concurrency wastes work under high contention (constant retries → livelock-ish thrash).
  • Distributed locks are genuinely hard to make correct — most Redis-lock tutorials are subtly wrong.

Trade-offs

  • Throughput vs latency: a bigger thread pool / more concurrency raises throughput but queues raise tail latency (Little's Law: L = λ × W).
  • Consistency vs concurrency: SERIALIZABLE isolation kills anomalies but serializes conflicting txns (aborts/retries); READ COMMITTED is fast but allows lost updates.
  • Lock granularity: coarse locks are simple but serialize everything; fine-grained locks scale but invite deadlock and ordering bugs.
  • Pessimistic vs optimistic: hold-a-lock (blocking, deadlock risk) vs retry-on-conflict (wasted work, starvation risk).
  • Bounded concurrency: unbounded Promise.all over 10k items DDoSes your DB; a semaphore/p-limit trades peak speed for stability.

When NOT to use it

Watch out: Don't reach for these when they don't fit —
  • Node event loop for CPU-heavy compute (video transcode, ML inference, big crypto batch) — you'll block the loop; use a worker pool or a different runtime.
  • Redlock as a correctness guarantee for money movement without a fencing token — it's a best-effort mutual-exclusion optimization, not a safety property. If correctness depends on it, you also need the DB to reject stale writes.
  • Optimistic locking on a hot single row (a global counter everyone increments) — retry storms; use an atomic DB increment or shard the counter.
  • Threads with shared mutable state when message-passing/immutability would do — every shared variable is a future race report.
  • SERIALIZABLE on a high-throughput hot path where write skew can't actually happen — you're paying abort costs for nothing.

Production Architecture

A typical Node.js API tier: N pods, each running cluster (or one process per core via PM2) behind an L7 load balancer using SO_REUSEPORT so the kernel load-balances accepts across workers. CPU-bound endpoints offload to a worker-thread pool. Cross-instance mutual exclusion (e.g. "only one worker runs this cron") goes through Redis or etcd. Money/inventory correctness lives in Postgres with row locks or version columns — never solely in the app.

  LB --> P2["Pod B cluster master"]

Key point: the load balancer and cluster give you parallelism across cores/pods; the event loop inside each worker gives you concurrency across connections; Postgres and Redis provide the coordination that the stateless app tier deliberately does not.

Production Problems

  • Event loop lag spikes: a sync JSON parse or a bad regex pushes event loop delay from <5ms to 800ms; p99 latency and health checks tank, k8s restarts healthy pods.
  • Thread pool starvation: heavy crypto.pbkdf2 saturates the 4 libuv threads; unrelated fs reads queue; latency mysteriously correlates with login volume.
  • Lost updates: two requests read a counter, both write +1, one increment vanishes — reconciliation reports show money/stock drift.
  • Deadlocks: two transactions lock rows A then B vs B then A; Postgres kills one with deadlock detected (SQLSTATE 40P01) after deadlock_timeout (default 1s).
  • Cache stampede: a hot key expires; 5000 concurrent requests all miss and hammer the DB simultaneously.
  • Double-submit payments: user double-clicks / client retries a 504 that actually succeeded → two charges, no idempotency key.

Scaling

Vertical inside a process is capped at one core for JS. To use a 16-core box you run 16 worker processes (cluster/PM2) or 16 pods. State that must be shared (locks, counters, sessions) moves out to Redis/DB. CPU work goes to a bounded worker-thread pool sized to core count, not request count.

flowchart LR
  A["Incoming requests"] --> Q["Bounded queue semaphore"]
  Q --> WP["Worker pool size N cores"]
  WP --> R1["Task 1"]
  WP --> R2["Task 2"]
  WP --> R3["Task 3"]
  R1 --> D["Results"]
  R2 --> D
  R3 --> D

Little's Law sizes the pool: concurrency L = arrival rate λ × service time W. If 500 req/s each take 40ms, you need ~20 in-flight slots. Size the DB connection pool similarly — more connections than the DB can serve just moves the queue into Postgres and adds latency. Shard hot counters (N sub-counters, sum on read) to remove the single-row contention point.

Security

  • Race-condition auth bypass / TOCTOU: check-then-act on permissions or balance across an await gap lets attackers exploit the window. Re-validate inside the transaction, not before it.
  • Redis lock without fencing token: a paused (GC/STW) lock holder resumes after its lease expired and another holder took over — two writers. Attach a monotonically increasing fencing token and have the resource reject stale tokens.
  • ReDoS: catastrophic-backtracking regex on user input blocks the single event loop = trivial DoS. Use linear-time regex engines or timeouts.
  • SharedArrayBuffer + Spectre: high-res timing side channels; requires COOP/COEP headers to enable, isolate untrusted code.
  • Idempotency key spoofing: scope keys per-user and validate ownership so one user can't replay another's key.

Performance

  • Context switch: thread ~1-5µs, process heavier; an epoll wakeup for one ready socket avoids waking thousands of parked threads.
  • Uncontended mutex lock/unlock ~20-50ns (atomic + no syscall); contended lock = futex syscall + context switch ~1-5µs.
  • Atomic CAS ~10-30ns but a cache-line ping-pong under contention (false sharing — two hot variables on the same 64-byte line) can cost 100x; pad to separate cache lines.
  • Node event loop can push 50k-100k+ req/s of light I/O on one core; a single 10ms sync CPU chunk caps you at ~100 req/s on that endpoint.
  • Tuning knobs: UV_THREADPOOL_SIZE, --max-old-space-size, keep-alive agents (maxSockets), DB pool size (~= cores × 2 to 4 as a start), batch/pipeline round-trips, and offload CPU to workers.
Say this: "I size pools with Little's Law and I measure event-loop lag as my primary saturation signal, not CPU% — a Node box can be 30% CPU and completely stalled if one handler blocks."

Common Mistakes

  • Blocking the loop with fs.readFileSync, sync bcrypt, or huge JSON in a request handler. Fix: async APIs, worker threads, stream/chunk.
  • await inside a loop serializing independent calls. Fix: Promise.all — but bound it with p-limit for large N.
  • Unbounded Promise.all over thousands of items → connection-pool exhaustion. Fix: semaphore / p-limit / batching.
  • Read-modify-write in app code for counters/balances. Fix: atomic DB op or optimistic version check.
  • Inconsistent lock ordering across transactions → deadlocks. Fix: always acquire in a canonical order (e.g. by primary key ascending).
  • Forgetting idempotency on POST/payment endpoints. Fix: idempotency key with a unique constraint.
  • Swallowed promise rejections / missing await. Fix: lint no-floating-promises, handle unhandledRejection.
  • Holding a DB lock across an external HTTP call. Fix: do the network call outside the transaction.

Interview Follow-up Questions

  1. What's the difference between concurrency and parallelism?
    1. Structure vs execution; concurrency possible on one core, parallelism needs multiple.
  2. Node is single-threaded — how does it do thousands of concurrent connections?
    1. Event loop + epoll; blocking work offloaded to libuv pool / OS.
  3. Walk me through the event loop phases.
    1. timers → pending → poll → check → close, microtasks drained between each.
  4. Where do nextTick and Promise callbacks run?
    1. Microtask queues between phases; nextTick before promises; both can starve the loop.
  5. What runs on the libuv thread pool and how big is it?
    1. fs, dns.lookup, crypto, zlib; default 4, tune UV_THREADPOOL_SIZE.
  6. You have CPU-heavy work in a handler — what do you do?
    1. worker_threads / cluster / external service; never block the loop.
  7. Difference between worker_threads and cluster?
    1. Threads share memory (SharedArrayBuffer, MessagePort); cluster = separate processes, SO_REUSEPORT.
  8. What is a race condition? Give the canonical example.
    1. Result depends on interleaving; read-modify-write on a counter loses updates.
  9. How do you protect a critical section?
    1. Mutex/lock, or make op atomic (CAS), or serialize in DB.
  10. What are the four Coffman conditions for deadlock?
    1. Mutual exclusion, hold-and-wait, no preemption, circular wait — break any one.
  11. How do you prevent deadlock in practice?
    1. Global lock ordering, try-lock with timeout, lock-free designs.
  12. Optimistic vs pessimistic locking — when each?
    1. Optimistic (version CAS) low contention; pessimistic (FOR UPDATE) high contention.
  13. Explain the DB isolation levels and their anomalies.
    1. RU/RC/RR/Serializable vs dirty/non-repeatable/phantom/lost-update/write-skew.
  14. What is MVCC and how does SSI work?
    1. Versioned rows, readers don't block writers; SSI detects dangerous read-write dependency cycles and aborts.
  15. Is Redlock safe for correctness?
    1. No — Kleppmann: needs fencing tokens; it's a mutual-exclusion optimization, not a safety guarantee.
  16. What's a fencing token and who enforces it?
    1. Monotonic number; the protected resource rejects lower tokens.
  17. How do ZooKeeper/etcd locks work?
    1. Sequential ephemeral nodes; watch predecessor; ephemerality releases on session loss; leases.
  18. How do you make a payment endpoint idempotent?
    1. Client-supplied idempotency key + unique constraint; return the prior result on replay.
  19. How do you prevent a cache stampede?
    1. Single-flight lock, request coalescing, stale-while-revalidate, jittered TTL.
  20. How do you size a thread/connection pool?
    1. Little's Law L = λW; measure service time, don't overshoot the DB.

Incident 1 — Double-charged payments after a timeout

SymptomsCustomers report two charges; support tickets spike after a downstream gateway slowdown.
InvestigationLogs show client retried a request that returned 504; both requests reached the gateway and succeeded; no idempotency key on the endpoint.
Root CauseThe 504 was a proxy timeout, not a real failure — the original charge committed. Retry created a second charge.
SolutionRequire an idempotency key; store (key → response) with a unique DB constraint; on replay return the stored result instead of re-charging.
PreventionMake all money-moving POSTs idempotent by contract; treat timeouts as "unknown", not "failed"; short-circuit duplicate keys before hitting the gateway.
Interview Answer"Timeouts are ambiguous. Correctness comes from an idempotency key backed by a unique constraint, so a retry is a no-op that returns the first outcome."

Incident 2 — Lost counter increments on a viral post

SymptomsLike count visibly lower than actual likes; reconciliation shows drift proportional to traffic.
InvestigationCode does SELECT count → count+1 → UPDATE in app; concurrent requests read the same value.
Root CauseClassic lost update: read-modify-write outside a transaction/atomic op under high concurrency.
SolutionReplace with atomic UPDATE posts SET likes = likes + 1 (or Redis INCR); for extreme hotness, shard into N sub-counters and sum on read.
PreventionBan app-side read-modify-write on shared numeric state in review; default to atomic DB operations.
Interview Answer"Push the increment into the database as one atomic statement so there's no read-modify-write window; shard the counter if a single row gets too hot."

Incident 3 — Seat/inventory double-booking

SymptomsTwo users get confirmation for the same seat; oversold by a handful of units at peak.
InvestigationAvailability checked, then inserted booking — a TOCTOU gap; both requests passed the check before either wrote.
Root CauseCheck-then-act across concurrent transactions without a lock or constraint.
SolutionPessimistic: SELECT ... FOR UPDATE the seat row inside the txn; or optimistic decrement UPDATE seats SET taken=true WHERE id=? AND taken=false and treat 0 rows as "already gone"; or a unique constraint on (event, seat).
PreventionMake the invariant a DB constraint, not an app check; do the availability check and the write in the same atomic step.
Interview Answer"I collapse check-and-reserve into one conditional UPDATE guarded by a unique constraint, so the database — not a racy app check — enforces single ownership."

Incident 4 — API stall correlated with login traffic

SymptomsUnrelated endpoints slow down whenever login volume rises; CPU only ~40%.
InvestigationEvent-loop lag fine, but libuv pool queue depth spikes; logins use sync-ish crypto.pbkdf2 which runs on the 4-thread pool; fs reads queue behind them.
Root Causelibuv thread pool starvation — password hashing monopolized all 4 threads.
SolutionRaise UV_THREADPOOL_SIZE to match core count, move hashing to a dedicated worker pool, and use the async crypto API so it doesn't block the JS thread.

Incident 5 — Cache stampede takes down the DB

SymptomsDB CPU pegs and latency explodes exactly when a popular cache key expires.
InvestigationThousands of concurrent requests miss the same key simultaneously and all recompute against the DB.
Root CauseSynchronized expiry + no request coalescing = thundering herd on the origin.
SolutionSingle-flight: first miss takes a short lock and populates; others wait or serve stale. Add stale-while-revalidate and jittered TTLs.
PreventionProbabilistic early expiration (XFetch), TTL jitter, and per-key locks on recompute.
Interview Answer"I coalesce misses with a single-flight lock so only one request recomputes while the rest serve slightly-stale data, and I jitter TTLs to avoid synchronized expiry."

🎯 Deep-dive Q&A — model answers

Explain exactly what happens when you call setTimeout(fn,0), setImmediate(fn), and process.nextTick(fn) together.

nextTick runs first — it's drained before the loop even continues to the next phase, ahead of the Promise microtask queue. setImmediate fires in the check phase. setTimeout(,0) is clamped to ≥1ms and fires in the next timers phase. Ordering of setTimeout vs setImmediate at top level is non-deterministic (depends on how fast the loop entered), but inside an I/O callback setImmediate always wins because you're already past timers and about to hit check. Recursive nextTick starves I/O entirely because the nextTick queue must fully empty before the loop proceeds.

Why can raising UV_THREADPOOL_SIZE make things worse?

The pool threads are real OS threads competing for cores with your JS thread and GC. If you set it to 128 on a 4-core box, you get context-switch thrash and cache pollution; crypto tasks that are CPU-bound don't get faster past core count. The right size is roughly the number of cores you can spare for blocking work, and you should isolate genuinely CPU-heavy work into dedicated worker_threads instead of inflating the shared libuv pool that also serves fs/dns.

Redlock: what precisely does Kleppmann object to, and what's the fix?

Two failure classes: (1) timing — a client acquires the lock, then a GC pause or network stall exceeds the lease; the lock expires, another client acquires it, and the first client wakes up believing it still holds the lock — now two writers. (2) Redlock's reliance on bounded clock drift and majority-of-N independent masters doesn't survive process pauses. The fix isn't a better lock; it's a fencing token: the lock service hands out a monotonically increasing number, the client passes it to the protected resource (DB/storage), and the resource rejects any write carrying a token lower than the highest it has seen. That converts a liveness optimization into an actual safety guarantee.

What is write skew and why doesn't SNAPSHOT isolation prevent it?

Write skew: two transactions read an overlapping set, each checks an invariant that currently holds, then each writes to different rows in a way that jointly violates the invariant (classic: two doctors both on-call, each checks "at least one other is on-call", both go off-call → zero on-call). Snapshot isolation gives each txn a consistent read snapshot and prevents write-write conflicts on the same row, but here they write different rows, so no conflict is detected. Only SERIALIZABLE (in Postgres, Serializable Snapshot Isolation) catches it by tracking read-write dependencies and aborting one txn when it detects a dangerous cycle. Alternatively materialize the conflict with a lock (SELECT FOR UPDATE on a summary row).

How does Postgres MVCC actually implement snapshots, and what's the cost?

Every row version (tuple) carries xmin (creating txn) and xmax (deleting/updating txn). A transaction's snapshot is the set of committed txn IDs visible to it; a tuple is visible if its xmin is committed-and-visible and its xmax is not. UPDATE writes a new tuple and marks the old one's xmax — it doesn't overwrite. Cost: dead tuples accumulate → table/index bloat; VACUUM (and autovacuum) reclaims them and advances the frozen-XID horizon to avoid transaction-ID wraparound. Long-running transactions hold back the xmin horizon so vacuum can't clean up — a single idle-in-transaction connection can bloat the whole DB.

Design a correct, high-throughput global counter.

Never read-modify-write in app code. For moderate rates use one atomic statement (UPDATE ... SET n = n + 1) or Redis INCR (single-threaded, so atomic). For a viral hot key, shard: keep K rows/keys (counter_0..counter_K-1), each request increments a random shard, and reads SUM across shards. This trades read cost for eliminating the single-row lock contention. If you need exactness with durability, batch increments in memory and flush atomically, accepting a small loss window, or use an append-only event log and materialize the count.

Two services deadlock acquiring rows in different orders. Walk through the fix.

Deadlock needs all four Coffman conditions; the cheapest to break is circular wait via a global lock ordering — always lock rows in ascending primary-key order regardless of business order, so no cycle can form. Backups: acquire with SELECT ... FOR UPDATE NOWAIT or a lock_timeout so one txn fails fast and retries instead of hanging; keep transactions short; never call external services while holding locks. Postgres already runs a deadlock detector (after deadlock_timeout, default 1s) that aborts one victim with 40P01 — but you want to avoid triggering it, not rely on it.

How do ZooKeeper sequential ephemeral znodes implement a fair lock?

Each client creates an ephemeral sequential child under /lock, getting a monotonically increasing suffix. The client lists children; if it has the lowest sequence it holds the lock. Otherwise it sets a watch on the next-lower znode only (avoids herd effect) and waits. When the predecessor's client dies, its ephemeral node vanishes automatically (session timeout), the watch fires, and the waiter rechecks. This gives FIFO fairness and automatic release on crash. The session/lease is the safety anchor; combine with a fencing token (the sequence number works) for downstream safety.

What's false sharing and how do you detect and fix it?

CPUs move memory in 64-byte cache lines. If two threads write two different variables that happen to sit on the same line, each write invalidates the other core's cached line (MESI protocol), causing a cache-line ping-pong even though there's no logical sharing — throughput can drop 5-100x. Detect with perf c2c (cache-to-cache) or high LLC-miss counts on hot atomics. Fix by padding/aligning hot per-thread variables to their own cache line (e.g. 64-byte alignment, or spacing array elements).

When would you choose optimistic locking and how do you handle the retry?

Choose optimistic when conflicts are rare and you don't want to hold a lock across user think-time (editing a Jira issue, updating a profile). Add a version column; read it with the row; write with UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?. Zero rows affected means someone else won — you reload, reapply, and retry (bounded, with backoff) or surface a 409 to the user. Cap retries to avoid livelock; if retry rate climbs past ~10% the row is too hot and you should switch to pessimistic or atomic ops.

How do you bound concurrency in Node without a library, and why does it matter?

Unbounded Promise.all(items.map(fetchFromDb)) over 10k items opens 10k concurrent operations, exhausting the DB connection pool and often crashing downstreams. A semaphore bounds in-flight work: keep a counter of available permits, acquire before starting, release in a finally, and queue waiters. Or use p-limit (const run = pLimit(20)). Size the bound with Little's Law and the downstream's capacity, not your item count — the goal is steady throughput, not peak burst.

Explain backpressure in Node streams.

When a writable's internal buffer exceeds highWaterMark, write() returns false, signaling the producer to pause until the 'drain' event. pipe() / pipeline() wire this automatically: a slow consumer (disk, network) throttles a fast producer so memory doesn't balloon. Ignoring the false return and writing anyway buffers unbounded in RAM — the Node equivalent of a memory leak under load. Backpressure is flow control: it propagates the slowest stage's rate back up the pipeline.

Difference between livelock, starvation, and priority inversion.

Livelock: threads keep changing state in response to each other and make no progress (two people stepping aside in a hallway) — common with naive retry-on-conflict without backoff. Starvation: a thread never gets the resource because others keep jumping ahead (unfair scheduling, writer starved by constant readers). Priority inversion: a high-priority task waits on a lock held by a low-priority task that's itself preempted by a medium-priority task — the classic Mars Pathfinder bug; fixed by priority inheritance (raise the holder's priority to the waiter's).

Why is a single event-loop model good for WebSockets but bad for image processing?

WebSockets are mostly-idle long-lived connections doing tiny I/O — perfect for one thread + epoll servicing 100k sockets on a few MB. Image/video processing is pure CPU: a single frame's work occupies the one JS thread for tens of ms, during which every connection stalls (you can't even answer a ping). The fix is to keep the loop for I/O and hand CPU work to worker_threads or a separate service, so the event loop stays responsive and the heavy lifting parallelizes across cores.

How do you make webhook processing idempotent under at-least-once delivery?

Providers (Stripe, Razorpay) retry webhooks until you 2xx, so you'll get duplicates. Persist each event's provider ID with a unique constraint; on receipt, attempt insert — if it conflicts, you've seen it, ack and skip. Do the business side-effect and the dedup insert in the same transaction so a crash between them can't double-process. Also verify the signature and process idempotently at the effect level (e.g. "mark order paid" is naturally idempotent) as defense in depth.

What does Little's Law tell you about a saturating queue, and how do you use it operationally?

L = λ × W: average items in the system equals arrival rate times average time in system. Operationally, if arrival rate λ exceeds service capacity, W grows without bound — the queue and latency explode. You use it to size pools (needed concurrency = λ × service time), to predict when adding load will tip you over, and to reason about tail latency: shedding load (rejecting excess) keeps W bounded, whereas an unbounded queue converts an overload into a latency catastrophe. Bounded queues + load shedding beat infinite queues.
