AWS: Databases — RDS & DynamoDB EY Sheet 03

The JD names RDS and DynamoDB explicitly. In a cloud-native round this section is really testing data modelling judgement: can you tell when a relational model is the right answer and when a single-table NoSQL design is, and can you talk about the failure modes of each under load?

The line that wins this section: "I choose the database from the access patterns, not from the data. If I can enumerate every query the service will make and they're all key-based lookups with predictable shape, DynamoDB gives me flat single-digit-millisecond latency at any scale. If the queries are open-ended, ad-hoc, or need joins and transactions across entities, that's RDS — and paying for a relational engine is much cheaper than reinventing joins in application code."

RDS & Aurora

CertainMulti-AZ vs read replicas — what does each solve?

They solve completely different problems and interviewers love that people confuse them.

Multi-AZ is availability and durability. RDS keeps a synchronous standby in a second AZ. The standby is not readable — it does nothing for performance. On failure (hardware, AZ event, or a manual reboot-with-failover) RDS promotes the standby and flips the DNS CNAME; clients see a connection drop and must reconnect. Typical failover is 60–120 seconds for RDS, often under 30 for Aurora.

Read replicas are read scaling. Asynchronous replication, so there's replica lag — you must not read your own writes from a replica unless the use case tolerates staleness. They can be in the same region, cross-region (for DR and locality), and can be promoted to standalone primaries, but promotion is manual and lossy relative to the async lag.

The senior addition: after a Multi-AZ failover the classic bug is a connection pool or DNS cache still pinned to the old endpoint IP, so the app keeps failing after the database is healthy. Mitigate with short DNS caching, connection validation in the pool, or RDS Proxy.

What does Aurora do differently, and when is it worth it?

Aurora decouples compute from storage: instead of replicating a block device, the database writes log records to a distributed storage layer that keeps six copies across three AZs with quorum writes (4 of 6) and quorum reads (3 of 6). Consequences: replicas share the same storage volume, so replica lag is typically milliseconds rather than seconds; you can have up to 15 replicas; failover is fast because there's no data to move; and storage auto-grows.

Worth it when you need high read fan-out with low lag, fast failover, or Aurora-specific features — Global Database for cross-region DR with sub-second replication, or Serverless v2 for workloads with genuinely variable load. Not worth it when you have a modest steady workload that vanilla RDS PostgreSQL serves fine, since Aurora carries a price premium and adds I/O-based charges that can surprise you on write-heavy workloads.

Depth probeA query got slow in production. Walk me through your diagnosis.

I'd narrow it in layers rather than guessing:

  1. Is it the query or the box? CloudWatch: CPU, freeable memory, read/write IOPS versus the volume's provisioned ceiling, and DatabaseConnections. A saturated IOPS budget or burst-balance exhaustion on gp2 looks exactly like "the query got slow" but isn't.
  2. Which query? Performance Insights ranks by database load and shows top waits. Slow query log as the fallback.
  3. Why that query? EXPLAIN ANALYZE. I'm looking for a sequential scan where I expected an index scan, a bad row-count estimate (planner thinks 10 rows, reality is 2 million), or a nested loop that should be a hash join.
  4. Common causes in order of likelihood: missing or unusable index (a function or implicit cast on the indexed column defeats it); stale statistics after a bulk load, fixed by ANALYZE; data growth crossing the threshold where the planner flips strategy; a new N+1 query pattern introduced by an ORM change; table bloat from churn without autovacuum keeping up; or lock contention from a long-running transaction.
  5. Fix, then prevent. The fix might be an index, a query rewrite, or pagination. The prevention is the part that matters in an interview: a p99 query-latency alarm, a slow-query budget in CI, and a rule that migrations adding indexes on large tables use CREATE INDEX CONCURRENTLY so they don't lock writes.
How do you handle schema migrations with zero downtime?

Expand / migrate / contract. Never change a column in one deploy that both old and new code must work against.

  1. Expand — add the new nullable column or new table. Old code ignores it; deploy is safe.
  2. Migrate — deploy code that dual-writes to both old and new, then backfill existing rows in batches (batched so you don't hold a giant transaction or blow replica lag).
  3. Contract — once all readers use the new column and the backfill is verified, stop writing the old one and drop it in a later deploy.

Rules I'd state: migrations run as a separate pipeline step before the app deploy, never inside application startup (otherwise N instances race). Adding a NOT NULL column with a default rewrites the table on older engines — check the engine version. Renames are never done in place; they're an expand/contract. And every migration needs a tested rollback path, which usually means "additive only, drops come later".

DynamoDB

CertainPartition key design — what makes a good one, and what's a hot partition?

DynamoDB hashes the partition key to choose a physical partition. All items sharing a partition key live together — that's what makes a query by partition key fast, and it's also the trap. Each physical partition holds up to 10 GB and serves roughly 3,000 RCU / 1,000 WCU.

A hot partition is when traffic concentrates on one key: table-level capacity sits idle while one partition throttles. Classic causes are a low-cardinality key (status, country, tenant where one tenant is 90% of traffic) or a time-based key like 2026-09-14 where all of today's writes hit one partition.

Fixes: (1) higher-cardinality key — use the entity's own ID instead of its category. (2) Write sharding — append a suffix, 2026-09-14#7 with a random or calculated shard 0–N, then scatter-gather on read. (3) Adaptive capacity now auto-boosts hot partitions and isolates very hot keys, which softens the problem but doesn't remove the 10 GB/partition ceiling or the need for a sane key. The right answer is almost always a better key, not more capacity.

Depth probeLSI vs GSI — when do you use which?

LSI (Local Secondary Index) — same partition key, different sort key. Must be created with the table and can never be added later. Shares the table's throughput, supports strongly consistent reads, and imposes a 10 GB limit per partition-key value across the table and its LSIs. Use when you need an alternative sort order within the same partition.

GSI (Global Secondary Index) — different partition key entirely, effectively a separate table maintained asynchronously. Can be added or dropped any time, has its own provisioned capacity, and is eventually consistent only. Use when you need a genuinely different access pattern — "find the order by customer email" when the table is keyed by order ID.

The gotcha worth volunteering: if a GSI is under-provisioned it throttles, and because writes to the base table must propagate to the GSI, a throttled GSI can throttle writes to the base table. Also project only the attributes you need — KEYS_ONLY or INCLUDE rather than ALL — because every projected attribute is duplicated storage and duplicated write cost.

Explain single-table design. Would you always use it?

Single-table design puts multiple entity types in one table with generic keys (PK, SK) and overloaded values — PK=CUSTOMER#123, SK=PROFILE alongside PK=CUSTOMER#123, SK=ORDER#456. Because related entities share a partition, one Query returns a customer and their orders in a single round trip, which is the whole point: it replaces the join.

No, I wouldn't always use it. It only pays off when you can enumerate the access patterns up front and they're stable. The costs are real: the model is opaque to newcomers, analytics queries become impossible without exporting to S3/Athena, and adding an unanticipated access pattern later can mean a migration or another GSI. On a consulting engagement where requirements shift, I'd rather have two or three purposeful tables than one clever one nobody else on the team can read. I'd say that out loud, because "always single-table" is a cargo-cult answer.

On-demand vs provisioned capacity. And what are DynamoDB Streams for?

On-demand — pay per request, no capacity planning, instant scaling within limits. Right for new workloads with unknown traffic, spiky traffic, or dev environments. Roughly 5–7x the per-request price of well-utilised provisioned capacity, so it gets expensive at steady high volume. Provisioned with auto-scaling — cheaper for predictable sustained load, but auto-scaling reacts in minutes, so a sudden spike throttles before capacity catches up. Reserved capacity cuts provisioned cost further for a 1–3 year commitment.

Streams give you an ordered, 24-hour change log per partition key — every insert, modify and delete, with configurable before/after images. That's the foundation for event-driven patterns: trigger a Lambda to update a search index, materialise an aggregate, fan out a domain event to EventBridge, or implement the transactional outbox so a state change and its event can't diverge. Lambda consumes Streams via an event source mapping with batching, and I'd always configure a failure destination and bisectBatchOnFunctionError so one poison record doesn't stall the shard forever.

CertainRDS or DynamoDB for this service — how do you decide?

I ask four questions:

  1. Can I enumerate the access patterns? If yes and they're key-based, DynamoDB. If queries are exploratory, reporting-style, or will change with the business, relational.
  2. Do I need joins, multi-row transactions, or referential integrity? DynamoDB has TransactWriteItems, but it's limited and expensive compared to a real transaction. Complex invariants across entities → RDS.
  3. What's the scale and shape? Millions of small key-based ops with a strict latency SLO and unpredictable spikes → DynamoDB, which doesn't care. Moderate volume with complex reads → RDS is simpler and cheaper.
  4. What does the team know? A team fluent in SQL will build a correct relational system faster than a mediocre NoSQL one. On a consulting engagement that's a legitimate, defensible input.

And I'd note the hybrid is common and fine: RDS as the system of record, DynamoDB for the high-volume session/cart/idempotency-key workload, kept in sync by events.

What is DAX, and when do you need ElastiCache instead?

DAX is a DynamoDB-specific write-through cache cluster that sits in front of the table and speaks the DynamoDB API, so adoption is nearly transparent — it takes eventually-consistent reads from single-digit milliseconds to microseconds. It only helps DynamoDB, only helps eventually-consistent reads, and lives in your VPC.

ElastiCache (Redis) is a general-purpose cache and data structure server: it caches anything (RDS query results, computed aggregates, rendered fragments), and it gives you primitives DAX doesn't have — sorted sets for leaderboards, TTL'd keys for sessions, distributed locks, rate-limiter counters, pub/sub. I'd use DAX for a read-heavy DynamoDB hot-key problem and Redis for basically everything else, including as the token-bucket store for API rate limiting.
