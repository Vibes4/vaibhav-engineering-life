Distributed Systems Mastery

A distributed system is a set of independent nodes that appear to the user as one coherent system, coordinating over an unreliable, asynchronous network with partial failures and no shared clock. Everything hard about distributed systems reduces to three facts: the network can drop/delay/reorder messages, nodes can crash at any point, and there is no global "now". This page pushes past definitions into CAP/PACELC, consistency models, replication, consensus (Raft/Paxos), 2PC vs Saga, idempotency, clocks (Lamport/vector/HLC/TrueTime), consistent hashing, failure detection, fencing, and CRDTs.

Interview Explanation — 30 seconds

Say this: "A distributed system spreads state and work across machines connected by an unreliable network, so you're always trading off consistency, availability, and latency under failure. CAP says during a network partition you must choose consistency or availability; PACELC adds that even with no partition you trade consistency for latency. The whole discipline is about coping with partial failure and the lack of a global clock — replication for durability, consensus (Raft/Paxos) for agreement, quorums for correctness, idempotency because you can't get exactly-once delivery, and logical clocks because wall-clock time lies."

Interview Explanation — 2 minutes

Frame it around three impossibilities and how we work around them:

  • Impossibility 1 — you can't have C, A and partition-tolerance all at once (CAP). Partitions will happen (P is not optional), so the real choice under a partition is CP (reject writes to stay consistent, like ZooKeeper/etcd) or AP (accept writes, reconcile later, like Dynamo/Cassandra). PACELC completes the picture: Else (no partition) you still trade Latency vs Consistency — Spanner is CP+PC (pays latency for linearizability), Dynamo is AP+EL (fast, eventually consistent).
  • Impossibility 2 — exactly-once delivery is impossible (FLP + the two-generals problem). You get at-least-once or at-most-once on the wire. So we build exactly-once processing with idempotency keys + dedup stores + fencing tokens.
  • Impossibility 3 — there is no global clock. NTP gives you ~1–10ms skew that can go negative; so for causality we use Lamport clocks (total-ish order, no causality detection), vector clocks (detect concurrency), HLC (physical + logical), or Google's TrueTime (GPS/atomic clocks with a bounded uncertainty interval that Spanner waits out).

Then name the machinery: replication (single-leader / multi-leader / leaderless-quorum with R+W>N), consensus (majority quorum to avoid split-brain), atomic commit (2PC — blocking; Saga — compensations), partitioning (consistent hashing + virtual nodes), failure detection (phi-accrual), and backpressure/load-shedding to survive overload. Close with the 8 fallacies as the anti-pattern checklist.

Internal Working

Walk through what actually happens on a single replicated, partitioned write in a leaderless (Dynamo-style) store — this exercises most of the internals at once.

  1. Route the key. Client hashes the key with a stable hash (MD5/Murmur) onto a 2^128 ring. The coordinator walks clockwise to find the first virtual node, then the next N-1 distinct physical nodes = the preference list (N replicas). Virtual nodes (100–256 per physical node) smooth the load so adding/removing a node only re-maps 1/N of keys.
  2. Attach causality metadata. The write carries a vector clock (or version vector) so concurrent writes can be detected later. HLC timestamps are stamped for ordering.
  3. Send to N, wait for W acks. Coordinator dispatches to all N replicas in the preference list, returns success once W replicas ack. With R + W > N the read and write quorums overlap, guaranteeing a reader sees at least one node with the latest write.
  4. Handle a down replica — hinted handoff. If a replica is unreachable, a healthy node stores the write with a hint ("this belongs to node C") and replays it when C recovers, so W is still met without sacrificing durability.
  5. Read path — read-repair. A read contacts R replicas; if versions diverge, the coordinator returns the newest (or all concurrent siblings) and asynchronously writes the merged value back — read-repair.
  6. Background reconciliation — anti-entropy with Merkle trees. Replicas periodically compare Merkle-tree hashes of their key ranges; only subtrees whose hashes differ are exchanged, so divergence is repaired with O(log n) data transfer instead of full scans.
  7. Conflict resolution. If vector clocks show concurrent (non-ancestor) versions, the store either keeps siblings for app-level merge (Dynamo) or applies LWW by HLC timestamp (Cassandra) or merges deterministically (CRDT).

For a leader-based system the internals are: leader election via consensus → client writes go to leader → leader appends to its replicated log → replicates entries to followers → advances the commit index once a majority persisted → applies to the state machine → acks client. This is exactly Raft, covered below.

Why was this built?

Single machines hit hard ceilings: finite CPU/RAM/disk, a single failure domain, and a fixed geographic location (latency to far users). Before distributed systems, scaling meant vertical scaling (bigger boxes — expensive, still one failure domain) and manual failover (a hot standby DB with a human or heartbeat script flipping a VIP — minutes of downtime, split-brain risk).

  • Availability: replicate so one crash doesn't take you down.
  • Scale: partition so you can add machines linearly instead of buying a mainframe.
  • Latency: put replicas near users (multi-region).
  • Durability: multiple copies survive disk/rack/DC loss.

The cost is that correctness now depends on agreement across an unreliable network — which is why consensus, quorums and consistency models exist.

Advantages

  • Fault tolerance: survive node/rack/DC failure with no data loss (replication + quorums).
  • Horizontal scale: add commodity nodes for near-linear capacity via partitioning.
  • Geographic locality: serve reads/writes near the user, multi-region.
  • Elasticity: scale up/down with load; consistent hashing minimizes re-shuffling.
  • Tunable guarantees: pick consistency vs latency per operation (e.g. Cassandra ONE vs QUORUM vs ALL).

Drawbacks

  • Partial failure is the norm — a call can succeed on one node, fail on another, or time out with unknown outcome. Every RPC needs a timeout, retry, and idempotency story.
  • No global clock — ordering and "latest" are genuinely ambiguous without logical clocks.
  • Emergent complexity — debugging spans many nodes; you need distributed tracing, correlation IDs, and clock-aware logs.
  • Consistency is expensive — linearizability costs round-trips and coordination; strong cross-region consistency costs tens of ms per op.
  • Testing is hard — bugs hide in timing/partition scenarios; need Jepsen-style fault injection.

Trade-offs

  • Consistency vs Availability (during partition): CP rejects writes to stay correct; AP accepts writes and reconciles.
  • Consistency vs Latency (no partition, PACELC): synchronous replication / read quorums add round-trips; async is fast but can lose recent writes.
  • Latency vs Durability: acks=all, min.insync.replicas=2 (Kafka) ~doubles write latency but survives one broker loss; acks=1 is fast but can lose the tail on leader crash.
  • Throughput vs Ordering: a single leader/partition gives total order but caps throughput; sharding scales throughput but only gives per-key order.
  • Freshness vs Cost: read-your-writes needs sticky routing or read from leader; eventual reads are cheap but stale.

When NOT to use it

Watch out: Distributed is not free — reach for it only when a single node genuinely can't meet availability, scale, or geo requirements. Don't distribute when:
  • Your data fits comfortably on one node and one region SLA is fine — a single Postgres with a replica beats a 5-node cluster you can't operate.
  • You need multi-object ACID transactions across entities constantly — cross-shard 2PC/Saga complexity will dominate; keep it on one node.
  • The team lacks ops maturity for consensus systems, backpressure, and fault injection — an under-operated distributed system is less reliable than a good monolith.
  • Strong consistency + low latency + high availability are all hard requirements simultaneously — physics (CAP/PACELC) says you can't have all three; re-scope.

Production Architecture

A realistic multi-region, sharded, replicated deployment: stateless services behind a global load balancer, a leaderless data tier partitioned by consistent hashing with N=3 replicas spread across availability zones, a consensus-backed metadata/coordination service (etcd/ZooKeeper) for leader election and config, and an async event backbone (Kafka) for cross-service state propagation.

Key points: services are stateless so any node handles any request; the coordination service holds the single source of truth for leadership and topology (kept tiny, only metadata, so consensus latency doesn't hurt the data path); the data tier uses quorum reads/writes and background anti-entropy; and Kafka decouples regions/services so a slow consumer applies backpressure instead of collapsing producers.

Production Problems

  • Split-brain: a network partition leaves two nodes each believing they're leader; both accept writes → divergence. Fixed by majority quorum + fencing tokens.
  • Retry storms / metastable failure: a blip causes timeouts → clients retry → amplified load keeps the system down even after the trigger is gone. Needs jittered backoff, retry budgets, circuit breakers, load shedding.
  • Hot shards: a celebrity key or monotonic key (timestamp/auto-increment) sends all traffic to one partition. Needs key salting/virtual nodes/re-sharding.
  • Clock skew bugs: LWW conflict resolution silently drops writes when a node's clock is ahead; NTP jumps break TTLs and leases.
  • Zombie leaders: a GC-paused or partitioned leader wakes up and writes with a stale lease. Fencing tokens reject it.
  • Cascading failure: one slow dependency saturates thread pools upstream; no bulkheads → whole call graph stalls.
  • Duplicate processing: at-least-once delivery + non-idempotent handler = double charge / double email.

Debugging Guide

  • Establish a timeline across nodes: use a correlation/trace ID on every request; pull traces from Jaeger/Tempo/Zipkin — traceID spans show which hop added latency or errored.
  • Check clock skew first for ordering bugs: chronyc tracking / ntpq -p on each node; look at offset and root dispersion. Alert if skew > a few ms.
  • Cluster health / leadership: etcdctl endpoint status --cluster -w table (shows leader, raftIndex, dbSize); etcdctl endpoint health. For Kafka: kafka-topics.sh --describe to see under-replicated partitions and ISR.
  • Quorum / replication lag: Cassandra nodetool status, nodetool netstats, nodetool tpstats (dropped mutations = overload). Kafka consumer lag via kafka-consumer-groups.sh --describe.
  • Partition suspicion: ping/mtr between nodes, check phi-accrual detector state / gossip logs for flapping nodes.
  • Find the retry storm: graph request-rate vs upstream-rate; a downstream at 100% with rising client RPS during an outage = amplification.
  • Reproduce with fault injection: tc qdisc add dev eth0 root netem delay 200ms loss 5%, or Toxiproxy/Chaos Mesh to inject partitions; Jepsen to test linearizability claims.

Scaling

Two axes: vertical (bigger node — quick, but hits a ceiling and one failure domain) and horizontal (more nodes — the real path). Horizontal scale means partitioning the keyspace and replicating each partition.

  • Consistent hashing + virtual nodes so adding node N+1 only moves ~1/N of keys, not a full re-hash.
  • Range vs hash partitioning: hash spreads load evenly but kills range scans; range enables scans but creates hot shards on sequential keys.
  • Replication factor (N=3 typical) across AZs for durability; read replicas for read-heavy scale.
  • Limits: a single leader/partition caps write throughput; coordination (consensus) caps at ~majority-round-trip; cross-region adds RTT to every synchronous op.
  • Backpressure & load shedding are part of scaling — reject/deprioritize excess load (429s, priority queues) so the system degrades gracefully instead of collapsing.

Security

  • AuthN between services: mutual TLS (mTLS) with short-lived certs (SPIFFE/SPIRE), or signed service tokens; never trust the network (zero-trust).
  • AuthZ: per-service RBAC/ABAC; scoped tokens; principle of least privilege on data-tier access.
  • Encryption in transit: TLS 1.3 on every hop including intra-cluster gossip/replication.
  • Encryption at rest: disk/volume encryption + per-tenant keys via KMS; rotate keys.
  • Network isolation: private subnets, security groups, service mesh policies; data tier not internet-reachable.
  • Common CVEs / pitfalls: unauthenticated coordination endpoints (open etcd/ZooKeeper/Redis on 0.0.0.0 — a classic breach), missing mTLS letting a compromised node join the cluster, replay attacks (mitigated by nonces + fencing tokens), and SSRF into internal service discovery.
  • Auditability: tamper-evident audit logs; correlation IDs to trace an actor across nodes.

Performance

  • Latency numbers to anchor on: same-DC RTT ~0.5ms, cross-region RTT 20–150ms, SSD random read ~100µs, disk fsync 1–10ms. A cross-region synchronous quorum write is dominated by the far-replica RTT.
  • Bottlenecks: the single leader (all writes funnel through it), fsync durability, network RTT for quorums, lock/coordination contention, and GC pauses (which look like partitions).
  • Tuning knobs: quorum levels (Cassandra LOCAL_QUORUM to stay in-region), Kafka batch.size/linger.ms/compression for throughput, connection pooling, request hedging (send to 2 replicas, take first) to cut tail latency, and read replicas for read scale.
  • Tail-latency tricks: hedged requests, tied requests, and adaptive timeouts; a p999 outlier on one node shouldn't stall the whole fan-out.
  • Batching & pipelining amortize per-request overhead; but batching adds latency — tune linger.ms against your SLO.

Common Mistakes

  • Assuming exactly-once delivery. Fix: at-least-once + idempotency keys + dedup store for exactly-once processing.
  • Non-idempotent retries. Fix: idempotent handlers keyed by a client-generated request ID; store the result and return it on replay.
  • Trusting wall-clock time for ordering / LWW. Fix: HLC or logical clocks; never use raw System.currentTimeMillis() to decide "latest".
  • No fencing on locks/leases. Fix: monotonically increasing fencing token checked by the resource so zombie holders are rejected.
  • Retries without jitter/backoff/budget. Fix: exponential backoff + full jitter + retry budget + circuit breaker.
  • Unbounded queues / no backpressure. Fix: bounded queues, load shedding, 429s, priority tiers.
  • Ignoring the 8 fallacies (network reliable, latency zero, bandwidth infinite, network secure, topology stable, one admin, transport cost zero, homogeneous network). Fix: design for each explicitly.
  • Distributed transactions everywhere. Fix: model boundaries so most ops are single-shard; use Sagas for the rare cross-service flow.

Interview Follow-up Questions

  1. Define CAP precisely.
    1. Answer pointer: During a network partition you can guarantee consistency OR availability, not both; P is not a choice.
  2. Why is CAP "only during a partition"? What about the rest of the time?
    1. Answer pointer: With no partition you don't have to sacrifice either — PACELC's "Else": you trade Latency vs Consistency.
  3. Give me PACELC classifications for Spanner, Dynamo, and MongoDB.
    1. Answer pointer: Spanner PC/EC(→C), Dynamo/Cassandra PA/EL, MongoDB PA/EC (default) — tunable.
  4. Walk me down the consistency hierarchy from linearizable to eventual.
    1. Answer pointer: Linearizable > sequential > causal > read-your-writes/monotonic > eventual; each drops a guarantee for latency/availability.
  5. What's the difference between linearizability and serializability?
    1. Answer pointer: Linearizability = single-object real-time recency; serializability = multi-object transaction isolation; strict serializability = both.
  6. In a leaderless store, why does R+W>N give you consistency, and does it actually?
    1. Answer pointer: Read and write quorums overlap in ≥1 node; but concurrent writes, sloppy quorums, and read-repair timing weaken it — not truly linearizable.
  7. How does Raft elect a leader and prevent two leaders?
    1. Answer pointer: Randomized election timeouts, votes need majority, terms are monotonic; a candidate needs a majority so two leaders in one term is impossible.
  8. How does Raft commit an entry, and what's the commit index?
    1. Answer pointer: Leader appends, replicates; once a majority persists, commit index advances; only then applied to state machine and acked.
  9. Why a majority quorum specifically, not any subset?
    1. Answer pointer: Any two majorities intersect, so a committed entry is seen by any future leader's majority — prevents lost writes/split-brain.
  10. Paxos vs Raft — real difference?
    1. Answer pointer: Same safety; Raft restructures for understandability (strong leader, log contiguity, explicit membership change). Multi-Paxos ≈ Raft in practice.
  11. 2PC vs Saga for a checkout across 4 services?
    1. Answer pointer: 2PC = atomic but blocking on coordinator failure, holds locks; Saga = compensating transactions, eventually consistent, no locks, needs idempotency.
  12. Why is exactly-once delivery impossible but exactly-once processing possible?
    1. Answer pointer: Two-generals/FLP — you can't know the message arrived without an ack that can also be lost; so retry (at-least-once) + dedup by idempotency key at the consumer.
  13. How do you detect that a node has failed vs is just slow?
    1. Answer pointer: You can't be certain; phi-accrual gives a suspicion level from heartbeat-interval history instead of a fixed timeout.
  14. A leader GC-pauses for 10s and its lease expires — what breaks and how do you fix it?
    1. Answer pointer: Zombie leader may write after a new one is elected → split-brain; fencing tokens (monotonic) rejected by the resource fix it.
  15. Lamport vs vector clocks — when do you need which?
    1. Answer pointer: Lamport gives a total order but can't detect concurrency; vector clocks detect causal vs concurrent (needed for conflict detection); size grows with nodes.
  16. What is TrueTime and how does Spanner use it?
    1. Answer pointer: An API returning [earliest, latest] bounded by ε; Spanner does commit-wait until ε passes so timestamps respect real-time order → external consistency.
  17. How do CRDTs avoid coordination, and their limits?
    1. Answer pointer: Commutative/associative/idempotent merges converge regardless of order; great for counters/sets/text, but can't express arbitrary invariants (e.g. non-negative balance).
  18. Your system melts under a small blip and stays down — name it and fix it.
    1. Answer pointer: Metastable failure from retry amplification; fix with backoff+jitter, retry budgets, circuit breakers, load shedding, and reducing work-per-retry.
  19. How would you prove your store is actually linearizable?
    1. Answer pointer: Jepsen — inject partitions/clock skew, record a history, check with a linearizability checker (Knossos/Elle).
  20. How does adding a node reshuffle data, and why virtual nodes?
    1. Answer pointer: Consistent hashing moves only ~1/N of keys; vnodes spread each physical node across many ring positions for even load and faster rebalancing.

Common Cross Questions

  • After CAP/PACELC → databases: "Which DB is CP vs AP?" Expected angle: etcd/ZK/HBase/Spanner = CP; Cassandra/Dynamo/Riak = AP (tunable); explain the config that shifts it.
  • After consistency models → caching: "How do you keep cache consistent with the DB?" Angle: TTL vs write-through vs invalidation, thundering herd, and that cache is eventual by nature.
  • After consensus → coordination services: "When ZooKeeper vs etcd vs Consul?" Angle: all consensus-backed; etcd for k8s/Raft, ZK for older Hadoop/Kafka, Consul for service discovery + health.
  • After 2PC/Saga → messaging: "Kafka vs RabbitMQ, and exactly-once in Kafka?" Angle: Kafka idempotent producer + transactions give effectively-once within Kafka; still need consumer idempotency for external effects.
  • After idempotency → API design: "How do you design an idempotent POST?" Angle: client-supplied Idempotency-Key header, server dedup table with stored response + status.
  • After clocks → distributed tracing: "How do you order events across services with skewed clocks?" Angle: logical/HLC timestamps + trace spans, not wall-clock.
  • After partitioning → hot keys: "How do you handle a celebrity/hot shard?" Angle: key salting, dedicated replicas, request coalescing, caching.
  • After failure detection → load balancing: "How does the LB avoid routing to a dead node?" Angle: health checks, outlier detection, EWMA/least-loaded, circuit breaking.

🎯 Deep-dive Q&A — model answers

Explain why "P" in CAP is not optional, and what CP/AP really mean operationally.

Partitions are physical reality — packets drop, links fail, GC pauses look like partitions. Since you can't opt out of P, CAP is really a binary choice made during a partition: a CP system (etcd, ZooKeeper, HBase) refuses operations on the minority side to preserve a single consistent view — you get errors/timeouts but never divergence. An AP system (Cassandra, Dynamo) keeps accepting reads/writes on both sides and reconciles afterward (read-repair, anti-entropy, vector clocks) — you stay available but can read stale/conflicting data. Operationally: CP trades availability for correctness; AP trades correctness for availability. The nuance interviewers want: outside a partition neither guarantee must be sacrificed — that's where PACELC's latency-vs-consistency trade governs.

Derive why a majority quorum guarantees no lost committed writes.

Let there be N nodes. A write is committed only when a majority (⌊N/2⌋+1) persists it. A new leader is elected only with votes from a majority. Any two majorities of an N-set must intersect in at least one node (pigeonhole: two sets each >N/2 can't be disjoint). Therefore the electing majority contains at least one node that holds the last committed entry, and Raft's election restriction forces a candidate's log to be at least as up-to-date as that voter's — so a committed entry is never overwritten. This is also why even cluster sizes are wasteful: N=4 tolerates the same 1 failure as N=3 but needs 3 for quorum.

Why is exactly-once delivery provably impossible, and how do systems still claim it?

The two-generals problem: to know a message was delivered you need an ack, but the ack can be lost, and the ack-of-the-ack can be lost, ad infinitum — so no finite protocol guarantees both sides agree over a lossy channel. FLP formalizes that consensus can't be guaranteed in a fully async system with even one crash. So on the wire you pick at-least-once (retry, risk duplicates) or at-most-once (don't retry, risk loss). "Exactly-once" claims (Kafka transactions, Flink) are exactly-once processing/state-update: at-least-once delivery plus deduplication via idempotency keys, sequence numbers (Kafka idempotent producer), and transactional/atomic state commits, so duplicate deliveries don't produce duplicate effects. External side effects (charging a card, sending email) still need consumer-side idempotency.

Compare Lamport clocks, vector clocks, HLC, and TrueTime — what does each buy and cost?

Lamport clocks: single integer, increment on event, take max+1 on receive; give a total order consistent with causality but can't tell you if two events are concurrent or causally related — cheap, O(1). Vector clocks: one counter per node; can decide happened-before vs concurrent (essential for conflict detection in Dynamo) but size grows O(nodes) and needs pruning. HLC (hybrid logical clocks): combines a physical component (close to wall time, useful for humans/TTLs) with a logical counter to preserve causality even under skew — bounded drift from real time, used by CockroachDB. TrueTime: Google's API returning an interval [earliest, latest] with bounded uncertainty ε (few ms, backed by GPS + atomic clocks); Spanner waits out ε (commit-wait) so timestamps respect global real-time order, buying external consistency at the cost of that wait latency and specialized hardware.

2PC vs Saga: walk through failure modes concretely.

2PC: coordinator sends prepare; participants lock resources and vote yes/no; coordinator sends commit/abort. Atomicity is real, but it's blocking: if the coordinator crashes after some participants voted yes, those participants hold locks indefinitely, unsure whether to commit — availability collapses (3PC tries to fix this but adds assumptions and still fails under partition). Saga: model the transaction as a sequence of local transactions each with a compensating action. If step 4 fails, run compensations for steps 3,2,1 (semantic undo — refund, not rollback). No distributed locks, so it's available and scalable, but it's eventually consistent (other readers can see intermediate states) and compensations must be idempotent and commutative-ish. Choreography (events) vs orchestration (a coordinator like Temporal) are the two Saga styles; orchestration is easier to reason about at scale.

How does a leaderless quorum store repair divergence in the background?

Three mechanisms layered: (1) read-repair — on a quorum read, if replicas disagree, the coordinator pushes the newest/merged value back to stale replicas synchronously or async; fixes hot keys naturally. (2) hinted handoff — when a replica is down at write time, another node stores the write with a hint and replays it on recovery, so the write count is still met. (3) anti-entropy with Merkle trees — replicas build a hash tree over their key ranges and exchange top-down; only subtrees whose root hashes differ get drilled into and repaired, so two replicas holding millions of identical keys sync in O(log n) comparisons rather than a full scan. Together they bound the staleness window even for cold keys never read.

What exactly is a fencing token and why do leases alone fail?

A lease (time-bounded lock) fails because the holder can be paused (GC, VM freeze) past the lease expiry without noticing; a new holder is granted the lease, then the old one wakes and writes — two writers. A fencing token is a monotonically increasing number handed out with each lease grant (e.g., from the lock service / Raft index). Every write to the protected resource includes its token; the resource remembers the highest token it has seen and rejects any write with a lower token. So the zombie's stale token is refused at the storage layer — the fix must be enforced by the resource, not by the client trusting its own clock. This is how you make a lock actually safe.

Why do people say "the network is not reliable" is the first fallacy, and how does it change your code?

The 8 fallacies (network reliable, zero latency, infinite bandwidth, secure, stable topology, one admin, zero transport cost, homogeneous) are the assumptions that quietly creep into code and blow up in prod. "Network reliable" changes everything: every remote call needs a timeout (never infinite), a bounded retry with jittered backoff, idempotency so retries are safe, a circuit breaker so a dead dependency doesn't cascade, and a fallback/degraded path. It means you never treat an RPC like a local function call, you design for the "unknown outcome" (timed out — did it apply?), and you make partial failure a first-class state in your data model, not an exception you log and ignore.

How do you decide sync vs async replication, and what's the data-loss math?

Sync replication: the write isn't acked until ≥K replicas persist it — zero data loss up to K-1 simultaneous failures, but every write pays the slowest replica's latency (tail-latency sensitive; cross-region is brutal). Async: leader acks immediately, ships to followers in the background — fast, but a leader crash loses the un-shipped tail (bounded by replication lag). Semi-sync (Kafka acks=all + min.insync.replicas=2) is the pragmatic middle: durable against one broker loss, roughly 2x latency vs acks=1. The decision is your RPO: if RPO=0 you need sync (and accept the latency and the availability hit when a replica is down); if you can tolerate seconds of loss, async with lag monitoring is far cheaper and faster.

What is linearizability, and why can't you get it "for free" with R+W>N?

Linearizability: every operation appears to take effect atomically at some instant between its invocation and response, and once a write is acknowledged all later reads (by real time) see it or a later value — it's the single-object "as if there's one copy" guarantee. R+W>N only guarantees the read and write quorums overlap in one node, but that node might return an in-progress write, concurrent writes create siblings the quorum can't linearize, sloppy quorums (hinted handoff to non-preference nodes) break the overlap, and read-repair races mean a value can appear then disappear across successive reads. Achieving true linearizability needs consensus on every operation (like a Raft log) or read-modify-write with quorum + read-repair blocking — which is why Dynamo-style stores are explicitly eventually consistent, not linearizable.

How does consistent hashing with virtual nodes actually balance load and speed rebalancing?

Plain consistent hashing places each node at one random point on a ring; keys map to the next node clockwise. Problem: with few nodes the arcs are uneven (some nodes own huge ranges) and removing a node dumps its entire range onto a single neighbor. Virtual nodes fix both: each physical node is hashed to many points (100–256), so its ownership is the sum of many small arcs → statistically even load, and when a node dies its many small ranges scatter across many neighbors (not one), spreading the rebalancing load and speeding recovery. Adding a node steals ~1/N of keys total, drawn evenly from everyone. Weighted nodes (heterogeneous hardware) just get more vnodes. This is why Cassandra, DynamoDB, and Riak all use vnodes.

Explain phi-accrual failure detection and why it beats a fixed timeout.

A fixed heartbeat timeout is a binary, brittle choice: too short → false positives during transient slowness (triggers needless failovers/rebalances); too long → slow detection of real failures. Phi-accrual (used by Cassandra, Akka) instead outputs a continuous suspicion value φ derived from the statistical distribution (mean + variance) of recent inter-arrival times. φ = -log10(probability that a heartbeat this late is still "normal"). Apps set a threshold (e.g. φ=8 ≈ 1-in-10^8 chance of false positive) and can even use different thresholds for different actions (low φ to stop routing reads, high φ to trigger expensive rebalancing). It adapts automatically to a link that's normally 5ms vs one that's normally 50ms, giving far fewer false positives without sacrificing detection speed.

When do CRDTs shine and where do they fall down?

CRDTs (Conflict-free Replicated Data Types) are structures whose merge is commutative, associative, and idempotent, so replicas converge to the same value regardless of message order/duplication/delay — no coordination needed. State-based (CvRDT) ship whole state and merge via a join (lattice); op-based (CmRDT) ship operations that must be commutative. Great for: G-counters/PN-counters (likes, view counts), OR-sets (shopping carts, add/remove), LWW-registers, and sequence CRDTs (RGA/Logoot) powering collaborative editors like Figma/Confluence. Where they fall down: they only guarantee convergence, not arbitrary invariants — you can't express "balance must stay ≥0" or "at most 100 seats" because two replicas can independently make valid decisions that violate the global constraint after merge. They also carry metadata overhead (tombstones for removed elements) that must be garbage-collected. Use them for eventual-consistency data where any converged value is acceptable, not for invariants that need consensus.

Describe how you'd verify a distributed store is actually correct, not just "seems fine".

Unit tests can't catch timing/partition bugs, so you use property-based, fault-injecting verification. Jepsen is the standard: it drives concurrent client operations against a real cluster while a "nemesis" injects partitions, clock skew (bumping NTP), process pauses/kills, and packet loss (via iptables/tc netem); it records the full history of invocations/responses and then runs a checker (Knossos for linearizability, Elle for transactional isolation anomalies like G2/write-skew) to find any history that no legal single-copy execution could produce. Complement with chaos engineering in prod (Chaos Monkey/Chaos Mesh) under real traffic, deterministic simulation testing (FoundationDB's approach — run the whole system on a simulated network/clock so failures are reproducible), and continuous invariant checks (reconciliation jobs comparing replicas). The mindset: you can't prove correctness by testing the happy path — you have to actively inject the failures the system claims to survive.

How does Spanner give globally-consistent transactions, and what's the catch?

Spanner combines Paxos (per shard/"split", for replication and leader election), two-phase commit across shards (for multi-shard transactions), and TrueTime for ordering. On commit it picks a timestamp ≥ TrueTime.now().latest, then does commit-wait: it holds locks and waits until TrueTime.now().earliest > that timestamp — i.e., until it's certain the chosen timestamp is in the real past everywhere. This guarantees external (strict-serializable) consistency: if T1 commits before T2 starts in real time, T1's timestamp < T2's. The catch: latency. Commit-wait is proportional to TrueTime uncertainty ε (a few ms, kept small by GPS + atomic clocks in every datacenter), so every read-write transaction pays roughly 2ε plus cross-region Paxos/2PC round-trips. It's a deliberate PACELC PC/EC choice — pay latency to never give up consistency — and it's only feasible because Google built the clock infrastructure to keep ε tiny and bounded.

What is backpressure and load shedding, and how are they different from just autoscaling?

Autoscaling adds capacity over minutes — useless against a sub-second overload spike, and it can't scale a bottleneck like a single DB. Backpressure is flow control: a slow consumer signals upstream to slow down (bounded queues that block/reject when full, TCP-style windows, reactive streams' request(n), gRPC flow control) so producers don't overwhelm consumers and memory doesn't blow up. Load shedding is the last line: when you're already over capacity, deliberately drop or reject the lowest-value work (return 429/503, drop low-priority requests, degrade features) so the system serves some requests well instead of serving all requests badly (or dying). Together they prevent the metastable collapse where unbounded queues + retries turn a spike into an outage. The principle: it's better to reject 10% of traffic fast than to accept 100% and fail everything — and you should shed at the edge, cheaply, before the work consumes scarce resources.
