Advanced Hooks React

Beyond useState and useEffect sits a second tier of hooks that exist for specific, narrow problems: action-driven state transitions, measuring the DOM before paint, exposing an imperative handle, generating SSR-safe ids, keeping the UI responsive during expensive updates, and subscribing to state that lives outside React.

Each one has a precise reason to exist. Knowing which problem each solves — and when the plain hook is the right answer instead — is what separates a senior answer from a list of API names.

useReducer: state transitions as data

const [state, dispatch] = useReducer(reducer, initialArg, init?);
// reducer: (state, action) => newState        — a pure function
dispatch({ type: 'added', text });             // describe WHAT HAPPENED, not what to set

The optional third argument is a lazy initializer: React calls init(initialArg) once on mount, the same pattern as useState(() => …).

When it beats useState

  • Several fields change together. One dispatch({ type: 'submitFailed', error }) replaces three coordinated setters that could interleave inconsistently.
  • The next state depends on the meaning of an event, not just a value — form wizards, undo/redo, drag state, anything shaped like a state machine.
  • You want the logic testable. A reducer is a pure function; you can unit-test every transition with no component, no renderer, no DOM.
  • Deeply nested update logic is easier to read collected in one switch than scattered across handlers.

Rules

  • Reducers must be pure: same (state, action) in, same new state out. No fetches, no timers, no mutation, no Math.random() or Date.now() — put those in the action payload. (StrictMode double-invokes reducers in development to surface impurity.)
  • Return a new object when something changed; returning the identical reference makes React bail out of the re-render.
  • Actions describe events, past tense, from the user's point of view: 'added_todo', not 'setTodos'.
  • dispatch has a stable identity for the component's lifetime — it never needs to be in a dependency array, and it is safe to pass down through context without breaking memoized children.
Senior tip: useReducer + useContext is the standard dependency-free "global state" pattern: put state in one context and dispatch in another, so components that only dispatch never re-render when state changes.

useLayoutEffect vs useEffect

useEffectuseLayoutEffect
RunsAfter paintAfter DOM mutation, before paint
Blocks paintNoYes — synchronous
Use forEverything (default)Measuring or mutating layout to avoid a visible flicker
 
useLayoutEffect(() => {
  const { height } = ref.current.getBoundingClientRect();
  setTooltipTop(height > space ? top - height : top);   // reposition before the user sees it
}, [content]);

With useEffect the tooltip would paint in the wrong place for one frame and then jump. With useLayoutEffect React runs the measurement and the resulting re-render before the browser paints, so only the corrected position is ever shown.

Gotcha: it blocks painting, so heavy work here freezes the frame. And it does not run during server rendering — there is no layout on the server — which produces the familiar "useLayoutEffect does nothing on the server" warning. Default to useEffect; reach for the layout variant only when you have an actual flicker.

forwardRef and useImperativeHandle

Refs are not props in React 18: passing ref to a function component does nothing unless the component is wrapped in forwardRef. useImperativeHandle then lets you decide what the ref exposes, instead of handing out the raw DOM node.

const Modal = forwardRef(function Modal(props, ref) {
  const dialog = useRef(null);
  useImperativeHandle(ref, () => ({
    open:  () => dialog.current.showModal(),
    close: () => dialog.current.close(),
  }), []);                            // deps: recreate the handle only if these change
  return <dialog ref={dialog}>{props.children}</dialog>;
});

// parent
modalRef.current.open();              // a narrow, intentional API — no innerHTML access
React 19: ref is a normal prop for function components, so function Modal({ ref }) works and forwardRef is no longer needed (it stays supported, and is deprecated going forward). useImperativeHandle is unchanged and still the way to expose a curated handle.

Use it sparingly. Imperative handles are for things declarative props cannot express: focus(), scrollIntoView(), play(), opening a native dialog. Anything that is really state should be a prop.

useId

const id = useId();
<label htmlFor={id}>Email</label>
<input id={id} />

Generates an identifier that is stable between the server-rendered HTML and the client hydration, which a counter or Math.random() is not — a mismatch there breaks hydration. One call can supply several ids by suffixing: {`${id}-email`}, {`${id}-name`}.

useId is not for list keys. Keys must come from the data's own identity so React can match items across renders; a per-component id tells React nothing about which row is which.

Concurrent hooks: useTransition and useDeferredValue

React 18's concurrent renderer can prepare a render in the background and interrupt it when something more urgent arrives. These two hooks are how you mark work as interruptible.

const [isPending, startTransition] = useTransition();

function onChange(e) {
  setQuery(e.target.value);                       // urgent: the input must feel instant
  startTransition(() => setResults(filter(e.target.value)));   // non-urgent: interruptible
}
{isPending && <Spinner />}

Without a transition, one keystroke triggers one blocking render of a 10,000-row list, and the caret lags behind the typing. With it, the input updates immediately and the list render is thrown away and restarted as each new key arrives.

const deferredQuery = useDeferredValue(query);    // lags one render behind
const results = useMemo(() => filter(deferredQuery), [deferredQuery]);

Two limits worth knowing: updates inside startTransition must be synchronous, and transitions do not help a controlled input — never wrap the input's own value update, or the field itself will lag.

useSyncExternalStore and tearing

const value = useSyncExternalStore(
  subscribe,          // (onStoreChange) => unsubscribe
  getSnapshot,        // () => current value, must be cached/immutable
  getServerSnapshot?, // optional, for SSR/hydration
);

Tearing is the concurrent-rendering hazard this hook exists to prevent: because React can pause a render mid-tree, an external store that mutates during that pause can be read with one value by the components rendered before the pause and a different value by those rendered after. The single committed frame then shows two inconsistent values for the same piece of state — the UI is "torn".

State inside React cannot tear, because React renders from a consistent snapshot. Anything outside — a Redux store, a Zustand store, window.matchMedia, navigator.onLine, a raw event emitter — can. useSyncExternalStore forces those reads to be consistent within a commit and re-renders synchronously if the store changed underneath.

function useOnlineStatus() {
  return useSyncExternalStore(
    (cb) => {
      window.addEventListener('online', cb);
      window.addEventListener('offline', cb);
      return () => {
        window.removeEventListener('online', cb);
        window.removeEventListener('offline', cb);
      };
    },
    () => navigator.onLine,     // client snapshot
    () => true,                 // server snapshot
  );
}
Gotcha: getSnapshot must return a cached value. Returning a fresh object or array each call means Object.is always reports a change and React throws "The result of getSnapshot should be cached to avoid an infinite loop."

You rarely call this directly — it is the integration point library authors use. Redux, Zustand and Jotai already build on it, which is how they became concurrent-safe.

React 19 additions (clearly labelled)

  • use(promiseOrContext) — reads a promise or a context. Unlike other hooks it may be called conditionally and inside loops. With a promise it suspends the component until the promise resolves, integrating with Suspense and error boundaries.
  • useOptimistic(state, updateFn) — shows an optimistic value while an async action is in flight, and automatically reverts to the real state when it settles.
  • useActionState(action, initialState) — wraps a form action, returning [state, formAction, isPending]; pairs with <form action={formAction}> and Server Actions.

Also in 19: ref as a regular prop, ref callbacks that can return a cleanup function, and the React Compiler (separate, opt-in) which auto-memoizes and removes most manual useMemo/useCallback.

🎯 Interview questions

When would you choose useReducer over useState?

When several fields change together, when transitions are driven by named events rather than raw values (state-machine-shaped state), or when you want the transition logic unit-testable outside the component. A reducer is a pure function, so every transition can be tested with no renderer at all. dispatch also has a stable identity, which keeps memoized children and dependency arrays clean.

Why must a reducer be pure?

React may call it more than once for the same action — StrictMode double-invokes it in development, and concurrent rendering can replay work. Side effects would then run twice or produce different results. Keep fetches, timers, randomness and timestamps out; pass them in on the action payload.

useEffect or useLayoutEffect?

useEffect by default: it runs after paint and never blocks the frame. useLayoutEffect runs synchronously after DOM mutation but before paint, so use it only to measure or adjust layout when otherwise the user would see a flicker. It blocks painting and does not run during server rendering.

What is tearing, and how does useSyncExternalStore prevent it?

Concurrent rendering can pause mid-tree. If an external store mutates during that pause, components rendered before and after read different values and one committed frame shows inconsistent state. useSyncExternalStore subscribes and reads through a cached snapshot, forcing a consistent read within a commit and re-rendering synchronously if the store changed. React's own state cannot tear.

useTransition vs useDeferredValue?

Same mechanism, different entry point. Use useTransition when you own the state update — wrap the setState in startTransition and use isPending for a spinner. Use useDeferredValue when you only have the value, typically a prop: it renders with the old value first and re-renders with the new one at low priority.

Why not just use a counter for element ids?

Server and client would generate different sequences and hydration would mismatch. useId derives an id from the component's position in the tree, so it is identical on both. It must not be used for list keys, which need to come from the data's identity.

How do you expose an imperative API from a child component?

useImperativeHandle defines exactly what the parent's ref receives — { open, close } rather than the DOM node — keeping the surface narrow. In React 18 the component must be wrapped in forwardRef; in React 19 ref is a normal prop so forwardRef is unnecessary.
