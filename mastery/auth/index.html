Auth · OAuth2 / OIDC / JWT / mTLS Mastery

Authentication proves who you are; authorization decides what you may do. This page pushes past "we use JWTs and OAuth" into the token bytes, the signing algorithms, the PKCE dance, the revocation problem, JWKS key rotation, mTLS/SPIFFE for service-to-service, and the war-stories — the alg:none bypass, the token-in-localStorage XSS bleed, the OAuth mix-up attack — that separate an SDE2 from a Staff answer.

Interview Explanation — 30 seconds

Say this: "Authentication is proving identity; authorization is granting access. Modern systems delegate both. OAuth2 is an authorization-delegation framework — a client gets a scoped access token to call an API on the user's behalf without ever seeing their password; the default flow is Authorization Code + PKCE. OIDC layers authentication on top of OAuth2 by adding an ID token — a JWT that describes who the user is. A JWT is a signed header.payload.signature, base64url-encoded, verified with a shared secret (HS256) or a public key from a JWKS endpoint (RS256/ES256), so any service can validate it statelessly. For service-to-service we use mTLS, where both sides present X.509 certs — often SPIFFE identities in a service mesh. The core trade-off is stateless JWTs (fast, no lookup, hard to revoke) versus opaque server-side sessions (instant revocation, needs a shared store)."

Interview Explanation — 2 minutes

The fuller answer names the internals the interviewer is fishing for:

  • AuthN vs AuthZ. Authentication answers "who are you" (login, MFA, OIDC ID token). Authorization answers "what can you do" (scopes, RBAC roles, ABAC policies). OAuth2 is fundamentally about authorization delegation; people bolt authentication onto it with OIDC.
  • Sessions vs tokens. Classic sessions store state server-side and hand the browser an opaque, high-entropy session id in an httpOnly Secure SameSite cookie. Revocation is trivial — delete the row. The cost: every request hits a shared session store (Redis) so it scales horizontally. JWTs flip this: the token is the state, self-contained and signed, so any service verifies it with zero lookups — but you cannot un-issue it before exp without extra machinery.
  • JWT anatomy. Three base64url segments: header (alg, kid, typ), payload (registered claims iss/sub/aud/exp/nbf/iat/jti plus custom), and a signature over base64url(header) + "." + base64url(payload). HS256 uses one shared secret (symmetric); RS256/ES256 sign with a private key and let anyone verify with the public key published at a /.well-known/jwks.json endpoint keyed by kid.
  • The revocation problem. Because a JWT is valid until exp, the industry answer is short-lived access tokens (5–15 min) plus a long-lived refresh token that is rotated on every use and can be denylisted; theft of a refresh token is detected when an already-used token is replayed.
  • OAuth2 roles & grants. Resource owner (user), client (app), authorization server (issues tokens), resource server (the API). Authorization Code + PKCE is the default for web/SPA/mobile; Client Credentials is for machine-to-machine; Implicit and Resource-Owner-Password grants are deprecated.
  • OIDC additions. ID token, userinfo endpoint, standard scopes (openid profile email), and a discovery document. mTLS handles the trust between microservices where there is no human, typically via SPIFFE SVIDs issued by a service mesh.

Internal Working

End-to-end, the Authorization Code + PKCE flow plus JWT validation, step by step:

  1. PKCE prep. The client generates a random code_verifier (43–128 chars, high entropy) and derives code_challenge = base64url(SHA256(code_verifier)) with code_challenge_method=S256. This binds the eventual token exchange to this client instance, defeating authorization-code interception.
  2. Authorization request. Browser is redirected to the authorization server's /authorize with response_type=code, client_id, redirect_uri, scope, state (CSRF/round-trip binding), nonce (replay binding for the ID token), and the code_challenge.
  3. User authenticates. The authorization server runs its own login (password + MFA/TOTP, or an existing SSO session), obtains consent for the requested scopes, and 302-redirects back to redirect_uri with a short-lived, single-use code and the original state.
  4. Token exchange (back channel). The client POSTs to /token with grant_type=authorization_code, the code, redirect_uri, and the raw code_verifier. The server recomputes the SHA-256 and compares to the stored challenge. On match it returns access_token, refresh_token, and (for OIDC) id_token.
  5. JWKS fetch. The resource server reads the token header's kid, looks it up in a cached copy of /.well-known/jwks.json (a set of public keys). Cache-miss or unknown kid triggers a refetch — this is how key rotation works without redeploys.
  6. Signature verification. Recompute the signature over header.payload with the public key (RS256 = RSASSA-PKCS1-v1_5 + SHA-256; ES256 = ECDSA P-256 + SHA-256) and constant-time compare. Pin the expected alg from server config — never trust the token's own header, which is how alg:none and the RS256→HS256 confusion attack work.
  7. Claim validation. Check exp > now (with small leeway, e.g. 60s), nbf <= now, iss equals the expected issuer, and aud contains this resource server. Optionally check jti against a replay/denylist cache.
  8. Authorization decision. Map scopes/roles/claims to a permission decision (RBAC role check or ABAC policy evaluation), then serve the request. No database call needed for identity — that is the entire point.
Watch out: The signature proves integrity, not freshness. A stolen but unexpired token is fully valid. Short TTLs and token binding (DPoP / mTLS-bound tokens) are the only real mitigations.

Why was this built?

Before OAuth, the "password anti-pattern" reigned: to let a third-party app read your Gmail contacts, you literally handed the app your Google password. It could then do anything, forever, and you could only revoke by changing your password (breaking every other app). OAuth 1.0 (2007, HMAC request signing) fixed delegation but was painful to implement. OAuth 2.0 (RFC 6749, 2012) simplified it by leaning on TLS and bearer tokens.

Separately, stateful sessions worked fine for a single monolith but became a bottleneck in microservices and horizontally-scaled fleets: every service needed to hit the session store on every request, and sticky sessions broke elastic autoscaling. Self-contained signed tokens (JWT, JWS/JWE from the JOSE family) let any service verify identity locally. OIDC (2014) then standardized the "log in with X" flow because everyone was abusing OAuth2 for authentication in subtly insecure ways. mTLS/SPIFFE emerged because in a zero-trust mesh you cannot assume the network is safe — every service call must be mutually authenticated.

Advantages

  • Stateless verification. JWTs verify with a public key in microseconds; no round-trip to a session store, so services scale independently and survive store outages.
  • Delegation without password sharing. OAuth2 gives third parties scoped, revocable, time-limited access — the user's credentials never leave the authorization server.
  • Standardized & interoperable. OIDC discovery, JWKS, standard claims mean libraries interoperate across Auth0, Okta, Keycloak, Cognito, Google without custom glue.
  • Key rotation without downtime. The kid + JWKS pattern lets the IdP roll signing keys; verifiers pick up new keys automatically.
  • Fine-grained scoping. Scopes and audiences constrain a token to exactly one API and one set of operations.
  • mTLS = mutual trust + encryption in one handshake for the service tier, with SPIFFE giving portable, short-lived workload identity.

Drawbacks

  • Revocation is hard. A valid JWT cannot be recalled before exp without a denylist — which reintroduces the stateful lookup you were avoiding.
  • Token size. A fat JWT (many claims/roles) can be 1–4 KB, sent on every request; it inflates headers and can blow past proxy header limits (nginx large_client_header_buffers).
  • Client-side storage is a minefield. localStorage is XSS-readable; cookies invite CSRF. There is no perfectly safe browser storage.
  • Clock skew & JWKS caching bugs cause intermittent "invalid token" errors that are painful to debug.
  • OAuth is a framework, not a protocol — dozens of extensions (PKCE, PAR, DPoP, token introspection), and easy to implement subtly wrong (mix-up, open redirect).
  • mTLS operational cost. Cert issuance, rotation, and revocation (CRL/OCSP) at scale need a full PKI or a mesh CA.

Trade-offs

  • Statelessness vs revocability. Long JWT TTL = fewer refreshes but wider blast radius on theft. Short TTL = safer but more refresh traffic and more IdP load. Typical sweet spot: 5–15 min access token, 8–30 day rotating refresh token.
  • HS256 vs RS256/ES256. HS256 is faster and simpler but the verifier holds the signing secret — any verifier can forge tokens. Asymmetric keeps signing capability at the IdP only; mandatory the moment more than one party verifies. ES256 is smaller/faster than RS256 for equivalent strength.
  • Cookie vs Authorization header. Cookies get automatic CSRF exposure but httpOnly XSS protection; bearer headers avoid CSRF but require JS to hold the token (XSS exposure).
  • Access token in JWT vs opaque + introspection. JWT = fast local verify, stale until expiry; opaque + /introspect = instant revocation but a network hop per request.
  • Central gateway auth vs per-service. Gateway verifies once (simple, single choke point); per-service verify is defense-in-depth for zero-trust but duplicates JWKS handling.

When NOT to use it

Watch out: Do not reach for OAuth2/JWT when a plain session cookie is correct.
  • Simple first-party monolith login — a server-side session in Redis is simpler, instantly revocable, and has none of the JWT revocation pain. Don't build an OAuth server to log into your own app.
  • Storing sensitive data in the JWT payload — it is signed, not encrypted; anyone can base64-decode it. No PII, no secrets, no PANs.
  • Long-lived JWTs as "sessions" — a 30-day access token with no revocation path is a security incident waiting to happen.
  • mTLS for end-user browsers — distributing and rotating client certs to millions of users is operationally infeasible; use OIDC.
  • JWT as a database of record — putting mutable authorization state (roles that change often) in a token means stale permissions until expiry.

Production Architecture

A typical topology: an edge gateway terminates TLS and does coarse token validation; an identity provider owns login and token issuance; services do fine-grained authZ and talk to each other over mTLS inside a mesh.

flowchart TD
  U["Browser or SPA"] --> GW["API Gateway"]
  GW -->|"redirect to login"| IDP["Auth Server / OIDC IdP"]
  IDP -->|"JWKS public keys"| GW
  GW -->|"verified JWT"| SVC1["Orders Service"]
  SVC1 -->|"mTLS SPIFFE"| SVC2["Payments Service"]
  SVC1 -->|"mTLS SPIFFE"| SVC3["Inventory Service"]
  IDP --> RS["Refresh + session store Redis"]
  GW --> DENY["Denylist cache Redis"]

The gateway holds a cached JWKS and rejects unsigned/expired tokens at the edge, shedding bad traffic early. Valid requests carry the JWT (or a gateway-minted internal token) downstream. Service-to-service hops use mTLS with SPIFFE SVIDs issued by the mesh CA (Istio/Linkerd/SPIRE), so even inside the cluster every call is mutually authenticated and encrypted — zero-trust. The refresh-token store and the denylist live in Redis; revocation writes a jti to the denylist which the gateway checks for the short access-token window.

The refresh + rotation loop

sequenceDiagram
  participant C as "Client"
  participant A as "Auth Server"
  participant R as "Redis Store"
  C->>A: POST token grant_type refresh_token RT1
  A->>R: check RT1 valid and unused
  R-->>A: ok
  A->>R: invalidate RT1 store RT2
  A-->>C: new access token plus RT2
  C->>A: replay old RT1 stolen
  A->>R: RT1 already used
  A-->>C: reject and revoke whole family

This is refresh-token rotation with reuse detection: each refresh issues a new refresh token and invalidates the old one. If an already-consumed refresh token is ever presented, the server assumes theft and revokes the entire token family, forcing re-login.

Production Problems

  • JWKS unavailable / stale. IdP rotates keys, verifiers have a stale cache with no kid match, and every request 401s. Fix: cache with TTL + on-miss refetch + negative-cache backoff, and overlap-publish new keys before signing with them.
  • Clock skew. A verifier's clock is 90s fast; freshly issued tokens fail nbf/iat checks. Fix: NTP everywhere + small validation leeway.
  • Token bloat 431/502. Roles baked into the JWT grow; header exceeds proxy limits, causing "431 Request Header Fields Too Large" or upstream 502s. Fix: keep claims lean, move roles behind a lookup.
  • Refresh storms. Access TTL too short + many tabs → thundering herd on /token. Fix: jittered refresh, single-flight refresh per client, silent-renew coordination.
  • Redirect URI / open redirect abuse. Loose redirect_uri matching leaks codes/tokens. Fix: exact-match allowlist, no wildcards.
  • mTLS cert expiry. A workload cert expires mid-deploy and the whole service tier starts refusing connections. Fix: short SVIDs with automated rotation well before expiry (rotate at ~50% of lifetime).

Debugging Guide

Exact tools and signals:

# Decode a JWT without verifying (inspect header/claims)
echo "$TOKEN" | cut -d. -f1 | base64 -d 2>/dev/null   # header: alg, kid
echo "$TOKEN" | cut -d. -f2 | base64 -d 2>/dev/null   # payload: iss/aud/exp

# Human-friendly decode + verify against JWKS
jwt decode "$TOKEN"                     # mike-engel/jwt-cli
step crypto jwt verify --jwks jwks.json --iss "$ISS" --aud "$AUD" &lt; token

# See the IdP config and keys
curl -s https://idp.example.com/.well-known/openid-configuration | jq .
curl -s https://idp.example.com/.well-known/jwks.json | jq '.keys[].kid'

# Introspect an opaque/reference token
curl -s -u "$CID:$SECRET" -d "token=$TOKEN" https://idp/introspect | jq .

# Inspect an mTLS handshake and peer cert
openssl s_client -connect svc:8443 -cert client.pem -key client.key -CAfile ca.pem
openssl x509 -in cert.pem -noout -dates -subject -ext subjectAltName
  • 401 with valid-looking token → compare token kid to JWKS kids; check exp vs server clock; confirm aud matches this service.
  • Intermittent 401s → almost always JWKS cache/rotation or clock skew across a fleet.
  • mTLS "certificate verify failed" → check CA chain, SAN/SPIFFE ID mismatch, and cert dates.

Scaling

JWT verification is CPU-bound and embarrassingly parallel — each service verifies locally, so throughput scales with the fleet with no shared bottleneck. The stateful pieces (refresh store, denylist, session store) are what you must scale.

flowchart LR
  LB["Load Balancer"] --> G1["Gateway 1 JWKS cache"]
  LB --> G2["Gateway 2 JWKS cache"]
  LB --> G3["Gateway 3 JWKS cache"]
  G1 --> RC["Redis Cluster refresh and denylist"]
  G2 --> RC
  G3 --> RC
  G1 --> IDP["IdP autoscaled"]
  • Cache JWKS aggressively so the IdP is not on the hot path — verifiers only fetch keys on rotation.
  • Denylist stays small because access tokens are short-lived: entries expire at token exp, so it never grows unbounded.
  • Refresh/session store is the real scaling concern — shard Redis, or use Redis Cluster, and keep values small.
  • IdP is the choke point for logins, not for API traffic — scale it for peak login/refresh rate, not request rate.
  • Prefer ES256 over RS256 at extreme scale: smaller signatures, faster verify, less header bytes.

Security

  • alg confusion / alg:none. Attacker sets header alg:none (no signature) or swaps RS256→HS256 so the RSA public key is used as an HMAC secret. Mitigation: pin the accepted algorithm(s) server-side; never derive it from the token.
  • Weak HS256 secret. Short shared secrets are brute-forceable offline. Use ≥256-bit random secrets, or better, asymmetric keys.
  • Token leakage. Tokens in URLs (query strings) end up in access logs, referrer headers, and browser history. Keep them in headers/bodies; scrub tokens from logs.
  • XSS vs CSRF. localStorage tokens are stolen by any XSS; httpOnly Secure SameSite=Lax/Strict cookies resist both XSS reads and cross-site CSRF. Add anti-CSRF tokens if you must relax SameSite.
  • OAuth mix-up & open redirect. Validate state, iss in the response, and exact-match redirect_uri. Use PKCE even for confidential clients.
  • Replay. Bind tokens with jti + nonce, short TTLs, and consider sender-constrained tokens (DPoP, mTLS-bound tokens).
  • Password storage. Never plaintext, never fast hashes (MD5/SHA). Use argon2id (or bcrypt/scrypt), per-user salt, tuned work factor (bcrypt cost 12+, argon2 ~64MB memory), and pepper if feasible.
  • MFA/TOTP. RFC 6238 time-based codes over a shared secret; enforce for privileged actions. WebAuthn/passkeys are phishing-resistant and superior.

Performance

  • Verify latency. RS256 verify ≈ 0.1–1 ms; ES256 similar or faster; HS256 fastest (~microseconds). The bottleneck is rarely crypto — it is JWKS fetch, JSON parsing, and denylist lookups. Cache the parsed key object, not just the JWKS JSON.
  • Signing cost. RS256 signing is ~10–50× slower than verifying (RSA math); this hits the IdP, not verifiers — size the IdP for token-issuance rate.
  • Token size on the wire. Every request carries the token; a 2 KB JWT × millions of RPS is real bandwidth. Trim claims; ES256 signatures are ~64 bytes vs RS256 ~256+.
  • mTLS handshake. A full TLS 1.3 handshake with client auth adds ~1 RTT; amortize with connection reuse / keep-alive / session resumption so it is paid once per connection, not per request.
  • bcrypt/argon2 by design are slow (tens to hundreds of ms) — this is a feature for password checks, but never put them on a hot per-request path; they run at login only.
  • Tuning: raise JWKS cache TTL, keep denylist in local + Redis two-tier cache, batch introspection, and use ES256 to shrink both CPU and bytes.

Common Mistakes

  • Not verifying aud/iss. A token minted for service A is accepted by service B. Fix: always assert audience and issuer.
  • Trusting the token's alg. Enables alg:none / confusion. Fix: allowlist algorithms in verifier config.
  • Putting secrets/PII in the payload. It's public. Fix: only identifiers and claims; encrypt (JWE) if you truly must carry sensitive data.
  • Long-lived access tokens with no revocation. Fix: short access TTL + rotating refresh + denylist.
  • Storing tokens in localStorage. XSS = full account takeover. Fix: httpOnly Secure SameSite cookies, or in-memory + silent refresh.
  • Skipping PKCE / using Implicit grant. Fix: Authorization Code + PKCE everywhere, including SPAs.
  • Wildcard redirect_uri. Fix: exact-match allowlist.
  • Fast password hashing. Fix: argon2id/bcrypt with proper cost.
  • No key rotation. A single static signing key forever. Fix: kid + JWKS + scheduled rotation.

Interview Follow-up Questions

  1. What is the difference between authentication and authorization?
    1. AuthN = who you are (login, ID token); AuthZ = what you can do (scopes/RBAC/ABAC).
  2. Walk me through a JWT byte by byte.
    1. base64url(header).base64url(payload).signature; header has alg/kid, payload has iss/sub/aud/exp/iat/jti.
  3. HS256 vs RS256 — when each?
    1. HS256 shared secret, one trust party; RS256 asymmetric, mandatory when multiple parties verify.
  4. How does the verifier get the public key?
    1. Reads kid, fetches cached JWKS at /.well-known/jwks.json, refetches on unknown kid.
  5. What exactly do you validate on a JWT?
    1. Signature (pinned alg), exp/nbf, iss, aud, optionally jti against denylist.
  6. What is the alg:none attack?
    1. Token declares no signature; naive libs accept it. Fix: allowlist algorithms server-side.
  7. Why can't you just revoke a JWT?
    1. It's self-contained and valid until exp; need a denylist or short TTL + rotation.
  8. Explain access vs refresh tokens.
    1. Short-lived access token for API calls; long-lived refresh token to mint new access tokens, rotated on use.
  9. What is PKCE and what does it prevent?
    1. code_verifier/challenge binds the code exchange to the client; stops authorization-code interception.
  10. Which OAuth2 grant for a mobile app? For a cron job?
    1. Authorization Code + PKCE for the app; Client Credentials for the cron/machine.
  11. Why are Implicit and Password grants deprecated?
    1. Implicit leaks tokens via redirect/URL; Password grant makes the client handle credentials — both unsafe.
  12. How does OIDC differ from OAuth2?
    1. OIDC adds authentication: ID token (JWT about the user), userinfo endpoint, standard scopes.
  13. Sessions vs JWTs — trade-offs?
    1. Sessions: revocable, stateful, shared store. JWTs: stateless, fast, hard to revoke.
  14. How do you store tokens in a browser safely?
    1. httpOnly Secure SameSite cookies (or in-memory + silent refresh); never localStorage.
  15. How does mTLS establish service identity?
    1. Both peers present X.509 certs; SPIFFE SVID encodes workload identity; mesh CA issues/rotates.
  16. RBAC vs ABAC?
    1. RBAC = roles→permissions; ABAC = policy over attributes (user, resource, context) — finer but complex.
  17. How do you handle signing-key rotation with zero downtime?
    1. Publish new key in JWKS first, then start signing with new kid; verifiers pick it up via kid lookup.
  18. How do you detect refresh-token theft?
    1. Rotation + reuse detection: a replayed old refresh token revokes the whole family.
  19. What breaks under clock skew?
    1. exp/nbf/iat checks fail intermittently; fix with NTP + validation leeway.
  20. How do you scale token verification to millions of RPS?
    1. Local stateless verify + cached JWKS; only the refresh/denylist store needs scaling.

Production Scenarios

Incident 1 — Fleet-wide 401 storm after key rotation

SymptomsAll services start returning 401; error rate spikes to ~100% within seconds of an IdP deploy.
InvestigationDecode a failing token: its kid is not present in the verifiers' cached JWKS. IdP rotated the signing key and began signing with a new kid immediately.
Root CauseNew key was not published to JWKS before it was used for signing; verifiers' cache had no matching key and did not refetch fast enough.
SolutionForce JWKS refetch on all verifiers; roll IdP back to overlap-publishing keys.
PreventionPublish-then-sign: add new key to JWKS, wait past cache TTL, then switch signing. Verifiers refetch on unknown kid with backoff.
Interview Answer"Key rotation must publish the public key before signing with it, and verifiers must refetch JWKS on an unknown kid — otherwise there's a window where valid tokens can't be verified."

Incident 2 — Account takeovers via stolen tokens

SymptomsSupport reports users seeing others' data; fraud spikes from a range of IPs.
InvestigationTokens found in an SPA's localStorage; a third-party script had an XSS sink exfiltrating them. Access tokens were also long-lived (24h).
Root CauseTokens stored in localStorage (XSS-readable) + long TTL + no revocation.
SolutionMove tokens to httpOnly Secure SameSite cookies, cut access TTL to 10 min, add refresh rotation + denylist, rotate signing keys to invalidate outstanding tokens.
PreventionCSP to limit script origins, no tokens in JS-accessible storage, short TTLs, subresource integrity.
Interview Answer"localStorage tokens are one XSS away from mass takeover. httpOnly cookies + short TTL + rotation shrink the blast radius and let you actually revoke."

Incident 3 — Service tier goes dark at midnight

SymptomsAt 00:00 UTC, half the microservices start failing all outbound calls with TLS handshake errors.
Investigationopenssl s_client shows peer certs expired at midnight; mesh cert rotation job had silently failed the day before.
Root CausemTLS workload certs expired; automated rotation broke and there was no expiry alerting.
SolutionManually reissue SVIDs / restart SPIRE agents to re-mint certs; restore connectivity.
PreventionRotate at ~50% of cert lifetime, alert on cert_expiry_seconds at 25% remaining, and monitor the rotation job itself.
Interview Answer"Short-lived certs are safer but demand reliable rotation and expiry alerting; rotate at half-life, never at the edge of expiry."

Incident 4 — OAuth mix-up leaks authorization codes

SymptomsSecurity researcher reports that codes can be redirected to an attacker-controlled endpoint.
InvestigationApp supported multiple IdPs and did not validate which issuer returned the code; redirect_uri matching used a prefix wildcard.
Root CauseMissing issuer/state validation (mix-up attack) + loose redirect URI allowing an open redirect.
SolutionValidate state and the returned iss, enforce exact-match redirect_uri, require PKCE.
PreventionPer-IdP state binding, exact redirect allowlist, PKCE mandatory, adopt PAR where available.
Interview Answer"Mix-up attacks exploit multi-IdP clients that don't check which issuer replied; bind state, verify iss, and never wildcard redirect URIs."

Incident 5 — Refresh storm melts the IdP

🎯 Deep-dive Q&A — model answers

Why is a JWT signed but not encrypted, and what are the consequences?

A standard JWT is a JWS — signed for integrity/authenticity, not confidentiality. The payload is base64url, trivially decodable by anyone who holds the token. Consequence: never put secrets or PII in it. If you genuinely need confidential claims you use JWE (encrypted), but that's rare because the token flows over TLS anyway; the usual answer is "carry identifiers, not secrets." The signature guarantees the claims weren't tampered with; it says nothing about who can read them.

Explain the RS256→HS256 algorithm-confusion attack in detail.

If a verifier picks the algorithm from the token header and looks up "the key" generically, an attacker takes the server's public RSA key (which is public), sets the header to alg:HS256, and signs the token using that public key as the HMAC secret. The verifier, seeing HS256, does HMAC with the same public key and it validates. The fix is to pin the expected algorithm(s) from configuration and select the key type accordingly — RS256 tokens must be verified only with the RSA public key using RSA verification, never HMAC. Modern libraries require you to pass the allowed algorithms explicitly for exactly this reason.

How do you actually revoke a JWT before it expires?

Three layers. (1) Keep access tokens short (5–15 min) so the exposure window is small. (2) Maintain a denylist of jti values in Redis with a TTL equal to the token's remaining lifetime — checked at the gateway; it stays small because entries auto-expire. (3) For "log out everywhere" or key compromise, rotate the signing key (invalidates all tokens signed with the old kid) or bump a per-user token version claim that you check against a fast lookup. Refresh tokens are revoked directly since they're stored server-side.

Walk through PKCE and why confidential clients should also use it.

Client generates code_verifier, sends code_challenge=SHA256(verifier) on /authorize. On /token it sends the raw verifier; the server hashes and compares. An attacker who intercepts the authorization code (e.g., via a malicious app registered for the same custom URI scheme on mobile, or a leaked redirect) can't exchange it without the verifier, which never left the client. Even confidential clients (with a secret) benefit because it defends against code injection/replay independent of the client secret, and it's now recommended by OAuth 2.1 for all clients.

Sessions vs JWTs — give me the honest engineering answer, not the marketing one.

For a single first-party app, server-side sessions are usually the better choice: instant revocation, no key management, no revocation gymnastics, and Redis is cheap. JWTs win specifically when you have many independent services that must verify identity without a shared store, or cross-organization delegation. The common mistake is adopting JWTs for statelessness and then bolting on a denylist — at which point you've reinvented sessions with worse revocation. Pick JWTs for the microservice/delegation case; pick sessions for the monolith.

How does JWKS key rotation work end to end?

The IdP holds a keyset; each key has a kid. Tokens carry the signing kid in their header. Rotation is: generate a new keypair, add its public key to the JWKS document (now the set has both old and new), wait longer than the max verifier cache TTL so everyone has both keys, then switch the IdP to sign with the new kid. Old tokens still verify against the old key until they expire; then you retire the old key from JWKS. Verifiers fetch JWKS on startup, refresh on a TTL, and force-refresh when they see an unknown kid (with backoff to avoid stampeding the IdP).

What's the difference between the ID token and the access token in OIDC?

The ID token is for the client — it authenticates the user to the app (claims like sub, name, email, nonce to prevent replay, aud=client_id). You should not send it to APIs. The access token is for the resource server — it authorizes API calls (scopes, aud=API). Confusing them (sending the ID token to APIs) is a classic bug; APIs must reject tokens whose audience isn't them. The access token may be opaque or a JWT; the ID token is always a JWT.

Why is Client Credentials the right grant for service-to-service, and how does it differ from mTLS?

Client Credentials: a service authenticates with its own client_id/secret (no user) to get a scoped access token from the IdP, then calls APIs with it — good when you want centralized scoping and audit through the IdP. mTLS authenticates at the transport layer with certs and gives you mutual identity + encryption for the channel itself, with no IdP round-trip per token. They compose: mTLS for channel/workload identity in the mesh, plus a Client Credentials token carrying scopes for application-level authorization. Use both in a mature zero-trust setup.

How do you safely store tokens in a SPA?

Best: keep no long-lived token in JS at all — use the BFF (backend-for-frontend) pattern where the server holds tokens and the browser gets an httpOnly Secure SameSite session cookie; the BFF attaches the real token server-side. If you must hold a token client-side, keep the access token in memory only (lost on refresh, re-obtained via silent renew) and the refresh token in an httpOnly cookie. Never localStorage/sessionStorage — any XSS reads them. Pair with a strict CSP.

Explain SameSite cookie modes and how they relate to CSRF.

CSRF works because browsers auto-attach cookies to cross-site requests. SameSite=Strict withholds the cookie on all cross-site requests (breaks inbound links to authed pages). SameSite=Lax (default in modern browsers) sends it on top-level GET navigations but not on cross-site POST/XHR, killing most CSRF. SameSite=None (requires Secure) sends it everywhere — needed for cross-site embeds but reopens CSRF, so you add anti-CSRF tokens. Combine Lax + httpOnly + Secure for a solid default.

What is SPIFFE/SVID and why does a mesh need it?

SPIFFE is a standard for workload identity; an SVID is the credential — typically a short-lived X.509 cert whose SAN is a SPIFFE ID like spiffe://cluster/ns/orders/sa/orders-svc. SPIRE (the reference implementation) attests workloads (via k8s service account, node identity, etc.) and issues SVIDs that rotate automatically every few minutes to an hour. The mesh needs it because IP-based trust is meaningless in a dynamic cluster — pods come and go — so identity must be cryptographic and portable, and mTLS between services uses these SVIDs to mutually authenticate every call.

How should passwords be stored, and why not SHA-256?

Use a memory-hard, deliberately-slow adaptive hash: argon2id (preferred), scrypt, or bcrypt — each with a per-user random salt and a tuned cost so a single hash takes ~100–250ms. SHA-256 is a fast hash: a GPU computes billions per second, so a leaked table is cracked quickly. bcrypt/argon2 are slow and (argon2/scrypt) memory-hard, defeating GPU/ASIC parallelism. Add a server-side pepper (secret not in the DB) for defense in depth, and migrate cost factors upward over time. Never store plaintext, never reversible encryption.

RBAC vs ABAC — when do you outgrow RBAC?

RBAC maps users→roles→permissions; simple, cacheable, auditable. You outgrow it when access depends on attributes: resource ownership ("edit only your own docs"), context (time, IP, device posture), or relationships ("manager of the requester"). ABAC evaluates a policy over subject/resource/action/environment attributes (often with a policy engine like OPA/Cedar). The cost is complexity and harder reasoning about "who can access what." Many systems do RBAC for coarse gates + ABAC/ReBAC (relationship-based, like Google Zanzibar) for fine-grained resource access.

What's the token-introspection endpoint and when do you use it instead of local JWT verification?

/introspect (RFC 7662) lets a resource server send an opaque or reference token to the authorization server and get back {active, scope, sub, exp, ...}. You use it when tokens are opaque (not JWTs) or when you need real-time revocation checks that local JWT verification can't give. The cost is a network hop per request, so you cache introspection results for a few seconds. The design trade-off is the classic one: JWT = fast, stale until expiry; introspection = fresh, but a dependency and latency per call.

How do you propagate user identity across a chain of microservices?

Two patterns. (1) Token passthrough: forward the original access token downstream; each service verifies it and checks its own audience — clean but the token must be audienced for all of them, or you accept broad audiences. (2) Token exchange (RFC 8693): the gateway/service swaps the user token for a narrowly-scoped downstream token, preserving the original subject as an act/may_act claim — better least-privilege and clear delegation chains. Both ride over mTLS. Avoid the anti-pattern of stripping identity at the edge and trusting the network internally.

What breaks with clock skew and how do you make validation robust?

JWT time claims (exp, nbf, iat) are absolute epoch seconds compared against the verifier's clock. If a verifier is fast, freshly-issued tokens fail nbf/iat; if slow, expired tokens are wrongly accepted. Fixes: run NTP/chrony on every host, allow a small clock-skew leeway (30–60s) in the validation library, and keep access-token TTLs comfortably larger than expected skew. In multi-region fleets skew is the most common cause of "works on some pods, fails on others" 401s.
