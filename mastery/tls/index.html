TLS / SSL Mastery

TLS (Transport Layer Security, the successor to SSL) is the protocol that turns a raw TCP or UDP byte stream into an authenticated, confidential, integrity-protected channel. Senior interviews rarely stop at "it encrypts traffic" — they drill into the handshake state machine, ECDHE forward secrecy, the X.509 chain of trust, 0-RTT replay, OCSP soft-fail, and the classic cert-expiry outage. This page pushes past the basics into the wire-level internals.

Interview Explanation — 30 seconds

Say this: "TLS gives you three things over TCP: confidentiality, integrity, and server authentication. The handshake uses asymmetric crypto (an ECDHE key exchange plus a certificate signature) only to authenticate the server and agree on a shared secret. From that secret we derive symmetric AEAD keys — AES-GCM or ChaCha20-Poly1305 — and every byte after the handshake is bulk-encrypted with those cheap symmetric keys. Because the key-exchange keys are ephemeral, we get forward secrecy: stealing the server's private key later can't decrypt yesterday's traffic. TLS 1.3 does this in one round trip; 1.2 needed two."

Interview Explanation — 2 minutes

The fuller answer names the moving parts:

  • Two crypto systems, two jobs. Asymmetric (ECDHE for key agreement, RSA/ECDSA signatures for authentication) is used only during the handshake because it is ~1000x slower. Symmetric AEAD ciphers do the bulk data encryption because they are fast and hardware-accelerated (AES-NI).
  • Authentication via X.509. The server presents a certificate chain: leaf → intermediate → root. The client verifies each signature up to a root already in its trust store, checks validity dates, and checks the hostname against the certificate's SubjectAltName (SAN). The certificate is not the secret — it's a signed statement binding a public key to a domain.
  • Key agreement is ephemeral. ECDHE means both sides generate a throwaway key pair per connection, exchange public parts (X25519 or P-256 key_share), and combine them. The shared secret is fed through HKDF to derive handshake secrets, then application traffic secrets. Ephemeral keys give forward secrecy.
  • TLS 1.3 is a rewrite. It removed RSA key transport, static DH, RC4, CBC MACs, compression, and renegotiation. Only AEAD suites remain. The handshake is 1-RTT: the client speculatively sends its key_share in the ClientHello, so the server can reply with its key_share, encrypted certificate, CertificateVerify, and Finished in one flight. It also adds 0-RTT resumption.
  • Negotiation lives in extensions. SNI tells the server which virtual host (so it can pick the right cert), ALPN negotiates the app protocol (h2 vs http/1.1 vs h3), supported_versions selects TLS 1.3, and key_share/supported_groups pick the curve.

Internal Working

TLS 1.3 handshake — step by step (1-RTT)

  1. ClientHello. Client sends: a random nonce, a list of cipher suites (e.g. TLS_AES_128_GCM_SHA256), and extensions — supported_versions (advertises 1.3), supported_groups (X25519, secp256r1), key_share (an actual ephemeral X25519 public key, guessing the group), server_name (SNI, plaintext), signature_algorithms, and application_layer_protocol_negotiation (ALPN).
  2. ServerHello. Server picks a cipher suite and group, and returns its own key_share. At this instant both sides can compute the ECDHE shared secret.
  3. Key schedule. The raw ECDHE secret is run through HKDF-Extract/Expand with labels ("c hs traffic", "s hs traffic") to derive handshake traffic secrets. From this point, everything is encrypted.
  4. EncryptedExtensions. Remaining non-secret negotiation (ALPN result, etc.), now under handshake keys.
  5. Certificate. Server sends its X.509 chain (leaf + intermediates), encrypted.
  6. CertificateVerify. Server signs a transcript hash of everything so far with the private key matching the leaf cert's public key. This proves it owns the key, binding the cert to this handshake.
  7. Finished (server). An HMAC over the full transcript using a derived finished_key — integrity check that nothing was tampered with (anti-downgrade).
  8. Client verifies the chain, hostname (SAN), dates, and the CertificateVerify signature; then derives application traffic secrets.
  9. Finished (client) flight, plus optional early application data. Channel is now open.

TLS 1.2 handshake — why it needed 2-RTT

  1. ClientHello (no key_share — 1.2 negotiates the group first).
  2. ServerHello + Certificate + ServerKeyExchange (contains the ECDHE params + signature) + ServerHelloDone. First round trip done.
  3. Client sends ClientKeyExchange (its ECDHE public), ChangeCipherSpec, Finished.
  4. Server ChangeCipherSpec + Finished. Second round trip. Only now can data flow.
Say this: "The reason 1.3 saves a round trip is that the client guesses the key-exchange group and pre-sends its key_share in the ClientHello. If it guessed wrong, the server sends a HelloRetryRequest and you fall back to 2-RTT."

Record layer

After the handshake, application bytes are chunked into TLS records (max 16 KB plaintext), each sealed with an AEAD cipher. AEAD (Authenticated Encryption with Associated Data) means the same operation encrypts and authenticates — no separate MAC, no padding oracle. A per-record nonce is derived from a static IV XOR'd with the record sequence number, so nonces never repeat under one key.

Why was this built?

  • The pre-TLS world was plaintext. HTTP, FTP, Telnet, SMTP all sent credentials and data in the clear. Anyone on the path — a coffee-shop Wi-Fi sniffer, a malicious ISP, a compromised router — could read and modify traffic (a man-in-the-middle).
  • SSL 2.0 (1995, Netscape) was the first attempt, quickly broken. SSL 3.0 (1996) was better but died to POODLE in 2014. TLS 1.0 (1999) was SSL 3.1 rebranded under the IETF.
  • TLS 1.2 (2008) added SHA-256, AEAD suites, and became the workhorse of the 2010s.
  • TLS 1.3 (2018, RFC 8446) was a security-and-latency-driven redesign after a decade of attacks (BEAST, CRIME, Lucky13, Heartbleed context, downgrade attacks) taught the community that "negotiable legacy options" are a liability. It ripped out everything non-forward-secret and non-AEAD.

Advantages

  • Forward secrecy by default in 1.3 (ephemeral ECDHE) — compromise of the long-term key doesn't retroactively decrypt captured traffic.
  • Hardware-accelerated bulk crypto. AES-GCM runs at multiple GB/s per core with AES-NI; TLS overhead is single-digit % CPU at scale.
  • Ubiquitous PKI. The CA/browser trust store means clients authenticate servers with zero prior contact.
  • AEAD everywhere in 1.3 eliminates whole attack classes (padding oracles, MAC-then-encrypt bugs).
  • 1-RTT and 0-RTT make encryption nearly latency-free for repeat visitors.
  • Layer-agnostic: works under HTTP, gRPC, SMTP, AMQP, Postgres, Kafka, etc.

Drawbacks

  • Handshake latency on first connect: 1-2 extra round trips before any data. Painful on high-RTT links (satellite, cross-region).
  • Certificate operations are a liability — the number one cause of TLS outages is expired certs, not crypto breaks.
  • Revocation is broken in practice — CRLs are huge, OCSP is slow and privacy-leaking, and browsers soft-fail (treat "can't reach OCSP" as "OK").
  • Observability cost: encrypted traffic is opaque to network monitoring/IDS; you must terminate or use SSLKEYLOGFILE to inspect.
  • 0-RTT is replayable and must be handled carefully.
  • Complexity: version/cipher/curve negotiation is a big attack surface historically.

Trade-offs

  • Security vs latency: 0-RTT resumption saves a round trip but opens a replay window. You trade a bit of safety for speed and must restrict it to idempotent requests.
  • Termination location: terminate at the edge (LB/CDN) for cheap central cert management and observability, or run end-to-end mTLS for zero-trust — but then you manage certs on every pod.
  • Session resumption vs forward secrecy: long-lived session tickets encrypted under a static ticket key can undermine forward secrecy if that key isn't rotated frequently.
  • Cipher choice: AES-GCM is fastest with AES-NI hardware; ChaCha20-Poly1305 wins on mobile/ARM without AES acceleration. Servers should prefer per-client.
  • OCSP stapling improves privacy and latency but adds a moving part that can itself fail (stale/expired staple).

When NOT to use it

Watch out: Don't reach for TLS termination-then-plaintext across an untrusted hop and call it "secure end-to-end" — it isn't. And don't add TLS where it buys nothing:
  • Loopback-only IPC on the same host (unix sockets) where the kernel already isolates — TLS just adds CPU and cert headaches.
  • Inside a trusted, physically isolated network segment where the compliance model already covers it (though zero-trust says encrypt anyway).
  • Ultra-constrained IoT devices that can't do ECDHE at your required rate — consider pre-shared-key TLS-PSK or DTLS profiles instead of full X.509.
  • When you need message-level end-to-end secrecy through intermediaries — TLS only protects hop-by-hop; use app-layer encryption too.

Production Architecture

A typical layered deployment terminates TLS at the CDN/edge for public traffic, re-encrypts to origin, and runs mTLS between internal services via a service mesh sidecar. Certs come from public CAs (ACME/Let's Encrypt) at the edge and from an internal CA (e.g. mesh CA / Vault PKI) inside.

  U["Client browser"] -->|"TLS 1.3 public cert"| CDN["CDN edge"]
  CDN -->|"TLS re-encrypt"| LB["Regional load balancer"]
  LB -->|"TLS termination"| GW["API gateway"]
  GW -->|"mTLS sidecar"| S1["Service A"]
  GW -->|"mTLS sidecar"| S2["Service B"]

  VAULT -.->|"short lived certs"| S2
  • Edge: public certs, HSTS enabled, OCSP stapling on, ALPN negotiates h2/h3.
  • Origin hop: re-encrypted; the LB validates the origin cert or a pinned CA.
  • Mesh: mTLS with short-lived (hours) certs auto-rotated by the mesh control plane (Istio/Linkerd) — no human touches these.

Production Problems

  • Cert expiry outage — the classic. A cert on a rarely-touched internal service or an intermediate expires; everything depending on it hard-fails at midnight UTC.
  • Chain incomplete — server sends only the leaf, not the intermediate. Works in browsers that cache the intermediate, fails in curl/Java/mobile. Intermittent and maddening.
  • Clock skew — a host with a wrong clock rejects valid certs as "not yet valid" or "expired."
  • SNI mismatch — client omits SNI (old Java, some IoT) and gets the wrong virtual host's default cert.
  • Protocol/cipher mismatch after disabling TLS 1.0/1.1 — legacy clients can't connect.
  • OCSP stapling stale — the staple expires and strict clients (Must-Staple) reject; soft-fail clients proceed.
  • Session ticket key not rotated — undermines forward secrecy across the whole fleet.
  • Handshake CPU spike under a connection storm (no keep-alive, no resumption) — asymmetric ops saturate CPU.

Debugging Guide

# Full handshake, chain, negotiated version and cipher
openssl s_client -connect example.com:443 -servername example.com -tls1_3

# Show the leaf cert dates, SANs, issuer
openssl s_client -connect example.com:443 -servername example.com &lt;/dev/null 2&gt;/dev/null \
  | openssl x509 -noout -dates -subject -issuer -ext subjectAltName

# Verify the chain server actually sends (missing intermediate?)
openssl s_client -connect example.com:443 -showcerts

# Check OCSP stapling
openssl s_client -connect example.com:443 -status -servername example.com | grep -A5 "OCSP"

# Test a specific protocol / cipher is offered or refused
openssl s_client -connect example.com:443 -tls1_2 -cipher ECDHE-RSA-AES128-GCM-SHA256

# Decrypt in Wireshark: export session keys
export SSLKEYLOGFILE=/tmp/keys.log   # then point Wireshark TLS pref at it
  • Signals to read: Verify return code (0 = ok, 10 = expired, 20 = unable to get local issuer = missing intermediate, 21 = self-signed in chain).
  • curl -vI https://host to see the negotiated protocol and cert error without a browser cache masking a missing intermediate.
  • SSL Labs / testssl.sh for a full posture scan (protocols, ciphers, HSTS, forward secrecy, chain).
  • nmap --script ssl-enum-ciphers -p443 host to enumerate accepted ciphers.

Scaling

TLS scales along two axes: handshake throughput (asymmetric, expensive) and bulk throughput (symmetric, cheap). You attack the expensive part with resumption and offload.

flowchart TD
  C1["New client"] -->|"full handshake ECDHE"| LB["TLS terminator pool"]
  C2["Returning client"] -->|"PSK resumption ticket"| LB
  LB -->|"session ticket key"| KMS["Shared ticket key store"]
  LB -->|"offload"| NIC["AES NI or QAT card"]
  LB --> APP["App servers plaintext or reencrypt"]
  • Session resumption (tickets/PSK) skips the certificate + signature, cutting a full handshake to a fast symmetric one — the biggest throughput lever.
  • Shared ticket keys across the terminator pool so any node can resume any session; rotate them (e.g. hourly) to preserve forward secrecy.
  • Keep-alive / connection reuse and HTTP/2 multiplexing amortize one handshake over many requests.
  • Hardware offload: AES-NI is universal; dedicated cards (Intel QAT) offload ECDHE for extreme handshake rates.
  • Terminate at the edge to concentrate cert management and CPU on a specialized fleet.

Security

  • Downgrade attacks: a MITM strips the ClientHello to offer only weak versions. Mitigations: TLS_FALLBACK_SCSV (signals "this is a fallback, reject if you support better"), and the Finished MAC covering the whole transcript so any tampering breaks the handshake. TLS 1.3 also embeds a downgrade sentinel in the ServerHello random.
  • Renegotiation attacks: the 2009 renegotiation flaw allowed prefix injection. TLS 1.3 removed renegotiation entirely; 1.2 needs the renegotiation_info (RFC 5746) extension.
  • HSTS: Strict-Transport-Security: max-age=31536000; includeSubDomains; preload forces HTTPS and stops SSL-strip. Preloading bakes it into browsers.
  • SNI leaks the hostname in plaintext — a network observer sees which site you visit. ECH (Encrypted Client Hello) encrypts the SNI under a public key published in DNS (HTTPS/SVCB records).
  • Revocation: CRL (big lists), OCSP (per-cert query, privacy leak + latency), OCSP stapling (server fetches and staples, fixing both), Must-Staple (cert flag forcing strict validation). The soft-fail problem: most clients treat an unreachable OCSP responder as "valid," so revocation is weak in practice — hence short-lived certs as the real answer.
  • mTLS / zero trust: both sides present certs; identity is cryptographic, not a bearer token that can leak. Foundation of service meshes (SPIFFE/SPIFFE IDs in SAN URIs).
  • Weak crypto: disable TLS 1.0/1.1, RC4, 3DES, CBC suites, static RSA key exchange. Require forward-secret ECDHE suites.

Performance

  • Handshake latency: 1.2 = 2-RTT (~2x your RTT before data); 1.3 = 1-RTT; resumption/0-RTT = 0 added RTT. On a 100 ms RTT link, that's 200 ms saved going 1.2 → 1.3+resumption.
  • Asymmetric cost: an ECDHE + ECDSA handshake is thousands of times pricier than a symmetric record op. A single core does tens of thousands of ECDSA-P256 signs/sec; resumption is ~10x cheaper.
  • Bulk throughput: AES-128-GCM with AES-NI hits multiple GB/s/core; ChaCha20-Poly1305 is comparable in software and faster on non-AES-NI ARM.
  • Record size: 16 KB max plaintext per record; small first records (dynamic record sizing) reduce time-to-first-byte by not buffering a full 16 KB.
  • Tuning knobs: enable session tickets (ssl_session_tickets on), size the session cache (ssl_session_cache), set ssl_buffer_size 4k for latency-sensitive, prefer ECDHE + AEAD, enable OCSP stapling, turn on 0-RTT only for idempotent GETs.

Common Mistakes

  • Serving an incomplete chain (leaf only). Fix: concatenate leaf + intermediates in ssl_certificate; verify with openssl s_client -showcerts.
  • No expiry monitoring. Fix: alert at &lt;21 days on every cert; automate renewal with ACME.
  • Manual renewal on many hosts expiring the same day. Fix: automate + stagger expiry so a bug doesn't take everything down at once.
  • Enabling 0-RTT for all methods. Fix: restrict early data to idempotent, non-state-changing requests; add anti-replay windows.
  • Using CN for hostname. Fix: CN is deprecated for hostname matching; modern clients require SAN — put every name in subjectAltName.
  • Never rotating session ticket keys. Fix: rotate hourly/daily to preserve forward secrecy.
  • Trusting soft-fail OCSP for security. Fix: use short-lived certs + stapling; use Must-Staple only if you can guarantee the staple.
  • Pinning certs in mobile apps rigidly. Fix: pin to the intermediate/public key with backup pins, or you brick the app on rotation.

Interview Follow-up Questions

  1. What does TLS actually provide over TCP?
    1. Confidentiality, integrity, and server authentication (optionally client auth).
  2. Why use both asymmetric and symmetric crypto?
    1. Asymmetric only for auth + key agreement (slow); symmetric AEAD for bulk data (fast, hardware-accelerated).
  3. Walk me through the TLS 1.3 handshake.
    1. ClientHello with key_share → ServerHello + encrypted cert + CertificateVerify + Finished → client Finished; 1-RTT.
  4. Why is 1.3 one round trip when 1.2 was two?
    1. Client pre-sends its ephemeral key_share, guessing the group, so the server can reply in one flight.
  5. What is forward secrecy and where does it come from?
    1. Ephemeral ECDHE keys per connection; stealing the long-term key later can't decrypt captured sessions.
  6. How are the actual encryption keys derived?
    1. ECDHE shared secret fed through HKDF-Extract/Expand with labels into handshake then application traffic secrets.
  7. What is AEAD and why does 1.3 require it?
    1. Combined encrypt+authenticate (AES-GCM, ChaCha20-Poly1305); removes padding-oracle and MAC-order bugs.
  8. Explain the certificate chain of trust.
    1. Leaf signed by intermediate signed by root in the client trust store; verify signatures + dates + SAN up the chain.
  9. SAN vs CN — which matters?
    1. SAN; CN is deprecated for hostname matching and ignored by modern clients.
  10. What does SNI do and what's its privacy problem?
    1. Selects the virtual host so the server picks the right cert; it's plaintext, leaking the hostname — ECH fixes it.
  11. What is ALPN used for?
    1. Negotiates the application protocol (h2 / http/1.1 / h3) inside the handshake.
  12. How does session resumption work and what's the risk?
    1. Session IDs / tickets / PSK skip cert+signature; static ticket keys undermine forward secrecy unless rotated.
  13. What is 0-RTT and why is it dangerous?
    1. Early data on resumption saves a round trip but is replayable; restrict to idempotent requests + anti-replay windows.
  14. How is a cert revoked and why is revocation weak?
    1. CRL/OCSP/stapling; clients soft-fail on unreachable responders, so short-lived certs are the practical fix.
  15. What is mTLS and where is it used?
    1. Both sides present certs; cryptographic identity for zero-trust service meshes.
  16. How do downgrade attacks work and how are they stopped?
    1. MITM strips to weak versions; TLS_FALLBACK_SCSV, transcript Finished MAC, and 1.3 downgrade sentinel prevent it.
  17. Where should you terminate TLS?
    1. Edge for central management/observability; end-to-end mTLS for zero-trust, at the cost of per-pod cert ops.
  18. What's the number-one cause of TLS outages?
    1. Expired certificates — automate renewal (ACME) and monitor days-to-expiry on every endpoint.
  19. How would you scale TLS to millions of handshakes/sec?
    1. Resumption + shared rotating ticket keys, keep-alive, edge termination, AES-NI/QAT offload.
  20. Why did TLS 1.3 remove RSA key transport?
    1. Static RSA key exchange has no forward secrecy — one stolen key decrypts all past traffic.

🎯 Deep-dive Q&A — model answers

Walk me through exactly what bytes cross the wire in a TLS 1.3 handshake and when encryption begins.

The ClientHello goes in plaintext: client random, cipher suite list, and extensions including supported_versions (1.3), supported_groups, an actual X25519 key_share, SNI, ALPN, and signature_algorithms. The server replies with ServerHello (its key_share, chosen suite) in plaintext — but the instant both sides have each other's key_share, they compute the ECDHE shared secret and run HKDF to derive handshake traffic secrets. From EncryptedExtensions onward everything is encrypted: EncryptedExtensions, Certificate, CertificateVerify (signature over the transcript proving key ownership), and the server Finished (HMAC over the transcript). The client verifies the chain and signature, derives application secrets, sends its Finished, and data flows. So only ClientHello and ServerHello are ever cleartext.

Why does CertificateVerify exist if the client already has the certificate?

Because possessing a certificate proves nothing — certs are public. CertificateVerify is a signature, made with the private key corresponding to the leaf cert's public key, over a hash of the entire handshake transcript. It proves the server actually controls the private key and binds that proof to this specific handshake (preventing replay of a captured signature). Without it, anyone could present someone else's cert.

Explain the HKDF key schedule — why not just use the ECDHE secret directly as the AES key?

The raw ECDHE output isn't uniformly random and you need many independent keys (client/server handshake, client/server application, finished keys, resumption secret). HKDF-Extract first "whitens" the shared secret into a pseudorandom key; HKDF-Expand then derives each labeled key ("c hs traffic", "s ap traffic", etc.) from it. Distinct labels guarantee the keys are cryptographically independent, and mixing in the transcript hash binds the keys to what was actually negotiated, defeating tampering.

How does forward secrecy actually work, and how did TLS 1.2 with static RSA lack it?

Forward secrecy comes from ephemeral key exchange: each connection generates a fresh ECDHE key pair, uses it once, and discards it. The long-term certificate key only signs — it never encrypts the session key. So capturing traffic and later stealing the cert's private key yields nothing. Old TLS 1.2 RSA key transport had the client encrypt the premaster secret to the server's long-term RSA public key; anyone who later obtained that private key could decrypt every recorded session. That's why 1.3 removed static RSA/DH entirely.

What's the difference between session IDs, session tickets, and PSK resumption?

Session IDs (1.2) require the server to store session state keyed by an ID — stateful, hard to share across a pool. Session tickets (1.2/1.3) push the state to the client: the server encrypts the session under a server-held ticket key and hands it back; on resume the client presents the ticket, keeping the server stateless. In 1.3 this is unified as PSK (pre-shared key) resumption — the ticket becomes a PSK identity used in the ClientHello's pre_shared_key extension, enabling 1-RTT or 0-RTT resumption. The catch: the ticket key must be rotated, or forward secrecy is lost for resumed sessions.

Why is 0-RTT replayable when nothing else in TLS is?

0-RTT early data is encrypted under a key derived solely from the PSK (the resumption secret) — there's no fresh server contribution yet, because the whole point is the client sends data before hearing from the server. Without a server nonce mixed in, an attacker can capture the early-data flight and replay it to the same or another server in the pool, and it'll decrypt and process identically. Mitigations: single-use tickets, anti-replay windows (bounded by clock skew) tracked across the fleet, and — most importantly — only allowing 0-RTT for idempotent requests plus server-side idempotency keys.

Walk through chain validation and the common failure codes.

The client builds a path from the leaf up to a trust anchor: verify each certificate's signature was made by the next issuer's key, check each is within its notBefore/notAfter window, check basic constraints (CA:TRUE for issuers, path length), check key usage / EKU (serverAuth), and match the requested hostname against the leaf's SubjectAltName. It must terminate at a root already in the trust store. Common openssl verify codes: 0 = OK, 10 = certificate expired, 20 = unable to get local issuer (missing intermediate), 21 = unable to verify the first certificate / self-signed, 18 = self-signed in chain. Code 20 is the classic incomplete-chain bug.

SNI is plaintext — what actually leaks and how does ECH fix it?

SNI carries the target hostname in the ClientHello so a server hosting many domains picks the right cert. Because it's cleartext, a passive observer learns exactly which site you're visiting even though the payload is encrypted (and DNS may be encrypted via DoH). ECH (Encrypted Client Hello) fixes this: the server publishes an ECH public key in a DNS HTTPS/SVCB record; the client encrypts the sensitive part of the ClientHello (including the real SNI) to that key, sending only an outer, generic "public" SNI in the clear. The fronting server decrypts the inner ClientHello and routes accordingly. It relies on many domains sharing one ECH config to provide an anonymity set.

Why is certificate revocation considered broken, and what's the modern answer?

CRLs are large and slow to distribute. OCSP queries a responder per-certificate, adding latency and leaking to the CA which sites you visit. OCSP stapling fixes latency/privacy by having the server fetch and attach ("staple") a recent signed OCSP response — but it can go stale or the server can just omit it. The killer is soft-fail: if the OCSP responder is unreachable, virtually all browsers proceed as if the cert is valid, so an attacker who can block OCSP defeats revocation. Must-Staple hardens this per-cert but risks outages if stapling breaks. The practical answer the industry converged on is short-lived certificates (days to hours, auto-rotated) so the revocation window is tiny and you rarely need to revoke at all.

How does mTLS give you zero-trust identity, and how is it operationally different from server-only TLS?

In mTLS both peers present certificates and each verifies the other's chain, so a service's identity is a cryptographically-verifiable cert (often a SPIFFE URI in the SAN) rather than a bearer token that can be stolen and replayed. This is the backbone of zero-trust meshes: every hop authenticates both ends regardless of network location. Operationally it multiplies the cert-management problem — now every workload needs a cert and a rotation story. Meshes (Istio, Linkerd) solve this with a control-plane CA issuing very short-lived certs to sidecars automatically, so humans never touch them. The trade-off is added latency/CPU per connection and heavy dependence on the mesh control plane.

Explain downgrade attacks and every layer of defense against them.

A MITM tampers with the ClientHello to remove strong options, forcing a weak protocol/cipher. Defenses stack: (1) the Finished message is an HMAC over the entire handshake transcript, so any modification breaks it; (2) TLS_FALLBACK_SCSV is a signaling cipher that a client includes when it deliberately retries with a lower version — a server that supports higher rejects it, catching forced fallbacks; (3) TLS 1.3 embeds a sentinel in the last 8 bytes of the ServerHello random ("DOWNGRD\x01") that a genuine 1.3-capable server sets when negotiating 1.2, so a 1.3 client detects the downgrade; (4) HSTS prevents protocol-level SSL-strip by forcing HTTPS at the browser.

Where would you terminate TLS in a large architecture and why?

Usually a hybrid. Terminate public TLS at the CDN/edge and the regional load balancer: it centralizes public cert management and OCSP stapling, concentrates handshake CPU on a specialized fleet, and lets you inspect/route traffic. Then re-encrypt the origin hop (edge→origin TLS) so the internal network isn't cleartext. Inside the cluster, run end-to-end mTLS via mesh sidecars for zero-trust service identity. The trade-off axis is management simplicity + observability (edge termination) versus true end-to-end confidentiality and cryptographic identity (mTLS everywhere), at the cost of per-workload cert operations.

AES-GCM vs ChaCha20-Poly1305 — how do you choose?

Both are AEAD and equally secure when used correctly. AES-128/256-GCM is fastest on hardware with AES-NI (essentially all modern x86 and recent ARM), reaching multiple GB/s per core. ChaCha20-Poly1305 is a software stream cipher that's faster and more constant-time on devices without AES acceleration — older phones, low-end ARM, some embedded. Best practice: the server offers both and lets the client's preference (advertised order) or a per-client policy pick, so mobile clients get ChaCha and datacenter clients get AES-GCM. The one hard rule for GCM is never repeat a nonce under the same key — TLS handles this via the sequence-number-derived nonce.

How do you scale to millions of handshakes per second without melting CPUs?

The expensive part is the per-handshake asymmetric operation (ECDHE + signature), not the symmetric bulk crypto. Levers, in order of impact: (1) maximize session resumption — tickets/PSK turn a full handshake into a cheap symmetric one, aim for &gt;60% resumption; (2) share and rotate ticket keys across the whole terminator pool so any node can resume any session (rotate hourly to keep forward secrecy); (3) connection reuse — keep-alive and HTTP/2 multiplexing amortize one handshake over thousands of requests; (4) hardware offload — AES-NI is free, and Intel QAT cards can offload ECDHE for extreme rates; (5) only then scale out terminator nodes. Load-testing must exercise handshake rate, not just steady-state throughput, because the storm is on new connections.

A cert rotation bricked our mobile app. What went wrong and how should pinning be done?

The app almost certainly pinned the leaf certificate's exact public key or fingerprint; when the cert rotated, the new key didn't match any pin and every install failed TLS. Correct pinning pins higher and with backups: pin the intermediate CA or an SPKI (public key) hash, and always ship at least one backup pin for a key you'll rotate to next, so rotation is seamless. Include an expiry/kill-switch and a remote-config path to update pins. Many teams have moved away from hard pinning toward Certificate Transparency monitoring plus short-lived certs because rigid pinning is a self-inflicted outage risk.

How would you debug a report of "TLS handshake failed" from one client population only?

First reproduce with openssl s_client -connect host:443 -servername host and read the negotiated version, cipher, and Verify return code. Compare a working vs failing client's offered protocols/ciphers with nmap --script ssl-enum-ciphers — a failing population usually has no cipher/version overlap after a hardening change. Check -showcerts for a missing intermediate (fails strict clients only). Check clock skew on the client (not-yet-valid errors). Confirm SNI is sent (old Java/clients that omit it get the default vhost cert). For deep inspection, set SSLKEYLOGFILE and decrypt in Wireshark to see exactly which flight fails and the alert code (e.g. handshake_failure(40), protocol_version(70), certificate_expired(45)). The alert code usually names the root cause directly.
