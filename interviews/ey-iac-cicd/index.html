IaC, CI/CD & Testing EY Sheet 08

The JD lists CloudFormation and Terraform as primary skills and CI/CD, automated builds, testing and deployments as secondary. In a 60-minute round this is usually 5–8 minutes of rapid fire near the end. You don't need syntax; you need to show you understand declarative desired state, drift, and why nobody touches the console in production.

The line that wins this section: "Every environment I own is reproducible from source. If someone deleted the whole account, I could rebuild it from the repo plus the data backups. That means no console changes in anything above dev, IaC reviewed through pull requests like application code, and pipelines that assume a role via OIDC rather than holding long-lived keys."

CertainWhat is Terraform state, and why is it dangerous?

State (terraform.tfstate) is Terraform's map from your configuration to real-world resource IDs, plus cached attributes and dependency metadata. Terraform needs it to know that aws_instance.web means instance i-0abc123 — without it, Terraform can't tell "create this" from "this already exists".

Why it's dangerous:

  • It contains secrets in plaintext — database passwords, generated keys, anything a resource returns. So the backend must be encrypted and access-controlled like a credential store, and state must never be committed to git.
  • Concurrent applies corrupt it. Two engineers or two pipeline runs applying simultaneously can produce a state that no longer matches reality. Hence state locking — an S3 backend with DynamoDB for locks (or S3's native locking now), or Terraform Cloud.
  • Losing it is worse than losing the code. Terraform will try to create everything again, colliding with resources that already exist. Hence versioning on the S3 bucket, so you can roll back a bad state.
  • Manual state surgery (state rm, import, mv) is occasionally necessary and is the highest-risk operation in the tool — always back up the state file first.

And the blast-radius point: I split state by environment and by lifecycle — networking in one state, data stores in another, applications in a third — so an apply on the app layer can never accidentally propose destroying the VPC. One giant state file for a whole account is an outage waiting for a bad plan.

Depth probeWhat is drift, how do you detect it, and how do you handle it?

Drift is when the real infrastructure no longer matches what the code and state say it should be — almost always because someone changed something in the console during an incident, or an auto-scaling process or a managed service mutated a resource.

Detect: terraform plan refreshes state against the real world and shows the difference; running it on a schedule in CI (a nightly drift check that alerts if the plan is non-empty) turns drift from a surprise into a ticket. CloudFormation has native drift detection; AWS Config can continuously evaluate resource compliance.

Handle, and the key point is that the response depends on why it drifted: if the console change was wrong, apply to revert. If the console change was right — an emergency fix during an incident — you back-port it into the code and then apply, so the fix survives the next deployment. If the resource is legitimately managed outside Terraform (an auto-scaling desired count, a tag applied by a governance tool), add a lifecycle { ignore_changes = [...] } so it stops showing up as noise.

The cultural answer matters as much: drift is a symptom of the console being reachable. I'd move production access to read-only for humans, with break-glass roles that are alerted on and time-boxed, so console changes become a deliberate, logged event rather than a habit.

How do you structure IaC for multiple environments?

Modules for reusable components (a "service" module producing an ECS service, task definition, target group, alarms and log group), and thin per-environment root configurations that call those modules with different variables. The environment difference should be parameters — instance sizes, counts, CIDRs — not forked copies of the code, because forked environments drift apart and then "it worked in staging" stops meaning anything.

Separate AWS accounts per environment, not just separate VPCs — it's the strongest blast-radius boundary AWS offers and it makes cost attribution trivial. Separate state per environment, with the pipeline assuming a different role per account.

On Terraform workspaces: I mostly avoid them for environment separation. They share a backend and a configuration, so a mistake is one CLI flag away from hitting prod, and they encourage conditional logic in the code (count = terraform.workspace == "prod" ? 3 : 1) that becomes unreadable. Separate directories with separate backends are more verbose and much safer.

Finally, version and pin: pin provider versions and module versions, so an apply next month produces the same result as today. An unpinned provider means your infrastructure can change because someone else released software.

CI/CD

CertainWalk me through the pipeline you'd build for a Node.js service on AWS.

Triggered on pull request and on merge to main, with different scopes:

  1. On PR: install with a locked dependency tree (npm ci), lint, type-check, unit tests, integration tests against Testcontainers, build the container image, and run security scanning — dependency audit, SAST, IaC scanning (tfsec/checkov), and a container image scan. Plus terraform plan posted as a PR comment so the reviewer sees the infrastructure diff alongside the code diff. Nothing merges without a green pipeline and a review.
  2. On merge: build once, tag the image with the git SHA, push to ECR. The same artifact is promoted through every environment — never rebuilt per environment, because a rebuild is a different artifact and invalidates everything you tested.
  3. Deploy to dev/staging automatically, run smoke tests and a short load test against the SLO.
  4. Production behind a manual approval gate (or fully automated with canary + automatic rollback if the team's maturity supports it). Deploy strategy: rolling or blue/green via CodeDeploy, with CloudWatch alarms wired as the rollback trigger so a deploy that raises the error rate reverts itself.
  5. Post-deploy: verify health, watch the error budget, and annotate the dashboards with the deploy marker so the next person debugging can correlate.

Cross-cutting: the pipeline authenticates to AWS via OIDC federation, assuming a role per environment — no long-lived access keys in CI secrets. Least privilege per stage, so the dev deploy role literally cannot touch production.

Blue/green vs canary vs rolling — and how do you roll back?

Rolling: replace instances in batches. Cheapest, no extra infrastructure, but rollback means another rolling deploy (slow) and two versions serve traffic simultaneously, so backward compatibility is mandatory.

Blue/green: full parallel environment, flip the load balancer target group, keep blue warm. Rollback is instant — flip back — which is why I'd choose it for anything high-stakes. Costs double capacity during the window, and stateful concerns (in-flight sessions, database migrations) need thought.

Canary: shift 1% → 10% → 50% → 100% with automated metric evaluation between steps. Best risk-to-cost ratio if you have trustworthy metrics and automated rollback; without those it's just a slow rolling deploy with extra steps.

The honest closing point: the rollback path matters more than the deploy strategy. I'd rather have a boring rolling deploy with a tested one-command rollback than a sophisticated canary nobody has ever reverted. And database migrations don't roll back with the code — that's why expand/migrate/contract is a hard requirement, not a nicety.

How do you handle secrets in a pipeline?

Nothing long-lived, and nothing in the repository. Concretely: CI authenticates to AWS through OIDC federation — GitHub Actions or GitLab presents a signed identity token, AWS trusts the provider and issues short-lived STS credentials scoped by a trust policy that pins the repo and branch. That removes the single biggest secret from the pipeline.

Application secrets are never injected by the pipeline at all — the running workload reads them from Secrets Manager or SSM Parameter Store at startup using its own task/execution role. The pipeline therefore never sees production credentials, which means a compromised build agent doesn't hand over the database.

Supporting controls: secret scanning in pre-commit and on push, masked output in CI logs (and the awareness that masking is defeated by base64-encoding, so scanning matters more), short-lived environment-scoped roles, and an approval gate on the job that can touch production. For third-party tokens with no OIDC option, store them in the platform's secret store scoped to a protected environment, and rotate on a schedule.

Quality & security in the SDLC

What security checks live in your pipeline?
  • SCA / dependency scanning — npm audit, Snyk or Dependabot against the lockfile. Most real-world vulnerabilities arrive through transitive dependencies, not your code.
  • SAST — static analysis on the source (CodeQL, SonarQube, Semgrep) for injection, unsafe deserialisation, hard-coded secrets.
  • Secret scanning — gitleaks/trufflehog on the diff and on history.
  • IaC scanning — checkov, tfsec or cfn-nag catching a public S3 bucket, an unencrypted volume, or an over-broad security group before it exists rather than in a quarterly audit.
  • Container scanning — Trivy or ECR scanning on the built image, plus a policy against running as root and against :latest tags.
  • DAST — running the deployed staging environment against OWASP ZAP for the authenticated paths.

The policy point that matters: gate the build on new high and critical findings rather than on the total count. A pipeline that fails on 400 pre-existing medium findings gets bypassed within a week, and a bypassed gate is worse than no gate.

The JD says "defect prevention" — what does that mean beyond writing tests?

Tests catch defects; prevention stops them being written. The levers I'd name:

  • Make invalid states unrepresentable — strict TypeScript, discriminated unions, branded ID types, schema validation at every boundary. A whole class of bugs becomes a compile error.
  • Shift left — the same checks run in pre-commit hooks and in CI, so feedback arrives in seconds rather than at review time.
  • Design review before implementation for anything non-trivial. The cheapest defect to fix is one in a document.
  • Blameless post-incident reviews with action items that are tracked. The question isn't "who broke it" but "what made this failure possible, and what class of failure does the fix eliminate". A post-mortem whose only output is "be more careful" has prevented nothing.
  • Definition of done that includes observability — a feature isn't done without logs, metrics and an alarm that would catch it failing.
  • Track escaped defects by root cause over time, so you fix categories rather than instances.
