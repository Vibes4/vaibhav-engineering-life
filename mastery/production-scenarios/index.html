Production Scenarios Mastery

This page is a battle-tested incident-response reference: for every failure mode an interviewer can throw at you ("the database is at 100% CPU — what do you do?"), you get the exact symptoms, the exact command to run, the real root cause, the fast mitigation, the durable prevention, and a crisp way to narrate it. The meta-skill under all of it is the same: stabilize first, diagnose second, root-cause third, prevent fourth — and always mitigate before you fully understand.

Interview Explanation — 30 seconds

Say this: "Every incident I run the same loop. Symptoms — what's the customer-facing pain and which SLO is burning. Hypothesize — what changed (deploy, traffic spike, dependency). Verify with data — confirm the hypothesis against metrics, logs, and traces before touching anything. Mitigate fast — roll back the last deploy, scale out, shed load, or fail over; restore the customer first even if I don't yet know the root cause. Root-cause — blameless 5-whys once the bleeding stops. Prevent — a runbook entry, an alert on the leading indicator, and a regression test so it never pages me twice for the same reason."

Interview Explanation — 2 minutes

The full lifecycle an interviewer wants to hear is detect → triage → mitigate → diagnose → RCA → prevent:

  • Detect: A page fires from an SLO burn-rate alert (e.g. "2% error budget burned in 1 hour" — a fast-burn multi-window alert), not from a raw threshold. Detection should be on symptoms (elevated error rate / p99 latency), not causes.
  • Triage & severity: Assign a SEV. SEV1 = major outage / data loss / payments down, all-hands, exec comms. SEV2 = significant degradation, key feature broken. SEV3 = minor/partial, single tenant. SEV4 = cosmetic. Declare the incident, open a channel/bridge, name an Incident Commander (drives), a Comms lead, and an Ops/scribe.
  • Mitigate: Fastest lever wins — roll back the last deploy (usually the cause), scale out replicas, shed load (rate-limit / drop non-critical traffic), fail over to a healthy replica/region, flip a feature flag. Time-to-mitigate matters more than elegance.
  • Diagnose: Use the four golden signals — latency, traffic, errors, saturation — plus the RED (Rate/Errors/Duration) and USE (Utilization/Saturation/Errors) methods. Metrics tell you where, traces tell you which hop, logs tell you why.
  • RCA: Blameless post-mortem, 5 whys, timeline with UTC timestamps, contributing factors, and action items with owners and due dates.
  • Prevent: Runbook, alert on the leading indicator, chaos/load test, and a guardrail (constraint, circuit breaker, quota).
Watch out: Don't diagnose before you mitigate. Interviewers love the candidate who says "I'd roll back first and investigate from logs afterward" over the one who wants to attach a debugger to prod while customers are down.

The First 5 Minutes

A concrete on-call playbook the moment the pager goes off:

  1. 0:00 — Ack the page. Silence the alarm so it stops re-paging. Read the alert: which SLO, what threshold, which service.
  2. 0:30 — Open the service dashboard. Look at the four golden signals for the last 1h and 24h. Is it errors, latency, or saturation? Is it one endpoint or all?
  3. 1:00 — "What changed?" Check the deploy timeline. kubectl rollout history deploy/api, the CI/CD dashboard, feature-flag changes, config/infra changes, and any dependency's status page. 70%+ of incidents correlate with a recent change.
  4. 2:00 — Decide: mitigate now. If a deploy correlates, roll it back: kubectl rollout undo deploy/api or flip the flag off. Don't wait for full understanding.
  5. 3:00 — Declare if needed. If customer impact is real and mitigation isn't instant, declare a SEV, open the incident channel, and post the first status: "Investigating elevated 5xx on checkout, started 14:32 UTC, IC is me."
  6. 4:00 — Comms cadence. Post updates every 15-30 min even if "still investigating." Internal stakeholders + status page for customers. Silence during an incident is the real failure.
Say this: "My first question is always 'what changed in the last hour?' — deploy, flag, config, traffic, or a dependency. Then I mitigate against that hypothesis before I fully diagnose."

Golden Signals & Where to Look

The four golden signals (Google SRE) and the tool I reach for each:

SignalWhat it tells youKey metricTool
LatencyHow slow — split success vs error latencyp50/p95/p99 request durationPrometheus histograms + Grafana, distributed traces (Jaeger/Tempo)
TrafficHow much demandrequests/sec, QPS per endpointPrometheus rate(http_requests_total[1m])
ErrorsRate of failure, explicit + implicit5xx rate, error ratioGrafana error panel, log aggregation (Loki/ELK/Datadog)
SaturationHow full the system isCPU %, memory %, connection pool used, queue depth, event-loop lagtop/htop, node_exporter, cAdvisor, DB pool metrics

RED (Rate, Errors, Duration) for request-driven services; USE (Utilization, Saturation, Errors) for resources like DB/disk/CPU. Start at the edge (load balancer 5xx), then walk inward with traces to find the slow/failing hop, then open logs on that hop.

Database Incidents

Database CPU reaches 100%

SymptomsAPI p99 latency spikes, query timeouts, connection pool waits, error rate climbing. DB host CPU pinned at 100%.
InvestigationPostgres: SELECT pid, now()-query_start AS dur, state, query FROM pg_stat_activity WHERE state!='idle' ORDER BY dur DESC; and pg_stat_statements ordered by total_exec_time. MySQL: SHOW FULL PROCESSLIST;, pt-query-digest on the slow log, SHOW ENGINE INNODB STATUS. On the host: top to confirm it's the DB process, not a neighbor. Run EXPLAIN ANALYZE on the top offender.
Root CauseUsually a missing index causing a sequential scan on a large table, a bad plan after stats went stale, a new N+1 from a recent deploy, or a runaway analytics query on the primary. Sometimes a lock storm / autovacuum contention.
SolutionKill the runaway: SELECT pg_terminate_backend(pid);. Add the missing index (CREATE INDEX CONCURRENTLY in Postgres to avoid a table lock). Roll back the offending deploy. If a report is hammering the primary, move it to a read replica. Short term: scale up the instance / add read replicas.
PreventionSlow-query alerts (queries > 500ms), pg_stat_statements in CI perf tests, index review on new queries, mandatory EXPLAIN on migrations, separate OLAP replica, statement timeout (statement_timeout=5s).
Interview Answer"First I confirm it's the DB and not a noisy neighbor with top. Then pg_stat_activity ordered by duration to find the hog, EXPLAIN ANALYZE to see the seq scan. I kill the query to restore service, add a concurrent index or route reports to a replica, then add a slow-query alert so it's caught in staging next time."

Dashboard query taking 30 seconds

SymptomsOne analytics/dashboard endpoint is slow while the rest of the app is fine. Gateway 504s on that route.
InvestigationEXPLAIN (ANALYZE, BUFFERS) — look for Seq Scan, huge rows removed by filter, nested loops over millions of rows, or a sort spilling to disk (external merge Disk). Check if it aggregates over unbounded date ranges.
Root CauseAggregation over raw rows with no covering index, no date-range bound, or joins producing a cross-product. Real-time GROUP BY over months of events.
SolutionAdd composite/covering index on the filter+sort columns; pre-aggregate into a materialized view or rollup table refreshed on a schedule; paginate; cap the date range. Cache the result in Redis with a short TTL.
PreventionMaterialized views / summary tables for dashboards, query budget per endpoint, async report generation for heavy exports.
Interview Answer"Dashboards should never run a live aggregate over raw event tables. I'd EXPLAIN it, confirm the seq scan, then move it to a materialized rollup refreshed every few minutes and cache the response — turning 30s into single-digit ms."

Connection pool exhausted

SymptomsErrors like timeout acquiring a connection from the pool / remaining connection slots are reserved. Requests queue and time out even though DB CPU is low.
InvestigationCompare app pool size × replica count vs DB max_connections. Postgres: SELECT count(*), state FROM pg_stat_activity GROUP BY state; — lots of idle in transaction is the smoking gun. Check for a leaked connection (missing release in a code path) or long transactions holding connections.
Root CausePool too small for load, connections leaked (not released on error paths), idle in transaction holding connections, or too many app replicas × pool size overwhelming the DB. A slow query holding connections longer under load = cascading exhaustion.
SolutionImmediate: bounce the app to reset the pool, kill idle-in-transaction sessions. Add PgBouncer (transaction pooling) so many app connections share few DB connections. Set idle_in_transaction_session_timeout. Fix the leak. Right-size the pool (total connections ≤ DB max with headroom).
PreventionMetric + alert on pool utilization > 80%; connection lifetime cap; PgBouncer in front; ensure every acquire has a finally-release; statement timeout.
Interview Answer"Pool exhaustion with low DB CPU means connections are held, not busy — usually idle-in-transaction or a leak. I check pg_stat_activity by state, kill the idle transactions, and put PgBouncer in front so app-side pool size decouples from DB max_connections."

Replication lag

SymptomsReads return stale data ("I updated my profile but it shows the old one"), read replicas fall behind. In queues, downstream sees old state.
InvestigationPostgres: SELECT now()-pg_last_xact_replay_timestamp() AS lag; or compare pg_current_wal_lsn() vs pg_last_wal_replay_lsn(). MySQL: SHOW SLAVE STATUS\G → Seconds_Behind_Master. Check replica CPU/IO and long-running queries blocking WAL replay on the replica.
Root CauseWrite burst outpacing replica apply, a big batch/migration flooding WAL, replica underpowered, or a long read query on the replica blocking replay (Postgres single-threaded replay conflict).
SolutionRoute critical reads to the primary temporarily (read-your-writes), throttle the write batch, scale up the replica, kill blocking queries on the replica. For consistency-sensitive reads, use "read from primary within N seconds of a write."
PreventionAlert on lag > 5-10s; batch writes in chunks; monotonic-read / sticky routing after writes; separate replicas for heavy reporting.
Interview Answer"I measure lag directly with pg_last_xact_replay_timestamp. If it's a write burst, I throttle the batch; if it's a blocking read on the replica, I kill it. For correctness I route read-your-writes traffic to the primary for a short window after each write."

MongoDB primary crashes

SymptomsWrites fail with not master / NotWritablePrimary for a few seconds, brief write unavailability, then recovery.
Investigationrs.status() to see member states and who's PRIMARY now; rs.printReplicationInfo() for oplog window; check mongod logs for the crash cause (OOM, disk full, segfault). Confirm the driver reconnected.
Root CauseHost OOM (WiredTiger cache too large), disk full, hardware failure, or a network partition. Election takes a few seconds during which writes to the old primary fail.
SolutionReplica set auto-elects a new primary (needs majority). Ensure the app uses retryWrites=true and w:majority so a single failover is transparent. Fix the crashed node's root cause and rejoin. Restore the failed member from a healthy secondary if data is corrupt.
PreventionOdd number of voting members (3/5), an arbiter or hidden member for quorum, retryWrites, memory limits sized below host RAM, disk-usage alerts, oplog window > peak downtime.
Interview Answer"A single primary crash should be a non-event: with a 3-node replica set, retryWrites=true, and w:majority, the driver retries the write against the newly elected primary. My job is to fix the crashed node's root cause — usually OOM or disk — and rejoin it."

Replica-set election / failover

SymptomsElevated write errors during a ~2-12s window, temporary read-preference confusion, apps logging "topology changed."
Investigationrs.status() during/after; check for repeated elections (flapping) — a sign of network instability or an overloaded primary failing heartbeats. Review electionMetrics.
Root CausePrimary lost majority heartbeat (network blip, GC/IO pause, CPU saturation), or planned maintenance stepdown. Flapping = heartbeat timeouts too tight or a struggling node.
SolutionLet the election complete; ensure clients use majority write concern + retryable writes. For flapping, isolate the unhealthy member (rs.freeze()), fix the network/resource issue, tune settings.electionTimeoutMillis if truly needed.
PreventionDeploy members across AZs, stable low-latency links, priority settings to prefer a strong node, avoid arbiters in split-brain-prone topologies, monitor election count.
Interview Answer"An election is expected during failover; the concern is repeated elections. I look at rs.status for flapping, which almost always traces to network latency between AZs or a resource-starved primary missing heartbeats, and I stabilize that node."

Cache Incidents

Redis memory full (OOM / eviction)

SymptomsOOM command not allowed when used memory > 'maxmemory' on writes, sudden cache-miss surge, DB load spikes as cache stops absorbing reads.
Investigationredis-cli INFO memory → used_memory, maxmemory, evicted_keys, mem_fragmentation_ratio. redis-cli --bigkeys to find memory hogs. INFO keyspace to see keys without TTL. Check the maxmemory-policy.
Root CauseNo TTLs so keys accumulate forever, a few giant keys (a 2GB list/hash), fragmentation, or genuine growth past capacity. Policy set to noeviction so writes fail instead of evicting.
SolutionSet maxmemory-policy allkeys-lru (or volatile-lru) so it evicts instead of erroring; add TTLs to cache keys; split/expire big keys; scale memory or shard. Flush cold data. Check fragmentation and consider activedefrag.
PreventionEvery cache key gets a TTL; alert on used_memory > 80% of maxmemory and on evicted_keys rate; ban unbounded keys; capacity planning; separate cache from any persistence use-case.
Interview Answer"OOM on writes usually means noeviction plus keys with no TTL. I set allkeys-lru so it evicts gracefully, run --bigkeys to find the whale keys, and enforce TTLs. Long term I alert on used_memory percentage, not just OOM errors."

Redis cache stampede (thundering herd)

SymptomsA popular key expires and thousands of concurrent requests all miss and hit the DB simultaneously — DB CPU spikes to 100%, latency cliff, sometimes a full outage.
InvestigationCorrelate a DB load spike with a cache-miss spike at a round TTL boundary. Traces show many requests running the same expensive query at the same millisecond.
Root CauseMany keys share the same TTL and expire together, or one hot key expires with no coordination, so every request recomputes it.
SolutionSingle-flight / mutex: first miss takes a short SET key lock NX PX 5000 lock and recomputes; others wait or serve stale. TTL jitter: add ±10% randomness so keys don't expire in lockstep. Stale-while-revalidate: serve the old value while one worker refreshes. Pre-warm hot keys.
PreventionRandomized TTLs, per-key recompute lock, request coalescing at the app layer, background refresh for known-hot keys.
Interview Answer"Stampede is a coordination problem: N requests recomputing the same expired key. I fix it three ways — TTL jitter so they don't expire together, a single-flight lock via SET NX so only one request recomputes, and stale-while-revalidate so the rest serve slightly-old data instead of hammering the DB."

Hot key

SymptomsOne Redis shard/node is CPU-pinned while others idle; latency on operations touching one key (e.g. a celebrity's profile, a flash-sale product counter).
Investigationredis-cli --hotkeys (needs LFU), MONITOR briefly to spot a dominating key, per-shard CPU from INFO. Look for a single key with millions of ops/sec.
Root CauseAccess skew — one key far hotter than the keyspace, so consistent hashing can't spread the load; that key's single shard is the bottleneck.
SolutionReplicate the hot key across N copies (key#1..key#N) and read a random one; add a local in-process cache (L1) in front of Redis (L2) for that key; use client-side caching. For counters, shard the counter and sum.
PreventionDetect skew via key-access metrics, design for known hot entities (celebrities, flash sales) with local caching and key fan-out from day one.
Interview Answer"A hot key defeats sharding because it all lands on one node. I fan it out into N replica keys and read a random one, and I add a short-lived in-process L1 cache so the hottest reads never even reach Redis."

Cache-DB inconsistency

SymptomsUsers see stale data after an update; cache and DB disagree; the wrong value persists until TTL.
InvestigationTrace a write path: did it update DB then cache, or cache then DB? Look for a race where a concurrent read repopulates a just-deleted key with the old value.
Root CauseWrite-through/write-behind race, or the classic cache-aside race: reader misses, fetches old DB value, and writes it to cache after the writer's invalidation. Dual-write with no ordering guarantee.
SolutionPrefer cache-aside with invalidate-on-write (delete the key, don't update it) so the next read repopulates fresh. Use short TTLs as a safety net. For strict cases, delayed double-delete (delete, write DB, delete again after a short delay), or drive invalidation off the DB change stream / CDC (Debezium).
PreventionSingle source of truth = DB; cache is disposable; never dual-write two systems as if atomic; TTL bounds staleness; CDC-based invalidation for correctness-critical data.
Interview Answer"I invalidate rather than update the cache on writes, and keep a short TTL as a backstop. The subtle bug is the read-repopulate race — I handle it with delayed double-delete or by driving invalidations off the DB's change stream so ordering is guaranteed."

Messaging & Streaming Incidents

RabbitMQ consumer stuck

SymptomsQueue depth climbing, messages_unacknowledged high and not draining, consumers "connected" but not processing.
Investigationrabbitmqctl list_queues name messages messages_unacknowledged consumers; check consumer_utilisation in the management UI. Thread dump / event-loop check on the consumer — is it blocked on a downstream call or deadlocked? Is prefetch too high so one consumer grabbed everything?
Root CauseConsumer blocked on a slow/hung downstream (DB, HTTP), a poison message it keeps failing on, prefetch (QoS) too large so unacked messages pile on one consumer, or it crashed without closing the channel.
SolutionRestart/scale consumers; lower prefetch (basic.qos prefetch=10-50); add a dead-letter exchange so poison messages don't block the queue; add per-message timeout + nack-with-requeue-limit. Fix the blocked downstream.
PreventionDLQ with max-retries, sane prefetch, consumer heartbeats, ack only after successful processing, idempotent handlers, alert on unacked count and consumer_utilisation.
Interview Answer"Stuck consumer = messages delivered-unacked but not progressing. I check consumer_utilisation and prefetch. Usually it's a blocked downstream or a poison message. I add a DLQ so poison messages route out instead of blocking, and cap prefetch so work spreads."

Queue backlog growing

SymptomsQueue depth rising steadily, end-to-end processing latency growing, SLA for async jobs breached.
InvestigationCompare produce rate vs consume rate (both as msgs/sec). Is production spiking or consumption dropping? Check consumer CPU, downstream latency, and errors causing requeues.
Root CauseProducers outpacing consumers — traffic spike, a slow downstream throttling consumers, or consumers scaled too low. Requeue loops artificially inflating both rates.
SolutionScale consumers horizontally (add pods / partitions); optimize the handler; batch downstream calls; apply backpressure / rate-limit producers; shed low-priority messages. Autoscale on queue depth (KEDA).
PreventionKEDA/HPA autoscaling keyed on queue length, capacity headroom, priority queues, backpressure at producers, alert on backlog growth rate (derivative), not just absolute depth.
Interview Answer"I compare produce vs consume rate — a growing backlog is just produce > consume. Fastest lever is scaling consumers (autoscale on queue depth with KEDA); if the downstream is the limiter I batch calls or shed low-priority work."

Message duplication

SymptomsThe same side effect happens twice — two emails, two charges, two inventory decrements.
InvestigationTrace message IDs — same logical event processed twice. Check whether the consumer acks before or after processing, and whether a redelivery happened after a consumer crash.
Root CauseAt-least-once delivery is the norm: a consumer processes, crashes before ack, and the broker redelivers. Retries and rebalances also cause redelivery. There is no true exactly-once across a network without idempotency.
SolutionMake handlers idempotent: dedupe on a message/business key stored in a processed_messages table with a UNIQUE constraint, or use an idempotency key. For Kafka, enable the idempotent producer + transactions for exactly-once within the pipeline, but the consumer side still needs dedupe.
PreventionDesign every consumer to be idempotent from day one; unique constraints on effect tables; store processed offsets/keys; treat exactly-once as "at-least-once + idempotent."
Interview Answer"I never rely on exactly-once delivery — I design idempotent consumers. Each message carries a key I record in a table with a unique constraint; a duplicate hits the constraint and I skip the side effect. That's how you make at-least-once safe."

Kafka consumer lag

SymptomsConsumer group lag (latest offset − committed offset) growing per partition; real-time features fall behind; downstream data stale by minutes/hours.
Investigationkafka-consumer-groups.sh --describe --group g → LAG per partition. Is lag on all partitions (undersized group) or one (skewed key / one slow consumer)? Check consumer processing time, GC pauses, rebalance storms, and downstream latency.
Root CauseConsumers < partitions or too slow; hot partition from a bad partition key; frequent rebalances (long max.poll.interval processing) resetting progress; downstream (DB) throttling the handler.
SolutionAdd consumers up to the partition count; increase partitions if you need more parallelism; batch/pipeline downstream writes; tune max.poll.records and max.poll.interval.ms; fix the partition key to spread load; move heavy work off the poll thread.
PreventionPartition count ≥ target parallelism, even key distribution, alert on lag and lag-growth-rate (Burrow / kafka-exporter), idempotent processing so you can reset offsets safely, autoscale consumers.
Interview Answer"I describe the consumer group to see if lag is uniform or on one partition. Uniform means I'm consumer-bound — add consumers up to partition count. One partition means a hot key. I also check for rebalance storms from slow processing exceeding max.poll.interval, which silently resets progress."

Kubernetes & Infra Incidents

CrashLoopBackOff

SymptomsPod restarts repeatedly; kubectl get pods shows CrashLoopBackOff with rising restart count; backoff delay grows to 5min.
Investigationkubectl describe pod X (events, last state, exit code), kubectl logs X --previous (logs from the crashed container — the key command), kubectl get events --sort-by=.lastTimestamp. Exit code 1 = app error, 137 = SIGKILL/OOM, 143 = SIGTERM.
Root CauseApp throws on startup (bad config/secret, missing env var, unreachable dependency), failing liveness probe (too aggressive), OOMKilled, or a bad image. Migration failing on boot.
SolutionRead --previous logs → fix the actual error (config/secret/dependency). If liveness probe is too strict, relax initialDelaySeconds/failureThreshold or add a startup probe. Roll back the image: kubectl rollout undo deploy/X.
PreventionReadiness/startup probes separate from liveness, validate config at deploy time, canary/staged rollout, resource requests/limits set correctly, health check that reflects real readiness.
Interview Answer"First command is always kubectl logs --previous plus describe for the exit code. 137 tells me OOM, 1 tells me an app-level startup error — usually a missing secret or a dependency it can't reach. I roll back the image to stop the loop, then fix root cause."

OOMKilled

SymptomsContainer killed with exit code 137, Reason: OOMKilled in describe, periodic restarts under load.
Investigationkubectl describe pod → Last State OOMKilled. Compare memory limits vs actual usage (kubectl top pod, cAdvisor/Grafana). Is it a slow leak (sawtooth trending up) or a spike from a big request/batch?
Root CauseMemory limit too low for real working set, a memory leak, an unbounded in-memory buffer (loading a huge query result / file into RAM), or JVM/Node heap not aware of cgroup limit.
SolutionRaise the limit if it's genuinely undersized; fix the leak (heap snapshot); stream instead of buffering large payloads; set runtime heap to respect the container limit (Node: --max-old-space-size; JVM: -XX:MaxRAMPercentage). Add requests=limits for guaranteed QoS on critical pods.
PreventionRight-size from real usage + headroom, alert on memory > 80% of limit, leak tests, stream large data, set heap flags to the cgroup limit.
Interview Answer"137 with OOMKilled means working set exceeded the limit. I check the memory graph — a rising sawtooth is a leak (I take a heap snapshot), a spike is an unbounded buffer (I stream instead). I also make sure the runtime heap is capped to the cgroup limit, or it'll OOM before GC kicks in."

Kubernetes PVC stuck Pending

SymptomsPod stuck Pending; kubectl get pvc shows Pending; events say "waiting for a volume to be created" or "no persistent volumes available."
Investigationkubectl describe pvc X and describe pod events; check the StorageClass exists and matches (kubectl get storageclass); check the CSI provisioner pod is healthy; verify the requested AZ has capacity and the access mode (RWO vs RWX) is supported.
Root CauseNo/incorrect StorageClass, CSI driver down, cloud quota exhausted, AZ mismatch (volume in AZ-a, pod scheduled to AZ-b), or requesting RWX on a driver that only supports RWO.
SolutionSet the right StorageClass / mark one default; restart/fix the CSI provisioner; request quota increase; use topology-aware provisioning so volume and pod land in the same AZ; use an RWX-capable backend (EFS/NFS) if multi-attach is needed.
PreventionDefault StorageClass configured, CSI health alerts, quota monitoring, topology-aware volume binding (volumeBindingMode: WaitForFirstConsumer).
Interview Answer"Pending PVC is almost always provisioning: I describe the PVC for the event. Common causes are a missing StorageClass, a dead CSI driver, quota, or an AZ mismatch. WaitForFirstConsumer binding avoids the AZ trap by provisioning after the pod is scheduled."

Node NotReady

Symptomskubectl get nodes shows a node NotReady; pods on it go Unknown/Terminating; after ~5min they reschedule elsewhere.
Investigationkubectl describe node X → conditions (MemoryPressure, DiskPressure, PIDPressure, kubelet Ready). SSH: is kubelet running? systemctl status kubelet, journalctl -u kubelet. Check disk full (df -h), network to control plane, and the container runtime.
Root CauseKubelet crashed/hung, node out of disk (image/log buildup), network partition from control plane, container runtime down, or the underlying VM is unhealthy.
SolutionCordon + drain (kubectl drain X --ignore-daemonsets --delete-emptydir-data) so workloads move; restart kubelet/runtime; clear disk (prune images/logs); if the VM is dead, terminate it and let autoscaler replace it.
PreventionNode disk/pressure alerts, log rotation + image GC, cluster autoscaler to replace bad nodes, spread replicas across nodes/AZs with anti-affinity + PodDisruptionBudgets.
Interview Answer"NotReady means the control plane stopped hearing from the kubelet. I describe the node for pressure conditions — DiskPressure from log/image buildup is common — then drain it so pods reschedule, and either fix the kubelet/disk or replace the VM via the autoscaler."

Load Balancer health check failing

SymptomsTargets marked unhealthy, LB returns 503, traffic drops even though pods "look up." Sometimes flapping in/out of service.
InvestigationCheck the target-group health status and the exact health-check path/port/expected-code. curl the health endpoint from inside the cluster and from the LB's perspective. Compare readiness probe vs LB health check config. Check security-group/NACL/firewall between LB and targets.
Root CauseHealth path returns non-2xx (dependency check failing), wrong port/path, timeout too tight for a slow /health, security group blocking the LB, or app not bound to 0.0.0.0. A "deep" health check that fails when a non-critical dependency is down.
SolutionFix the health endpoint to reflect real serving readiness (shallow liveness vs deep readiness); align path/port/expected-code/timeout; open the security group; bind correctly. Increase healthy/unhealthy thresholds to stop flapping.
PreventionSeparate liveness (am I up) from readiness (can I serve); don't fail health checks on non-critical deps; alert on unhealthy target count; test health checks in staging.
Interview Answer"I curl the exact health path/port the LB uses. The classic bug is a 'deep' health check that returns 500 when a non-critical dependency blips, so the LB pulls every target and you get a self-inflicted outage. Health checks should reflect can I serve traffic, not is every dependency perfect."

Network & TLS Incidents

DNS resolution failure

Symptomsgetaddrinfo ENOTFOUND / Name or service not known, intermittent connection failures, in-cluster service discovery breaking.
Investigationdig svc.namespace.svc.cluster.local / nslookup; in k8s check CoreDNS pods (kubectl -n kube-system get pods -l k8s-app=kube-dns) and their logs; check /etc/resolv.conf ndots setting; test from inside a pod (kubectl run -it --rm debug --image=busybox -- nslookup). Watch for CoreDNS CPU throttling / query flood.
Root CauseCoreDNS overloaded or crashing, misconfigured upstream resolver, ndots:5 causing search-domain amplification (5 lookups per external name), TTL/cache issues, or an actual DNS provider outage.
SolutionScale/restart CoreDNS; add NodeLocal DNSCache; set ndots:1 or use FQDNs with trailing dot for external hosts; increase cache TTL; fix upstream resolver. For provider outage, fail over to secondary DNS.
PreventionNodeLocal DNSCache, CoreDNS autoscaling + alerts on query errors/latency, low ndots, health checks that don't spam DNS, multi-provider DNS.
Interview Answer"I confirm with dig from inside a pod, then check CoreDNS health. In Kubernetes the sneaky one is ndots:5 turning one external lookup into five, overloading DNS — I fix it with NodeLocal DNSCache and FQDNs, which usually collapses the problem."

TLS handshake failure

SymptomsSSL_ERROR / certificate has expired / unable to verify the first certificate / handshake failure; clients can't connect, mobile apps break.
Investigationopenssl s_client -connect host:443 -servername host → inspect the cert chain, notAfter, and whether intermediates are sent. echo | openssl s_client ... 2>/dev/null | openssl x509 -noout -dates. Check protocol/cipher mismatch (-tls1_2), SNI, and clock skew.
Root CauseExpired certificate (the #1 cause), missing intermediate cert in the chain, protocol mismatch (client wants TLS1.2, server only TLS1.3 or vice versa), SNI misconfig, or client trust store missing the CA.
SolutionRenew/rotate the cert (cert-manager / ACME auto-renew); include the full chain (fullchain.pem); align enabled protocols/ciphers; fix SNI; sync clocks (NTP). Roll the new cert without downtime.
PreventionAutomated renewal (cert-manager / Let's Encrypt), alert 30 days before notAfter, serve the full chain, monitor from an external prober, staged TLS policy changes.
Interview Answer"openssl s_client tells me everything — expiry, chain, protocol. Nine times out of ten it's an expired cert or a missing intermediate. The real fix is automation: cert-manager auto-renewal plus an alert 30 days before expiry so a human never has to remember."

502 Bad Gateway

SymptomsReverse proxy / LB returns 502; the proxy is up but got an invalid/empty/closed response from upstream.
InvestigationProxy logs (nginx error.log: "connection refused" / "upstream prematurely closed"). Are upstream pods running/ready? kubectl get pods, curl the upstream directly. Check if the app crashed, is still starting, or closed the connection (keep-alive mismatch).
Root CauseUpstream is down/crashed/not-ready, upstream crashed mid-response, keep-alive timeout mismatch (proxy reuses a connection the upstream already closed), or the app returned a malformed response.
SolutionRestore/roll back the upstream; fix readiness so the proxy doesn't route to not-ready pods; align keep-alive timeouts (upstream keepalive > proxy); add retry-on-idempotent-methods. Bounce crashed pods.
PreventionReadiness gating at the proxy, matched keep-alive timeouts, graceful shutdown (drain before SIGKILL), circuit breaker, canary deploys.
Interview Answer"502 means the proxy reached an upstream but got garbage or a closed connection — the app side is the problem, not the proxy. I check upstream readiness and logs; a subtle recurring 502 is usually a keep-alive timeout mismatch where the proxy reuses a connection the app already closed."

504 Gateway Timeout

SymptomsProxy/LB returns 504 after N seconds (e.g. 30s/60s); upstream never responded in time.
InvestigationTrace the slow request (distributed tracing) to find the slow hop — DB query, external API, lock wait. Compare proxy proxy_read_timeout vs actual upstream latency (p99). Check for saturation (all workers busy) and downstream dependency latency.
Root CauseUpstream genuinely too slow (slow query, blocked on a lock, slow third-party call), thread/worker pool exhausted so requests queue, or a downstream dependency degraded. Sometimes retries amplifying load.
SolutionFix the slow hop (index the query, add caching, timeout the third-party call and degrade gracefully); scale workers; add a client-side timeout shorter than the gateway's so you fail fast; circuit-break the slow dependency. Don't just raise the gateway timeout.
PreventionPer-dependency timeouts + circuit breakers, p99 latency SLO alerts, bulkheads so one slow dependency doesn't exhaust the pool, load shedding, async for long operations.
Interview Answer"504 is 'upstream too slow,' so I trace the request to the slow hop rather than blindly raising the timeout. Usually it's a slow query or a hanging third-party call. I fix the hop, add a timeout + circuit breaker on that dependency, and add a bulkhead so it can't exhaust the whole worker pool."

Node.js Runtime Incidents

High event loop delay

SymptomsLatency across all endpoints rises together, health checks time out, throughput drops though CPU may not be pinned. Event-loop lag metric > 100ms.
InvestigationMeasure lag with perf_hooks.monitorEventLoopDelay() or the nodejs_eventloop_lag_seconds prom metric; profile with clinic doctor / clinic flame or node --prof + --prof-process. Look for a synchronous hot path — JSON.parse of huge payloads, sync crypto, regex backtracking (ReDoS), big sync loops.
Root CauseCPU-bound synchronous work blocking the single-threaded loop: large JSON.parse/stringify, synchronous crypto/compression, fs.*Sync, catastrophic regex backtracking, or an unbounded loop over a big array.
SolutionMove CPU work off the loop: worker threads, streaming parsers, async crypto, chunk big loops with setImmediate. Fix the ReDoS regex. Cache expensive computations. Add a concurrency limit / load shed when lag is high.
PreventionEvent-loop-lag alert (> 70ms warn, > 200ms page), no *Sync on hot paths, payload size limits, regex safety review, offload CPU to workers, autocannon load tests.
Interview Answer"When every endpoint slows together but there's no DB culprit, I suspect the event loop is blocked. I measure lag with perf_hooks and flame-graph with clinic. The fix is to get CPU work — big JSON, crypto, a nasty regex — off the loop via worker threads or streaming, because in Node one blocked handler stalls everyone."

Memory leak

SymptomsRSS/heap grows steadily over hours/days, GC gets more frequent, eventually OOMKilled/137 and restart; sawtooth that trends upward.
InvestigationWatch process.memoryUsage().heapUsed trend; take heap snapshots at intervals (--inspect + Chrome DevTools, or v8.writeHeapSnapshot()), diff them to find the growing retained object. clinic heapprofiler. Common culprits: unbounded Map/cache, event listeners not removed, closures capturing big objects, global arrays.
Root CauseObjects kept reachable forever: an in-memory cache without eviction, emitter.on without off (listener leak, "MaxListenersExceeded"), timers not cleared, module-level arrays that only grow, or holding request/response references.
SolutionDiff two heap snapshots → find the retaining path → fix (bound the cache with LRU + max size, remove listeners, clear timers, use WeakMap for object-keyed caches). Short-term mitigation: scheduled restart / higher limit while you fix it.
PreventionBounded caches, listener hygiene, memory-trend alerts (not just OOM), heap-snapshot diff in soak tests, WeakMap/WeakRef for caches, load-soak in CI.
Interview Answer"A slow upward sawtooth ending in OOM is a classic leak. I take two heap snapshots an hour apart and diff them — the object with growing retained size and its retainer path is the culprit, usually an unbounded Map or unremoved event listeners. I bound the cache with an LRU and add a memory-trend alert so I catch it before OOM."

GC thrashing

SymptomsCPU high in GC, periodic latency spikes (stop-the-world pauses), throughput drops; --trace-gc shows frequent long Mark-Sweep pauses.
InvestigationRun with --trace-gc --trace-gc-verbose; look at GC pause frequency/duration and the ratio of GC time to total. Heap near --max-old-space-size forces constant full GCs. Check allocation rate (lots of short-lived objects churning the young generation).
Root CauseHeap pressure near the limit (so V8 GCs constantly), or a very high allocation rate — creating huge numbers of short-lived objects per request (big intermediate arrays, string concat in loops, JSON churn).
SolutionReduce allocations (reuse buffers, stream, avoid needless clones), raise --max-old-space-size if genuinely undersized, fix a partial leak keeping the heap full. Object pooling for hot allocations.
PreventionAlert on GC-time ratio > 10%, allocation profiling in perf tests, streaming over buffering, right-sized heap vs container limit.
Interview Answer"GC thrashing shows up as CPU burned in GC with periodic pause spikes. --trace-gc tells me if the heap is pinned near the limit (raise it or fix a leak) or if allocation rate is the issue — then I cut per-request garbage by streaming and reusing buffers instead of allocating fresh objects."

Application & Business-Logic Incidents

API latency suddenly increased

Symptomsp99 (and maybe p50) latency jumps at a specific timestamp; error rate may follow.
Investigation"What changed at that timestamp?" — deploy, flag, traffic, dependency. Trace a slow request to the bottleneck hop. Check DB slow log, downstream latency, cache hit rate drop, and saturation (CPU, event loop, pool).
Root CauseA deploy introduced an N+1 or removed a cache; cache hit rate dropped (cold/flushed cache); a downstream got slow; traffic spike saturated a resource; a new index-less query.
SolutionRoll back the correlated deploy; warm/repair the cache; scale; add the missing index. Mitigate first, RCA after.
PreventionLatency SLO alerts, per-deploy latency canary, cache-hit-rate monitoring, trace sampling always on.
Interview Answer"A sharp latency step change almost always maps to an event at that exact time — I overlay the deploy/flag timeline on the latency graph, roll back the correlated change, then trace to confirm the mechanism."

Duplicate payments

SymptomsCustomer charged twice for one order; reconciliation shows two captures for one intent; support tickets.
InvestigationTrace the payment request — a client retry (user double-click / network retry / mobile reconnect) or a gateway timeout where the first request actually succeeded. Check whether the create-charge call carried an idempotency key. Inspect logs for two requests with the same order but different request IDs.
Root CauseNon-idempotent charge endpoint: the client retried after a timeout, and the server treated the retry as a new charge. No idempotency key, no unique constraint on (order_id) in the payments table.
SolutionIdempotency key per payment attempt (client-generated UUID), stored server-side with a UNIQUE constraint: first request inserts + processes, a retry with the same key returns the stored result instead of charging again. Add a DB UNIQUE constraint on the business key (order_id/idempotency_key) as the last line of defense. Pass the idempotency key through to the payment gateway (Stripe/Razorpay support this natively). Refund the duplicate.
PreventionIdempotency keys mandatory on all mutating money endpoints; unique DB constraint; reconciliation job comparing gateway captures vs internal ledger daily; exactly-once semantics via at-least-once + idempotency.
Interview Answer"Duplicate charges come from retries on a non-idempotent endpoint. The fix is an idempotency key: the client sends a UUID, I store it with a UNIQUE constraint, and any retry with the same key returns the original result instead of charging again. I also forward that key to the payment gateway and back it with a unique DB constraint plus a daily reconciliation job."

Uber-style ride double-allocation

SymptomsOne driver assigned to two riders, or two drivers dispatched to one rider; concurrent matching races.
InvestigationTrace two concurrent assignment requests hitting the same driver in the same millisecond window. Check whether the "is driver free?" check and the "assign" write are atomic or a read-then-write race (TOCTOU).
Root CauseRead-modify-write race: two matcher instances both read driver as AVAILABLE, both assign. No locking / no atomic conditional update.
SolutionMake assignment atomic. Options: (1) Optimistic concurrency — UPDATE drivers SET status='BUSY', rider_id=? WHERE id=? AND status='AVAILABLE'; if 0 rows affected, someone else won, retry with another driver. (2) Distributed lock — Redis SET driver:{id} lock NX PX 3000 (Redlock) around the assign. (3) SELECT ... FOR UPDATE row lock in a transaction. Optimistic conditional-update is usually best — lock-free, single round trip, no lock-expiry risk.
PreventionAlways express "claim if still free" as a single atomic conditional write; unique constraint on active (driver_id) assignment; version columns; idempotent dispatch.
Interview Answer"Double-allocation is a TOCTOU race between check and assign. I make it one atomic operation — UPDATE ... SET status='BUSY' WHERE id=? AND status='AVAILABLE'. If rows-affected is 0, another matcher already claimed the driver and I pick someone else. That's optimistic concurrency: no lock to expire, one round trip, and the DB enforces the invariant."

Seat-booking race condition

SymptomsTwo users book the same seat/inventory unit; oversell; "seat already taken" only after payment.
InvestigationTwo concurrent bookings for seat 12A both succeed. Check the reserve flow: is availability checked and decremented atomically? Is there a unique constraint on (event_id, seat_id)?
Root CauseClassic lost-update / double-book race: both transactions read seat as free, both write a booking. No pessimistic lock, no optimistic version check, no unique constraint.
SolutionLayered defense: (1) Unique DB constraint on (event_id, seat_id) — the ultimate guarantee; the second insert fails with a constraint violation. (2) Pessimistic lock — SELECT ... FOR UPDATE on the seat row inside a transaction so the second waits. (3) Optimistic — version column, UPDATE ... WHERE version=?. For high-contention flash sales, a short Redis reservation lock/hold (SET NX with TTL) to hold the seat during checkout, then confirm to DB. Always keep the unique constraint as the backstop.
PreventionUnique constraint on the seat, hold/reservation with TTL during checkout, FOR UPDATE or version column, idempotent booking key so retries don't double-book.
Interview Answer"I never trust an application-level check for uniqueness under concurrency. The non-negotiable is a UNIQUE constraint on (event_id, seat_id) so the DB rejects the second booking. On top I use SELECT ... FOR UPDATE or an optimistic version check to serialize, and for flash sales a short Redis hold so users don't lose a seat mid-checkout — but the constraint is what makes overselling impossible."
Say this: "Optimistic concurrency (version column / conditional UPDATE) wins under low-to-moderate contention — no locks, no deadlocks, cheap retries. Pessimistic locking (SELECT ... FOR UPDATE) wins under high contention where retries would storm. A distributed lock (Redis Redlock) is for cross-service coordination but carries lock-expiry and clock-skew risk. And a UNIQUE DB constraint is the one guarantee that holds no matter how the app code races."

Production Architecture

An observability + incident-response pipeline: the app emits metrics, logs, and traces; a metrics backend evaluates alert rules and burns SLO budget; alerts route to on-call; the responder pulls up the runbook and dashboards to mitigate.

flowchart LR
  A["App services"] --> M["Metrics Prometheus"]
  A --> L["Logs Loki or ELK"]
  A --> T["Traces Jaeger"]
  M --> AL["Alertmanager rules"]
  AL --> OC["On-call PagerDuty"]
  OC --> RB["Runbook and dashboards"]
  RB --> MIT["Mitigate rollback scale failover"]
  MIT --> A

The three signals answer different questions: metrics say where and how bad (and drive alerts), traces say which hop, logs say exactly why. Alerts fire on symptoms (SLO burn), page the on-call, who reaches for the runbook — the loop closes when mitigation restores the app.

The incident timeline as a sequence — from alert to resolution:

sequenceDiagram
  participant Mon as Monitoring
  participant OC as OnCall
  participant IC as IncidentCommander
  participant Sys as Systems
  Mon->>OC: SLO burn alert fires
  OC->>OC: Ack and check what changed
  OC->>IC: Declare SEV2 open channel
  IC->>Sys: Roll back last deploy
  Sys-->>IC: Error rate recovering
  IC->>Mon: Confirm SLO back in budget
  IC->>OC: Schedule blameless RCA

Note the ordering: mitigate (rollback) happens before RCA. The commander restores service first and confirms recovery on the dashboards, then schedules the post-mortem. Comms (declare, open channel) run in parallel with the technical fix.

Alert on symptoms with actionable thresholds; page only when a human must act now.

SLO / error budget: Define an SLO (e.g. 99.9% availability = 43min/month of allowed downtime). Track the error budget (1 − SLO). When the budget is exhausted, freeze risky deploys until it recovers; that's the policy lever tying reliability to release velocity.

Common Mistakes

  • Alerting on causes, not symptoms. "CPU > 80%" pages at 3am for nothing; "error ratio > 2%" pages when customers actually hurt. Alert on user-facing SLOs.
  • No runbooks. Every alert should link a runbook: what it means, how to verify, how to mitigate. Tribal knowledge doesn't scale to 3am.
  • Restarting without RCA. A restart that "fixes it" hides a leak/loop that returns in 6 hours. Capture a heap snapshot / thread dump before restarting.
  • No idempotency. Any retryable mutation (payments, orders, messages) without an idempotency key will double-execute in production. Guaranteed.
  • Missing DB constraints. Enforcing uniqueness in app code instead of a UNIQUE constraint = eventual double-booking under concurrency.
  • Unbounded retries. Retries without exponential backoff + jitter + a circuit breaker turn a blip into a self-inflicted DDoS (retry storm / cascading failure).
  • Deep health checks. Health checks that fail on non-critical dependencies pull healthy nodes and cause self-outages.
  • No load shedding / bulkheads. One slow dependency exhausts the whole pool and takes everything down.
  • Raising timeouts to "fix" 504s. Masks the slow hop and lets more requests pile up. Fix the latency, don't hide it.
  • Blameful post-mortems. Kills honesty, so the real root cause never surfaces. Blameless only.

Interview Follow-up Questions

  1. How do you decide whether to roll back vs roll forward?
    1. Roll back by default (fastest, safest); roll forward only if rollback is impossible (irreversible migration) or the fix is trivial and verified.
  2. What's the difference between an SLI, SLO, and SLA?
    1. SLI = the measured metric; SLO = internal target on it; SLA = external contract with penalties, always looser than the SLO.
  3. Why alert on burn rate instead of a raw threshold?
    1. Burn rate ties alerts to budget consumption — pages fast for severe issues, ignores brief blips, reduces noise.
  4. How do you make a payment endpoint idempotent?
    1. Client-generated idempotency key stored with a UNIQUE constraint; return the stored result on retry; forward the key to the gateway.
  5. Optimistic vs pessimistic locking — when each?
    1. Optimistic (version/conditional update) for low contention; pessimistic (FOR UPDATE) for high contention where retries would storm.
  6. Why is a distributed lock (Redis) risky?
    1. Lock expiry + clock skew + GC pause can let two holders proceed; prefer atomic conditional writes or fencing tokens.
  7. How do you debug a memory leak in Node without restarting?
    1. Diff two heap snapshots to find growing retained objects and their retainer path; fix the retention (LRU/WeakMap/listener cleanup).
  8. What exit codes matter for containers?
    1. 137 = SIGKILL/OOM, 143 = SIGTERM, 1 = app error, 139 = segfault; drives whether you look at memory, config, or code.
  9. How do you prevent a cache stampede?
    1. TTL jitter + single-flight recompute lock + stale-while-revalidate + pre-warming hot keys.
  10. How do you handle a poison message?
    1. Retry with a cap, then dead-letter it so it doesn't block the queue; alert on DLQ depth; inspect and reprocess after fix.
  11. What causes Kafka rebalance storms?
    1. Processing exceeding max.poll.interval.ms so the consumer is kicked; fix by shortening work per poll or moving work off the poll thread.
  12. How do you stop a retry storm / cascading failure?
    1. Exponential backoff with jitter, retry budgets, circuit breakers, and load shedding at the edge.
  13. Difference between liveness and readiness probes?
    1. Liveness = restart if dead; readiness = remove from LB until it can serve; failing liveness on a dependency causes crash loops.
  14. How do you find a slow query fast?
    1. pg_stat_activity/pg_stat_statements or slow log + pt-query-digest, then EXPLAIN ANALYZE for the plan.
  15. What's a blameless post-mortem and why?
    1. Focus on systemic causes, not individuals, so people report honestly and you fix the real issue.
  16. How do you guarantee no double-booking of a seat?
    1. A UNIQUE DB constraint as the hard guarantee, plus FOR UPDATE or optimistic version check to serialize.
  17. How do you diagnose a 504 vs a 502?
    1. 502 = upstream returned bad/closed connection (app down/keepalive); 504 = upstream too slow (trace the slow hop).
  18. What's the first thing you check on any alert?
    1. "What changed?" — deploy, flag, config, traffic, dependency — because most incidents correlate with a recent change.

Common Cross Questions

  • SLO / SLI / error budgets: How to pick an SLI (customer-facing), set an SLO, and use the budget to gate deploys. Angle: reliability is a feature you budget for, not a maximize-at-all-costs goal.
  • Idempotency: Keys, dedupe tables, unique constraints; "exactly-once = at-least-once + idempotent." Angle: any retryable mutation needs it.
  • Distributed locks vs optimistic concurrency: Redlock's caveats, fencing tokens, conditional updates. Angle: prefer the DB to enforce invariants over app-level locks.
  • Circuit breakers: Closed/open/half-open states, thresholds, fallbacks. Angle: stop cascading failure by failing fast on a sick dependency.
  • Retries & backoff: Exponential backoff + jitter, retry budgets, idempotency requirement. Angle: naive retries amplify outages.
  • Rate limiting / load shedding: Token bucket, per-tenant quotas, shedding low-priority traffic under load. Angle: protect the core under overload.
  • Observability trio: Metrics vs logs vs traces and when each answers the question. Angle: metrics to detect, traces to localize, logs to explain.
  • Graceful degradation & bulkheads: Isolate resources so one dependency can't sink everything; serve reduced functionality. Angle: partial availability beats total outage.

🎯 Deep-dive Q&A — model answers

Database CPU is at 100%. Walk me through it end to end.

First I confirm the DB process is the culprit with top on the host, ruling out a noisy neighbor. Then SELECT pid, now()-query_start AS dur, state, query FROM pg_stat_activity WHERE state='active' ORDER BY dur DESC to find the longest-running queries, and pg_stat_statements ordered by total_exec_time for the aggregate hog. I EXPLAIN ANALYZE the top offender — almost always a Seq Scan on a large table from a missing index or a stale-stats bad plan. To restore service now I pg_terminate_backend(pid) the runaway, and if a report is hammering the primary I route it to a read replica. Then I add the index with CREATE INDEX CONCURRENTLY to avoid the table lock, roll back the deploy if it introduced the query, and add a slow-query alert plus a statement_timeout so it's caught in staging next time.

A hot cache key just expired and the DB is melting. What's happening and how do you fix it live?

That's a cache stampede — one hot key expired and thousands of concurrent requests all missed and are recomputing the same expensive query against the DB simultaneously. Live mitigation: I can manually re-populate the key or extend its TTL to stop the herd immediately, and scale/rate-limit if needed. The real fix is three-layered: TTL jitter (±10%) so keys don't expire in lockstep; a single-flight recompute lock via SET key:lock NX PX 5000 so only the first miss recomputes while others wait or serve stale; and stale-while-revalidate so the rest serve the slightly-old value instead of hammering the DB. For known-hot keys I add background refresh so they never expire under load.

Kafka consumer lag is growing on your group. Diagnose it.

kafka-consumer-groups.sh --describe --group g and look at LAG per partition. If lag is uniform across all partitions, I'm consumer-bound — add consumers up to the partition count (more consumers than partitions does nothing), or increase partitions for more parallelism. If lag is on one partition, it's a hot key from a bad partition key and I need to fix key distribution. I also check for rebalance storms: if processing per poll exceeds max.poll.interval.ms, the broker evicts the consumer and progress resets — I fix that by moving heavy work off the poll thread or lowering max.poll.records. Because processing is idempotent, I can safely reset offsets if needed. Long term: alert on lag and lag-growth-rate, and autoscale consumers.

A pod is in CrashLoopBackOff. What are your exact commands?

kubectl describe pod X for events and the last-state exit code, then the key one: kubectl logs X --previous to see the crashed container's output, plus kubectl get events --sort-by=.lastTimestamp. Exit code 137 means OOMKilled (bump the memory limit or fix a leak), 1 means an app-level startup error — usually a missing secret/env var or an unreachable dependency, sometimes a failing migration. If it's a too-aggressive liveness probe restarting a slow-starting app, I add a startup probe or relax initialDelaySeconds. To stop the loop immediately I kubectl rollout undo deploy/X to the last good image, then fix root cause and redeploy via canary.

Clients are getting 504 Gateway Timeout. How do you respond?

504 means the gateway reached the upstream but the upstream didn't respond within the timeout — an upstream latency problem, not a proxy problem. I trace a slow request end to end to find the slow hop: usually a slow DB query, a lock wait, or a hanging third-party call, sometimes worker-pool exhaustion queueing requests. I do not just raise the gateway timeout — that hides the problem and lets requests pile up. I fix the hop (index the query, cache, or add a hard timeout on the third-party call with graceful degradation), add a circuit breaker on that dependency, and a bulkhead so one slow dependency can't exhaust the whole worker pool. I also set client-side timeouts shorter than the gateway's to fail fast.

A customer was charged twice. Root cause and permanent fix?

Root cause is a non-idempotent charge endpoint: the client retried after a network timeout or gateway 5xx where the first request had actually succeeded, and the server treated the retry as a new charge. Permanent fix is an idempotency key — the client generates a UUID per payment attempt and sends it; the server stores it with a UNIQUE constraint, so the first request processes and stores the result while any retry with the same key returns the stored result instead of charging again. I forward that key to the payment gateway (Stripe/Razorpay support it natively) so even the gateway dedupes, and I add a UNIQUE DB constraint on the business key as the last line of defense plus a daily reconciliation job comparing gateway captures against our ledger. Then refund the duplicate.

Two users booked the same seat. How do you make that impossible?

The non-negotiable guarantee is a UNIQUE constraint on (event_id, seat_id) in the bookings table — no matter how the application races, the DB rejects the second insert with a constraint violation. Never rely on an app-level "is it free?" check under concurrency; that's a lost-update race. On top of the constraint I serialize with either SELECT ... FOR UPDATE on the seat row inside a transaction (pessimistic, good for high contention) or an optimistic version column with UPDATE ... WHERE version=?. For flash sales I add a short-lived Redis reservation hold (SET seat NX PX 120000) so users don't lose their seat mid-checkout, then confirm to the DB. But the constraint is what actually makes overselling impossible.

How do you prevent Uber-style double-allocation of a driver?

It's a TOCTOU race: two matcher instances both read the driver as AVAILABLE and both assign. I collapse check-and-assign into one atomic conditional write: UPDATE drivers SET status='BUSY', rider_id=? WHERE id=? AND status='AVAILABLE'. If rows-affected is 1 I won the driver; if it's 0, another matcher already claimed them and I pick a different driver. That's optimistic concurrency — lock-free, one round trip, no lock-expiry risk, and the DB enforces the invariant. I back it with a unique constraint on the active assignment and make dispatch idempotent so retries don't create a second assignment.

Your Node service has a memory leak. Find it without guessing.

I watch the heapUsed trend to confirm a rising sawtooth (grows, GC frees some, net climbs) heading toward OOM/137. Then I take two heap snapshots an hour apart — via --inspect + Chrome DevTools or v8.writeHeapSnapshot() — and diff them in the Comparison view. The object type with growing retained size, plus its retainer path, is the culprit; it's usually an unbounded Map/cache, event listeners added without removeListener (you'll see MaxListenersExceeded warnings), or timers never cleared. I fix the retention — bound the cache with an LRU + max size, use a WeakMap for object-keyed caches, remove listeners — and add a memory-trend alert so I catch the next one before OOM rather than after.

Every endpoint got slow at once but CPU looks fine. What's your hypothesis?

In Node, when all endpoints degrade together with no single DB culprit, my hypothesis is a blocked event loop — one synchronous CPU-bound operation is stalling the single thread for everyone. I confirm with the event-loop-lag metric (perf_hooks.monitorEventLoopDelay or the prom gauge); >100ms confirms it. Then I flame-graph with clinic flame or node --prof to find the hot synchronous path — typically a huge JSON.parse/stringify, synchronous crypto/compression, an fs.*Sync call, or catastrophic regex backtracking (ReDoS). The fix is to get CPU work off the loop: worker threads, streaming parsers, async crypto, chunk big loops with setImmediate, or fix the regex — plus a payload size limit and a lag-based load-shed.

Connection pool is exhausted but DB CPU is near zero. Explain the paradox.

Low CPU means connections are held, not busy — the classic signature is idle in transaction. I run SELECT count(*), state FROM pg_stat_activity GROUP BY state; a pile of idle-in-transaction confirms code that opens a transaction and then does slow non-DB work (or leaks the connection on an error path) without committing. Immediate mitigation: kill those sessions and bounce the app to reset the pool. Fixes: set idle_in_transaction_session_timeout, ensure every acquire has a finally-release, keep transactions short (no network calls inside them), and put PgBouncer in transaction-pooling mode in front so app pool size decouples from DB max_connections. Then alert on pool utilization > 80%.

How do error budgets change how you operate?

An SLO of 99.9% gives a monthly error budget of ~43 minutes of allowed unreliability. I track burn rate with multi-window multi-burn-rate alerts — a fast-burn alert (14.4× over 1h, confirmed over 5min) pages for acute problems, a slow-burn alert (6× over 6h) catches gradual degradation, and neither pages for harmless blips. The budget becomes a policy lever: when it's healthy we ship features and take risks; when it's exhausted we freeze risky deploys and spend the sprint on reliability. It converts "how reliable should we be?" from an argument into a number, and it aligns dev velocity with ops stability instead of pitting them against each other.

Redis is throwing OOM on writes. Walk me through recovery.

redis-cli INFO memory shows used_memory at maxmemory, and the OOM-on-write error tells me the policy is noeviction. Immediate recovery: switch to maxmemory-policy allkeys-lru so it evicts cold keys instead of erroring, which restores writes instantly. Then redis-cli --bigkeys to find whale keys (a multi-GB list/hash) and INFO keyspace to spot keys with no TTL — the usual root cause is cache keys accumulating forever with no expiry. I add TTLs, split or expire big keys, and check mem_fragmentation_ratio (enable activedefrag if fragmented). Prevention: every cache key gets a TTL, alert on used_memory > 80% and on evicted_keys rate, and capacity-plan or shard before it fills.

A message got processed twice and sent two emails. Why, and how do you guarantee once?

Because brokers are at-least-once: the consumer processed the message, crashed before acking, and the broker redelivered it — retries and rebalances do the same. There's no true exactly-once across a network. The guarantee comes from idempotent consumers, not the broker. Each message carries a stable key; before the side effect I insert that key into a processed_messages table with a UNIQUE constraint — if the insert succeeds I proceed, if it hits the constraint the message was already handled and I skip. That makes at-least-once safe. For Kafka I can add the idempotent producer + transactions for exactly-once within the pipeline, but the consumer's external side effects (sending email, charging) still need the dedupe key.

How do you run the first 5 minutes of an incident as the on-call?

Ack the page to stop re-alerting and read what fired — which SLO, which service. Open the service dashboard and read the four golden signals over 1h and 24h to classify it as errors, latency, or saturation, and whether it's one endpoint or all. Then the key question: "what changed in the last hour?" — deploys (kubectl rollout history), feature flags, config, traffic, dependency status pages; most incidents correlate with a recent change. If a change correlates, I mitigate against that hypothesis immediately — roll back or flip the flag — before I fully diagnose. If impact is real and not instantly fixed, I declare a SEV, open the incident channel, name myself IC, and post the first status update, then keep a 15-30 minute comms cadence. Diagnosis and RCA come after service is restored.

When do you choose a distributed lock over a DB constraint or optimistic concurrency?

Almost never for enforcing a data invariant — a UNIQUE constraint or an atomic conditional UPDATE is safer because the database enforces it transactionally with no expiry or clock assumptions. A distributed lock (Redis Redlock, etcd lease) is for coordinating work across services or resources the DB can't see — e.g. ensuring only one worker runs a scheduled job, or serializing access to an external non-transactional resource. Its risks are real: if the lock's TTL expires during a GC pause or the holder is slow, two workers can both believe they hold it, so you need fencing tokens (a monotonically increasing number the downstream checks) to make it safe. So my order of preference is: DB unique constraint → atomic conditional update (optimistic) → SELECT FOR UPDATE (pessimistic) → distributed lock with fencing tokens only when nothing else can express the invariant.
