State & useState React

State is memory that survives a re-render. A plain variable inside a component is recreated on every render, so it can never remember anything. useState asks React to keep a value in a slot attached to this component instance, hand it back on the next render, and — crucially — schedule a re-render whenever you replace it.

Everything confusing about React state comes from one fact: the value you hold in a render never changes during that render. It is a snapshot. Understanding that explains batching, stale closures, and why mutation silently does nothing.

The API, and lazy initialization

const [value, setValue] = useState(initial) returns the current value plus a setter. On the first render initial is stored; on every render after, the argument is ignored and the stored value is returned.

const [count, setCount] = useState(0);
const [user,  setUser]  = useState({ name: 'Ada', tags: [] });

If computing the initial value is expensive, pass a function instead of a value. React calls it once, on mount, rather than on every render:

// ❌ parse() runs on EVERY render, its result thrown away after the first
const [rows, setRows] = useState(parse(hugeCsv));

// ✅ lazy initializer — called once
const [rows, setRows] = useState(() => parse(hugeCsv));
Gotcha: useState(() => fn) is also how you store a function in state — otherwise React would call it as an initializer. Same trap applies to setState(fn), which is read as a functional update.

Updates are asynchronous, and batched

setCount(1) does not assign to count. It enqueues an update and asks React to re-render. The count variable in the current scope keeps its old value until the component runs again:

function handleClick() {
  console.log(count);   // 0
  setCount(count + 1);
  console.log(count);   // still 0 — this render's snapshot never changes
}

React 18 batches every update in the same tick into a single re-render — inside event handlers, and also in promises, setTimeout, and native handlers, which React 17 did not batch. Three setters in one handler produce one render, not three.

Escape hatch: flushSync(() => setX(1)) from react-dom forces a synchronous render. It exists for measuring the DOM immediately after an update, and it costs you the batching optimization — use it rarely.

Functional updates: setX(prev => next)

Because the snapshot is frozen, calling the setter twice with a computed value applies the same computation twice to the same stale base:

setCount(count + 1);   // queues "replace with 1"
setCount(count + 1);   // queues "replace with 1"  → final value 1, not 2

Pass a function and React feeds each update the result of the previous one in the queue:

setCount(c => c + 1);  // queues "add 1"
setCount(c => c + 1);  // queues "add 1"          → final value 2
Senior tip: Use the functional form whenever the next value depends on the previous one, and always inside setInterval, event listeners, or any callback that outlives the render it was created in. It is the standard cure for a stale-closure bug and it lets you drop the value from a useCallback dependency array.

Immutability: why mutation does nothing

After an update React compares old and new with Object.is. Mutating an object keeps the same reference, so React concludes nothing changed and bails out of re-rendering. This is not a style preference — it is how change is detected.

// ❌ same reference → no re-render, and memo/deps comparisons also miss it
user.tags.push('admin');
setUser(user);

// ✅ new references along the changed path
setUser({ ...user, tags: [...user.tags, 'admin'] });
Operation❌ Mutating✅ Immutable

Deeply nested spreads are a smell. Either flatten the state, or use Immer (useImmer), which lets you write mutating code against a draft and produces a correctly copied new object.

Bail-out subtlety: setting the same primitive also skips the re-render, but React may still render the component once more before deciding to stop. Never rely on the setter as a side-effect trigger.

Where state should live

  • Colocate first. Put state in the component that uses it. Local state is the cheapest state.
  • Lift only when shared. When two siblings need the same value, move it to their closest common parent and pass the value down and a callback up. That parent becomes the single source of truth.
  • Don't lift too far. State parked at the root re-renders the whole tree. Push it back down as soon as only one branch needs it.
  • Not everything belongs in state. Server data belongs in a data-fetching cache (React Query, SWR, RSC); URL state belongs in the URL; values that never trigger a render belong in useRef.
Senior tip: "Lifting state up" and "the URL is state" answer most architecture questions. A filter, a tab, a page number and an open modal are usually better in the query string than in useState — they survive reload, back-button and sharing for free.

Derived state is not state

If a value can be computed from existing props or state, compute it during render. Storing it duplicates the source of truth and the copies drift apart:

// ❌ two sources of truth, kept in sync by hand (and an extra render)
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);
useEffect(() => setTotal(items.reduce(sum, 0)), [items]);

// ✅ one source of truth
const [items, setItems] = useState([]);
const total = items.reduce(sum, 0);            // wrap in useMemo only if profiling says so

The same applies to props: copying a prop into state on mount freezes it, so later prop changes are ignored. If you genuinely need a "reset when the id changes", pass key={id} to remount the component instead — that is the idiomatic reset.

Structuring state: many useState or one object?

  • Separate variables when the fields change independently — the common, readable default.
  • One object when fields always change together (a form, a coordinate pair). Remember that the setter replaces rather than merges, unlike class this.setState: always spread the old object.
  • Avoid contradictory state. isLoading + isError + isSuccess as three booleans allows impossible combinations. One status string ('idle' | 'loading' | 'error' | 'success') cannot be inconsistent.
  • Reach for useReducer when several fields update together, when the next state depends on an action's meaning rather than a value, or when you want the transition logic testable outside the component.

🎯 Interview questions

Why does count still log the old value right after setCount?

State setters do not assign; they enqueue an update and schedule a re-render. The count binding belongs to the current render's snapshot and is immutable for that render. The new value appears in the next render.

What is the difference between setX(x + 1) and setX(v => v + 1)?

The first captures the value from the current render, so two calls in one handler both compute from the same stale base and the second overwrites the first. The functional form receives the latest queued value, so updates compose. Use it whenever the next value depends on the previous one.

What changed about batching in React 18?

Automatic batching was extended beyond React event handlers to promises, timeouts and native handlers, so all updates in a tick produce a single re-render. flushSync opts out when you need a synchronous DOM update.

Why does pushing to an array in state not re-render?

React compares with Object.is. Mutation preserves the reference, so the comparison says nothing changed and React bails out. The same reference also defeats React.memo, useMemo and dependency arrays. Create a new array instead.

When should a value be state at all?

Only if it changes over time, is used in rendering, and cannot be computed from existing props or state. Derived values are computed during render, non-rendering values go in a ref, server data belongs in a fetching cache, and navigational state belongs in the URL.

How do you reset a component's state when a prop changes?

Give it a key tied to that prop. Changing the key unmounts the old instance and mounts a fresh one with initial state — cleaner than syncing props into state inside an effect.

useState or useReducer?

useState for independent, simple values. useReducer when several fields change together, when transitions are driven by named actions, or when you want to unit-test the transition function separately from the component.
