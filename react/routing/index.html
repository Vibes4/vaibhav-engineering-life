Routing (React Router) React

Client-side routing is a trick played on the browser. Instead of letting a link trigger a full document request, the router intercepts the click, calls history.pushState to change the address bar, and re-renders a different component subtree. No network round-trip, no white flash, no lost JavaScript state — but also no server involvement, which is where every routing bug comes from.

React itself has no router. React Router is the de-facto library; v6 unified the API around <Routes>/<Route> and relative nested routes, and v6.4+/v7 added the data router (createBrowserRouter, loader, action) which moves fetching out of effects and into the route definition.

How client-side routing actually works

Three pieces, and that is the whole idea:

  • The History API — history.pushState(state, '', '/users/7') changes the URL and adds a history entry without requesting anything. replaceState does the same without adding an entry.
  • The popstate event — fired when the user presses Back/Forward. The router listens and re-matches. (Note pushState itself does not fire popstate, so the router updates its own state directly on navigation.)
  • Matching + rendering — the router compares the current pathname against its route table, picks the best match, extracts params, and renders that element.
flowchart LR
  C["Click on Link"] --> P["preventDefault"]
  P --> H["history pushState"]
  H --> S["Router state updates"]
  S --> M["Match pathname to route table"]
  M --> R["Render matched element"]

The 404-on-refresh bug

The browser only knows about client routes after your JS runs. If a user hard-loads or refreshes /users/7, the browser asks the server for /users/7 — a path that does not exist on disk — and gets a 404. The fix is a history fallback: the server must return index.html for any request that is not a real static file.

# nginx
location / { try_files $uri $uri/ /index.html; }

# Express
app.use(express.static('dist'));
app.get('*', (req, res) => res.sendFile(path.join(dist, 'index.html')));
Gotcha: "works in dev, 404 in prod" is almost always this. Vite/CRA dev servers do the fallback for you; S3, nginx and Apache do not until you configure it. On S3 + CloudFront you set the error document to index.html.

The core API: BrowserRouter, Routes, Route, Link

import { BrowserRouter, Routes, Route, Link, NavLink } from 'react-router-dom';

<BrowserRouter>
  <nav>
    <Link to="/">Home</Link>
    <NavLink to="/users" className={({ isActive }) => isActive ? 'on' : ''}>Users</NavLink>
  </nav>
  <Routes>
    <Route path="/" element={<Home />} />
    <Route path="/users/:id" element={<User />} />
    <Route path="*" element={<NotFound />} />
  </Routes>
</BrowserRouter>
ElementWhat it doesUse when
<Link to>Renders an <a> but intercepts the click and pushes historyAny in-app navigation
<NavLink to>A Link that exposes isActive/isPending to className, style or childrenNav bars, tabs, sidebars
<a href>Full document navigation: unmounts everything, re-downloads and re-boots the appExternal links, or a deliberate hard reload

Using <a href="/users"> for an internal link is the classic mistake: it throws away all in-memory state, refetches the bundle, and turns a 5 ms transition into a 1 s reload. <NavLink end> is worth knowing — without it, / is "active" on every page, because matching is prefix-based by default.

Note: <Routes> renders only the best match, not every match — unlike React Router v5's <Switch>+<Route>, where order in the file decided the winner. In v6 ranking is computed from the patterns themselves, so file order no longer matters.

Nested routes, layouts and <Outlet />

Nesting is v6's headline feature: a URL maps to a chain of components, not one. Each parent renders shared chrome and drops <Outlet /> where the child goes.

<Routes>
  <Route path="/" element={<RootLayout />}>          {/* layout route */}
    <Route index element={<Home />} />                {/* renders at "/" */}
    <Route path="dashboard" element={<DashLayout />}>
      <Route index element={<Overview />} />          {/* "/dashboard" */}
      <Route path="reports/:reportId" element={<Report />} />
    </Route>
  </Route>
</Routes>

function DashLayout() {
  return (
    <div className="dash">
      <Sidebar />
      <Outlet />      {/* the matched child route renders here */}
    </div>
  );
}
  • Child paths are relative. path="reports/:reportId" under dashboard means /dashboard/reports/:reportId. Relative <Link to="reports/1"> resolves against the current route too.
  • Index route (<Route index>) is the default child — what fills the Outlet when the URL matches the parent exactly.
  • Layout route = a <Route> with an element but no path. It adds shared UI (or a guard) to a group of routes without adding a URL segment.
  • Because parents stay mounted across child navigations, their state and scroll position survive — that is why a sidebar's open/closed state does not reset.

Dynamic segments, search params and the URL as state

// /users/:id/posts/:postId  →  { id: '7', postId: '42' }
const { id, postId } = useParams();          // ALWAYS strings, always possibly undefined

const [searchParams, setSearchParams] = useSearchParams();
const page  = Number(searchParams.get('page') ?? 1);
const query = searchParams.get('q') ?? '';
setSearchParams((prev) => { prev.set('page', String(page + 1)); return prev; },
                { replace: true });          // replace: don't spam the Back button

useSearchParams returns a real URLSearchParams object plus a setter that behaves like a state setter. The argument for putting filters, pagination, sort order, open tab and search text there instead of in useState:

  • Shareable — pasting the URL into Slack reproduces exactly what you were looking at.
  • Reload-proof and back-button-correct — the browser already persists it, for free.
  • Single source of truth — no syncing effect between local state and the address bar.
  • Server-renderable — an SSR pass can read the query string and render the right page immediately.
Senior tip: Keep navigational state in the URL, ephemeral state local (a hover, a half-typed character, whether a tooltip is open). And remember every param is a string: id === 7 is always false, and unvalidated params flow straight into your fetch URLs.

Programmatic navigation: useNavigate and useLocation

const navigate = useNavigate();
await save(form);
navigate(`/users/${user.id}`);                 // push
navigate('/login', { replace: true });         // replace — user can't Back into a dead page
navigate(-1);                                  // history.back()
navigate('/checkout', { state: { from: 'cart' } });   // opaque state, not in the URL

const location = useLocation();  // { pathname, search, hash, state, key }

Prefer a <Link> when the thing is a link — it gets middle-click, right-click "open in new tab", and correct semantics for screen readers for free. Use useNavigate for navigation that follows an action: after a form submit, after login, on a timeout. location.key changes on every navigation, which makes it a handy key or effect dependency for "re-run when the user navigated here again".

Ranking, splat routes and 404s

v6 scores every route pattern and renders the highest scorer, so declaration order is irrelevant. Roughly: a static segment beats a dynamic :param, which beats a splat *, and more matched segments beat fewer.

<Route path="/users/*"      element={<UserFiles />} />   {/* lowest */}
<Route path="/users/:id"    element={<User />} />
<Route path="/users/new"    element={<NewUser />} />     {/* wins for /users/new */}
<Route path="*"             element={<NotFound />} />    {/* catch-all 404 */}

So /users/new renders NewUser even though /users/:id also matches — no more ordering <Switch> children by hand. A trailing * captures the rest of the path, available as useParams()['*'] — used for file browsers, docs trees, and mounting a nested router. A bare path="*" at the top level is your 404 page. The runnable script for this page implements exactly this ranking algorithm.

Protected routes and lazy route-level code splitting

Guarding, and remembering where they were going

function RequireAuth() {
  const user = useAuth();
  const location = useLocation();
  if (user === undefined) return <Spinner />;              // still checking — don't bounce yet
  if (!user) return <Navigate to="/login" replace state={{ from: location }} />;
  return <Outlet />;                                       // layout route: guards a whole group
}

// after a successful login
const from = location.state?.from?.pathname ?? '/';
navigate(from, { replace: true });

Two details interviewers look for: replace (so Back does not bounce the user between login and the guarded page), and stashing location in navigation state so you can return them to the page they actually wanted. And the honest one — a client-side guard is UX, not security. The API must authorize every request independently; anyone can edit the JS bundle.

Lazy routes

const Reports = React.lazy(() => import('./Reports'));

<Route path="reports" element={
  <Suspense fallback={<Skeleton />}><Reports /></Suspense>
} />

Route boundaries are the best code-splitting seams you get: a user who never opens the admin section never downloads it. Put the <Suspense> at the layout level to avoid a flash per route, and prefetch on link hover for the big ones. (Data routers offer a route-level lazy option that also splits the route's loader and action, not just its component.)

Data routers: loaders, actions and errorElement

Fetch-in-useEffect creates a waterfall: render the route → mount → effect fires → request starts. Nested routes stack the waterfalls, so a three-deep layout does three sequential round-trips after paint. A data router hoists fetching into the route definition, so it can start every level's request in parallel, before rendering.

const router = createBrowserRouter([
  { path: '/', element: <Root />, errorElement: <RootError />, children: [
      { index: true, element: <Home /> },
      { path: 'users/:id',
        loader: async ({ params, request }) => {
          const res = await fetch(`/api/users/${params.id}`, { signal: request.signal });
          if (!res.ok) throw new Response('Not found', { status: 404 });
          return res.json();
        },
        action: async ({ request }) => {          // handles <Form method="post">
          const data = await request.formData();
          return updateUser(data);
        },
        element: <User />,
        errorElement: <UserError />,
      },
  ]},
]);

function User() {
  const user = useLoaderData();       // already resolved before this rendered
  const nav = useNavigation();        // 'idle' | 'loading' | 'submitting' — global pending UI
  ...
}
<RouterProvider router={router} />
  • errorElement catches thrown errors and thrown Responses from that route's loader/action/render, and bubbles to the nearest ancestor — proper per-route error boundaries, read via useRouteError.
  • After an action, loaders on the page automatically revalidate — no manual cache invalidation.
  • <Form> + action gives progressive-enhancement-shaped mutations; useFetcher does the same without navigating.
Gotcha: loaders replace fetch-on-mount, not a cache. They re-run on every navigation to the route. For dedup, background refetch and stale-while-revalidate you still want React Query/SWR, or the framework-mode caching in React Router v7 / Remix.

Scroll restoration, and hash vs browser history

The browser restores scroll on real navigations; SPAs must do it themselves, because the document never changed. React Router ships <ScrollRestoration /> (data routers) — drop it once in the root layout and it saves/restores scroll per history entry. Without it, users navigate to a new page already scrolled halfway down.

RouterURLNeeds server configUse when
BrowserRouter / createBrowserRouter/users/7Yes — history fallbackDefault. Clean URLs, SEO-friendly, SSR-compatible.
HashRouter / createHashRouter/#/users/7No — the fragment never reaches the serverStatic hosts you cannot configure, file://, Electron, an app embedded under a path you do not control.
MemoryRouter / createMemoryRouterNone (in memory)N/ATests, React Native, Storybook.

Hash routing's cost: search engines and analytics treat the fragment poorly, the server can never see the route (so no SSR and no per-route caching), and the URLs look dated. Use it only when you genuinely cannot control the server.

🎯 Interview questions

Why does a deep link 404 after deploying an SPA, and how do you fix it?

Client routes only exist once the JS runs. A hard load of /users/7 asks the server for a file that does not exist. Configure a history fallback so any non-asset request returns index.html (try_files ... /index.html in nginx, a catch-all route in Express, the error-document trick on S3/CloudFront). The router then matches the path on the client.

What is wrong with using <a href="/users"> inside the app?

It performs a full document navigation: the app unmounts, the bundle is re-downloaded and re-executed, and all in-memory state is lost. <Link> renders the same anchor but calls preventDefault and pushes onto the History API, so only the matched subtree re-renders. Keep real anchors for external links.

How does React Router decide which route wins when several match?

v6 ranks patterns by specificity rather than declaration order: more matched segments score higher, and within a segment a static literal beats a dynamic :param, which beats a splat *. So /users/new beats /users/:id regardless of the order you wrote them in.

What is <Outlet /> and what problem do nested routes solve?

A URL maps to a chain of matched routes, not one component. Each parent renders persistent layout chrome and places <Outlet /> where its matched child should go. Parents stay mounted across child navigations, so sidebars, tabs and their state survive; an index route supplies the default child.

Why prefer useSearchParams over useState for filters and pagination?

The URL is already shareable, bookmarkable, reload-proof and integrated with the back button, and it can be read on the server for SSR. Keeping it in local state duplicates the source of truth and needs a syncing effect. Keep only ephemeral UI state local.

How do you implement a protected route, and what does it not give you?

A layout route whose element checks auth, renders a spinner while the check is pending, and otherwise returns either <Outlet /> or <Navigate to="/login" replace state={{ from: location }} />; after login you navigate back to state.from. It is UX only — the bundle is public, so the API must authorize every request itself.

What do route loaders buy you over fetching in useEffect?

They remove the render → mount → effect → fetch waterfall, and nested loaders run in parallel instead of stacking one round-trip per level. The route renders with data already available (useLoaderData), errors and thrown Responses land in that route's errorElement, and loaders revalidate automatically after an action. They are not a cache — pair with React Query if you need dedup and stale-while-revalidate.
