Cloud Providers — AWS vs Azure vs GCP Comparison

The three hyperscalers offer roughly the same primitives under different names. Interviewers probe whether you understand the concepts (and can map them across clouds) rather than memorising one vendor's catalog. This page is the equivalence map plus what genuinely differentiates each provider.

Interview Explanation — 30 seconds

Say this: "All three give you the same building blocks — VMs, object storage, managed databases, serverless, Kubernetes, a VPC, IAM and observability — just with different names. AWS wins on breadth and maturity, Azure on enterprise/Microsoft and hybrid integration, GCP on data analytics (BigQuery), Kubernetes (GKE) and its global network. I pick based on the team's existing stack, the workload (analytics → GCP, Microsoft shop → Azure, widest service needs → AWS), data-gravity and egress cost, and how much managed-service lock-in is acceptable."

Interview Explanation — 2 minutes

The mental model is "learn the concept once, map the label three ways". Every provider has: compute (VMs, autoscaling, serverless functions, serverless containers, managed Kubernetes), storage (object/block/file/archive), databases (relational, NoSQL key-value/document, wide-column, in-memory cache, data warehouse), networking (a virtual network, L4/L7 load balancers, DNS, CDN, private connectivity), messaging (queue, pub/sub, event streaming, event bus), security/identity (IAM, secrets, KMS) and observability (metrics, logs, traces).

  • AWS — the widest and most mature catalog, most regions, biggest ecosystem and market share. Default when you want the most services and the deepest community/tooling.
  • Azure — deepest integration with the Microsoft stack (Entra ID/Active Directory, Microsoft 365, Windows/SQL Server licensing via Hybrid Benefit) and the strongest hybrid-cloud story (Azure Arc, Azure Stack, ExpressRoute). Default for enterprises already on Microsoft.
  • GCP — best-in-class for data/analytics (BigQuery, Dataflow), Kubernetes (Google invented K8s; GKE Autopilot is the most managed), a uniquely global VPC and load balancer, live-migrating VMs, and Spanner (globally-consistent SQL). Default for analytics-heavy and cloud-native/K8s teams.

The honest interview point: the differences are at the edges (analytics, hybrid, global networking, specific managed services and their semantics), not the core primitives — and egress/data-transfer cost and IAM model differences are what actually bite in production.

Unique / Differentiating Strengths

AWS — breadth & maturity

  • Largest service catalog and region footprint; earliest to market so the deepest feature depth per service and the biggest third-party ecosystem/marketplace.
  • Graviton (in-house ARM) for ~40% better price/performance; Nitro hypervisor offload; S3 is the de-facto object-storage standard others emulate.
  • Richest serverless ecosystem (Lambda + EventBridge + Step Functions) and the widest set of niche/primitive services.

Azure — enterprise & hybrid

  • Entra ID (formerly Azure AD) is the identity backbone for most large enterprises → seamless SSO with Microsoft 365 and on-prem AD.
  • Hybrid Benefit reuses existing Windows Server / SQL Server licenses; strongest hybrid/on-prem story via Azure Arc (manage any infra) and Azure Stack (run Azure services on-prem), plus ExpressRoute.
  • First-class for .NET, Windows workloads, and heavily-regulated/government tenants.

GCP — data, Kubernetes & global network

  • BigQuery: serverless warehouse with separated storage/compute — best-in-class for ad-hoc, petabyte-scale analytics with no cluster to manage.
  • Kubernetes heritage: Google created K8s (from Borg); GKE + Autopilot is the most mature managed offering.
  • Global VPC and global HTTP(S) load balancer behind a single anycast IP (AWS/Azure networks are regional); live migration of VMs during host maintenance (no reboot); premium-tier global backbone.
  • Cloud Spanner: globally distributed, strongly consistent relational DB using TrueTime — genuinely unique. Plus automatic sustained-use discounts and per-second billing.

Production Architecture

The same 3-tier web application maps cleanly across providers: edge/CDN → global or regional L7 load balancer → autoscaling stateless compute (containers on managed K8s) → managed relational primary + read replicas → managed cache → object storage → async work on a queue.

flowchart LR
  U["Users"] --> CDN["CDN CloudFront or Front Door or Cloud CDN"]
  CDN --> LB["L7 Load Balancer ALB or App Gateway or Global LB"]
  LB --> K["Managed Kubernetes EKS or AKS or GKE"]
  K --> DB["Managed SQL RDS or Azure SQL or Cloud SQL"]
  K --> CACHE["Cache ElastiCache or Azure Redis or Memorystore"]
  K --> OBJ["Object Storage S3 or Blob or GCS"]
  K --> Q["Queue SQS or Service Bus or Pub Sub"]

Only the service names change — the architecture, the failure domains (spread across zones), and the scaling story are identical. That portability is exactly why teams standardise on Kubernetes + Terraform to stay cloud-agnostic.

Common Mistakes

  • Assuming feature parity — equivalents differ in consistency, limits and pricing units. Fix: name the semantic difference.
  • Ignoring egress cost — multi-region/multi-cloud designs quietly rack up transfer charges. Fix: keep compute near data; budget egress.
  • Porting the IAM mental model — AWS roles+resource policies, Azure RBAC+Entra, GCP hierarchy (org→folder→project) are genuinely different. Fix: relearn per cloud.
  • Zonal vs regional confusion (esp. GCP) — a zonal disk/IP doesn't survive a zone outage. Fix: pick regional resources for HA.
  • Deep managed-service lock-in (DynamoDB/Cosmos/BigQuery) with no exit plan. Fix: accept it deliberately or abstract behind portable layers.

Interview Follow-up Questions

  1. What's the AWS/Azure/GCP equivalent of S3 / Lambda / EKS?
    1. Pointer: S3 → Blob → Cloud Storage; Lambda → Azure Functions → Cloud Functions/Run; EKS → AKS → GKE.
  2. How do Availability Zones differ across the three?
    1. Pointer: AWS AZs, Azure AZs + region pairs for DR, GCP zones with global VPC/LB.
  3. Why is GCP's VPC "global" and what does that buy you?
    1. Pointer: one VPC/subnetted network spans regions; single global anycast LB IP; simpler multi-region.
  4. DynamoDB vs Cosmos DB vs Firestore — how do they differ beyond the name?
    1. Pointer: consistency options, partition-key model, and pricing units (RCU/WCU vs RU/s vs ops) differ.
  5. What makes BigQuery different from Redshift/Synapse?
    1. Pointer: serverless, storage/compute separation, no cluster to size, pay-per-query scan.
  6. What is Cloud Spanner and why is it unique?
    1. Pointer: globally distributed, strongly consistent SQL using TrueTime (GPS+atomic clocks) to bound clock skew.
  7. Compare the IAM models.
    1. Pointer: AWS identity/resource policies + roles; Azure RBAC + Entra directory; GCP org→folder→project hierarchy with inherited bindings.
  8. What's Azure Hybrid Benefit and when does it matter?
    1. Pointer: reuse owned Windows/SQL licenses to cut VM cost; matters for Microsoft-heavy enterprises.
  9. How would you keep an app portable across clouds?
    1. Pointer: Kubernetes + Terraform + open formats; avoid proprietary managed services or abstract them.
  10. Where do egress costs come from and how do you control them?
    1. Pointer: data leaving cloud/region/AZ, NAT processing; keep compute near data, cache, CDN, compress.
  11. Serverless functions vs serverless containers — when each?
    1. Pointer: functions for event-driven short tasks; Cloud Run/Fargate/Container Apps for containerised HTTP services with more control.
  12. Which cloud for a Kubernetes-native startup and why?
    1. Pointer: GKE Autopilot maturity, but justify by team skills and workload, not hype.
  13. How does each do private connectivity to a managed service?
    1. Pointer: PrivateLink vs Private Link vs Private Service Connect — private IP, no public egress.
  14. Multi-cloud — real benefit or resume-driven?
    1. Pointer: avoids lock-in and outages but multiplies ops/egress/complexity; usually pick one + DR plan.
  15. What's the equivalent of Kafka on each?
    1. Pointer: MSK / Event Hubs (Kafka API) / Managed Service for Kafka; or Kinesis/Pub-Sub as native alternatives.
  16. How do you design for a region outage on each?
    1. Pointer: multi-AZ within region for zone failure; cross-region replication + failover DNS/global LB for region failure.
  17. Reserved vs Savings Plans vs committed-use vs sustained-use?
    1. Pointer: AWS RI/Savings Plans, Azure RI + Hybrid Benefit, GCP committed + automatic sustained-use.
  18. Which provider for GenAI and why?
    1. Pointer: Bedrock (AWS, model choice), Azure OpenAI (GPT access), Vertex/Gemini + TPUs (GCP).

🎯 Deep-dive Q&A — model answers

Give me the fastest way to map a service you don't know across clouds.

Anchor on the concept category — compute, storage, database, networking, messaging, identity, observability — then recall the concept's job. "It's the managed Kubernetes service" instantly gives EKS/AKS/GKE; "it's the serverless data warehouse" gives Redshift-serverless/Synapse/BigQuery. Interviewers care that you reason from the primitive, not that you memorised a table. Then I add the one meaningful difference (e.g., GKE's Autopilot maturity, BigQuery's serverless storage/compute split).

Why is data egress the cost that surprises teams, and how do you design around it?

Inbound data is usually free, but data leaving the cloud — or crossing regions/AZs — is billed per GB, and it's invisible until the bill arrives. A chatty cross-region architecture or a multi-cloud pipeline can dwarf compute cost. Design rules: keep compute in the same region/zone as its data (data gravity), cache aggressively and serve via CDN so bytes leave once, compress payloads, use private connectivity to avoid public-internet egress rates, and colocate services that talk a lot. Model egress explicitly in the cost estimate, not just VM hours.

Explain the real difference between DynamoDB, Cosmos DB and Firestore.

All are managed NoSQL, but: DynamoDB is key-value/document with a strict partition-key + optional sort-key model, eventual or strong reads, and capacity in RCU/WCU (or on-demand). Cosmos DB is multi-model (document/graph/column/key-value) with five tunable consistency levels (strong → bounded-staleness → session → consistent-prefix → eventual), global distribution built-in, priced in Request Units/s. Firestore is a document store with real-time listeners and strong consistency within a region, priced per read/write/delete operation. So the "equivalent" mapping hides different consistency guarantees, partitioning rules, and billing units — which directly change how you data-model and what you pay.

What makes Cloud Spanner able to offer global strong consistency when the CAP theorem says you can't?

Spanner doesn't violate CAP — during a network partition it chooses consistency over availability for the minority side. Its trick for global strong consistency at low latency is TrueTime: Google equips datacenters with GPS receivers and atomic clocks so every node knows the current time within a small bounded uncertainty (epsilon). Spanner assigns commit timestamps and then "waits out" that uncertainty (commit-wait) before releasing a write, guaranteeing that any transaction that starts later sees it. That bounded clock uncertainty is what lets Paxos-replicated, globally-distributed data behave linearizably — something you can't easily replicate without that clock infrastructure.

Why do teams standardise on Kubernetes + Terraform instead of native cloud services?

To bound lock-in and keep skills/portability. Kubernetes gives the same deployment, scaling, service-discovery and rollout model on EKS, AKS or GKE, so workloads move with minimal rewrite. Terraform gives one declarative IaC language across all three providers (vs CloudFormation/ARM-Bicep being single-cloud). The trade-off is you give up some of the deepest managed-service leverage and take on more operational responsibility (you manage the cluster, addons, upgrades). Most teams still use native managed data services (RDS/BigQuery) because rebuilding those isn't worth it — they accept lock-in where the value is highest and stay portable at the compute/orchestration layer.

Which cloud would you pick for an analytics-heavy product, and how would you justify it?

GCP is the strong default because BigQuery is a serverless warehouse — no cluster to size, storage and compute scale independently, and ad-hoc petabyte queries "just work" with per-query pricing, plus Dataflow (Beam) for streaming/batch ETL and Looker for BI. But I'd justify with the team and data, not hype: if the org is already on AWS with Redshift expertise and the analytics volume is moderate, staying on AWS avoids a migration and egress to move data. The decision is data-gravity + existing skills + query patterns, and BigQuery only wins decisively when ad-hoc, spiky, large-scan analytics dominate.

How do the three IAM models actually differ, in practice?

AWS: identities (users/roles/groups) get JSON policies, and resources can also carry resource-based policies (e.g., an S3 bucket policy); access is the union evaluated with explicit-deny precedence, and cross-account access uses role assumption via STS. Azure: authentication is via Entra ID (the directory), and authorization is Azure RBAC — role assignments scoped at management-group/subscription/resource-group/resource levels, inherited downward. GCP: a resource hierarchy of organization → folders → projects → resources, with IAM bindings (member → role) set at any level and inherited by descendants. So "grant read access" is a policy attach in AWS, a role assignment at a scope in Azure, and a binding on a node in the hierarchy in GCP — and mixing them up is a common source of over-privilege.

When would you deliberately go multi-cloud, and what does it cost you?

Good reasons: regulatory data-residency that one provider can't meet, avoiding a single vendor's outage/lock-in for a critical path, or leveraging a best-of-breed service (e.g., BigQuery on GCP while the app runs on AWS). The costs are real: you multiply operational surface (two IAM models, two networking stacks, two skill sets), you pay inter-cloud egress, you lose the deep integration each provider offers, and you're limited to the lowest-common-denominator (often Kubernetes) to stay portable. For most teams the pragmatic answer is single-cloud with a documented DR plan and portable IaC — full active-active multi-cloud is justified only when the business risk of one provider genuinely outweighs that overhead.
