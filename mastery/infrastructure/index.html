Infrastructure Mastery

Infrastructure is everything between "here is my compiled artifact" and "a user got a 200 in 40ms": the isolation primitives (namespaces/cgroups), the packaging (OCI images), the delivery (CI/CD), the ingress (reverse proxy/mesh), the secrets, and the observability that tells you it all still works. This page is the Staff-level drill-down.

Interview Explanation — 30 seconds

Say this: "Modern infra is immutable, declarative and isolated. We package the app once as an OCI image built on overlay layers, run it isolated by Linux namespaces and bounded by cgroups v2, and describe the whole platform as code in Terraform so every environment is reproducible from a state file. CI/CD turns a git SHA into a signed artifact and rolls it out with canary or blue-green so a bad deploy is contained. Ingress is an L7 proxy (Envoy/nginx) doing TLS termination and rate limiting, service-to-service traffic is mTLS through a mesh with retries/timeouts/circuit-breaking, secrets come from Vault/KMS with rotation, and everything emits metrics, logs and traces into Prometheus/Grafana/OpenTelemetry so we can debug from a single trace ID."

Interview Explanation — 2 minutes

Break it into layers, and for each name the concrete mechanism:

  • Isolation. A container is not a VM. There is no guest kernel — it's a normal Linux process whose view of the world is trimmed by 7 namespaces (pid, net, mnt, uts, ipc, user, cgroup) and whose resource ceiling is enforced by cgroups v2 (cpu.max, memory.max). A VM virtualises hardware (hypervisor + guest kernel, ~seconds to boot, hundreds of MB); a container shares the host kernel (~tens of ms, tens of MB).
  • Packaging. The image is a stack of read-only overlayfs layers described by an OCI manifest; the running container adds one writable layer via copy-up. Layers are content-addressed by digest, deduplicated in the registry, and pulled by digest for immutability.
  • Provisioning. Terraform keeps a state file mapping declared resources to real cloud IDs, diffs desired-vs-actual on plan, and reconciles on apply. Declarative, so drift is detectable.
  • Delivery. CI/CD: build → test → produce a versioned artifact → deploy. Rollout strategy (rolling / blue-green / canary) decides blast radius.
  • Runtime networking. Reverse proxy / API gateway at the edge (TLS, rate limit, auth), service mesh (Envoy sidecars) for east-west mTLS, retries, timeouts, circuit breaking and traffic shifting.
  • Secrets & config. Vault/KMS with short-lived, rotated credentials; secrets mounted as tmpfs files, not baked into images.
  • Observability. The three pillars — metrics (Prometheus), logs (Loki/ELK), traces (OpenTelemetry → Jaeger/Tempo) — correlated by trace/span IDs.

Internal Working

Trace a single deploy end-to-end and name what each layer actually does:

  1. Build. docker build reads the Dockerfile; each instruction (RUN, COPY) produces a new filesystem layer via the builder's snapshotter. BuildKit computes a content hash per step and reuses cached layers when inputs are unchanged.
  2. Image assembly. Layers are tar+gzip blobs; a config JSON records the rootfs diff-ids and the run config; a manifest lists layer digests. The manifest digest (sha256:...) is the immutable image identity.
  3. Push. Client pushes blobs the registry doesn't already have (deduped by digest) then the manifest. A multi-arch manifest list points to per-platform manifests.
  4. Schedule & pull. Orchestrator picks a node; containerd pulls missing layers and unpacks them into the snapshotter, stacking them as read-only overlay lowerdirs with a fresh writable upperdir.
  5. Namespace setup. containerd hands an OCI runtime spec to runc, which calls clone()/unshare() with CLONE_NEWPID|NEWNET|NEWNS|NEWUTS|NEWIPC|NEWUSER, sets up the cgroup, applies seccomp/AppArmor/capabilities, pivot_roots into the overlay mount, then execve()s the entrypoint. runc exits; the process is reparented to the containerd-shim.
  6. Resource enforcement. The kernel scheduler honours cpu.max (quota/period throttling) and the memory controller kills the process (OOM) if it exceeds memory.max.
  7. Networking. A CNI plugin creates a veth pair, one end in the container's net namespace, assigns an IP, programs routes; DNS-based service discovery resolves service names to virtual IPs; kube-proxy/IPVS or the mesh load-balances to endpoints.
  8. Ingress & mesh. Edge proxy terminates TLS and routes by host/path; the sidecar intercepts outbound traffic (iptables redirect to Envoy), applies mTLS, timeouts, retries and circuit breakers.
  9. Telemetry. The app/sidecar emits OpenTelemetry spans and Prometheus metrics scraped every 15–30s; logs stream to a collector. A trace ID threads the whole request.

Why was this built?

Before containers and IaC we had pets, not cattle:

  • "Works on my machine." Apps depended on host-installed libs, JVM/Node versions, OS packages. Deploy = SSH in, run a shell script, pray. Containers bundle the app and its userland into one immutable artifact so dev==staging==prod.
  • Full VMs were heavy. A VM per service wasted GBs of RAM on duplicate guest kernels and booted in minutes. Containers share the host kernel: tens of ms, tens of MB, 10–100x denser packing.
  • Snowflake servers. Manually-tuned boxes drifted; no one could rebuild them. IaC (Terraform) made infra reproducible and reviewable in git; immutable infra made "fix in place" obsolete — you rebuild and replace.
  • Manual deploys were risky. CI/CD automated build/test/deploy so releases became boring, frequent and reversible.

Advantages

  • Reproducibility. Same image digest runs identically everywhere; IaC rebuilds the whole platform.
  • Density & cost. Bin-pack many containers per node; cgroups give fair sharing.
  • Fast, safe rollout. Immutable artifacts + canary/blue-green = instant rollback (repoint traffic, no rebuild).
  • Isolation with low overhead. Namespaces + cgroups without a hypervisor tax.
  • Auditability. Every change is a git commit / signed artifact; drift is detectable.

Drawbacks

  • Shared-kernel blast radius. A kernel CVE (e.g. Dirty Pipe) can escape all containers on a host.
  • Operational complexity. Registry, orchestrator, mesh, IaC, secrets, observability — a lot of moving parts and YAML.
  • State is awkward. Terraform state files and container-based stateful workloads need care (locking, volumes).
  • Cgroup pitfalls. CPU-throttling and OOM-kills surprise teams that mis-size limits.
  • Supply-chain surface. Base images and transitive deps pull in CVEs you didn't write.

Trade-offs

  • Isolation vs density. Stronger isolation (VMs/microVMs) costs RAM and boot time; containers trade some isolation for packing efficiency.
  • Immutability vs iteration speed. Rebuild-and-replace is safe but slower than hot-patching; you gain reproducibility, lose in-place hotfixes.
  • Declarative (Terraform) vs imperative (scripts). Declarative gives drift detection and idempotency but a steeper mental model and state-file management.
  • Canary vs blue-green. Canary limits blast radius but needs good metrics and takes longer; blue-green flips instantly but doubles resource cost during cutover.
  • Sidecar mesh vs library. Sidecars give language-agnostic mTLS/retries but add ~1ms/hop latency and per-pod memory; in-process libraries are faster but couple every service to a language SDK.
  • Env-var secrets vs mounted secrets. Env vars leak into /proc, crash dumps and child processes; mounted tmpfs files are safer but need rotation-aware apps.

When NOT to use it

Watch out: Don't reach for the full container/mesh/IaC stack when:
  • A single monolith on one box serves your traffic fine — a mesh and multi-cluster IaC is pure overhead.
  • Hard multi-tenant isolation of untrusted code is the requirement and you only have plain containers — use microVMs or VMs.
  • Ultra-low-latency / kernel-bypass workloads (HFT, DPDK) where hypervisor/namespace overhead or noisy neighbours are unacceptable — bare metal.
  • Heavy stateful DBs with strict IO SLAs — often better on dedicated nodes/managed services than co-scheduled containers.
  • A tiny team early on — a PaaS gets you to market faster than building a platform.

Production Architecture

A typical multi-AZ, mesh-enabled deployment: edge L7 proxy terminates TLS and rate-limits, routes into a Kubernetes cluster where each pod runs an app container plus an Envoy sidecar; sidecars form the data plane governed by a control plane; secrets come from Vault; images from a private registry; everything emits telemetry.

Production Problems

  • CPU throttling from tight cpu.max. A service with a low CPU limit gets throttled during bursts; p99 latency spikes even though average CPU looks fine. Check cpu.stat nr_throttled/throttled_usec.
  • OOMKilled (exit 137). RSS exceeds memory.max; kernel kills the largest process. JVM/Node heaps that ignore cgroup limits are the classic cause.
  • Terraform state lock stuck. A killed apply leaves a DynamoDB/GCS lock; the next run blocks. Needs force-unlock.
  • Image pull backoff. Registry auth expiry, rate limits (Docker Hub 100–200 pulls/6h), or missing arch in the manifest list.
  • Retry storms / metastable failure. Mesh retries amplify load during a partial outage; a slow dependency gets 3x traffic and never recovers without a circuit breaker.
  • Secret rotation breakage. App caches a Vault lease that expires; DB rejects the stale credential mid-flight.
  • DNS TTL / stale endpoints. Service discovery caches a dead pod IP; requests hang until the timeout.
  • Cardinality explosion in Prometheus. A label with user IDs blows up series count and OOMs the TSDB.

Scaling

  • Vertical (up). Bigger nodes / higher cgroup limits; VPA right-sizes requests. Hits a per-node ceiling.
  • Horizontal (out). HPA scales replicas on CPU/custom metrics; Cluster Autoscaler / Karpenter adds nodes. Stateless services scale linearly.
  • Sharding/partitioning. Stateful tiers shard by key; cells/bulkheads isolate blast radius so one shard's failure doesn't sink the fleet.
  • Registry & build scale. Layer caching + distributed build cache keeps CI fast; regional registry mirrors avoid pull bottlenecks.
  • Control-plane limits. A single Kubernetes cluster tops out around ~5,000 nodes / 150k pods — beyond that, multi-cluster + federation.

Watch out: Set CPU requests for scheduling but be careful with CPU limits — aggressive limits cause CFS throttling that HPA can't fix because average CPU stays low while p99 explodes.

Security

  • AuthN/Z between services: mesh mTLS with SPIFFE identities; authorization policies scoped per service (zero-trust — no implicit trust from network location).
  • Edge auth: gateway validates JWT/OIDC, enforces rate limits and WAF rules before traffic reaches services.
  • Encryption in transit: TLS 1.3 at edge, mTLS inside; encryption at rest via KMS-managed keys / envelope encryption on volumes and object storage.
  • Secrets: Vault dynamic secrets (short TTL, auto-rotated); mount as tmpfs, never bake into images or logs; use IAM roles / workload identity instead of static keys.
  • Container hardening: run as non-root, read-only rootfs, drop Linux capabilities, seccomp + AppArmor/SELinux profiles, no privileged mode, user namespaces to remap root.
  • Supply chain: scan images (Trivy/Grype), pin by digest, sign with cosign / verify SLSA provenance, use an SBOM, minimal/distroless base images.
  • Network isolation: NetworkPolicies / security groups default-deny; private subnets; no public IPs on workloads.
Watch out: A shared-kernel container escape (privileged pod + kernel CVE, or a mounted docker socket) compromises the whole node. Never mount /var/run/docker.sock into an untrusted container.

Common Mistakes

  • Latest tag in prod. image:latest is mutable → non-reproducible deploys. Fix: pin by digest.
  • Tight CPU limits. Causes CFS throttling. Fix: set requests, drop or loosen limits.
  • JVM/Node ignoring cgroup memory. Heap grows past memory.max → OOMKill. Fix: container-aware flags.
  • Secrets in env vars / images. Leak into logs and layers (they persist in layer history even if deleted!). Fix: mounted secrets / Vault.
  • No circuit breaker with retries. Retry storms. Fix: budgeted retries + breaker + timeouts.
  • Committing Terraform state to git. Contains secrets and causes conflicts. Fix: remote backend with locking (S3+DynamoDB/GCS).
  • Running as root. Fix: non-root user, drop caps, read-only rootfs.
  • High-cardinality metric labels. Kills Prometheus. Fix: bounded label values, use exemplars/traces for per-request detail.
  • No health/readiness probes. Traffic hits a pod before it's ready. Fix: separate liveness vs readiness probes.

    1. Answer pointer: CFS quota/period in cpu.max; symptom is throttling (nr_throttled) and p99 latency spikes.
  4. What happens on an OOM kill and how do you diagnose it?
    1. Answer pointer: memory controller kills the process, exit 137; check memory.events and kubectl describe.
  5. How does an overlay filesystem give you copy-on-write?
    1. Answer pointer: read-only lowerdirs + writable upperdir; copy-up on first write to a file.

    1. Answer pointer: clone/unshare namespaces, set cgroup, apply seccomp/caps, pivot_root, execve; shim reparents.

    1. Answer pointer: tags are mutable; digest is content-addressed and immutable → reproducibility + tamper detection.
  8. What's in a Terraform state file and why is it dangerous?
    1. Answer pointer: resource→cloud-ID mapping, sometimes secrets; needs remote backend + locking, never in git.
  9. How does Terraform detect drift?
    1. Answer pointer: refresh real state, diff against desired; plan -detailed-exitcode returns 2.
  10. Canary vs blue-green vs rolling — when each?
    1. Answer pointer: canary = smallest blast radius, needs metrics; blue-green = instant flip, 2x cost; rolling = default, gradual.
  11. How does the mesh prevent a retry storm from taking you down?
    1. Answer pointer: retry budgets, per-try timeouts, circuit breakers (outlier detection ejects bad hosts).
  12. Env-var vs mounted secrets — which and why?

  17. How would you contain a kernel CVE that allows container escape?

  19. How do you make your build supply chain tamper-proof?

Scenario 1 — Latency spikes with low average CPU

Symptomsp99 latency 5x normal, dashboards show CPU at ~40%, no errors.
InvestigationChecked cpu.stat: nr_throttled climbing, throttled_usec high. HPA not scaling because average CPU is low.
Root CauseTight cpu.max limit; bursty workload hits the CFS quota each 100ms period and gets parked until next period.
SolutionRaised/removed the CPU limit (kept requests), latency normalised immediately.
PreventionAlert on throttled ratio >25%; avoid CPU limits for latency-sensitive services; load test with bursty traffic.
Interview Answer"Average CPU lies for bursty apps — the kernel throttles you inside each 100ms period. I read cpu.stat, saw throttling, dropped the limit, and p99 recovered. Now we alert on throttled ratio, not just utilisation."

Scenario 2 — Retry storm turns a blip into an outage

SymptomsOne slow downstream dependency; suddenly the whole call graph browns out and doesn't recover even after the dependency heals.
InvestigationMesh dashboards show request rate to the dependency at 3x normal; traces show each hop retrying 3 times with no budget.
Root CauseLayered retries multiplied load (metastable failure); no circuit breaker, so the dependency stayed saturated.
SolutionAdded retry budget (cap at 10% extra), per-try timeouts, and outlier-detection circuit breaking to eject slow hosts; shed load to break the loop.
PreventionRetries only at one layer, always budgeted; breakers everywhere; chaos-test dependency slowdowns.
Interview Answer"Classic metastable failure: retries amplified a transient slowdown into a self-sustaining overload. Fix is a retry budget plus circuit breaking so the system sheds load and recovers instead of hammering a dying dependency."

Scenario 3 — CrashLoopBackOff after a deploy (exit 137)

SymptomsNew version crash-loops; kubectl describe shows OOMKilled, exit 137.
InvestigationNew release bumped a dependency that increased heap; JVM defaulted to 1/4 host RAM ignoring the cgroup memory.max.
Root CauseRuntime not container-aware; RSS exceeded the cgroup limit → kernel OOM.
SolutionSet -XX:MaxRAMPercentage=75 (or Node --max-old-space-size), right-sized memory.max; rolled forward.
PreventionLoad-test memory before release; alert on working-set/limit >90%; container-aware runtime flags as a baseline.
Interview Answer"Exit 137 is the kernel OOM killer. The JVM wasn't cgroup-aware and sized its heap to the host, not the limit. I set MaxRAMPercentage and right-sized the limit. Prevention is memory load-testing plus a working-set alert."

Scenario 4 — Terraform apply blocks on a stale state lock

SymptomsCI deploy hangs: "Error acquiring the state lock."
InvestigationPrevious pipeline run was killed mid-apply; the DynamoDB lock record was never released. Confirmed the holder was dead.
Root CauseInterrupted apply left a dangling lock; no other apply could proceed.
SolutionVerified no apply was actually running, then terraform force-unlock <ID>; re-ran plan to confirm no partial state corruption.
PreventionSerialise applies in CI, add apply timeouts + cleanup traps, use remote backend with lock TTLs, never -lock=false.
Interview Answer"State locking prevents concurrent applies corrupting state; the flip side is a dead run leaves a stale lock. I confirm nothing is actually running, force-unlock, then re-plan to check state integrity before applying."

Scenario 5 — Secret rotation causes mid-day auth failures

SymptomsDB "authentication failed" errors spike hours after a healthy deploy, no code change.
InvestigationVault dynamic DB credential lease expired; app had cached the credential at startup and never renewed.
Root CauseApp not lease-aware; stale credential rejected when Vault rotated the underlying DB user.
SolutionMade the client renew leases / re-read the mounted secret on rotation; added overlap window so old and new creds are both valid during cutover.
PreventionRotation drills in staging; alert on lease TTL < threshold; treat secrets as dynamic, not startup-only.
Interview Answer"Dynamic secrets have TTLs — if the app caches a credential at boot it dies at rotation. The fix is lease-aware clients that re-read on rotation plus an overlap window, and I rehearse rotation in staging so prod rotation is a non-event."

🎯 Deep-dive Q&A — model answers

Explain precisely how a container achieves isolation at the syscall level.

At start, the runtime (runc) calls clone()/unshare() with the namespace flags (CLONE_NEWPID, NEWNET, NEWNS, NEWUTS, NEWIPC, NEWUSER, plus cgroup ns). Each namespace gives the process a private view of one kernel subsystem: its own PID 1, its own network stack/interfaces, its own mount tree, hostname, System V IPC, and UID/GID mapping. It writes the process into a cgroup (v2 unified hierarchy) that caps CPU (cpu.max quota/period), memory (memory.max), IO and pids. It applies a seccomp filter (blocking ~44 dangerous syscalls by default), drops Linux capabilities, sets an AppArmor/SELinux profile, then pivot_roots into the overlay rootfs and execves the entrypoint. Crucially there's still exactly one kernel — isolation is a policy the shared kernel enforces, which is why a kernel bug can break out.

Why is copy-on-write via overlayfs both a feature and a footgun?

Feature: image layers are read-only and shared across every container that uses them, so N containers from one image cost one copy of the base plus tiny per-container writable upperdirs — huge density and fast start. Footgun: the first write to any file triggers a full copy-up of that file into the upperdir, so rewriting a large file or heavy random writes to the container FS are surprisingly slow and consume space; also anything written to the container layer is ephemeral and lost on restart. The fix is to put mutable/hot data on a proper volume, not the overlay, and to keep images layered so cheap stable layers cache and only volatile layers rebuild.

Declarative vs imperative IaC — argue the trade-off with Terraform specifics.

Imperative (shell/Ansible playbooks in order) tells the machine how: run these steps. It's intuitive but non-idempotent and drift-blind — you can't ask "what would change?" Declarative (Terraform) states desired end-state; the engine builds a dependency graph, diffs desired vs the state file's record of reality, and computes the minimal set of create/update/destroy ops. Benefits: idempotency, plan as a dry-run/diff, drift detection, and a reviewable graph. Costs: you manage a state file (locking, secrets, backend), the diff engine can surprise you (a change forces resource replacement), and ordering/dependency bugs are subtler. For infra you want declarative; for one-off procedural glue, imperative is fine.

Walk through a full CI/CD pipeline and where caching and safety live.

Trigger on git push → checkout at SHA → restore dependency cache (keyed by lockfile hash) → build (BuildKit with layer + remote build cache) → unit/integration tests (fail fast) → static analysis + image vuln scan (Trivy) → produce a versioned, signed artifact (cosign) pushed to the registry keyed by SHA/digest → deploy to staging → smoke tests → progressive rollout to prod (canary: shift 5%→25%→100% gated by SLO analysis, or blue-green: deploy green, flip traffic, keep blue for rollback). Safety lives in: immutable digest-pinned artifacts (no rebuild between envs), automated gates (tests, scans, SLO burn), and instant rollback (repoint traffic / redeploy previous digest). Caching lives in dependency cache, Docker layer cache, and a shared remote build cache to keep builds under a couple of minutes.

Canary vs blue-green vs rolling — give the decision criteria with numbers.

Rolling (default): replace pods in batches (e.g. maxSurge 25%, maxUnavailable 0); gradual, no extra full fleet, but both versions serve simultaneously and rollback is another rolling wave. Blue-green: stand up a full parallel "green" fleet, run smoke tests, flip the load balancer atomically; rollback is instant (flip back) but you pay ~2x resources during cutover and DB migrations must be backward-compatible. Canary: route a small % (start 1–5%) to the new version, watch RED metrics/error budget, then ramp; smallest blast radius and catches real-traffic bugs, but slowest and needs solid metrics + automated analysis (Flagger/Argo Rollouts). Rule: canary for high-risk user-facing paths with good telemetry; blue-green when you need instant rollback and can afford 2x; rolling for routine low-risk internal services.

How does a service mesh implement circuit breaking, and why does it prevent metastable failure?

The Envoy sidecar tracks per-upstream-host health via outlier detection: consecutive 5xx or gateway failures beyond a threshold eject the host from the load-balancing pool for a base ejection time (backing off on repeated ejection). Combined with connection/pending-request limits (the actual "circuit breaker" thresholds) and per-try timeouts + a retry budget (cap retries at e.g. 20% of requests), it stops the amplification loop: without it, a slow dependency triggers retries that multiply its load 2–3x, keeping it saturated forever even after the trigger clears (metastable failure). The breaker sheds/fails fast so the dependency drains its queue and recovers, and the budget ensures retries can't dominate traffic.

Env-var vs mounted secrets — why do senior engineers insist on mounts?

Env vars are readable via /proc/<pid>/environ, inherited by every child process, dumped into crash reports/core dumps and often accidentally logged (many frameworks log the environment on boot). They're also fixed at process start, so rotation requires a restart. Mounted secrets are tmpfs-backed files (never on disk), scoped to the container, not inherited by unrelated child processes, and can be updated in place — a rotation-aware app re-reads the file without a restart. With Vault Agent / CSI driver the secret is fetched with the pod's identity at runtime, so it isn't in the image, the manifest, or the registry. The env-var convenience isn't worth the leak surface for anything sensitive.

Design secret rotation with zero downtime.

Use dynamic secrets with a TTL and a rotation with overlap. For a DB credential: Vault's database secrets engine issues a short-lived user per app instance; the app renews the lease before expiry and re-reads on renewal failure. For a rotated shared secret (API key), rotate in two phases: (1) create the new secret and make both old and new valid on the server side (grace window ≥ your longest cache/lease TTL), (2) roll the new value to clients (mounted file update or rolling restart), (3) revoke the old only after all clients confirm the new. Alert on lease TTL nearing zero, and rehearse rotation in staging. The invariant: there is always a window where both credentials work, so no in-flight request fails at the switch.

How does DNS-based service discovery actually resolve to a healthy pod?

In Kubernetes, a Service gets a stable ClusterIP and a DNS name (svc.ns.svc.cluster.local) served by CoreDNS. CoreDNS resolves the name to the ClusterIP (or, for headless services, directly to pod IPs). Traffic to the ClusterIP is intercepted by kube-proxy (iptables or IPVS) which DNATs to one of the Endpoints — and the EndpointSlice only lists pods that pass their readiness probe, so unready/dead pods are removed. In a mesh, Envoy gets endpoints via EDS from the control plane and load-balances with active/passive health checking and locality awareness. The failure mode: DNS or endpoint caching (TTL) briefly points at a terminated pod, so you need short TTLs, readiness gating, and connection retries/timeouts to route around it.

Your Prometheus fell over after a deploy. Diagnose and fix cardinality.

Root cause is almost always a new high-cardinality label — a metric labelled with something unbounded like user ID, request ID, or full URL path, which creates a distinct time series per value and explodes memory (each series ~ few KB; millions of series = many GB). Diagnose: topk(10, count by (__name__)({__name__=~".+"})) to find the offending metric, and check prometheus_tsdb_head_series trend against the deploy time. Fix: drop or relabel the offending label with metric_relabel_configs (drop action), aggregate at emission, and put per-request detail in traces/exemplars not labels. Prevention: enforce a label allowlist, set sample/series limits per target, and review new metrics in code review. Metrics are for bounded dimensions; unbounded identity belongs in logs/traces.

How do you make the software supply chain tamper-evident end-to-end?

Layers: (1) hermetic, reproducible builds (Bazel/BuildKit with pinned inputs) so the same source yields the same digest; (2) generate an SBOM (CycloneDX/SPDX) listing every component; (3) scan for CVEs (Trivy/Grype) and fail the build on criticals; (4) sign the image and its SBOM with cosign (keyless via OIDC + Fulcio/Rekor transparency log); (5) emit SLSA provenance attesting what built it from what source; (6) at deploy, an admission controller (Kyverno/OPA/sigstore-policy) verifies the signature and provenance and rejects unsigned or untrusted-base images; (7) pin everything by digest and use minimal/distroless bases to shrink attack surface. Now a compromised artifact fails verification and never runs.

Contrast Firecracker microVMs with containers and gVisor for isolating untrusted code.

Plain containers share the host kernel — a kernel exploit escapes to the host, so they're weak for hostile multi-tenancy. gVisor interposes a userspace kernel (Sentry) that reimplements syscalls, drastically shrinking the host kernel attack surface at a syscall-performance cost. Firecracker runs each workload in a minimal KVM microVM with its own guest kernel and a tiny device model (only virtio-net/block, no BIOS), booting in ~125ms with a few MB overhead — near-container speed with real VM isolation; it powers AWS Lambda and Fargate exactly because they run arbitrary customer code. Decision: trusted first-party → containers; untrusted-but-you-want-speed → Firecracker (or Kata); need syscall-level defence without a VM → gVisor.

How do CPU requests, limits, HPA and the scheduler interact — and where's the trap?

Requests are what the scheduler reserves for bin-packing and what guarantees a floor; limits are the cgroup cpu.max ceiling enforced by CFS throttling. HPA scales replicas on utilisation = usage/request. The trap: set a tight CPU limit and a bursty service gets throttled inside each 100ms period, so p99 latency explodes — but average utilisation stays low, so HPA never scales up and you can't see it on a CPU dashboard. Correct pattern: always set requests (for scheduling + HPA baseline), be very cautious with CPU limits for latency-sensitive services (often omit them), rely on requests + node capacity for fairness, and alert on the throttled-periods ratio, not just utilisation. Memory limits, by contrast, you do set because memory is incompressible and overcommit leads to OOM kills.

What breaks when you naively containerise a stateful database, and how do you do it right?

Naive problems: writes to the overlay layer are ephemeral and slow (copy-up), so data vanishes on reschedule; the scheduler may move the pod to another node losing its local disk; noisy neighbours steal IO/CPU; and a stateless-style rolling deploy can restart the primary. Right way: use a StatefulSet (stable network identity + ordered rollout) with PersistentVolumes backed by network/replicated storage (or local-PV pinned to a node), configure pod anti-affinity across AZs, set proper readiness so traffic waits for replica sync, use an operator (e.g. for Postgres/Cassandra) that understands failover, back up out-of-band, and treat storage IOPS as a first-class resource. Often the honest answer in an interview is "use a managed DB unless there's a strong reason not to" — co-scheduling databases with stateless apps is where teams get burned.

Design an observability strategy that lets you debug a single slow request across 20 services.

Instrument every service with OpenTelemetry: a trace ID is generated at the edge and propagated via W3C traceparent headers (and through the mesh sidecars) so each hop creates a child span with timing. Traces go to Jaeger/Tempo; you open the trace and immediately see which of the 20 hops ate the latency and whether it was network, queueing, or downstream. Metrics (Prometheus, RED per service) tell you that something is slow and how widespread; logs (structured, carrying the same trace ID) give the why at the offending span. Correlate all three by trace ID: alert fires on metrics → jump to an exemplar trace → pivot to logs for that span. Add span attributes for key dimensions (route, tenant tier) but keep them bounded. The payoff: mean-time-to-locate drops from grepping 20 log streams to one click on a flame graph.

Immutable infrastructure and golden images — what problem do they kill and what do they cost?

They kill configuration drift: instead of SSHing in to patch a running box (which makes every server a unique snowflake nobody can reproduce), you bake a versioned "golden image" (AMI/OCI) in CI with everything pre-installed, and to change anything you build a new image and replace the instance — never mutate in place. Benefits: every instance from an image is byte-identical and reproducible, rollback is redeploying the previous image, and provisioning is fast because nothing is installed at boot. Costs: a full rebuild+redeploy cycle for even small changes (no hotfix in place), image build/bake time, and you must externalise all state (config, secrets, data) since the instance is disposable. The mental shift is "servers are cattle, not pets" — and it's the foundation that makes reliable canary/blue-green rollbacks possible.
