HTTP/1.1 · 2 · 3 · QUIC Mastery

The application protocol that carries almost every request you'll ever debug — and a 25-year fight against one enemy: head-of-line blocking. Each version is an answer to where the previous one still stalled.

Interview Explanation — 30 seconds

Say this: "HTTP is a request/response protocol, and its versions are a story of removing head-of-line blocking. HTTP/1.1 reuses one TCP connection with keep-alive but sends one request at a time, so browsers open ~6 connections per origin. HTTP/2 multiplexes many streams over a single TCP connection with a binary framing layer and HPACK header compression — but a single lost TCP segment still stalls every stream because TCP delivers bytes in order. HTTP/3 moves onto QUIC over UDP: streams are independent at the transport layer so loss on one stream doesn't block the others, TLS 1.3 is baked into the handshake for 1-RTT (or 0-RTT) setup, and a connection ID lets a session survive an IP change. Same semantics — methods, status codes, headers, caching — different wire transport."

Interview Explanation — 2 minutes

HTTP semantics (methods, status codes, headers, caching, conditional requests) are stable across versions; what changes is the wire format and the transport underneath.

  • HTTP/1.0: one TCP connection per request — connect, send, receive, close. TLS + TCP handshakes paid on every object. Brutal on latency.
  • HTTP/1.1: persistent connections (Connection: keep-alive), chunked transfer-encoding for streaming unknown-length bodies, mandatory Host header (enables virtual hosting), and pipelining — which failed in practice because responses must return in order, so one slow response blocks the rest (application-level HOL blocking). Browsers worked around single-request-per-connection by opening 6 parallel connections per origin.
  • HTTP/2: a binary framing layer over one TCP connection. Requests become streams (odd-numbered IDs from client), each carrying HEADERS and DATA frames interleaved and multiplexed. HPACK compresses headers with static + dynamic tables. Per-stream and per-connection flow control via WINDOW_UPDATE. Fixes application HOL blocking — but TCP-level HOL blocking remains: TCP is a single ordered byte stream, so one dropped segment stalls delivery of all streams until retransmit.
  • HTTP/3 over QUIC: QUIC is a reliable multiplexed transport on top of UDP. Each stream is independently ordered, so packet loss on stream 3 does not block stream 5 — the real fix for HOL blocking. TLS 1.3 is integrated into the QUIC handshake (1-RTT, 0-RTT resumption). Connections are identified by a connection ID, not the 4-tuple, so a session survives Wi-Fi→cellular handoff (connection migration). Header compression is QPACK (HPACK adapted so it doesn't reintroduce HOL blocking).

The unifying metric: how many round trips before first byte, and whether one lost packet stalls unrelated work. HTTP/3 minimises both.

Internal Working

HTTP/1.1 on the wire

  1. Client opens TCP (1 RTT) + TLS (1 RTT for TLS 1.3) to host:443.
  2. Sends a text request line + headers ending in \r\n\r\n: GET /a HTTP/1.1, Host: x, Connection: keep-alive.
  3. Server responds with status line + headers + body. Body length is either Content-Length: N or Transfer-Encoding: chunked (hex-size chunks terminated by a 0\r\n\r\n chunk).
  4. Connection stays open for the next request (keep-alive). Only one request may be outstanding at a time on a given connection unless pipelining is used — and pipelined responses must come back in request order, so the head response blocks the line.

HTTP/2 framing

  1. After ALPN negotiates h2, the client sends the connection preface (PRI * HTTP/2.0...) then a SETTINGS frame.
  2. Everything is a frame: 9-byte header (24-bit length, 8-bit type, 8-bit flags, 31-bit stream ID) + payload. Types: HEADERS, DATA, SETTINGS, WINDOW_UPDATE, PRIORITY, RST_STREAM, PING, GOAWAY, PUSH_PROMISE.
  3. A request = a stream (client streams are odd IDs, server-initiated even). Frames from many streams interleave on the one connection — that's multiplexing.
  4. HPACK compresses headers against a static table (61 common header entries) plus a per-connection dynamic table; repeated headers become 1-byte references. Huffman coding for literals.
  5. Flow control: each stream and the whole connection have a window (default 65,535 bytes). Receiver sends WINDOW_UPDATE to grant more. A stuck consumer that never updates its window stalls the sender.
  6. Prioritization: PRIORITY frames form a dependency tree with weights (largely replaced by the simpler HTTP/3 priority scheme). Server push (PUSH_PROMISE) is deprecated — Chrome removed it in 2022 because it wasted bandwidth pushing already-cached assets.

QUIC / HTTP/3

  1. Handshake: a single QUIC Initial packet carries the TLS 1.3 ClientHello (crypto frames). Server responds; keys derived and data flows in 1 RTT. Resumption ticket enables 0-RTT early data.
  2. Reliability lives in QUIC: monotonically increasing packet numbers (never reused, unlike TCP seq), per-stream offsets, ACK ranges, and loss detection with RTT estimation and a Reno/CUBIC-style congestion controller in user space.
  3. Each stream has its own byte offset and ordering. Loss of a packet only blocks the streams whose bytes were in it, not all streams — no cross-stream HOL blocking.
  4. Connection ID: the connection is keyed by a server-chosen ID, so if your phone's IP/port changes (NAT rebinding, Wi-Fi→LTE) the session continues — connection migration.
  5. QPACK: like HPACK but uses a separate unidirectional stream for dynamic-table updates and lets encoders avoid references that would block a header block on a not-yet-received table update.

Why was this built?

Tim Berners-Lee's HTTP/0.9 (1991) was one line: GET /page, response was raw HTML, connection closed. HTTP/1.0 (1996) added headers, status codes and content types but still one connection per request — on a page with 50 assets you paid 50 TCP (and later TLS) handshakes. People hacked around it with image sprites, domain sharding, and inlining.

  • HTTP/1.1 (1997/1999) added keep-alive to amortise handshakes, Host to host many sites per IP, chunked encoding, caching headers, and ranges. Pipelining promised concurrency but broke on buggy proxies and HOL blocking, so it was never enabled by default.
  • SPDY (Google, 2009) proved multiplexing + header compression cut page load ~2×; it became HTTP/2 (RFC 7540, 2015).
  • HTTP/2 still sat on TCP, and mobile networks with 1-2% packet loss exposed TCP HOL blocking badly. Google's QUIC (2013, deployed on Chrome↔Google) became IETF QUIC and HTTP/3 (RFC 9114, 2022).

Advantages

  • Stable semantics: methods, status codes, headers and caching carry across every version — you upgrade transport without rewriting apps.
  • HTTP/2 multiplexing: dozens of parallel requests on one connection, one TLS handshake, one congestion window to warm up.
  • HPACK/QPACK: repeated headers (cookies, user-agent) shrink from hundreds of bytes to a byte or two.
  • HTTP/3 loss resilience: on a 2% loss mobile link, page load and video rebuffering improve markedly because unrelated streams keep flowing.
  • 0-RTT: returning clients send request data in the very first packet.
  • Connection migration: no reconnection storm when a phone switches networks.
  • Caching & conditional requests: ETag/Last-Modified turn most reloads into cheap 304 Not Modified.

Drawbacks

  • HTTP/1.1: no multiplexing, verbose uncompressed headers, connection-count limits, HOL blocking.
  • HTTP/2: TCP HOL blocking under loss; a single connection means one lost packet or one aggressive stream can starve others; HPACK dynamic table is a shared mutable state that complicates proxies.
  • HTTP/3: UDP is blocked/rate-limited on ~3-5% of networks (fallback to h2 needed); CPU cost is higher because congestion control and crypto run in userspace with no NIC segmentation offload (mitigated by UDP GSO/GRO); harder to debug — no plaintext, needs SSLKEYLOGFILE + Wireshark QUIC dissector.
  • 0-RTT early data is replayable — must be restricted to idempotent requests.

When NOT to use it

Watch out:
  • Don't force HTTP/3 where UDP is blocked (corporate proxies, some datacenter security groups) without a robust h2 fallback — you'll get silent stalls and timeouts.
  • Don't use HTTP/2 single connection for large bulk transfers on a lossy link where per-connection HOL blocking dominates — parallel HTTP/1.1 or HTTP/3 may beat it.
  • Don't reach for HTTP at all for low-latency full-duplex messaging where WebSocket/gRPC-streaming fits, or for sub-millisecond internal RPC where framing overhead matters — consider raw TCP/gRPC.
  • Don't enable 0-RTT for non-idempotent endpoints (payments, order creation) — replay risk.
  • Don't rely on HTTP/2 server push — deprecated and removed from Chrome; use 103 Early Hints + preload instead.

Production Architecture

Typical topology: clients speak HTTP/3 (with h2/h1.1 fallback) to a CDN/edge; the edge terminates TLS and translates to HTTP/2 or HTTP/1.1 toward the origin's L7 load balancer, which fans out to backend services (often gRPC over HTTP/2). Protocol is negotiated per hop.

flowchart LR
  C["Browser"] -->|"HTTP/3 QUIC UDP 443"| EDGE["CDN edge"]
  C -.->|"fallback h2 h1.1 TCP"| EDGE
  EDGE -->|"HTTP/2 TCP"| LB["L7 load balancer"]
  LB -->|"HTTP/1.1 keep-alive"| S1["Service A"]
  LB -->|"gRPC over HTTP/2"| S2["Service B"]
  EDGE --> CACHE["Edge cache ETag"]
  • ALPN during TLS chooses h2 vs http/1.1; HTTP/3 is advertised by the origin/CDN via the Alt-Svc: h3=":443" header so the browser retries over QUIC next time.
  • The edge maintains a warm pool of long-lived HTTP/2 connections to origin, amortising handshakes across millions of client requests.
  • Caching happens at the edge keyed by URL + Vary headers; conditional revalidation with If-None-Match keeps origin load low.

Production Problems

  • HTTP/2 connection coalescing gone wrong: browsers reuse one h2 connection for multiple hostnames sharing a cert + IP; a misrouted request lands on the wrong backend → 421 Misdirected Request.
  • Head-of-line under loss: h2 latency spikes on mobile even though throughput is fine — one connection, TCP retransmit stalls everything.
  • UDP throttling: some networks rate-limit UDP, so HTTP/3 is slower than h2; needs happy-eyeballs-style racing and fallback.
  • HPACK bomb / header table pressure: huge dynamic tables or many unique headers blow memory on proxies; enforce SETTINGS_HEADER_TABLE_SIZE and max header list size.
  • keep-alive vs LB idle timeout mismatch: client reuses a connection the LB already closed → sporadic 502/connection resets. Set client idle < server idle.
  • Rapid Reset (CVE-2023-44487): attacker opens+RST_STREAMs floods of h2 streams cheaply → DoS. Mitigate by capping stream churn per connection.

Scaling

HTTP scales horizontally behind L7 LBs and CDNs; the protocol choices interact with how connections spread load.

flowchart TD
  U["Millions of clients"] --> ANY["Anycast edge PoPs"]
  ANY --> T["TLS QUIC termination"]
  T --> POOL["Warm origin connection pool"]
  POOL --> A1["Backend replica 1"]
  POOL --> A2["Backend replica 2"]
  POOL --> A3["Backend replica N"]
  • Connection concentration: HTTP/2's single connection is great for clients but means an LB sees fewer, longer connections — balance on requests not connections (L7), or you get hot backends.
  • Origin pooling: edges keep persistent h2 pools to origin; tune SETTINGS_MAX_CONCURRENT_STREAMS (commonly 100-250) to bound per-connection concurrency.
  • QUIC CPU: scale UDP receive with SO_REUSEPORT sharding across cores + UDP GSO/GRO to batch packets; QUIC has no kernel TSO so this matters.
  • Anycast + connection migration: QUIC connection IDs let you steer a migrated connection back to the right server via routable CIDs.

Security

  • TLS everywhere: h2 and h3 are effectively HTTPS-only in browsers; h3 mandates TLS 1.3. Use HSTS (Strict-Transport-Security) to prevent downgrade.
  • Cookies: set Secure (HTTPS only), HttpOnly (no JS access — blocks XSS token theft), and SameSite=Lax/Strict (CSRF defense). SameSite=None requires Secure.
  • CORS: cross-origin requests trigger a preflight OPTIONS with Access-Control-Request-Method/Headers; the server must return matching Access-Control-Allow-*. Never reflect arbitrary Origin with credentials.
  • 0-RTT replay: early data can be replayed; restrict to safe/idempotent methods (GET/HEAD) and add anti-replay windows.
  • DoS: HTTP/2 Rapid Reset (CVE-2023-44487), HPACK memory bombs, Slowloris (slow headers) — cap concurrent streams, header sizes, and enforce request timeouts.
  • Request smuggling: conflicting Content-Length vs Transfer-Encoding between front/back proxies (CL.TE / TE.CL) lets attackers desync. Normalise/ reject ambiguous framing; h2/h3 binary framing removes this class.

Performance

  • Round trips: TCP+TLS1.3 = 2 RTT to first byte; QUIC = 1 RTT; QUIC 0-RTT ≈ 0 RTT. On a 100 ms RTT link that's 200 ms vs 100 ms vs ~0 saved before data.
  • Header size: HPACK/QPACK cut a ~800-byte cookie-laden header set to tens of bytes after the dynamic table warms.
  • Flow control default 65,535 bytes per stream stalls high-BDP transfers — raise SETTINGS_INITIAL_WINDOW_SIZE and connection window (e.g. to 16 MB) for CDN/large downloads.
  • Concurrency: h1.1 = 6 connections/origin; h2/h3 = up to MAX_CONCURRENT_STREAMS (default ~100) on one connection.
  • Loss sensitivity: at 2% packet loss h2 throughput can collapse due to TCP HOL blocking + cwnd cuts; h3 keeps unrelated streams moving.
  • CPU: QUIC ~2× the CPU/byte of TCP without offload; mitigate with GSO/GRO, hardware crypto (AES-NI), and pacing. Enable Brotli (br) for text (~15-20% smaller than gzip) via Accept-Encoding.

Common Mistakes

  • Domain sharding under HTTP/2 — splitting assets across hostnames defeats multiplexing and adds handshakes. Fix: single origin, let h2 multiplex.
  • Leaving flow-control windows at 65 KB for bulk transfer. Fix: raise initial window sizes.
  • Client idle timeout ≥ server idle → reuse of a half-closed socket → intermittent 502. Fix: client idle a few seconds below LB idle.
  • Using Cache-Control: no-cache thinking it means "don't store" — it means "revalidate before use". For secrets use no-store.
  • Forgetting Vary on content that changes by Accept-Encoding/Accept-Language → caches serve the wrong variant.
  • Non-idempotent GET or idempotent-but-side-effecting endpoints — breaks retries and caching assumptions.
  • Assuming server push helps — it's deprecated. Fix: 103 Early Hints + <link rel=preload>.
  • No h2/h1.1 fallback for h3 — UDP-blocked users hang. Fix: advertise via Alt-Svc and race.

  2. Why did HTTP/1.1 pipelining fail?
    1. Responses must return in request order → one slow response blocks all (application HOL blocking) + buggy proxies.
  3. Why 6 connections per origin in browsers?
    1. Only one in-flight request per h1.1 connection; 6 gives pseudo-concurrency within fairness limits.
  4. How does HTTP/2 multiplexing work internally?
    1. Binary frames tagged with stream IDs interleave on one TCP connection; HEADERS+DATA per stream.
  5. What is TCP head-of-line blocking and why does h2 still have it?
    1. TCP is one ordered byte stream; a lost segment stalls delivery of all multiplexed streams until retransmit.
  6. How does QUIC eliminate it?
    1. Independent per-stream offsets/ordering over UDP; loss affects only the streams whose bytes were lost.
  7. How does HPACK compression work?
    1. Static table (61 entries) + per-connection dynamic table + Huffman literals; repeats become index references.
  8. Why is QPACK different from HPACK?
    1. HPACK's ordered table updates would reintroduce HOL blocking on independent QUIC streams; QPACK uses a separate encoder stream + blocked-references control.
  9. How does h2/h3 flow control work?
    1. Per-stream + per-connection windows; receiver grants credit via WINDOW_UPDATE; default 65,535 bytes.
  10. Explain the QUIC handshake RTTs.

  17. What is HTTP/2 Rapid Reset?

🎯 Deep-dive Q&A — model answers

Walk me through exactly what happens on the wire from typing a URL to first byte over HTTP/3.

DNS resolves the name (possibly HTTPS/SVCB record hinting h3). The client sends a QUIC Initial UDP packet to :443 carrying CRYPTO frames with the TLS 1.3 ClientHello (key share, SNI, ALPN=h3). The server replies with its ServerHello, cert and Finished inside QUIC packets; both derive keys via ECDHE. After one RTT the handshake completes and the client opens an HTTP/3 request stream (a QUIC bidirectional stream), sends a QPACK-encoded HEADERS frame, and the server responds with HEADERS + DATA. If the client had a resumption ticket it could have sent the request as 0-RTT early data in that first flight. Meanwhile packet numbers, ACK ranges and a userspace congestion controller manage loss and pacing.

Why can't HTTP/2 just fix HOL blocking by itself?

Because the blocking lives one layer below HTTP/2, in TCP. TCP presents a single in-order byte stream to the application; if segment N is lost, the kernel buffers N+1, N+2… and refuses to deliver them to the h2 layer until N is retransmitted and arrives. So even though h2 logically has independent streams, they're all serialised through one TCP receive buffer. No amount of h2 framing can reorder around a missing TCP segment. The only fix is a transport that keeps per-stream ordering — QUIC.

Explain HPACK and the specific way it can be dangerous.

HPACK compresses headers using a static table of 61 common entries and a per-connection dynamic table that both peers mutate as headers repeat, plus Huffman-encoded literals. Repeated headers collapse to a 1-2 byte index. Danger: the dynamic table is shared mutable state — a malicious peer can force large tables (memory pressure) or, historically, CRIME/BREACH-style attacks used compression to leak secrets, which is why HPACK never compresses across the security boundary the way naive gzip did. You bound it with SETTINGS_HEADER_TABLE_SIZE and a max header list size. QPACK exists because HPACK's requirement that both sides process table updates in order would reintroduce HOL blocking across QUIC's independent streams.

How does QPACK avoid reintroducing HOL blocking?

QPACK splits dynamic-table maintenance onto dedicated unidirectional QUIC streams (encoder and decoder streams) separate from the request streams. A header block on a request stream may reference dynamic-table entries, but the encoder can choose to only reference entries it knows the decoder already has, or mark a block as "blocked" with a required insert count. The decoder tracks how many insertions it's seen; a block that references not-yet-received entries waits only for that specific table update, not for unrelated streams. The SETTINGS_QPACK_BLOCKED_STREAMS knob bounds how many streams may be blocked at once, letting you trade compression ratio against blocking risk.

0-RTT sounds free — what's the catch and how do you use it safely?

0-RTT lets a returning client send request data in the first packet using keys derived from a prior session's PSK. The catch is replay: because there's no round trip to prove freshness, an on-path attacker can capture and resend that early data, and the server can't distinguish it from a legitimate retransmit. So 0-RTT must be limited to idempotent, side-effect-free requests (GET/HEAD). Servers implement anti-replay via single-use tickets or a bounded replay window, and reject or defer non-idempotent requests to 1-RTT. For payments/order creation you additionally require server-side idempotency keys regardless of 0-RTT.

A single h2 connection concentrates load — how do you keep backends balanced?

Because one client uses one long-lived h2 connection, an L4 load balancer that hashes on connection would pin all that client's requests to one backend, creating hot spots and making draining hard. You balance at L7, distributing per request (per stream) across backends, or you split the client-facing connection from origin connections at the edge and pool many short requests over a warm origin fleet. You also use GOAWAY for graceful connection draining during deploys, and cap MAX_CONCURRENT_STREAMS so no single connection monopolises a backend.

Contrast Cache-Control no-cache, no-store, must-revalidate, and private.

no-store: never write to any cache — for secrets. no-cache: you may store it, but must revalidate with the origin (conditional request) before serving. must-revalidate: once stale, you must revalidate rather than serve stale on error. private: only the browser may cache, not shared/CDN caches (for per-user content); public: shared caches may store even normally-uncacheable responses. max-age=N sets freshness lifetime. A common correct combo for versioned static assets is public, max-age=31536000, immutable; for HTML often no-cache so it always revalidates.

How do conditional requests turn a reload into a 304?

On first response the server sends a validator: ETag: "v1" (a content hash/version) and/or Last-Modified. The cache stores it. On revalidation the client sends If-None-Match: "v1" (or If-Modified-Since). If unchanged the server returns 304 Not Modified with no body — the client reuses its cached copy. This saves the body bytes but still costs a round trip; strong caching with max-age avoids even that. ETags also power optimistic concurrency on writes via If-Match (return 412 Precondition Failed on conflict).

Explain the CORS preflight sequence precisely.

For a "non-simple" cross-origin request (custom headers, methods beyond GET/POST/HEAD, or JSON content-type), the browser first sends an OPTIONS preflight with Origin, Access-Control-Request-Method and Access-Control-Request-Headers. The server must respond with matching Access-Control-Allow-Origin (a specific origin, or * but not * with credentials), Access-Control-Allow-Methods/Headers, and optionally Access-Control-Max-Age to cache the preflight. Only then does the browser send the real request. With credentials: include you must echo the exact origin and set Access-Control-Allow-Credentials: true. CORS is browser-enforced; it doesn't protect servers, so don't rely on it for authorization.

What exactly is HTTP request smuggling and how do the versions differ?

In HTTP/1.1 a message body length is defined by either Content-Length or Transfer-Encoding: chunked. If a front-end proxy and back-end server disagree on which to honour (CL.TE, TE.CL, TE.TE), an attacker crafts a request whose boundary each parses differently, "smuggling" a partial request that prepends to the next victim's request — enabling cache poisoning, auth bypass, credential theft. Fixes: reject messages with both headers, normalise before forwarding, use the same parser front/back. HTTP/2 and /3 use explicit binary length framing with no ambiguous dual-length signalling, so this whole class largely disappears — though downgrade points (h2→h1.1 at a proxy) can re-expose it.

Why is QUIC more CPU-hungry and how do you mitigate it?

TCP benefits from decades of kernel optimisation and NIC offload (TSO/GSO/GRO, checksum offload) plus segmentation in hardware. QUIC runs congestion control, loss detection, and per-packet crypto (AEAD) in userspace over UDP, and historically sent one packet per syscall — so it can cost ~2× CPU per byte. Mitigations: UDP Generic Segmentation/Receive Offload (GSO/GRO) to batch many QUIC packets per syscall, SO_REUSEPORT to shard UDP flows across cores, AES-NI hardware crypto, sendmmsg/recvmmsg batching, and pacing to smooth bursts. Kernel and NIC QUIC/UDP-segmentation offload is closing the gap.

When would you deliberately keep HTTP/1.1 in 2026?

Internal service-to-service calls on a reliable low-latency LAN where multiplexing buys little and h1.1's simplicity/debuggability wins; environments where UDP and even h2 are blocked; bulk parallel downloads where several independent TCP connections each get their own congestion window and HOL blocking is contained per-file; tooling and quick curl/log debugging where plaintext framing is a feature. For a browser-facing site at scale, though, you want h2/h3.

How does connection migration actually work and why doesn't it break security?

QUIC identifies a connection by a server-chosen Connection ID carried in each packet, not by the UDP 4-tuple. When a client's address changes (NAT rebind, Wi-Fi→cellular), packets arrive from a new IP/port but the same Connection ID, so the server maps them to the existing connection and its keys — no new handshake. To prevent an attacker spoofing a migration to redirect traffic, QUIC requires path validation: the server sends a PATH_CHALLENGE random token to the new address and only fully migrates after a matching PATH_RESPONSE, proving the peer actually owns the new path. Connection IDs are also rotated to avoid linkability/tracking across paths.

Your h2 service is being DoS'd by Rapid Reset — what's happening and what do you do?

CVE-2023-44487: an attacker opens a stream (HEADERS) and immediately sends RST_STREAM, cancelling it before the server finishes. Because canceled streams don't count against MAX_CONCURRENT_STREAMS, the attacker can churn effectively unlimited request work per connection at almost no client cost, exhausting server CPU/memory. Mitigation: track and rate-limit RST_STREAM / stream-creation churn per connection, cap total streams (including reset ones) per connection over time, and close/GOAWAY connections that exceed a reset ratio. Patched server libraries (nghttp2, Go net/http, Envoy) added exactly these counters.

Explain HTTP/2 flow control and a realistic way it stalls throughput.

There are two windows: per-stream and per-connection, both default 65,535 bytes. The sender may have at most that many unacknowledged DATA bytes in flight; the receiver replenishes credit via WINDOW_UPDATE as it consumes data. On a high bandwidth-delay-product link (say 100 Mbps, 100 ms RTT → ~1.25 MB BDP) a 64 KB window caps throughput far below the pipe because the sender keeps waiting for updates. Fix: raise SETTINGS_INITIAL_WINDOW_SIZE and the connection window (e.g. to a few MB), and ensure the app drains fast so WINDOW_UPDATEs flow. A slow/blocked reader that never updates its window will stall the sender entirely.

What's the difference between idempotent and safe, and why does it matter for retries and caches?

Safe = no server state change (GET, HEAD, OPTIONS) — cacheable and prefetchable. Idempotent = repeating the request has the same effect as doing it once (GET, HEAD, PUT, DELETE, OPTIONS). POST and PATCH are neither safe nor guaranteed idempotent. This matters because middleboxes, browsers and client libraries will automatically retry idempotent requests on connection failure — safe to do for PUT/DELETE, dangerous for POST (double-charge). It also governs caching: only safe methods are cached. To make a POST safely retryable you add an idempotency key so the server dedupes replays.
