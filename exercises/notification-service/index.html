Notification Service — Requirements Exercise

Design brief: Design a centralized notification service that lets other systems send messages to users across multiple channels such as push, SMS, email, and in-app.

Functional Requirements

  • Client systems can submit a notification request specifying recipient(s), channel(s), and content via an API.
  • The system must support multiple delivery channels: mobile push, SMS, email, and in-app notifications.
  • The system must support templated messages with per-recipient personalization variables.
  • Users can manage per-channel and per-category preferences and opt out / unsubscribe.
  • The system must respect user preferences, quiet hours, and do-not-disturb settings before sending.
  • The system must support both immediate and scheduled/deferred delivery.
  • The system must deduplicate and rate-limit notifications so a user is not spammed for the same event.
  • The system must track and expose delivery status (queued, sent, delivered, failed, opened) per notification.
  • The system must retry failed sends and support fallback to an alternate channel when configured.
  • The system must support fan-out to large audiences (e.g., broadcast to millions) as well as targeted single-user sends.
  • The system must maintain an audit trail of what was sent to whom and when.

Non-Functional Requirements

  • Support sending on the order of billions of notifications per day with peaks of hundreds of thousands per second.
  • Accept-and-enqueue latency for a send request should be under ~100 ms at p99.
  • Availability target of 99.99% for the ingestion API; no accepted request should be dropped.
  • Delivery must be at-least-once with deduplication so a user is not shown duplicates.
  • The system must degrade gracefully and absorb bursts via buffering when downstream providers throttle.
  • User preferences and opt-out compliance must be enforced reliably (regulatory: CAN-SPAM, GDPR, TCPA).
  • Message content and recipient contact data must be encrypted in transit and at rest.
  • The system must be horizontally scalable and isolate channels so one slow provider does not block others.
  • Time-sensitive notifications (e.g., OTP) should be prioritized and delivered within seconds.
  • Cost per message should be optimized, including choosing efficient providers per region/channel.

Assumptions & Out of Scope

  • Actual last-mile delivery relies on third-party providers (APNs, FCM, SMS gateways, SMTP) treated as external dependencies.
  • Composing business logic that decides when to notify lives in calling services, not this service.
  • User identity, contact-detail collection, and device-token registration source of truth are assumed provided.
  • Rich analytics dashboards and campaign management UI are out of scope.
