Dropbox — Requirements Exercise

Design brief: Design a file hosting and synchronization service that keeps a designated set of folders identical across a user's devices and the cloud.

Functional Requirements

  • Users can place files in a synced folder and have them uploaded to the cloud automatically.
  • The system must detect local file changes (add, modify, rename, delete) and propagate them to the cloud and other devices.
  • The system must download remote changes to each linked device so all devices converge to the same state.
  • Users can link and unlink multiple devices to a single account.
  • Users can share a folder with collaborators who then sync the same folder, with view or edit permissions.
  • Users can create public/private share links to individual files.
  • The system must keep file version history and allow restoring or reverting to earlier versions.
  • Users can recover deleted files within a retention window.
  • The system must support selective sync so a device syncs only chosen folders to save local space.
  • The system must upload and download large files reliably, resuming after interruptions.
  • The system must show sync status per file (syncing, synced, error/conflict) to the user.

Non-Functional Requirements

  • Support hundreds of millions of registered users and tens of millions of concurrently connected devices.
  • Handle files up to several GB each, with aggregate storage at hundreds of petabytes growing continuously.
  • A saved change on one device should begin appearing on other online devices within a few seconds.
  • Only changed portions of a file should traverse the network to minimize bandwidth and speed up sync.
  • Durability target of eleven nines with no acknowledged upload ever lost.
  • Availability target of 99.9%+ for the sync and storage backend.
  • Data must be encrypted in transit and at rest, and share permissions strictly enforced.
  • Metadata sync (which files changed) should be lightweight and scale to accounts with millions of files.
  • Concurrent conflicting edits must be preserved (e.g., conflicted copies) rather than silently overwritten.
  • Storage cost should be reduced by avoiding storing identical content redundantly.

Assumptions & Out of Scope

  • In-app document editing and previewing beyond basic status is out of scope.
  • Assume account signup, authentication, and payment/subscription handling already exist.
  • Team administration, compliance holds, and advanced admin controls are excluded.
  • Assume clients run a background daemon capable of watching the filesystem for changes.
