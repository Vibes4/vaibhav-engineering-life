Node.js & TypeScript EY Sheet 06

The JD's only named backend language is Node.js / TypeScript. For a 4–8 year band the questions are predictable — event loop, async, error handling, memory, TypeScript typing discipline — but the bar is that you explain mechanism, not definitions. "Node is single-threaded and non-blocking" is a fresher answer. "Node runs your JavaScript on one thread and offloads I/O to the kernel or to libuv's thread pool, and here's what that means for a CPU-bound endpoint" is a senior answer.

The line that wins this section: "Node gives me one thread for my code and excellent concurrency for I/O. That means the failure modes I design against are: blocking the event loop with CPU work, unbounded memory from unconsumed streams or growing caches, and unhandled promise rejections killing the process. Those three account for nearly every production Node incident I've dealt with."

The runtime

CertainExplain the event loop — properly.

V8 executes your JavaScript on a single thread. Anything asynchronous is handed to libuv, which either uses a kernel async mechanism (epoll/kqueue/IOCP for sockets) or, for things with no async kernel API, its thread pool — default 4 threads, sized by UV_THREADPOOL_SIZE — which handles file system operations, DNS lookups via getaddrinfo, and crypto functions like pbkdf2 and randomBytes. That distinction matters: network I/O scales to thousands of concurrent operations, but file and crypto work contends for 4 threads by default.

Each loop iteration passes through phases in order: timers (expired setTimeout/setInterval), pending callbacks, idle/prepare (internal), poll (retrieve new I/O events and run their callbacks — this is where the loop blocks waiting for work), check (setImmediate), and close callbacks (e.g. socket.on('close')).

Between every phase transition — and after each individual callback — Node drains two microtask queues: process.nextTick first, then the promise microtask queue. That's why nextTick can starve the loop: a recursive nextTick never lets the loop advance a phase, whereas a recursive setImmediate yields between iterations.

The practical payoff: a synchronous 200 ms computation in a request handler doesn't slow that one request — it stalls every concurrent request on that process for 200 ms, because nothing else can run. That's the answer to "why is my p99 terrible under load".

Depth probeOrder these: setTimeout(0), setImmediate, process.nextTick, Promise.resolve().then.

Inside an I/O callback the order is deterministic: process.nextTick → Promise.then (microtasks, nextTick queue drains fully first) → setImmediate (check phase, which comes right after poll) → setTimeout(0) (timers phase of the next iteration).

At the top level of a module, setTimeout(0) versus setImmediate is non-deterministic — it depends on how long the process took to start relative to the timer's 1 ms minimum resolution. Run it twice and you can get different orders. Interviewers love this because most candidates confidently give the wrong deterministic answer. The correct answer is "it's non-deterministic at the top level, deterministic inside an I/O cycle — and if my code depends on that ordering, the code is wrong."

CertainHow do you handle a CPU-bound task in Node?

Options in the order I'd consider them:

  1. Don't do it in the request path. Push the job onto a queue (SQS) and process it in a worker. This is nearly always the right answer for report generation, image processing, PDF rendering, large exports.
  2. Worker threads — real OS threads sharing memory via SharedArrayBuffer/transferable objects, with a MessagePort for communication. Right for CPU work that must stay in-process and in the same request lifecycle. Use a pool (e.g. piscina); spawning a thread per task costs more than the work for small tasks.
  3. Chunk and yield — break the loop into batches with setImmediate between them so the event loop can service other requests. Crude, but it keeps a service responsive without new infrastructure.
  4. Child processes / a different runtime — if it's genuinely heavy numeric work, a native addon or a separate service is more honest than fighting the runtime.
  5. Cluster — cluster or a process manager forks one process per core, each with its own event loop, behind a shared listening socket. This raises total throughput but does not fix a single slow request; a 5-second computation still blocks everything on its own worker. Worth saying explicitly, because candidates often offer cluster as a fix for blocking, and it isn't.
Streams and backpressure — why do they matter?

Streams process data in chunks instead of buffering it all in memory. The reason they matter operationally: reading a 2 GB file with fs.readFile tries to allocate 2 GB in the heap and either OOMs the process or triggers a long GC pause; streaming it processes it in 64 KB chunks at constant memory.

Backpressure is the flow-control mechanism. writable.write() returns false when its internal buffer exceeds highWaterMark; a correct producer stops writing and waits for the 'drain' event. If you ignore that return value — the classic manual readable.on('data', d => writable.write(d)) — a fast source and a slow sink cause unbounded memory growth until the process dies. This is one of the most common real-world Node memory incidents.

The fix is to not hand-roll it: use pipeline() from node:stream/promises, which wires backpressure correctly and propagates errors and destroys every stream in the chain on failure — which plain .pipe() famously does not, leaking file descriptors on error.

CertainHow do you handle errors correctly in a Node service?

I separate two categories, because they need opposite treatment. Operational errors are expected runtime conditions — a downstream timeout, invalid user input, a 429 from an API, a full disk. These are handled: retry with backoff, return a 4xx/5xx, degrade gracefully. Programmer errors are bugs — reading a property of undefined, a failed invariant. You do not handle these; you let the process crash and restart, because after a bug fires the process state is unknown and continuing risks corrupting data.

Mechanically:

  • async/await with try/catch, and a centralised error-handling middleware in Express that maps typed errors to status codes — one place that decides what the client sees and what gets logged.
  • Wrap async route handlers so a rejected promise reaches the error middleware (Express 4 doesn't do this for you; Express 5 does).
  • process.on('unhandledRejection') and 'uncaughtException': log with full context, then exit — don't swallow and continue. Let the orchestrator (ECS, Kubernetes, PM2) restart a clean process.
  • Custom error classes carrying a status code, an error code and an isOperational flag, so the middleware has something to branch on other than string matching.
  • Never lose the stack: throw new WrappedError(msg, { cause: err }) rather than throw new Error(err.message).
  • Every error log carries the correlation ID, so an error in one service can be joined to the request that caused it across the whole call chain.
Depth probeA Node service is leaking memory in production. Walk me through it.

Confirm it's a leak, not just a large heap: plot RSS and heap-used over time. A leak trends upward across GC cycles and doesn't recover after traffic drops. A sawtooth that returns to baseline is normal.

Capture evidence: take heap snapshots at two points under load (v8.writeHeapSnapshot(), or the inspector) and diff them in Chrome DevTools, sorting by retained size. The diff tells you which constructor is accumulating and the retainer path tells you what's holding it.

The usual culprits, in the order I'd check them:

  • An unbounded cache or Map keyed by something high-cardinality (user ID, request ID) with no eviction. The most common cause by a distance. Fix: an LRU with a size cap and a TTL.
  • Event listeners added per request to a long-lived emitter and never removed — the "possible EventEmitter memory leak detected" warning is literally Node telling you this.
  • Closures captured in module-scope arrays — a pending-requests array that's appended to but never drained.
  • Missing backpressure on a stream, buffering an entire response in memory.
  • Timers (setInterval) that keep a large object reachable forever.

Then prevent: a memory alarm at, say, 80% of the container limit so you find out before the OOM kill; a container memory limit with --max-old-space-size set below it so V8 GCs hard rather than getting SIGKILLed with no diagnostics; and load tests long enough to expose a slow leak, because a 30-second test never will.

TypeScript

CertainWhat does TypeScript actually buy you on a backend service?

Concretely: refactoring safety (rename a field and the compiler finds every caller, which on a 40-service estate is the difference between a 20-minute change and a week of grep), executable documentation at API boundaries, and a whole class of runtime errors — undefined property access, wrong argument order, unhandled union case — moved to compile time.

The limitation I'd state unprompted, because it's the senior point: types are erased at runtime and guarantee nothing about data crossing a boundary. An HTTP body typed as CreateOrderDto is an assertion, not a check. So at every boundary — HTTP requests, queue messages, third-party responses, environment variables — I validate with a runtime schema validator (zod, io-ts, class-validator) and derive the static type from the schema, so there's a single source of truth that's enforced both at compile time and at runtime.

What TypeScript settings and practices do you insist on?

strict: true, non-negotiable — and specifically strictNullChecks, which is where most of the value lives. Beyond that: noUncheckedIndexedAccess (so arr[i] is T | undefined, which is the truth), noImplicitOverride, and exactOptionalPropertyTypes on new codebases.

Practices: ban any via lint — use unknown and narrow, which forces you to actually handle the shape. Prefer discriminated unions over optional-field soup, so the compiler can exhaustively check a switch (with a never default case that fails to compile when a variant is added). Use branded types for IDs (type UserId = string & { __brand: 'UserId' }) so you can't pass an order ID where a user ID belongs. And avoid the trap of typing everything as an interface that mirrors the database row — model the domain, then map at the edges.

Explain unknown vs any vs never.

any disables the type checker for that value and everything it touches — it's contagious and each one is a hole in the type system. unknown is the type-safe top type: you can assign anything to it, but you can't do anything with it until you narrow via a type guard. It's what JSON.parse and a caught error should be typed as. never is the bottom type — no value inhabits it. It's the return type of a function that always throws, and its practical use is exhaustiveness checking: in the default branch of a switch over a union, assign the discriminant to never, and adding a new union member becomes a compile error at every switch that forgot it.

Practical backend

How do you make an outbound HTTP call resilient?

Five things, and I'd list them as a checklist because that's how I actually apply them: (1) A timeout — always, on every call. The default in most clients is no timeout, and a hung downstream that never responds is what turns one slow dependency into a full outage as your connection pool fills. (2) Retries with exponential backoff and jitter — jitter matters because synchronised retries from 200 instances create a thundering herd that keeps the downstream down. (3) Retry only idempotent operations, or send an idempotency key so the server can dedupe. (4) A circuit breaker — after N consecutive failures, fail fast for a cooling-off period instead of queueing doomed requests; this protects you from a dependency's latency and gives it room to recover. (5) A bulkhead — cap concurrent calls per dependency so one slow downstream can't consume your whole connection pool or event-loop capacity.

Plus connection reuse: an HTTP agent with keepAlive: true so you're not paying TCP and TLS handshake cost on every call, which is often a bigger latency win than anything else on this list.

What does your testing pyramid look like for a Node service?

Unit tests on domain logic with no I/O — fast, numerous, run on every save. Integration tests on the layer that talks to real infrastructure: I'd use Testcontainers to run a real PostgreSQL or LocalStack in Docker rather than mocking the database driver, because mocked repository tests pass while the actual SQL is wrong. Contract tests between services so a provider can't break a consumer silently — this matters far more in microservices than more unit tests do. A thin layer of end-to-end tests on the critical business paths only, because they're slow and flaky in proportion to their number.

What I'd add beyond the pyramid, since the JD asks about "defect prevention": coverage as a signal rather than a target (90% coverage of getters proves nothing); mutation testing on the genuinely critical modules if the team will tolerate it; and a load test in the pipeline for services with a latency SLO, because performance regressions are invisible to functional tests.

Node 22/24-era features you'd actually use.

The built-in test runner (node --test) and node:assert, which removes a dependency for simple services. The stable fetch and AbortController for timeouts on outbound calls. node:stream/promises pipeline(). AsyncLocalStorage — genuinely important, because it's how you propagate a correlation ID through an async call chain without threading a context parameter through every function signature; it's the foundation of request-scoped logging. The permission model (--permission) for locking down what a process can read, write or spawn. Native .env loading via --env-file. And ESM as the default for new code, with the awareness that top-level await and the lack of require change how you structure startup.
