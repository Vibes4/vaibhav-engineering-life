Forms & Events React

React does not attach a listener to every element you write onClick on. It attaches a small set of listeners to the root container you passed to createRoot and uses delegation, then hands your handler a SyntheticEvent — a normalized, cross-browser wrapper around the native event.

Forms are where that event system meets state. The whole design question is one line: who owns the value — React or the DOM? Controlled inputs make React the source of truth (predictable, but every keystroke is a render). Uncontrolled inputs leave the value in the DOM and read it with a ref (fast, but you cannot derive UI from it).

The synthetic event system

  • Normalization. SyntheticEvent smooths over browser differences and gives a consistent API: type, target, currentTarget, preventDefault(), stopPropagation(). The real event is always available as e.nativeEvent.
  • Delegation to the root container. Since React 17, listeners are attached to the container passed to createRoot(container) — not to document, as React 16 did. This is what makes multiple React versions, and React embedded inside a non-React page, coexist safely.
  • Event pooling is gone. React 16 reused event objects and required e.persist() to read an event asynchronously. That was removed in React 17. Reading e.target.value inside a setTimeout or a promise is fine today, and repeating the e.persist() advice as current is a dated-knowledge tell in an interview.
Gotcha: attaching a native listener with document.addEventListener and calling stopPropagation() there will kill React handlers, because React's listener sits on the root container — below document in the bubble path. Conversely, e.stopPropagation() in a React handler cannot stop a listener already on document, since React's delegated listener has not finished bubbling yet.

Handlers: naming, arguments, phases

// camelCase, and you pass the FUNCTION, not a call
<button onClick={handleClick}>         // ✅
<button onClick={handleClick()}>       // ❌ runs during render

// passing arguments: wrap in an arrow, or bind the data to the element
<button onClick={() => remove(item.id)}>
<button data-id={item.id} onClick={(e) => remove(e.currentTarget.dataset.id)}>
  • e.preventDefault() stops the browser's default action (form submit navigating, link following, checkbox toggling). Returning false from a React handler does nothing — that is a jQuery habit.
  • e.stopPropagation() stops the event travelling further along the React tree. Use it for a click inside a dropdown that must not reach the "click outside to close" handler.
  • Every handler has a capture twin: onClickCapture, onFocusCapture. Capture runs top-down before the target, bubble runs bottom-up after. Capture is the right phase for an analytics or "close everything" handler that must run before a child can cancel it.
  • Ordering with native listeners: a native listener attached to an inner element runs before React's, because React's listener is on the root container and only fires once the event bubbles up to it. onFocus/onBlur in React actually use native focusin/focusout, so unlike the raw DOM events, they bubble.

Controlled inputs

A controlled input has both value and onChange. React state is the single source of truth; the DOM only ever displays what state says.

const [email, setEmail] = useState('');

<input
  value={email}
  onChange={(e) => setEmail(e.target.value)}
/>

You get this for free: live validation, formatting/masking as the user types, disabling submit until valid, mirroring the value elsewhere, and resetting the form by setting state. Note that React's onChange is really the native input event — it fires on every keystroke, not on blur like the DOM's change.

The read-only bug: passing value without onChange makes the input impossible to type in — React re-renders it back to the state value on every keystroke — and logs "You provided a value prop to a form field without an onChange handler." If you genuinely want display-only, use readOnly; if you want an initial value the user can edit, you wanted defaultValue. Also never do value={user.name ?? undefined} — an input flipping between controlled and uncontrolled warns and loses state; use value={user.name ?? ''}.

Uncontrolled inputs, and when they are right

const emailRef = useRef(null);

function onSubmit(e) {
  e.preventDefault();
  send(emailRef.current.value);        // read from the DOM, once
}

<input ref={emailRef} defaultValue="a@b.com" name="email" />
  • File inputs must be uncontrolled. <input type="file"> is read-only for security — you cannot set its value from JS.
  • Integrating a non-React widget (a legacy date picker, a rich-text editor) that owns its own DOM.
  • Very large forms where a keystroke re-rendering 80 fields is measurable.
  • Simple "read on submit" forms — you can even skip refs entirely and use new FormData(e.currentTarget), which is why name attributes still matter.

Performance, and why react-hook-form exists

A controlled form re-renders the component that owns the state on every keystroke. With a handful of inputs that is invisible. With dozens of fields, or heavy children, or an expensive validation running in render, typing gets laggy.

Fixes, cheapest first:

  1. Push state down. Put the state in the smallest component that owns the field, so a keystroke re-renders one field, not the page.
  2. Memoize siblings. React.memo on expensive children plus stable handler identities via useCallback.
  3. Debounce the expensive consequence (the search request, the validation), never the input's own value — debouncing the displayed value makes typing feel broken.
  4. Go uncontrolled with subscriptions — which is exactly react-hook-form: it registers inputs uncontrolled via refs and lets components subscribe to just the slices they render (this field's error, isDirty). Formik, by contrast, is controlled-by-default and re-renders the form on every keystroke, which is the main reason RHF displaced it.
Senior tip: "Controlled vs uncontrolled" is not a purity contest. Controlled is the default because it is predictable; you switch to uncontrolled when a profiler shows typing cost, or when the DOM genuinely owns the value.

Validation and submit as a state machine

Three booleans (isSubmitting, isError, isSuccess) permit impossible combinations. One status field cannot lie:

const initial = { values: { email: '' }, errors: {}, touched: {}, status: 'editing' };
// status: 'editing' | 'validating' | 'submitting' | 'error' | 'success'

function reducer(state, action) {
  switch (action.type) {
    case 'change':  return { ...state, values: { ...state.values, [action.name]: action.value },
                             errors: { ...state.errors, [action.name]: undefined }, status: 'editing' };
    case 'blur':    return { ...state, touched: { ...state.touched, [action.name]: true },
                             errors: { ...state.errors, ...validateField(state.values, action.name) } };
    case 'submit':  return { ...state, status: 'submitting' };
    case 'invalid': return { ...state, errors: action.errors, status: 'error' };
    case 'success': return { ...state, status: 'success' };
    default: return state;
  }
}

When to validate: on blur for first feedback (validating on every keystroke shouts "invalid email" at someone who has typed one character); on change only after a field has been touched or a submit has failed, so corrections clear the error live; and always again on submit, which is the only moment you may show errors for fields never visited. Server-side validation is non-negotiable regardless.

Native form semantics and accessibility

<form onSubmit={handleSubmit} noValidate>
  <label htmlFor="email">Email</label>
  <input
    id="email" name="email" type="email"
    aria-invalid={!!errors.email}
    aria-describedby={errors.email ? 'email-error' : undefined}
    ref={emailRef}
  />
  {errors.email && <p id="email-error" role="alert">{errors.email}</p>}
  <button type="submit" disabled={status === 'submitting'}>Save</button>
</form>
  • Use a real <form> with onSubmit, not a <div> with a click handler — you get Enter-to-submit, browser autofill, password managers and mobile "Go" keys for free. Call e.preventDefault().
  • A <button> inside a form defaults to type="submit". Any button that is not submitting needs type="button" — forgetting this is a classic accidental-submit bug.
  • Associate every label with htmlFor/id (or wrap the input). A placeholder is not a label.
  • On a failed submit, move focus to the first invalid field (ref.current.focus()) and announce errors with role="alert". Never rely on colour alone.
  • Disable the submit button while submitting to prevent double submission, and keep entered values on failure — never clear the form.
React 19: adds form Actions — <form action={fn}>, useActionState, useFormStatus and useOptimistic — which fold pending/error state into the form primitive itself. Useful to name, but the controlled/uncontrolled trade-off underneath is unchanged.

🎯 Interview questions

What is a SyntheticEvent, and where are React's listeners attached?

A cross-browser wrapper around the native event with a normalized API (e.nativeEvent gives you the original). Since React 17 the delegated listeners live on the root container passed to createRoot, not on document, so multiple React roots or versions can coexist on a page.

Do you still need e.persist()?

No. Event pooling was removed in React 17, so the event object is no longer reused and you can read its properties asynchronously. e.persist() still exists as a no-op for compatibility; recommending it as current practice signals pre-17 knowledge.

Controlled vs uncontrolled — which and why?

Controlled means value + onChange with React state as the source of truth: predictable and needed for live validation, masking or derived UI, at the cost of a render per keystroke. Uncontrolled leaves the value in the DOM and reads it via a ref or FormData: no renders, but you cannot derive UI from it. Use uncontrolled for file inputs, third-party widgets and very large forms.

Why did my input stop accepting typing?

You passed value without onChange, so React re-renders it back to the same state value after every keystroke. Add the handler, or use defaultValue for an uncontrolled initial value, or readOnly if display-only is the intent.

How do you keep a big controlled form fast?

Move state down so a keystroke renders one field, memoize expensive siblings with stable callbacks, debounce the expensive consequence rather than the displayed value, and if that is not enough switch to an uncontrolled + subscription library like react-hook-form.

When should validation run?

On blur for first feedback, on change only once a field is touched or a submit has failed, and always on submit — plus on the server. Model it with a single status field rather than several booleans so impossible states are unrepresentable.

What does capture phase give you that bubbling does not?

onClickCapture runs top-down before the target's handler, so a parent can act before any child has a chance to call stopPropagation(). That is the correct phase for analytics, global "close all overlays", or intercepting clicks in a container you do not control.
