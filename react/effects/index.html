useEffect & Lifecycle React

An effect synchronizes a component with an external system. That is the whole definition. A subscription, a timer, a network request, a browser API, a non-React widget (a map, a chart, a video player) — anything that lives outside React's render output and has to be kept in step with your props and state.

useEffect is not a lifecycle hook. Thinking "this is my componentDidMount" is the single biggest source of React bugs: it makes you write effects that fire once, capture stale values, and never clean up. Think in terms of synchronization that starts and stops, not moments in time.

The signature, and the three dependency forms

useEffect(() => {
  // setup: start synchronizing
  return () => {
    // cleanup: stop synchronizing
  };
}, [deps]);

The second argument is not "when to run" — it is "what this effect reads from the render". React compares each entry with Object.is against the previous render's array; if any differ, it cleans up and re-runs.

FormRunsMeans
useEffect(fn)After every render"I depend on everything." Almost always a bug or a deliberate measurement.
useEffect(fn, [])Once on mount, cleanup on unmount"I read nothing reactive." Only legitimate if the body truly closes over no props/state.
useEffect(fn, [a, b])On mount, and whenever a or b changesThe normal case: resynchronize when the inputs change.
Gotcha: [] is a claim, not a filter. If the body references userId, an empty array does not "run it once" — it freezes the effect on the first userId forever. The dependency array must be a truthful list of every reactive value the body reads.

Timing: effects run after paint

Render is a pure calculation, commit writes to the DOM, then the browser paints. useEffect callbacks are deferred until after the paint, so they never block the user seeing the update.

flowchart LR
  R["Render: compute JSX"] --> C["Commit: mutate DOM"]
  C --> P["Browser paints"]
  P --> E["useEffect runs"]
  E --> S["setState here causes a second render"]

This is why setting state inside an effect that feeds back into the render causes a visible flash: the user sees the intermediate frame. useLayoutEffect runs synchronously after commit but before paint precisely to avoid that flicker — covered on the Advanced Hooks page.

Cleanup semantics and the exact ordering

The function you return is called before every re-run of the effect, and once more on unmount. It is not "on unmount only". React never runs two setups without the matching teardown in between.

useEffect(() => {
  const conn = connect(roomId);         // setup for roomId = "general"
  return () => conn.disconnect();       // teardown for roomId = "general"
}, [roomId]);

With roomId going "general" → "travel" → unmount, the console order is exactly:

connect("general")
disconnect("general")     ← cleanup of the OLD value runs first
connect("travel")
disconnect("travel")      ← unmount

The cleanup closes over the render that created it, so it sees the old roomId — which is exactly what you want, because you must disconnect the connection you actually opened.

A cleanup is required for anything that outlives a render: subscriptions, setInterval/setTimeout, addEventListener, observers, websockets, and in-flight requests (via AbortController or an ignore flag to prevent an out-of-order response overwriting newer state).

useEffect(() => {
  let ignore = false;
  fetch(`/api/user/${id}`).then(r => r.json()).then(data => {
    if (!ignore) setUser(data);         // drop the response of a superseded request
  });
  return () => { ignore = true; };
}, [id]);

StrictMode double-invocation, and why it helps

In development only, React 18+ <StrictMode> mounts every component, unmounts it, and mounts it again. Effects therefore run setup → cleanup → setup. Production is unaffected.

This is a deliberate stress test. An effect that is correctly resilient — every setup balanced by a cleanup — is indistinguishable from a single mount. An effect that leaks shows up immediately as two subscriptions, two intervals, or a doubled counter.

Senior tip: the answer to "StrictMode fires my effect twice, how do I stop it?" is never a hasRunRef guard. The double invocation is telling you cleanup is missing or incomplete. Suppressing it hides a real bug that will surface as a leak when the component remounts in production (a route change, a conditional render, a key change).

The classic bugs

1. Missing dependencies → stale closures

Each render creates a new effect function closing over that render's values. Lie about the deps and the effect keeps running the old closure:

// ❌ interval callback captured count === 0 forever
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);                                  // lies: it reads `count`

// ✅ the updater needs no snapshot, so the deps are honestly empty
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);

The fix is never "delete the dependency". It is to remove the need for it: functional updates, moving the value into a ref, moving the function inside the effect, or extracting non-reactive logic outside the component.

2. Object / array / function deps → infinite loops

Non-primitive values are recreated on every render, so Object.is always reports a change: effect runs → sets state → re-render → new object → effect runs…

// ❌ new object literal every render → infinite loop
const options = { userId, sort: 'asc' };
useEffect(() => { load(options); }, [options]);

// ✅ depend on the primitives it is really made of
useEffect(() => { load({ userId, sort: 'asc' }); }, [userId]);

3. setState in an effect with no guard

An effect whose only job is to set state from other state is almost always derived state in disguise — it costs an extra render and can loop. Compute it during render instead.

You Might Not Need an Effect

SituationDo this instead
Value computable from props/stateCompute during render; useMemo only if profiling demands it
Transforming a list for display (filter/sort)Do it in the render body — not an effect + extra state
Something must happen because the user did XPut it in the event handler
Reset all state when an id changesPass key={id} and let React remount the component
Reset part of state when a prop changesAdjust it during render (compare to a stored previous prop) — not an effect
Copying a prop into state to "keep it in sync"Just read the prop; the copy freezes and drifts
Notifying a parent of a changeCall the parent's callback in the same handler that made the change
Fetching dataAn effect works, but prefer a framework loader / React Query / RSC — they handle races, caching and dedupe
Gotcha: chained effects ("effect A sets state that triggers effect B that triggers C") are the worst version of this. Each link is a full render pass, the intermediate states are visible, and the flow is impossible to follow. Compute the whole result in one place.

Effect or event handler? The decision rule

  • Event handler: the code should run because a specific interaction happened — a click, a submit, a keypress. Buying a product, showing a toast, sending an analytics click. Running it twice is wrong.
  • Effect: the code should run because the component is displayed with these values, regardless of how it got there. Connecting to a chat room, subscribing to a store, starting a timer. Running the setup twice with a cleanup between is harmless.

Litmus test: if you can't answer "what external system is this keeping in sync?", it probably belongs in a handler or in the render body.

Senior tip: in an interview, describe an effect by its lifecycle in words — "start synchronizing with X; stop synchronizing with X" — rather than "on mount / on update / on unmount". It signals you think in React 18 terms and it makes the cleanup obviously mandatory.

🎯 Interview questions

What is useEffect actually for?

Synchronizing a component with an external system — subscriptions, timers, network, non-React widgets. It is not a lifecycle hook. If nothing external is involved, the logic usually belongs in the render body (derived values) or an event handler (user interactions).

When exactly does cleanup run?

Before every re-run of the effect and once on unmount. React never runs a second setup without the matching cleanup in between, and the cleanup closes over the render that created it, so it tears down the value it actually set up.

Why does StrictMode run my effect twice, and how should I fix it?

In development React mounts, unmounts and remounts the component so effects run setup → cleanup → setup. It is a probe for missing cleanup. Fix it by making the effect resilient to being re-run — not with a ref guard, which just hides a leak that will appear on any real remount.

Why does an empty dependency array cause stale data?

The effect closes over the first render's values. Claiming no dependencies while the body reads props or state freezes it on those initial values. The dependency array must list everything reactive the body reads; if that feels wrong, restructure (functional updates, move the function inside the effect, or use a ref).

An effect depends on an object and loops forever. Why?

Object, array and function literals get a new identity every render, so the Object.is comparison always reports a change. Depend on the primitive fields instead, construct the object inside the effect, or stabilize it with useMemo/useCallback.

How do you avoid a race condition when fetching in an effect?

Use the cleanup: set an ignore flag or abort with an AbortController, so a response from a superseded request is discarded rather than overwriting newer state. Better still, use a data library or framework loader that handles this for you.

How do you reset state when a prop changes — and why not an effect?

Pass key={id} so React remounts the component with fresh state. An effect that syncs props into state renders once with stale data, then renders again, and the copied value silently drifts from its source.
