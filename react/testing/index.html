Testing React React

The one rule: "The more your tests resemble the way your software is used, the more confidence they can give you" — Kent C. Dodds. React Testing Library exists to make the easy path the user-facing path: it deliberately gives you no API for reading state, props, or a component's internals, because a test that asserts on those breaks the moment you refactor, without the app ever having been broken.

Concretely: find elements the way a user or a screen reader would (by role and accessible name), interact with them the way a user does (real event sequences), and assert on what is visible on screen. Everything below follows from that.

Philosophy: test behaviour, not implementation

Enzyme let you call wrapper.instance().setState() and assert wrapper.state('count') === 1. Two problems: renaming count to total fails the test although nothing broke (a false negative), and the test passes even when the number never reaches the screen (a false positive). RTL removes both by removing the access.

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('adds an item to the list', async () => {
  const user = userEvent.setup();
  render(<TodoApp />);

  await user.type(screen.getByRole('textbox', { name: /new todo/i }), 'Buy milk');
  await user.click(screen.getByRole('button', { name: /add/i }));

  expect(await screen.findByText('Buy milk')).toBeInTheDocument();
});

Nothing in that test knows whether TodoApp uses useState, useReducer, Redux or a server action. Rewrite the internals entirely and the test still passes — which is the entire point.

Note: render mounts into a real DOM (jsdom, or a browser with Vitest's browser mode). screen is just queries bound to document.body — prefer it over destructuring the return value of render, so tests do not silently miss content rendered in a portal.

Query priority — and why it doubles as an accessibility audit

RTL orders its queries by how closely they mirror how a user finds things. Go down the list only when the one above genuinely does not apply:

#QueryFindsNotes
1getByRole(role, { name })Element by ARIA role + accessible nameThe default. Covers buttons, links, textboxes, headings, checkboxes, dialogs.
2getByLabelTextForm field by its <label>How a user fills in a form.
3getByPlaceholderTextInput by placeholderOnly when there is genuinely no label (there usually should be one).
4getByTextNon-interactive textParagraphs, list items, error messages.
5getByDisplayValueInput by its current valuePrefilled forms.
6getByAltText / getByTitleImages, iframesSemantic-ish fallbacks.
7getByTestIddata-testidLast resort. Invisible to users and to assistive tech.

The accessibility payoff is real: if you cannot reach a control with getByRole('button', { name: /save/i }), a screen-reader user cannot reach it either. A <div onClick> has no role and no name; an icon-only button with no aria-label has a role but no name. Fixing the test fixes the app.

// ❌ couples the test to markup and hides a real a11y bug
screen.getByTestId('submit-btn');

// ✅ fails loudly until the button is actually a labelled button
screen.getByRole('button', { name: /submit order/i });

screen.getByRole('heading', { level: 2, name: /orders/i });
screen.getByRole('checkbox', { name: /remember me/i, checked: true });
screen.getByRole('textbox', { name: /email/i });
Senior tip: When a query fails, RTL prints the DOM — and screen.logTestingPlaygroundURL() or getRoles(container) tells you what roles actually exist. data-testid is not forbidden; it is the right tool for a chart canvas or a wrapper with no semantics. It is just never the first tool.

getBy vs queryBy vs findBy (and the All variants)

PrefixNot foundFoundAsync?Use for
getBy*Throws (with the DOM printed)ElementNoAsserting something IS there, now
queryBy*Returns nullElementNoOnly way to assert absence
findBy*Rejects after timeout (1000 ms)Promise<Element>YesSomething that appears later

getAllBy/queryAllBy/findAllBy return arrays; the singular forms throw if more than one element matches, which is a useful accident-detector.

// ✅ present
expect(screen.getByRole('alert')).toHaveTextContent(/failed/i);

// ✅ absent — getBy would throw before expect ever runs
expect(screen.queryByRole('alert')).not.toBeInTheDocument();

// ❌ this ALWAYS passes: findBy returns a promise, and a promise is truthy
expect(screen.findByText('done')).toBeInTheDocument();
// ✅
expect(await screen.findByText('done')).toBeInTheDocument();
Gotcha: await screen.findByX is waitFor(() => getByX) under the hood, so it retries. There is no "waitFor it to be gone" version of findBy — use await waitForElementToBeRemoved(() => screen.queryByText(/loading/i)), which throws helpfully if the element was never there in the first place.

user-event over fireEvent

fireEvent.click(el) dispatches exactly one synthetic click. A real click is a sequence: pointerdown, mousedown, focus, pointerup, mouseup, click. Typing is keydown, keypress, input, keyup per character, with selection and cursor bookkeeping in between.

const user = userEvent.setup();          // once per test, BEFORE render
await user.click(button);                // every method is async in v14 — always await
await user.type(input, 'hello{enter}');
await user.keyboard('{Shift>}{Tab}{/Shift}');
await user.selectOptions(select, 'uk');
await user.upload(fileInput, file);
  • user-event respects reality: it refuses to type into a disabled or readOnly input, and clicking moves focus — so a test that passes with fireEvent can be broken for real users.
  • It catches bugs in onFocus/onBlur/onKeyDown handlers that fireEvent.change would skip entirely.
  • Keep fireEvent for events a user cannot perform directly: scroll, resize, a synthetic animationend, or a low-level event you need in isolation.

Async, and what the act(...) warning really means

// three ways to wait, in order of preference
const row = await screen.findByRole('row', { name: /ada/i });   // element appears
await waitForElementToBeRemoved(() => screen.queryByText(/loading/i));
await waitFor(() => expect(mockSave).toHaveBeenCalledTimes(1)); // non-DOM assertion

act() is React's marker for "I am about to change state — flush effects and re-render before anyone looks at the DOM". "An update to X was not wrapped in act(...)" means state changed outside anything the test was awaiting: usually a promise resolving after the test finished, or a timer firing later. It is a real warning about a test that is inspecting a half-settled tree.

  • You almost never call act yourself — RTL wraps render, user-event and fireEvent in it already.
  • The cure is to await the resulting change (findBy/waitFor) instead of asserting immediately.
  • Fake timers? Advance them inside act, and pass userEvent.setup({ advanceTimers: jest.advanceTimersByTime }).
  • A warning after the test ended usually means a missing cleanup, an unaborted fetch, or a component updating after unmount — a genuine bug worth fixing.
Gotcha: Never put a bare expect with side effects inside waitFor, and never waitFor around a whole block — it re-runs the callback until it passes, so a user.click in there can fire many times.

Mocking: modules, fetch, and why MSW wins

// module mock — the component's dependency is swapped at import time
jest.mock('../api/users', () => ({ getUsers: jest.fn().mockResolvedValue([{ id: 1 }]) }));

// hand-rolled fetch stub — brittle: you now maintain a fake Response
global.fetch = jest.fn().mockResolvedValue({ ok: true, json: async () => [] });

MSW (Mock Service Worker) intercepts at the network layer instead, so your code runs its real fetch/axios call, real URL building, real headers, real JSON parsing, real error branches:

import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/users', () => HttpResponse.json([{ id: 1, name: 'Ada' }])),
);
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test('shows the error state', async () => {
  server.use(http.get('/api/users', () => new HttpResponse(null, { status: 500 })));
  render(<Users />);
  expect(await screen.findByRole('alert')).toHaveTextContent(/couldn't load/i);
});
  • The same handlers work in tests, Storybook, and the browser during development.
  • Swapping axios for fetch does not touch a single test.
  • Error, empty and slow states become one-line overrides instead of new mock shapes.
  • onUnhandledRequest: 'error' catches requests you forgot existed — a genuinely useful safety net.

Custom hooks, and what NOT to test

import { renderHook, act } from '@testing-library/react';

const { result, rerender } = renderHook(({ start }) => useCounter(start),
                                        { initialProps: { start: 0 } });
expect(result.current.count).toBe(0);
act(() => result.current.increment());     // state updates go inside act
expect(result.current.count).toBe(1);

renderHook (in @testing-library/react since v13.1 — it used to be a separate package) is for hooks you ship as a library or that carry real logic. For a hook that only exists to serve one component, testing it through that component is more valuable: it proves the wiring too. Note result.current is a snapshot — re-read it after every update rather than destructuring once.

Do not test

  • State internals. "count is 1" matters only if the user can see it.
  • Implementation details — that useMemo was used, that a child received a specific prop, how many times something rendered (unless render count is the requirement, e.g. a perf regression test).
  • Third-party libraries. React Router, React Query and date-fns have their own test suites. Test your use of them.
  • CSS classes as a proxy for behaviour. Assert on visible text, toBeDisabled(), toBeVisible(), aria-*.

Snapshots

The failure mode is well known: a 400-line snapshot nobody reads, and every diff is "resolved" with -u. That is a test that can never fail meaningfully. Keep snapshots small and intentional — expect(el).toMatchInlineSnapshot() on one node, a serialized reducer result, an error message — and write explicit assertions for anything you actually care about.

RTL is identical on both — it is testing-runner-agnostic. Pick Vitest for a Vite app, Jest for an existing Jest/Next.js/CRA codebase; it is not an architectural decision.

flowchart TD
  E["E2E with Playwright or Cypress - few, slow, highest confidence"] --> I["Component and integration with RTL - the bulk"]
  I --> U["Unit tests for pure logic - reducers, formatters, utils"]

The classic pyramid undersells the middle for React. Pure unit tests of a component's internals are cheap but prove little; E2E tests prove everything but are slow and flaky at volume. Component-integration tests — render a feature with its children and a mocked network, then drive it as a user — give the best confidence per second of CI time. Keep unit tests for genuinely pure logic (reducers, date maths, permission checks) and a thin E2E layer for the two or three flows that must never break: sign-in, checkout, the money path.

🎯 Interview questions

Why does Testing Library refuse to let you read state or props?

Because assertions on internals produce both false negatives (a pure refactor fails the test) and false positives (state is right but never rendered). Restricting you to what is on screen means tests describe behaviour, survive refactors, and fail only when the user-visible contract breaks.

What is the query priority order and why does it matter beyond tests?

getByRole with an accessible name first, then label, placeholder, text, display value, alt/title, and getByTestId last. Roles and accessible names are exactly what assistive tech uses, so a control you cannot query by role is a control a screen reader cannot describe — the test doubles as an accessibility check.

getBy, queryBy or findBy?

getBy throws immediately and is for things that must already be there. queryBy returns null and is the only correct choice for asserting absence. findBy returns a promise that retries until a timeout, for elements that appear after async work — and must be awaited, since an un-awaited promise is truthy and the assertion silently always passes.

Why prefer user-event over fireEvent?

fireEvent dispatches a single synthetic event; user-event reproduces the real sequence (pointer, mouse, focus, key, input events) and honours disabled/readonly and focus behaviour. That catches handler bugs and impossible interactions a lone click or change would miss. In v14 you call userEvent.setup() and await every interaction.

What does the "not wrapped in act(...)" warning tell you?

A state update happened outside anything the test awaited — typically a promise or timer resolving after the assertions or after the test ended, so the tree was inspected mid-update. RTL already wraps render and events in act, so the fix is to await the resulting change with findBy/waitFor, or to fix the component updating after unmount.

Why MSW instead of mocking fetch or the API module?

Mocking the module skips your URL building, headers, response parsing and error handling; a stubbed fetch means hand-maintaining fake Response objects. MSW intercepts at the network layer so all of that real code runs, the same handlers serve tests, Storybook and dev, error and empty states are one-line overrides, and swapping HTTP client does not touch the tests.

Where should a React team spend its testing budget?

Mostly on component/integration tests with RTL: render a feature with real children and a mocked network and drive it as a user — highest confidence per second of CI. Keep unit tests for pure logic (reducers, formatters) and a small E2E suite for the critical flows. Avoid large snapshot tests, which get rubber-stamped and stop catching anything.
