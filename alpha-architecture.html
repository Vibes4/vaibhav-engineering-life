INTERVIEW BRIEF

Alpha Platform — Architecture

Enterprise low-code case-management & workflow platform · Nx monorepo · NestJS + Angular + PostgreSQL

① The one-liner

Alpha is a metadata-driven case-management & BPM platform. Business users design case types, forms/pages, inboxes and workflows in Workflow Studio; other users operate on those cases through a Case Manager workbench that renders itself from configuration. It's an Nx monorepo of Angular 18 frontends + ~13 NestJS microservices on PostgreSQL, shipped via Jenkins → Docker → Helm/K8s.

Metadata-driven runtime
The config is the product — behaviour changes without code deploys.
CQRS-style split
jBPM + case DB = write side; “enquiry” = rebuildable read projection.
Config-as-code
Config is versioned with git-like branch / diff / commit / PR.

③ The read/write split (the flow to explain)

Case action→ jBPM task/process state→ DB trigger fills task_index_outbox→ GTS cron polls outbox→ enquiry read model→ fast inbox / search
  • Write side: alpha-case-service orchestrates workflow; alpha-jbpm-service owns process/task state via KIE-Server REST (/server/containers/.../processes).
  • Read side: libs/enquiry is a CQRS read projection (SDKs: enquiry-sdk, task-sync-sdk, recovery-sdk).
  • Bridge: transactional outbox — a jBPM taskevent trigger writes the outbox; GTS polls & pushes to enquiry, with a legacy createdon poll + recovery as fallback. Resilient to missed events.

④ Config-as-code (the “Delta” story)

Studio edits config→ config-service persists + recordChangeEvent (commit on branch)→ Delta UI shows branches/diffs/PRs→ PR merge → lifecycle event → back to config-service
  • alpha-config-service — source-of-truth persistence + ledger write side.
  • alpha-delta-service — git-like API surface: branch / commit / diff / pull-request / tag / comment controllers.
  • libs/change-tracking-utils — per-config-type adapters (load/save/describe/diff) for case_definition, pages, inbox, bpm, ui_theme, translation…
  • Engine caveat: the actual commit/branch/merge algorithm lives in an external SDK @neutrinos/project-sdk-config-ledger — this repo shows how it's wired & consumed, not the internal storage model.

⑤ Auth

  • alpha-auth-service runs a full OIDC authorization-code flow with PKCE (openid-client).
  • Browser = server-side session cookie holding the tokenset; API/service calls = bearer-token introspection.
  • IDS = Neutrinos Identity Server (OIDC issuer); libs/ids-adapter supports V1/V2 via IDS_V2_ENABLED.

⑥ Multi-tenancy

  • Row-level isolation in a shared DB + configurable schema (not schema-per-tenant).
  • tenants table keyed by subdomain.
  • Tenant resolved from the IDS token: middleware sets req.tenant = introspection.organisationId, which scopes all queries.

⑦ What to emphasize  ·  and the gotchas

LEAD WITH
  1. Metadata-driven runtime — designers change behaviour with no code deploy.
  2. CQRS read/write split — jBPM is truth; enquiry is a rebuildable projection kept in sync by a resilient outbox.
  3. Config-as-code — versioned config with promotion/diff between environments.
  4. Uniform service chassis — every NestJS service shares session/IDS/tracing/feature-flag middleware; Nx tags enforce module boundaries.
DON'T MISSTATE
  • Not a single API gateway — per-service direct calls behind ingress, one admin BFF, one outbound connector proxy.
  • Tenancy is row-level, not schema-per-tenant.
  • RabbitMQ is used only for pull-task; the event-emitter bus is in-process within config-service, not cross-service. No first-party Redis.
  • The ledger engine is an external SDK — know the boundary of what's in-repo.
