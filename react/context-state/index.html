Context & State Management React

Context solves one problem: getting a value from a provider to a deeply nested consumer without threading it through every component in between. That is dependency injection. It is not a state manager — it has no selectors, no subscriber-level batching, no devtools, no middleware, and no way for a consumer to say "wake me only when this slice changes".

The senior version of this topic is knowing (a) that composition often removes the prop drilling for free, (b) that every consumer re-renders when the provider value changes identity, and (c) that most of the state people reach for Redux to manage is actually server cache, which needs a different tool entirely.

Prop drilling, and the cheaper fix people forget

Prop drilling is passing a prop through components that do not use it, purely to reach a descendant. Three levels is usually fine and readable. Ten levels of user through layout components is real coupling: every intermediate signature changes when the shape changes.

Before reaching for Context, try component composition — render the subtree in the component that already owns the data and pass it down as children:

// ❌ Layout and Sidebar don't care about `user`, but must accept and forward it
<Layout user={user}>
  <Sidebar user={user} />
</Layout>

// ✅ the element is created where the data lives; Layout just renders a hole
function Layout({ sidebar, children }) {
  return <div>{sidebar}<main>{children}</main></div>;
}

<Layout sidebar={<Avatar user={user} />}>
  <Feed />
</Layout>

This has a second, underrated benefit: an element passed as children was created by the parent, so when Layout re-renders, that element object is the same reference and React can skip re-rendering it. Composition is both less plumbing and fewer renders.

Senior tip: Reach for Context when a value is genuinely ambient — theme, locale, current user, a router, a design-system config — and is read by many unrelated components. Values that flow down one branch are usually a composition problem, not a Context problem.

The API: createContext, Provider, useContext

const ThemeContext = createContext('light');   // default used ONLY when no Provider above

function App() {
  const [theme, setTheme] = useState('dark');
  return (
    <ThemeContext.Provider value={theme}>
      <Page />
    </ThemeContext.Provider>
  );
}

function Button() {
  const theme = useContext(ThemeContext);       // nearest Provider above, in the TREE
  return <button className={theme} />;
}
  • useContext reads the nearest provider above in the React tree, not the nearest in the file. Nested providers of the same context shadow each other — that is a feature (per-subtree themes).
  • The createContext default value only applies when there is no matching Provider. A common bug is forgetting the Provider in tests and silently getting the default instead of an error. Guard it:
const AuthContext = createContext(null);
export function useAuth() {
  const ctx = useContext(AuthContext);
  if (ctx === null) throw new Error('useAuth must be used inside <AuthProvider>');
  return ctx;
}

In React 19, <ThemeContext> can be rendered directly as the provider (<ThemeContext value={x}>); .Provider still works and is what you will see in most codebases.

Context is dependency injection, not a state manager

Context has no store. It holds whatever value you hand it and broadcasts identity changes. The state itself still lives in a useState/useReducer somewhere above. What a real state manager adds on top:

CapabilityContextA store (Redux / Zustand / Jotai)
Selector granularityNone — all consumers wake on any changeSubscribe to a slice; skip if the slice is equal
Read outside ReactNoYes (store.getState())
Devtools / time travelNoYes
Middleware (logging, persistence, async)NoYes
Cost of a changeRe-render every consumer subtreeRe-render only components whose selection changed
Note: "Context re-renders everything" is imprecise but the practical conclusion is right. React walks from the Provider and re-renders the consumers — components that called useContext — regardless of React.memo, because memo cannot block a context update. Non-consumers in between are skipped if they are memoized and their props are unchanged.

The performance pitfall: value identity

React compares the provider value with Object.is. An object literal in JSX is a new object on every render of the provider component, so every consumer re-renders even when the data is deeply equal:

// ❌ new object identity every single render — all consumers wake up
<UserContext.Provider value={{ user, setUser }}>

// ✅ stable identity while user is unchanged
const value = useMemo(() => ({ user, setUser }), [user]);
<UserContext.Provider value={value}>

Four escalating fixes, in the order you should try them:

  1. Memoize the value. Free, and removes the "provider re-rendered for an unrelated reason" churn.
  2. Split state and dispatch into two contexts. dispatch and setters from useState/useReducer are already stable for the component's lifetime, so components that only dispatch never re-render when state changes.
  3. Split by update frequency. A cursor position that changes 60×/s and a theme that changes twice a session must not share a context.
  4. Use a selector-based store. When consumers need different slices of one frequently-changing object, only per-subscriber selection fixes it. This is exactly what Zustand/Jotai/Redux give you (and what useSyncExternalStore lets you build).
const StateCtx    = createContext(null);
const DispatchCtx = createContext(null);   // dispatch is referentially stable forever

function Provider({ children }) {
  const [state, dispatch] = useReducer(reducer, init);
  return (
    <DispatchCtx.Provider value={dispatch}>
      <StateCtx.Provider value={state}>{children}</StateCtx.Provider>
    </DispatchCtx.Provider>
  );
}
Gotcha: Memoizing the value does not help if the state object itself is recreated on every change — and it shouldn't, that is the point. Memoization removes accidental churn; it cannot give you selector granularity. Do not expect useMemo to fix a genuinely hot context.

Context + useReducer: the legitimate small-app pattern

For state that is app-wide but changes rarely — auth session, theme, a shopping cart, a wizard — useReducer + two contexts is a real architecture, not a compromise. You get named actions, a pure and unit-testable transition function, and zero dependencies.

function cartReducer(state, action) {
  switch (action.type) {
    case 'add':    return { ...state, items: [...state.items, action.item] };
    case 'remove': return { ...state, items: state.items.filter(i => i.id !== action.id) };
    default:       throw new Error('unknown action ' + action.type);
  }
}

Outgrow it when: consumers start needing slices (perf), you want devtools/time-travel, you need to read or write state outside React, or the reducer becomes a place where async lives.

The distinction that matters most: server state vs client state

Most "global state management" pain is people storing a cache of someone else's data in a tool designed for UI state. Server data is asynchronous, shared, owned elsewhere, and goes stale. It needs caching, deduplication, revalidation and retries — none of which Redux gives you out of the box.

Senior tip: Answer "how do you manage state in a large React app?" with this table. Once server cache goes to React Query and navigational state goes to the URL, the genuinely global client state left over is usually small enough that Context or a 20-line Zustand store is sufficient.

How to choose: start with local state. Move server data to React Query. Put navigational state in the URL. If something is still global and rarely changes, use Context. 🎯 Interview questions

Is Context a state management solution?

No. Context is a transport mechanism — dependency injection for a subtree. The state still lives in useState/useReducer above the Provider. Context provides no selectors, no subscriber-level granularity, no devtools and no middleware, which is exactly what distinguishes a store from a broadcast channel.

Why does value={{user, setUser}} hurt performance?

The object literal is a new reference on every render of the Provider component. React compares provider values with Object.is, so every consumer re-renders even though the data is identical. Wrap it in useMemo, and split state from dispatch so dispatch-only consumers never wake.

Does React.memo stop a context update?

No. memo only skips re-renders caused by unchanged props. A component that calls useContext is subscribed directly and will re-render on any provider value change. memo does help the non-consuming components in between, which is why splitting contexts works.

How do you avoid prop drilling without Context?

Component composition: render the subtree where the data already lives and pass it through as children or as element props. Intermediate components accept a hole to fill instead of a value to forward, and the passed element keeps a stable identity so React can skip re-rendering it.

Server state vs client state — why does it matter?

Server data is an asynchronous, shared cache that goes stale; it needs deduplication, background revalidation, retries and invalidation. Client UI state is synchronous and owned by you. Putting server data in Redux means hand-writing a cache badly; React Query/SWR/RTK Query exist to own that layer, which usually shrinks the remaining global state dramatically.

When would you actually pick Redux Toolkit today?

Large apps with complex, highly interconnected client state, a team that benefits from strict conventions, a need for time-travel devtools or cross-cutting middleware (analytics, undo, offline queues). For "a few global values" Zustand or Context is less machinery for the same result.

How do you get selector-like behaviour without a library?

Keep the state in an external store object with a subscribe/getSnapshot API and read it via useSyncExternalStore, comparing the selected slice yourself. That is roughly what Zustand is. It is a real option when you want one hot store without a dependency.
